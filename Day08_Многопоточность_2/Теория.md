## 1. `synchronized` vs `Lock`

### 1.1. Зачем вообще сравнивать

` synchronized` — это встроенная в язык (на уровне JVM) синхронизация. `Lock` — это обычный Java-интерфейс `java.util.concurrent.locks.Lock` с реализациями вроде `ReentrantLock`.

Аналогия из жизни. `synchronized` — это **автоматическая дверь в лифте**: зашёл — дверь закрылась сама, вышел — открылась сама. Удобно и почти невозможно забыть. `Lock` — это **ключ от кладовки**: ты сам открываешь, сам закрываешь. Больше свободы (можно попробовать открыть и не ждать, можно открыть в другом порядке), но если забудешь закрыть — беда.

### 1.2. Сравнительная таблица

| | `synchronized` | `Lock` (`ReentrantLock`) |
|---|---|---|
| Уровень | ключевое слово / JVM | API (`java.util.concurrent.locks`) |
| Освобождение | автоматически при выходе из блока | **вручную** в `finally` |
| `tryLock` (без ожидания) | нет | да |
| `tryLock` с таймаутом | нет | да |
| Прерываемое ожидание | нет | `lockInterruptibly()` |
| Честность (fairness) | нет | опционально (в конструкторе) |
| Условия ожидания | один монитор (`wait`/`notify`) | много `Condition` |
| Read/Write-разделение | нет | `ReadWriteLock` |
| Производительность в Java 6+ | сопоставима (JVM оптимизировала) | сопоставима |
| Простота использования | выше (меньше шансов ошибиться) | ниже (нужно `try/finally`) |

**Важный вывод:** в современной JVM `synchronized` оптимизирован (biased locking, lightweight locking, lock elision), поэтому «`Lock` всегда быстрее» — миф. `Lock` берут ради **функциональности**, а не ради скорости.

### 1.3. Базовое использование `ReentrantLock`

```java
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class Counter {
    private final Lock lock = new ReentrantLock();
    private int count = 0;

    public void increment() {
        lock.lock();          // захватываем замок
        try {
            count++;          // критическая секция
        } finally {
            lock.unlock();    // ОБЯЗАТЕЛЬНО освобождаем
        }
    }

    public int get() {
        lock.lock();
        try {
            return count;
        } finally {
            lock.unlock();
        }
    }
}
```

**Почему `unlock()` именно в `finally`?** Потому что если внутри критической секции выбросится исключение, без `finally` замок останется захваченным навсегда — и все остальные потоки зависнут. `finally` гарантирует освобождение при любом сценарии.

### 1.4. Реентерабельность (reentrancy)

`ReentrantLock` (как и `synchronized`) — **реентерабельный**: поток, уже владеющий замком, может захватить его ещё раз. Внутри ведётся счётчик удержаний (`hold count`); замок реально освобождается, когда счётчик дойдёт до нуля.

Аналогия: если ты уже в кладовке, тебе не нужно искать ключ заново, чтобы зайти в неё ещё раз.

```java
public class ReentrantDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void outer() {
        lock.lock();
        try {
            System.out.println("hold count = " + lock.getHoldCount()); // 1
            inner();                                                   // повторный вход
        } finally {
            lock.unlock();
        }
    }

    private void inner() {
        lock.lock();
        try {
            System.out.println("hold count = " + lock.getHoldCount()); // 2
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) {
        new ReentrantDemo().outer();
    }
}
```

Ожидаемый вывод:
```
hold count = 1
hold count = 2
```

Если бы замок не был реентерабельным, `inner()` заблокировался бы навсегда (поток ждал бы сам себя).

### 1.5. `tryLock()` — попробовать и не ждать

Иногда ждать захвата нельзя: лучше сразу сделать что-то другое, чем висеть. `tryLock()` возвращает `true`, если удалось захватить, и `false`, если замок занят — **не блокируя поток**.

```java
Lock lock = new ReentrantLock();

if (lock.tryLock()) {
    try {
        // получилось — работаем
    } finally {
        lock.unlock();
    }
} else {
    // не получилось — делаем альтернативу, не стоим в очереди
    System.out.println("Занято, попробую позже");
}
```

Версия с таймаутом — ждём не больше заданного времени:

```java
try {
    if (lock.tryLock(2, TimeUnit.SECONDS)) {
        try { /* работа */ }
        finally { lock.unlock(); }
    } else {
        System.out.println("Не дождались за 2 секунды");
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

`tryLock` — ключевой инструмент **борьбы с дедлоками** (см. раздел 4).

### 1.6. `lockInterruptibly()` — прерываемое ожидание

Обычный `lock()` игнорирует `Thread.interrupt()` во время ожидания. `lockInterruptibly()` позволяет прервать ожидание и бросить `InterruptedException`.

```java
try {
    lock.lockInterruptibly();
    try { /* работа */ }
    finally { lock.unlock(); }
} catch (InterruptedException e) {
    // нас прервали, пока мы ждали замок
    Thread.currentThread().interrupt();
    return;
}
```

Зачем: если задача отменена или приложение завершается, поток не должен висеть в ожидании замка вечно.

### 1.7. Fairness (честность)

По умолчанию `ReentrantLock` **нечестный** (non-fair): при освобождении замка «победить» может любой поток, в том числе только что подошедший (barging — «влезание без очереди»). Это даёт большую пропускную способность.

Честный режим (`new ReentrantLock(true)`) отдаёт замок потоку, который ждал дольше всех. Это защищает от **starvation** (голодания), но снижает throughput.

```java
Lock fairLock = new ReentrantLock(true);   // честный
Lock fastLock = new ReentrantLock(false);  // по умолчанию: нечестный, быстрее
```

**Правило:** берите fair только когда реально есть риск голодания. В 95% случаев нужен быстрый нечестный режим.

### 1.8. `Condition` — аналог `wait`/`notify`

`synchronized` даёт только один «зал ожидания» — монитор объекта (`wait`/`notify`/`notifyAll`). У `Lock` можно создать **сколько угодно отдельных очередей ожидания** — `Condition`.

Аналогия: в поликлинике один общий коридор (монитор) — все толпятся вместе. А `Condition` — это отдельные кабинеты: «ожидание, что очередь не полна» и «ожидание, что очередь не пуста» — разные комнаты, и будить можно только нужную.

| Монитор (`synchronized`) | `Condition` |
|---|---|
| `wait()` | `await()` |
| `notify()` | `signal()` |
| `notifyAll()` | `signalAll()` |
| Один на объект | Много на один `Lock` |
| Нужно владеть монитором | Нужно владеть `Lock` |

```java
import java.util.concurrent.locks.*;

Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

### 1.9. Пример: producer-consumer на `Lock` + `Condition`

Это классическая задача собеседования. Есть ограниченный буфер; производители кладут, потребители забирают. Если буфер полон — производитель ждёт; если пуст — потребитель ждёт.

```java
import java.util.ArrayDeque;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedBuffer<T> {
    private final Queue<T> queue = new ArrayDeque<>();
    private final int capacity;
    private final Lock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBuffer(int capacity) {
        this.capacity = capacity;
    }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            // while, а НЕ if: после пробуждения условие могло снова стать ложным
            while (queue.size() == capacity) {
                notFull.await();            // освобождает lock и ждёт сигнала
            }
            queue.add(item);
            notEmpty.signal();              // будим одного потребителя
        } finally {
            lock.unlock();
        }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (queue.isEmpty()) {
                notEmpty.await();
            }
            T item = queue.poll();
            notFull.signal();               // будим одного производителя
            return item;
        } finally {
            lock.unlock();
        }
    }
}
```

Почему `while`, а не `if`? Потому что после `await()` поток просыпается и **заново захватывает замок**. За это время другой поток мог снова заполнить буфер (или забрать элемент). Условие нужно перепроверить. Это называется **spurious wakeup** и защита от него.

### 1.10. Типичные ошибки (раздел 1)

1. **`unlock()` не в `finally`** → замок «залипает» при исключении.
2. **`await()`/`signal()` без владения замком** → `IllegalMonitorStateException`.
3. **`if` вместо `while` вокруг `await()`** → потерянный сигнал / гонка.
4. **`unlock()` без предварительного `lock()`** → `IllegalMonitorStateException`.
5. **Использование `tryLock()` и `unlock()` без проверки результата** — если `tryLock()` вернул `false`, нельзя вызывать `unlock()`.
6. **Fairness по умолчанию** — люди думают, что очередь честная, и удивляются голоданию.
7. **`Condition` создан от другого `Lock`** — тихая ошибка, сигнал не доходит.

### 1.11. Часто спрашивают на собеседовании (раздел 1)

- **Чем `Lock` лучше `synchronized`?** Функциональностью: `tryLock`, таймауты, `lockInterruptibly`, fairness, несколько `Condition`, `ReadWriteLock`.
- **А чем хуже?** Нужно вручную освобождать, легко ошибиться; нет автоматического освобождения при выходе из блока.
- **Что такое реентерабельность?** Поток может повторно захватить уже удерживаемый замок; ведётся счётчик.
- **`Condition` vs `wait/notify`?** Несколько очередей ожидания, точные сигналы, прерываемое ожидание.
- **Когда `tryLock` спасает от дедлока?** Когда не удалось захватить второй замок — можно освободить первый и отступить.

## 2. `ReadWriteLock` и `StampedLock`

### 2.1. Идея

Часто данные **читают намного чаще, чем меняют**. Если разрешить нескольким читателям работать одновременно (они не портят данные), а писателю давать эксклюзивный доступ — получим выигрыш в производительности.

`ReadWriteLock` держит две пары замков:
- **read lock** — разделяемый (shared): много читателей одновременно;
- **write lock** — эксклюзивный (exclusive): только один писатель, читателей нет.

Аналогия: **библиотека**. Много людей могут одновременно читать одну книгу (читательский зал), но чтобы переписать книгу, нужно, чтобы никто её не читал.

```java
import java.util.concurrent.locks.*;

public class Cache {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final Lock read = rw.readLock();
    private final Lock write = rw.writeLock();
    private String data = "initial";

    public String read() {
        read.lock();
        try {
            return data;             // несколько читателей параллельно
        } finally {
            read.unlock();
        }
    }

    public void write(String value) {
        write.lock();
        try {
            data = value;            // только один писатель, читателей нет
        } finally {
            write.unlock();
        }
    }
}
```

### 2.2. Правила совместимости

| Держит \ Запрашивает | read | write |
|---|---|---|
| **read** | совместимо | блокируется |
| **write** | блокируется | блокируется |

**Важно:** писатель не может получить write, пока есть хоть один читатель, и наоборот. Также один поток **не может** взять write, уже держа read (в `ReentrantReadWriteLock` это дедлок для самого себя — замок поддерживает понижение write→read, но не повышение read→write).

### 2.3. `StampedLock` (Java 8)

`StampedLock` — более быстрый, но менее гибкий. Вместо объектов-замков он использует `long stamp` (штамп-версию). Три режима:

- `writeLock()` / `unlockWrite(stamp)` — эксклюзивная запись;
- `readLock()` / `unlockRead(stamp)` — обычное чтение;
- `tryOptimisticRead()` / `validate(stamp)` — **оптимистичное чтение**.

```java
import java.util.concurrent.locks.StampedLock;

public class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    // Писатель
    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try {
            x += dx;
            y += dy;
        } finally {
            sl.unlockWrite(stamp);
        }
    }

    // Оптимистичное чтение: без блокировки!
    public double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();   // читаем "на удачу"
        double curX = x, curY = y;             // копируем в локальные переменные
        if (!sl.validate(stamp)) {             // если во время чтения была запись...
            stamp = sl.readLock();             // ...берём честный read lock
            try {
                curX = x;
                curY = y;
            } finally {
                sl.unlockRead(stamp);
            }
        }
        return Math.sqrt(curX * curX + curY * curY);
    }
}
```

**Optimistic read** работает так: мы не ставим блокировку, а запоминаем версию (stamp) и читаем. Потом проверяем `validate`: если никто не писал — данные консистентны, и мы сэкономили на блокировке. Если писали — перечитываем уже под честным read lock.

**Ограничения `StampedLock`:**
- **не реентерабелен** (нельзя повторно захватить);
- не поддерживает `Condition`;
- `stamp` нельзя забывать — иначе замок «залипнет».

### 2.4. Когда что использовать

| Ситуация | Что выбрать |
|---|---|
| Чтение >> запись, нужна простота | `ReentrantReadWriteLock` |
| Чтение >> запись, максимум скорости | `StampedLock` (optimistic read) |
| Нужна реентерабельность/`Condition` | `ReentrantLock` |
| Смешанная нагрузка | `synchronized` / `ReentrantLock` |

### 2.5. Типичные ошибки (раздел 2)

1. **Попытка «повысить» read→write** в `ReentrantReadWriteLock` — дедлок.
2. **Долгие операции под write lock** — блокирует всех читателей.
3. **Использование `StampedLock` без проверки `validate`** — читаешь «порванные» данные.
4. **Забыть сохранить `stamp`** и вызвать `unlockRead()` без него — ошибка компиляции/`IllegalMonitorStateException`.
5. **Слишком мелкая гранулярность** — накладные расходы на замки больше выгоды.

### 2.6. Часто спрашивают (раздел 2)

- **Когда `ReadWriteLock` реально быстрее?** Когда читателей заметно больше писателей и операции чтения не микроскопические.
- **Чем `StampedLock` отличается от `ReentrantReadWriteLock`?** Быстрее, optimistic read, но не реентерабелен и без `Condition`.
- **Что такое optimistic read?** Чтение без блокировки с последующей проверкой версии.

## 3. `volatile` и модель памяти Java (JMM)

### 3.1. Проблема, которую решает `volatile`

В многопоточном мире у каждого ядра CPU есть кэш. Поток может писать в локальный кэш, а другой поток — не видеть изменений. Компилятор и процессор ещё и **переупорядочивают** инструкции ради оптимизации.

`volatile` даёт:
- **видимость (visibility)** — запись сразу становится видимой всем потокам, чтение всегда идёт в «свежее» значение;
- **запрет переупорядочивания** вокруг этой переменной (memory barrier);
- **НЕ** даёт атомарность составных операций (`count++` из трёх шагов).

Аналогия: `volatile` — это **доска объявлений в офисе**. Ты пишешь — все сразу видят. Но если двое одновременно пишут на одну строку, получится каша (нет атомарности).

### 3.2. Пример без `volatile` (зависший цикл)

```java
public class VisibilityProblem {
    static boolean running = true;   // НЕ volatile

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (running) {
                // JIT может "закэшировать" running в регистр
            }
            System.out.println("Worker остановлен");
        });
        worker.start();
        Thread.sleep(1000);
        running = false;              // worker может НЕ увидеть это!
        System.out.println("main выставил running=false");
    }
}
```

Возможный (часто наблюдаемый) вывод:
```
main выставил running=false
```
…и программа висит: `worker` никогда не завершится. С `volatile boolean running` — завершится сразу.

### 3.3. Почему `volatile` не спасает `count++`

```java
volatile int count = 0;

// Два потока одновременно:
count++;   // это ТРИ операции: read → increment → write
```

Оба потока могут прочитать `0`, оба записать `1`. Результат `1`, а ожидали `2`. `volatile` гарантирует, что запись видна, но не делает три операции единым целым.

| Операция | Атомарна? |
|---|---|
| `x = 5` (запись ссылки/литерала) | да |
| `x++`, `x += n` | нет |
| Проверка-и-действие (`if (x==0) x=1`) | нет |
| `long`/`double` без `volatile` | нет (в 64-бит может разорваться) |

Для атомарности — `synchronized`, `Lock` или атомики (раздел 7).

### 3.4. Memory barriers (барьеры памяти)

`volatile` вставляет барьеры:

- **volatile write** → все предыдущие записи сбрасываются в память до этой записи;
- **volatile read** → все последующие чтения происходят после неё.

Это и даёт одновременно видимость и запрет переупорядочивания. Барьеры бывают: LoadLoad, StoreStore, LoadStore, StoreLoad (самый дорогой).

### 3.5. Happens-before — сердце JMM

**Happens-before (hb)** — отношение частичного порядка: если действие A happens-before B, то результат A виден в B, и A не переупорядочится после B.

Основные правила:

| Правило | Смысл |
|---|---|
| Program order | Внутри одного потока — по порядку программы |
| Monitor lock | `unlock` монитора hb последующий `lock` того же монитора |
| Volatile | Запись `volatile` hb последующее чтение этой же переменной |
| Thread start | `Thread.start()` hb любой код нового потока |
| Thread join | Всё, что сделал поток, hb возврат из `join()` |
| Transitivity | A hb B и B hb C ⇒ A hb C |
| Final fields | Запись `final`-полей в конструкторе hb чтение после публикации |
| Interruption | `interrupt()` hb обнаружение прерывания |
| Default init | Значения по умолчанию (0, null) hb любое действие |

**Пример использования:** публикация объекта через `volatile`-ссылку без полной синхронизации.

```java
public class SafePublication {
    private volatile Config config;   // volatile-ссылка

    public void init() {
        Config c = new Config();      // 1. строим
        c.load();                     // 2. настраиваем
        config = c;                   // 3. публикуем (volatile write)
    }

    public void use() {
        Config c = config;            // volatile read — видим полностью готовый объект
        if (c != null) c.print();
    }
}
```

Благодаря hb «volatile write → volatile read», поток, увидевший ненулевую ссылку, увидит и все поля, записанные до публикации.

### 3.6. Final field semantics

Если поле объявлено `final` и присвоено в конструкторе, то после корректной публикации объекта **все потоки увидят его правильное значение** без дополнительной синхронизации. JMM гарантирует, что запись `final`-полей «замораживается» до конца конструктора.

Аналогия: `final` — это **запечатанная коробка**. Как только объект «вышел» из конструктора, коробку уже не переупакуют.

```java
public class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) {
        this.name = name;   // final-поля
        this.age = age;
    }
    // После публикации ссылки любой поток увидит корректные name и age
}
```

**Ловушка:** если `this` «утекает» из конструктора (например, регистрируется в статическом списке или запускается поток), final-гарантия может нарушиться.

### 3.7. Когда `volatile` достаточно

- один поток **пишет**, другие только **читают**;
- флаг остановки (`volatile boolean stopped`);
- «публикация» готового объекта по ссылке (как в примере 3.5);
- статус, который не зависит от предыдущего значения (`volatile State state; state = DONE;`);
- шаблон double-checked locking (в паре с локальной переменной).

**Когда недостаточно:** счётчики, накопление, «проверить-и-изменить», несколько связанных переменных.

### 3.8. Double-checked locking (правильный)

```java
public class Singleton {
    private static volatile Singleton instance;   // volatile обязателен!

    public static Singleton getInstance() {
        Singleton local = instance;               // локальная переменная
        if (local == null) {
            synchronized (Singleton.class) {
                local = instance;
                if (local == null) {
                    local = new Singleton();
                    instance = local;             // volatile write
                }
            }
        }
        return local;
    }
}
```

Без `volatile` второй поток мог бы увидеть **частично сконструированный** объект из-за переупорядочивания.

### 3.9. Типичные ошибки (раздел 3)

1. **Ждать от `volatile` атомарности** (`count++`).
2. **Забыть `volatile` в double-checked locking.**
3. **Считать, что `volatile` решает все проблемы видимости** для групп переменных.
4. **`this`-escape из конструктора** — ломает final-гарантии.
5. **Использовать `volatile` для «несколько писателей»** — нужна атомарность, а не видимость.
6. **Путать `volatile` с `AtomicInteger`**: первый — видимость, второй — видимость + атомарность.

### 3.10. Часто спрашивают (раздел 3)

- **Что гарантирует `volatile`?** Видимость и запрет переупорядочивания, но не атомарность.
- **Что такое happens-before?** Отношение, при котором результаты A видны в B.
- **Зачем `volatile` в DCL?** Чтобы избежать публикации частично построенного объекта.
- **Почему `long`/`double` особенные?** 64-битные значения могли разрываться при записи; `volatile` это чинит.

## 4. Проблемы конкурентности

### 4.1. Race condition (состояние гонки)

**Определение:** результат зависит от того, как чередуются потоки. Классика — `count++`.

```java
public class Race {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) count++;   // не атомарно!
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("count = " + count);  // почти всегда < 200000
    }
}
```

Ожидаемый вывод (примерный):
```
count = 137482
```

**Почему так:** `count++` = read + increment + write. Потоки перезаписывают результаты друг друга.

**Лечение:** `synchronized`, `AtomicInteger`, `LongAdder`.

### 4.2. Deadlock (взаимная блокировка)

**Определение:** потоки ждут ресурсы друг друга по кругу — никто не может продолжить.

Пример:

```java
public class DeadlockDemo {
    private static final Object A = new Object();
    private static final Object B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (A) {
                System.out.println("t1 держит A");
                try { Thread.sleep(100); } catch (InterruptedException ignored) {}
                synchronized (B) { System.out.println("t1 держит A и B"); }
            }
        });
        Thread t2 = new Thread(() -> {
            synchronized (B) {
                System.out.println("t2 держит B");
                try { Thread.sleep(100); } catch (InterruptedException ignored) {}
                synchronized (A) { System.out.println("t2 держит B и A"); }
            }
        });
        t1.start(); t2.start();
    }
}
```

Вывод (программа зависает):
```
t1 держит A
t2 держит B
```

#### Условия Коффмана (Coffman conditions)

Дедлок возможен, только когда выполнены **все четыре** условия:

| # | Условие | Суть |
|---|---|---|
| 1 | Взаимное исключение | Ресурс нельзя разделить, только один владелец |
| 2 | Удержание и ожидание | Поток держит один ресурс и ждёт другой |
| 3 | Отсутствие вытеснения | Ресурс нельзя отобрать силой |
| 4 | Циклическое ожидание | Цикл: A ждёт B, B ждёт A |

Достаточно разорвать **одно** условие, чтобы дедлок стал невозможен.

#### Как найти дедлок через `jstack`

```bash
jstack <pid> > dump.txt
```

В выводе ищите:
```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x... (object B),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x... (object A),
  which is held by "Thread-1"
```

Также `jconsole` / `jvisualvm` → кнопка **Detect Deadlock**.

#### Профилактика

1. **Единый порядок захвата** — главный приём: всегда брать замки в одном и том же порядке (например, сначала A, потом B).
2. **`tryLock` с таймаутом** — не удалось взять второй → отпустить первый и повторить.
3. **Минимизировать время удержания** и количество замков.
4. **Избегать вложенных блокировок**, где можно.
5. **Open call / не вызывать чужой код под замком.**

### 4.3. Livelock (живая блокировка)

**Определение:** потоки активны (не спят), но не продвигаются: бесконечно уступают друг другу.

Аналогия: двое в узком коридоре шагают в одну сторону, потом оба одновременно в другую — и так бесконечно.

```java
// Псевдокод: два потока пытаются уступить друг другу
while (true) {
    if (!otherThreadWantsToGo) { go(); break; }
    // уступаем
}
```

**Лечение:** рандомизация задержек (backoff), разный приоритет, порядок.

### 4.4. Starvation (голодание)

**Определение:** поток не получает ресурс из-за приоритетов или нечестной синхронизации, хотя система «работает».

Причины: высокоприоритетные потоки постоянно «обгоняют», нечестные локи, долгие критические секции.

**Лечение:** честные локи (`fair=true`), отказ от зависимости от приоритетов, справедливые очереди.

### 4.5. Сравнительная таблица проблем

| Проблема | Потоки работают? | Прогресс? | Причина |
|---|---|---|---|
| Race condition | да | да, но результат неверен | нет атомарности |
| Deadlock | нет (заблокированы) | нет | циклическое ожидание |
| Livelock | да (активны) | нет | бесконечные уступки |
| Starvation | да | у некоторых нет | приоритет/нечестность |

### 4.6. Типичные ошибки (раздел 4)

1. **Разный порядок захвата замков** — самый частый источник дедлока.
2. **Вызов внешнего/колбэк-кода под замком** — провоцирует дедлок.
3. **Долгие операции под замком** — увеличивает окно гонок и голодание.
4. **Игнорирование `Thread.interrupt()`** — потоки не отменяются.
5. **Уверенность, что «у меня дедлока не будет»** — без аудита порядка захвата.

### 4.7. Часто спрашивают (раздел 4)

- **Четыре условия дедлока?** Взаимное исключение, удержание-и-ожидание, отсутствие вытеснения, циклическое ожидание.
- **Как предотвратить?** Единый порядок захвата, `tryLock` с таймаутом.
- **Чем livelock отличается от deadlock?** Потоки активны, но прогресса нет.
- **Что такое starvation?** Поток не получает ресурс из-за конкуренции/приоритетов.

## 5. Вспомогательные синхронизаторы

Это готовые классы из `java.util.concurrent`, решающие типовые задачи координации. Не изобретайте велосипед на `wait/notify` — берите их.

### 5.1. `Semaphore` — счётчик разрешений

Семафор хранит число разрешений (permits). `acquire()` забирает одно (блокируется, если нет), `release()` возвращает.

Аналогия: **парковка на 3 места**. Пока есть места — заезжай; нет — жди у шлагбаума.

```java
import java.util.concurrent.Semaphore;

public class ConnectionPool {
    private final Semaphore semaphore;
    private final int poolSize;

    public ConnectionPool(int poolSize) {
        this.poolSize = poolSize;
        this.semaphore = new Semaphore(poolSize);   // N разрешений
    }

    public void useConnection(int id) throws InterruptedException {
        semaphore.acquire();               // ждём свободное соединение
        try {
            System.out.println("Поток " + id + " занял соединение");
            Thread.sleep(500);             // имитация работы
        } finally {
            semaphore.release();           // ВСЕГДА возвращаем разрешение
            System.out.println("Поток " + id + " освободил соединение");
        }
    }

    public static void main(String[] args) {
        ConnectionPool pool = new ConnectionPool(2);   // только 2 одновременно
        for (int i = 1; i <= 5; i++) {
            final int id = i;
            new Thread(() -> {
                try { pool.useConnection(id); }
                catch (InterruptedException ignored) {}
            }).start();
        }
    }
}
```

Вывод (порядок может отличаться, но не более 2 «занял» подряд):
```
Поток 1 занял соединение
Поток 2 занял соединение
Поток 1 освободил соединение
Поток 3 занял соединение
...
```

Методы: `acquire()` (блокирующе), `tryAcquire()`, `tryAcquire(timeout)`, `release(n)`, `availablePermits()`. Можно сделать fair-семафор `new Semaphore(n, true)`.

### 5.2. `CountDownLatch` — одноразовый забор

Счётчик, который считает **вниз**. Потоки ждут (`await()`), пока счётчик не станет 0 через `countDown()`. После этого — всё, использовать повторно нельзя.

Аналогия: **обратный отсчёт перед стартом ракеты**. Все ждут «0», потом бегут.

```java
import java.util.concurrent.CountDownLatch;

public class LatchDemo {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch ready = new CountDownLatch(3);   // ждём 3 задачи
        CountDownLatch start = new CountDownLatch(1);   // общий старт

        for (int i = 1; i <= 3; i++) {
            final int id = i;
            new Thread(() -> {
                try {
                    System.out.println("Поток " + id + " готов");
                    ready.countDown();      // сообщаем о готовности
                    start.await();          // ждём сигнал старта
                    System.out.println("Поток " + id + " побежал!");
                } catch (InterruptedException ignored) {}
            }).start();
        }

        ready.await();                       // главный ждёт всех
        System.out.println("Все готовы. Старт!");
        start.countDown();                   // запускаем всех разом
    }
}
```

Ожидаемый вывод:
```
Поток 1 готов
Поток 3 готов
Поток 2 готов
Все готовы. Старт!
Поток 1 побежал!
Поток 2 побежал!
Поток 3 побежал!
```

### 5.3. `CyclicBarrier` — многоразовый барьер

Барьер, который **считает вверх**: N потоков должны дойти до точки и ждать друг друга. Когда пришёл N-й — все продолжают, а счётчик **сбрасывается** и барьер можно использовать снова. Опционально можно задать действие, выполняемое при прохождении барьера.

Аналогия: **группа туристов на перевале**. Все ждут последнего, потом идут дальше. И так на каждом этапе.

```java
import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CyclicBarrier;

public class BarrierDemo {
    public static void main(String[] args) {
        int parties = 3;
        // Действие при достижении барьера (выполняет последний пришедший)
        CyclicBarrier barrier = new CyclicBarrier(parties,
            () -> System.out.println("--- Все собрались, следующий этап ---"));

        for (int i = 1; i <= parties; i++) {
            final int id = i;
            new Thread(() -> {
                try {
                    for (int phase = 1; phase <= 2; phase++) {
                        System.out.println("Поток " + id + " завершил фазу " + phase);
                        barrier.await();   // ждём остальных
                    }
                } catch (InterruptedException | BrokenBarrierException ignored) {}
            }).start();
        }
    }
}
```

Ожидаемый вывод:
```
Поток 1 завершил фазу 1
Поток 2 завершил фазу 1
Поток 3 завершил фазу 1
--- Все собрались, следующий этап ---
Поток 1 завершил фазу 2
Поток 2 завершил фазу 2
Поток 3 завершил фазу 2
--- Все собрались, следующий этап ---
```

### 5.4. `CountDownLatch` vs `CyclicBarrier`

| | `CountDownLatch` | `CyclicBarrier` |
|---|---|---|
| Направление | вниз (`countDown`) | вверх (все `await`) |
| Многоразовость | нет (одноразовый) | да (сбрасывается) |
| Кто ждёт | ожидающие ждут «счётчиков» | потоки ждут **друг друга** |
| Действие при достижении | нет | есть (Runnable) |
| Типичный сценарий | старт после инициализации | фазы вычислений |

### 5.5. `Phaser` — гибкий барьер с фазами

`Phaser` — это «умный» `CyclicBarrier`: число участников можно **динамически** менять (`register`/`arriveAndDeregister`), есть номер фазы (`getPhase()`).

Аналогия: **барьер на конвейере**, куда рабочие могут приходить и уходить, а фазы нумеруются.

```java
import java.util.concurrent.Phaser;

public class PhaserDemo {
    public static void main(String[] args) {
        Phaser phaser = new Phaser(1);   // главный поток — участник

        for (int i = 1; i <= 3; i++) {
            final int id = i;
            phaser.register();           // добавляем участника
            new Thread(() -> {
                System.out.println("Поток " + id + " фаза " + phaser.getPhase());
                phaser.arriveAndAwaitAdvance();   // барьер
                System.out.println("Поток " + id + " продолжает");
                phaser.arriveAndDeregister();     // вышел
            }).start();
        }

        phaser.arriveAndDeregister();    // главный отпускает себя
    }
}
```

### 5.6. `Exchanger` — обмен между двумя потоками

Точка, где два потока обмениваются объектами. Оба вызывают `exchange(obj)` и получают объект собеседника.

Аналогия: **передача эстафеты** между двумя бегунами.

```java
import java.util.concurrent.Exchanger;

public class ExchangerDemo {
    public static void main(String[] args) {
        Exchanger<String> exchanger = new Exchanger<>();
        new Thread(() -> {
            try {
                String got = exchanger.exchange("от Потока-1");
                System.out.println("Поток-1 получил: " + got);
            } catch (InterruptedException ignored) {}
        }).start();
        new Thread(() -> {
            try {
                String got = exchanger.exchange("от Потока-2");
                System.out.println("Поток-2 получил: " + got);
            } catch (InterruptedException ignored) {}
        }).start();
    }
}
```

Вывод:
```
Поток-1 получил: от Потока-2
Поток-2 получил: от Потока-1
```

### 5.7. `LockSupport` — низкоуровневые `park`/`unpark`

`LockSupport.park()` усыпляет текущий поток, `unpark(thread)` будит конкретный поток. Это «строительные блоки», на которых построены `AQS` (а значит `ReentrantLock`, семафоры, латчи). Отличие от `wait/notify`: не нужно владеть монитором, можно будить конкретный поток, `unpark` «запоминается» (разрешение).

```java
import java.util.concurrent.locks.LockSupport;

public class ParkDemo {
    public static void main(String[] args) {
        Thread worker = new Thread(() -> {
            System.out.println("Worker: паркуюсь");
            LockSupport.park();          // спим
            System.out.println("Worker: разбудили!");
        });
        worker.start();
        try { Thread.sleep(500); } catch (InterruptedException ignored) {}
        System.out.println("Main: бужу worker");
        LockSupport.unpark(worker);      // будим конкретный поток
    }
}
```

### 5.8. Таблица сравнения синхронизаторов

| Класс | Назначение | Многоразовый | Особенность |
|---|---|---|---|
| `Semaphore` | ограничение параллелизма | да | счётчик разрешений |
| `CountDownLatch` | ждать завершения N событий | нет | считает вниз |
| `CyclicBarrier` | встреча N потоков | да | считает вверх, действие |
| `Phaser` | фазы + динамика участников | да | register/deregister |
| `Exchanger` | обмен между 2 потоками | да | парный обмен |
| `LockSupport` | park/unpark | — | основа AQS |

### 5.9. Типичные ошибки (раздел 5)

1. **Забыть `release()` у семафора** — разрешения «утекают», пул встаёт.
2. **Пытаться переиспользовать `CountDownLatch`** — он одноразовый.
3. **Неверное число parties у барьера** — потоки висят вечно.
4. **`BrokenBarrierException`** игнорировать — барьер «сломан», нужно восстанавливать логику.
5. **Дедлок между семафорами** при неправильном порядке `acquire`.

### 5.10. Часто спрашивают (раздел 5)

- **`CountDownLatch` vs `CyclicBarrier`?** Одноразовый вниз vs многоразовый вверх.
- **Зачем `Semaphore`?** Ограничить число одновременных доступов (пул, rate limit).
- **Что делает `Phaser`?** Динамические фазы с изменяемым числом участников.
- **`LockSupport` vs `wait/notify`?** Не нужен монитор, точный `unpark`, разрешение запоминается.

## 6. Concurrent-коллекции

Обычные `ArrayList`, `HashMap` **не потокобезопасны**. Есть два пути: оборачивать в `Collections.synchronized...` (грубо, медленно) или использовать специальные коллекции из `java.util.concurrent`.

### 6.1. `ConcurrentHashMap`

Самая важная коллекция. В Java 8+ устроена так:

- **нет сегментов** (в отличие от Java 7);
- используется **CAS** для пустых корзин и **`synchronized` на головном узле корзины** (`bin`) для конфликтов;
- степень параллелизма — фактически число корзин;
- **запрещены `null`** (ни ключ, ни значение) — иначе нельзя отличить «нет ключа» от «значение null» в конкурентном контексте;
- потокобезопасные составные операции: `putIfAbsent`, `computeIfAbsent`, `compute`, `merge`.

```java
import java.util.concurrent.ConcurrentHashMap;

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

map.put("a", 1);
map.putIfAbsent("a", 99);                       // не перезапишет → останется 1
map.merge("a", 1, Integer::sum);                // a = 2

// computeIfAbsent: атомарно создаёт значение, если ключа нет
map.computeIfAbsent("b", k -> expensiveLoad(k));

System.out.println(map);   // {a=2, b=...}
```

**Почему `computeIfAbsent` важен:** это атомарная операция «проверить-и-создать». Без неё классический паттерн `if (!map.containsKey(k)) map.put(k, v)` — гонка.

**Внутреннее чтение не блокирует:** `get` почти всегда без блокировок (volatile-чтение узлов), запись синхронизируется только на конкретной корзине.

### 6.2. `CopyOnWriteArrayList` / `CopyOnWriteArraySet`

**Copy-on-write (COW):** при каждой записи создаётся **новая копия** всего массива, а ссылка атомарно подменяется. Читатели работают со старым снимком без блокировок.

Аналогия: **доска с расписанием**. Чтобы изменить — стираешь всю доску и пишешь заново на новой, а старую показываешь тем, кто уже смотрит.

```java
import java.util.concurrent.CopyOnWriteArrayList;

CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("A");
list.add("B");
for (String s : list) {          // безопасный обход даже при изменении
    System.out.println(s);
}
```

**Когда использовать:** чтений намного больше, чем записей (списки слушателей, конфигурации, подписчики). **Когда нет:** частая запись — копирование дорого (O(n) на каждую запись).

### 6.3. `BlockingQueue` — сердце producer-consumer

Интерфейс с блокирующими операциями. Реализации отличаются буферизацией и блокировками.

| Реализация | Буфер | Блокировки | Особенность |
|---|---|---|---|
| `ArrayBlockingQueue` | фиксированный массив | одна (Lock) | честность опционально |
| `LinkedBlockingQueue` | опционально ограничен | две (put/take) | выше throughput |
| `PriorityBlockingQueue` | неограниченный | одна | приоритеты |
| `SynchronousQueue` | нет (0) | — | передача «из рук в руки» |
| `DelayQueue` | неограниченный | — | доступ по истечении задержки |
| `LinkedTransferQueue` | неограниченный | — | transfer(), эффективнее |

#### Методы `BlockingQueue`

| Действие | Блокирует | Возвращает спец. значение | Бросает исключение | Таймаут |
|---|---|---|---|---|
| Добавить | `put(e)` | `offer(e)` → false | `add(e)` | `offer(e, t, unit)` |
| Забрать | `take()` | `poll()` → null | `remove()` | `poll(t, unit)` |
| Посмотреть | — | `peek()` → null | `element()` | — |

```java
import java.util.concurrent.*;

BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

// Producer
new Thread(() -> {
    try {
        for (int i = 0; i < 5; i++) {
            queue.put(i);                       // блокируется, если полна
            System.out.println("Положил " + i);
        }
    } catch (InterruptedException ignored) {}
}).start();

// Consumer
new Thread(() -> {
    try {
        for (int i = 0; i < 5; i++) {
            Integer v = queue.take();           // блокируется, если пуста
            System.out.println("Забрал " + v);
        }
    } catch (InterruptedException ignored) {}
}).start();
```

#### `SynchronousQueue`

Очередь **без ёмкости**: `put` блокируется, пока кто-то не сделает `take`. Это «передача из рук в руки». Используется в `newCachedThreadPool()`.

### 6.4. `ConcurrentLinkedQueue`

Неблокирующая (lock-free) очередь на алгоритме Michael-Scott, через CAS. `size()` — дорогая операция (проходит по списку), поэтому не полагайтесь на неё в цикле.

```java
ConcurrentLinkedQueue<String> q = new ConcurrentLinkedQueue<>();
q.offer("x");
q.offer("y");
System.out.println(q.poll());   // x
```

### 6.5. `ConcurrentSkipListMap` / `ConcurrentSkipListSet`

Отсортированные (по ключу) и потокобезопасные, на основе **skip list** (вероятностная структура, дающая O(log n)). Заменяют `TreeMap`/`TreeSet` в многопоточном контексте.

```java
import java.util.concurrent.ConcurrentSkipListMap;

ConcurrentSkipListMap<Integer, String> m = new ConcurrentSkipListMap<>();
m.put(3, "three");
m.put(1, "one");
m.put(2, "two");
System.out.println(m);              // {1=one, 2=two, 3=three} — отсортировано
System.out.println(m.firstKey());   // 1
```

### 6.6. Типичные ошибки (раздел 6)

1. **`null` в `ConcurrentHashMap`** → `NullPointerException`.
2. **Составные операции без атомарных методов** (`get`+`put` вместо `computeIfAbsent`).
3. **`CopyOnWriteArrayList` при частой записи** → дикие тормоза.
4. **Итерация `synchronized`-обёрток без внешней синхронизации** → `ConcurrentModificationException`.
5. **`size()` в цикле у `ConcurrentLinkedQueue`** → O(n) каждый раз.

### 6.7. Часто спрашивают (раздел 6)

- **Как устроен `ConcurrentHashMap` в Java 8?** CAS + `synchronized` на корзине, без сегментов.
- **Почему запрещён `null`?** Невозможно отличить отсутствие ключа от значения `null` в конкурентном коде.
- **`ArrayBlockingQueue` vs `LinkedBlockingQueue`?** Одна блокировка и массив vs две блокировки и узлы.
- **Когда `CopyOnWriteArrayList`?** Много чтений, мало записей.
- **`ConcurrentHashMap` vs `Hashtable`?** Первый масштабируется, второй — один глобальный замок.

## 7. Атомарные классы и CAS

### 7.1. Что такое CAS

**CAS (Compare-And-Swap)** — атомарная инструкция процессора: «если значение в памяти равно ожидаемому, замени его на новое». Возвращает успех/неуспех.

```
boolean CAS(address, expected, update):
    if (*address == expected):
        *address = update
        return true
    return false
```

В Java реализован через `sun.misc.Unsafe` / `VarHandle`. CAS — основа **lock-free** алгоритмов: не нужно блокировок, потоки не спят, а «пробуют и повторяют» (retry loop).

```java
// Как устроен incrementAndGet у AtomicInteger (упрощённо):
do {
    int current = get();
    int next = current + 1;
} while (!compareAndSet(current, next));
```

### 7.2. Основные атомарные классы

| Класс | Для чего |
|---|---|
| `AtomicInteger` | счётчики int |
| `AtomicLong` | счётчики long |
| `AtomicBoolean` | флаги |
| `AtomicReference<T>` | ссылки на объекты |
| `AtomicIntegerArray` / `AtomicLongArray` | массивы |
| `AtomicStampedReference` | ссылка + версия (ABA) |
| `AtomicMarkableReference` | ссылка + boolean-метка |

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger count = new AtomicInteger(0);

System.out.println(count.incrementAndGet());   // 1
System.out.println(count.getAndIncrement());   // 1 (возвращает старое)
System.out.println(count.get());               // 2
System.out.println(count.compareAndSet(2, 10)); // true
System.out.println(count.get());               // 10

// Функциональные обновления (могут выполняться несколько раз — должны быть без side-effect!)
count.updateAndGet(x -> x + 5);
System.out.println(count.get());               // 15
```

### 7.3. ABA-проблема

**Сценарий:** поток A читает значение `X`. Пока A думает, поток B меняет `X → Y → X`. A делает CAS(`X`, new) — и думает, что ничего не менялось. Но структура могла уже быть перестроена.

Аналогия: ты оставил на столе **кошелёк**. Кто-то его забрал, положил деньги и вернул такой же кошелёк. Ты видишь «кошелёк на месте» — но содержимое изменилось.

**Решение:** добавить **версию** (stamp). `AtomicStampedReference` проверяет и ссылку, и версию.

```java
import java.util.concurrent.atomic.AtomicStampedReference;

AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);

int stamp = ref.getStamp();
boolean ok = ref.compareAndSet("A", "B", stamp, stamp + 1);
System.out.println(ok + ", значение=" + ref.getReference()
                   + ", версия=" + ref.getStamp());   // true, B, 1
```

Даже если значение вернётся к `A`, версия изменится — CAS заметит.

### 7.4. `LongAdder` vs `AtomicLong`

При **высокой конкуренции** `AtomicLong` страдает: все потоки CAS-ят одну ячейку и «передерутся». `LongAdder` держит **массив ячеек** (cells); каждый поток пишет в свою, а `sum()` складывает все.

| | `AtomicLong` | `LongAdder` |
|---|---|---|
| Запись при конкуренции | плохо (один адрес) | отлично (ячейки) |
| Чтение | O(1), точное | O(число ячеек), сумма |
| Точность в момент чтения | точная | приблизительная (сходится) |
| Когда брать | нужен точный текущий счётчик | статистика, метрики, много инкрементов |

```java
import java.util.concurrent.atomic.LongAdder;

LongAdder adder = new LongAdder();
adder.increment();
adder.add(10);
System.out.println(adder.sum());   // 11
```

### 7.5. `VarHandle` (Java 9+)

Современная замена `Unsafe`. Даёт типизированный доступ к полям с разными режимами памяти (`getVolatile`, `compareAndSet`, `getAcquire` и т. д.). Используется в `java.util.concurrent`. В обычном коде нужен редко.

```java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public class VarHandleDemo {
    private volatile int value;
    private static final VarHandle VALUE;
    static {
        try {
            VALUE = MethodHandles.lookup()
                .findVarHandle(VarHandleDemo.class, "value", int.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }

    public void set(int v)   { VALUE.setVolatile(this, v); }
    public int get()         { return (int) VALUE.getVolatile(this); }
    public boolean cas(int e, int u) { return VALUE.compareAndSet(this, e, u); }
}
```

### 7.6. Типичные ошибки (раздел 7)

1. **Использование `AtomicInteger` для составных инвариантов** (несколько полей).
2. **Side-effect в лямбдах `updateAndGet`/`compute`** — могут выполниться повторно.
3. **Игнорирование ABA** в lock-free структурах.
4. **`AtomicLong` как метрика под нагрузкой** — берите `LongAdder`.
5. **`set` вместо `compareAndSet`** там, где важна атомарность проверки.

### 7.7. Часто спрашивают (раздел 7)

- **Что такое CAS?** Атомарная «сравнить-и-заменить» на уровне CPU.
- **Что такое ABA?** Значение вернулось к исходному; лечится версией (`AtomicStampedReference`).
- **`AtomicLong` vs `LongAdder`?** Точность vs масштабируемость под конкуренцией.
- **Чем `volatile` отличается от `AtomicInteger`?** Видимость vs видимость + атомарность.

## 8. Executors и пулы потоков

### 8.1. Зачем пулы

Создавать новый поток на каждую задачу дорого (память ~1 МБ стека, время на создание). Пул переиспользует потоки. Аналогия: **такси-парк** — не покупать машину на каждую поездку, а держать несколько и развозить клиентов.

```java
import java.util.concurrent.*;

ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Integer> f = pool.submit(() -> 21 * 2);
System.out.println(f.get());     // 42

pool.shutdown();                                  // завершить после задач
pool.awaitTermination(1, TimeUnit.MINUTES);       // подождать
// pool.shutdownNow();                            // прервать активные
```

### 8.2. Виды пулов через `Executors`

| Фабрика | Потоки | Очередь | Риск |
|---|---|---|---|
| `newFixedThreadPool(n)` | фиксировано n | **неограниченная** `LinkedBlockingQueue` | **OOM** при перегрузке |
| `newCachedThreadPool()` | по необходимости, 60с idle | `SynchronousQueue` | рост числа потоков |
| `newSingleThreadExecutor()` | 1 | неограниченная | порядок гарантирован, но OOM |
| `newScheduledThreadPool(n)` | n | DelayedWorkQueue | периодические задачи |
| `newWorkStealingPool()` | по CPU | work-stealing | ForkJoinPool |

**Опасность `newFixedThreadPool`:** его очередь **неограниченная**. Если задачи приходят быстрее, чем обрабатываются, очередь растёт и в итоге — `OutOfMemoryError`. Именно поэтому в проде **лучше создавать `ThreadPoolExecutor` явно** и задавать ограниченную очередь + политику отказа.

### 8.3. `ThreadPoolExecutor` — все параметры

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4,                              // corePoolSize — базовое число потоков
    16,                             // maximumPoolSize — максимум
    60, TimeUnit.SECONDS,           // keepAliveTime — сколько живут лишние
    new ArrayBlockingQueue<>(100),  // workQueue — ограниченная очередь!
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // что делать при переполнении
);
```

**Как пул принимает решение:**

1. Если потоков меньше `corePoolSize` → создаёт новый поток.
2. Иначе если очередь не полна → кладёт задачу в очередь.
3. Иначе если потоков меньше `maximumPoolSize` → создаёт новый поток.
4. Иначе → вызывает `RejectedExecutionHandler`.

Важно: лишние потоки (сверх core) создаются **только когда очередь заполнена**. Поэтому маленькая очередь + большой max = более «отзывчивый» пул.

### 8.4. `RejectedExecutionHandler` — политики отказа

| Политика | Поведение |
|---|---|
| `AbortPolicy` (по умолчанию) | бросает `RejectedExecutionException` |
| `CallerRunsPolicy` | выполняет задачу в потоке-отправителе (backpressure) |
| `DiscardPolicy` | молча выбрасывает задачу |
| `DiscardOldestPolicy` | выбрасывает старейшую задачу в очереди, пробует снова |

### 8.5. Завершение пула: `shutdown` / `awaitTermination` / `shutdownNow`

```java
pool.shutdown();                              // 1. не берём новые задачи, доделываем текущие
if (!pool.awaitTermination(60, TimeUnit.SECONDS)) {
    pool.shutdownNow();                       // 2. прерываем всё оставшееся
}
```

| Метод | Новые задачи | Текущие задачи | Очередь |
|---|---|---|---|
| `shutdown()` | отклоняются | доделываются | доделывается |
| `shutdownNow()` | отклоняются | прерываются | возвращается список невыполненных |
| `awaitTermination()` | — | ждёт завершения | ждёт |

### 8.6. `ForkJoinPool` и work-stealing

Для задач «разделяй и властвуй». Каждый поток имеет **свою двустороннюю очередь**. Когда поток простаивает, он **крадёт** задачи с хвоста чужой очереди (work-stealing).

Аналогия: **команда грузчиков**. Каждый разгружает свой ящик; освободился — помогает соседу, беря задачу «с конца», чтобы меньше мешать.

```java
import java.util.concurrent.RecursiveTask;
import java.util.concurrent.ForkJoinPool;

public class SumTask extends RecursiveTask<Long> {
    private final int[] arr;
    private final int lo, hi;

    public SumTask(int[] arr, int lo, int hi) {
        this.arr = arr; this.lo = lo; this.hi = hi;
    }

    @Override
    protected Long compute() {
        if (hi - lo <= 1000) {          // маленькая задача — считаем сами
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += arr[i];
            return sum;
        }
        int mid = (lo + hi) / 2;
        SumTask left = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                    // запускаем левую асинхронно
        long rightResult = right.compute();
        long leftResult = left.join();  // ждём левую
        return leftResult + rightResult;
    }

    public static void main(String[] args) {
        int[] arr = new int[1_000_000];
        for (int i = 0; i < arr.length; i++) arr[i] = 1;
        long sum = new ForkJoinPool().invoke(new SumTask(arr, 0, arr.length));
        System.out.println(sum);        // 1000000
    }
}
```

`parallelStream()` использует общий `ForkJoinPool.commonPool()`.

### 8.7. `CompletableFuture`

Позволяет строить **цепочки асинхронных операций** без ручной блокировки на `Future.get()`.

| Метод | Смысл |
|---|---|
| `supplyAsync` | асинхронно вычислить значение |
| `runAsync` | асинхронно выполнить без результата |
| `thenApply` | преобразовать результат (map) |
| `thenCompose` | «сплющить» вложенный future (flatMap) |
| `thenCombine` | объединить два независимых future |
| `thenAccept` | потребить результат |
| `exceptionally` | обработать ошибку, вернуть fallback |
| `handle` | обработать и результат, и ошибку |
| `allOf` | ждать все |
| `anyOf` | ждать первый |

```java
import java.util.concurrent.CompletableFuture;

CompletableFuture<String> cf =
    CompletableFuture.supplyAsync(() -> "hello")          // асинхронно
        .thenApply(String::toUpperCase)                   // HELLO
        .thenApply(s -> s + "!")                          // HELLO!
        .exceptionally(ex -> "fallback");                 // при ошибке

System.out.println(cf.join());   // HELLO!
```

`thenApply` vs `thenCompose`:

```java
// thenApply вернёт CompletableFuture<CompletableFuture<T>> — "вложенность"
CompletableFuture<CompletableFuture<String>> nested =
    CompletableFuture.supplyAsync(() -> "a")
        .thenApply(s -> CompletableFuture.supplyAsync(() -> s + "b"));

// thenCompose "выравнивает" — CompletableFuture<String>
CompletableFuture<String> flat =
    CompletableFuture.supplyAsync(() -> "a")
        .thenCompose(s -> CompletableFuture.supplyAsync(() -> s + "b"));

System.out.println(flat.join());   // ab
```

`thenCombine` (два независимых источника):

```java
CompletableFuture<String> a = CompletableFuture.supplyAsync(() -> "A");
CompletableFuture<String> b = CompletableFuture.supplyAsync(() -> "B");
CompletableFuture<String> both = a.thenCombine(b, (x, y) -> x + y);
System.out.println(both.join());   // AB
```

`allOf` (ждём все):

```java
CompletableFuture<Void> all = CompletableFuture.allOf(
    CompletableFuture.runAsync(() -> System.out.println("1")),
    CompletableFuture.runAsync(() -> System.out.println("2")),
    CompletableFuture.runAsync(() -> System.out.println("3"))
);
all.join();
System.out.println("Все завершены");
```

### 8.8. Типичные ошибки (раздел 8)

1. **`newFixedThreadPool` в проде** с неограниченной очередью → OOM.
2. **Не вызывать `shutdown()`** — пул держит потоки, приложение не завершается.
3. **`shutdownNow()` без обработки `InterruptedException`** — задачи «глотают» прерывание.
4. **Блокирующие вызовы внутри задач ForkJoinPool** — ломает work-stealing.
5. **`thenApply` вместо `thenCompose`** — получаете вложенные future.
6. **Игнорирование исключений** в асинхронных цепочках → тихие потери.

### 8.9. Часто спрашивают (раздел 8)

- **Чем опасен `newFixedThreadPool`?** Неограниченная очередь → OOM.
- **Как работает `ThreadPoolExecutor`?** core → очередь → max → rejection.
- **`shutdown` vs `shutdownNow`?** Доделать текущие vs прервать.
- **Что такое work-stealing?** Простаивающий поток крадёт задачи у занятого.
- **`thenApply` vs `thenCompose`?** map vs flatMap.

## 9. ThreadLocal

### 9.1. Зачем нужен

`ThreadLocal` даёт каждому потоку **свою копию** переменной. Разные потоки не мешают друг другу, синхронизация не нужна.

Аналогия: **личный шкафчик** у каждого сотрудника. Одинаковый «адрес» (переменная), но у каждого свои вещи.

```java
public class ThreadLocalDemo {
    private static final ThreadLocal<Integer> counter =
        ThreadLocal.withInitial(() -> 0);

    public static void main(String[] args) {
        Runnable task = () -> {
            for (int i = 0; i < 3; i++) {
                counter.set(counter.get() + 1);
            }
            System.out.println(Thread.currentThread().getName()
                               + " -> " + counter.get());
        };
        new Thread(task, "A").start();
        new Thread(task, "B").start();
    }
}
```

Вывод:
```
A -> 3
B -> 3
```

Каждый поток видит свои `3` — копии независимы.

### 9.2. Классический пример: `SimpleDateFormat`

`SimpleDateFormat` **не потокобезопасен**. Вместо `synchronized` (медленно) можно дать каждому потоку свой экземпляр через `ThreadLocal`.

```java
import java.text.SimpleDateFormat;
import java.util.Date;

public class DateFormatter {
    private static final ThreadLocal<SimpleDateFormat> FORMATTER =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));

    public static String format(Date date) {
        return FORMATTER.get().format(date);   // у каждого потока свой объект
    }

    public static void main(String[] args) {
        System.out.println(format(new Date()));
    }
}
```

### 9.3. Где ещё применяют

- контекст запроса (request id, пользователь, security context);
- сессия, транзакция (Spring `RequestContextHolder`, `TransactionSynchronizationManager`);
- не-потокобезопасные буферы/парсеры;
- «неявные» параметры, чтобы не тащить их через все методы.

### 9.4. Утечка памяти и `remove()`

Внутри каждого `Thread` есть `ThreadLocalMap`. Ключ — **слабая ссылка** на `ThreadLocal`, значение — **сильная ссылка** на объект.

Проблема: в пуле потоки **живут долго**. Если `ThreadLocal`-ключ больше не используется, ключ может быть собран GC (слабая ссылка), но **значение останется висеть** (сильная ссылка) до следующего обращения к map. Это и есть утечка.

Аналогия: **шкафчик уволенного сотрудника**, который никто не освободил — занимает место вечно.

```java
private static final ThreadLocal<byte[]> BUFFER = new ThreadLocal<>();

public void handle() {
    try {
        BUFFER.set(new byte[1024 * 1024]);   // 1 МБ на поток
        // ... работа
    } finally {
        BUFFER.remove();                     // ОБЯЗАТЕЛЬНО! Иначе утечка в пуле
    }
}
```

**Правило:** всегда `remove()` в `finally`, если поток из пула (почти всегда).

### 9.5. `InheritableThreadLocal`

Обычный `ThreadLocal` **не наследуется** дочерними потоками. `InheritableThreadLocal` копирует значение родителя в момент **создания** дочернего потока.

```java
public class InheritableDemo {
    private static final ThreadLocal<String> normal = new ThreadLocal<>();
    private static final InheritableThreadLocal<String> inheritable =
        new InheritableThreadLocal<>();

    public static void main(String[] args) {
        normal.set("normal-value");
        inheritable.set("inheritable-value");

        new Thread(() -> {
            System.out.println("normal      = " + normal.get());       // null
            System.out.println("inheritable = " + inheritable.get());  // inheritable-value
        }).start();
    }
}
```

Вывод:
```
normal      = null
inheritable = inheritable-value
```

**Важно:** копирование происходит при создании потока, а не при его запуске. В пулах потоки создаются заранее, поэтому `InheritableThreadLocal` там почти бесполезен — для таких случаев есть `TransmittableThreadLocal` (внешняя библиотека).

### 9.6. Типичные ошибки (раздел 9)

1. **Не вызывать `remove()`** в пуле потоков → утечка и «грязные» значения между задачами.
2. **Хранить тяжёлые объекты** (гигабайтные буферы) в `ThreadLocal`.
3. **Ждать наследования в пуле** через `InheritableThreadLocal`.
4. **Использовать `ThreadLocal` как глобальную переменную** — теряется контекст.
5. **`static` + долгоживущий `ThreadLocal` без очистки** — классическая утечка в веб-приложениях.

### 9.7. Часто спрашивают (раздел 9)

- **Что такое `ThreadLocal`?** Своя копия переменной у каждого потока.
- **Почему утечка?** Ключ — слабая ссылка, значение — сильная; долгоживущий поток держит значение.
- **Как избежать?** `remove()` в `finally`.
- **`ThreadLocal` vs `InheritableThreadLocal`?** Второй копирует значение родителя при создании потока.

## 10. Шпаргалка

- **`Lock` vs `synchronized`:** `Lock` гибче (`tryLock`, таймауты, fairness, несколько `Condition`); `unlock` — всегда в `finally`.
- **Реентерабельность:** повторный захват замка тем же потоком, ведётся счётчик.
- **`Condition`:** несколько очередей ожидания на один `Lock`; `await`/`signal` в цикле `while`.
- **`ReadWriteLock`:** много читателей ИЛИ один писатель; `StampedLock` — optimistic read, но не реентерабелен.
- **`volatile`:** видимость + запрет переупорядочивания, **не** атомарность.
- **happens-before:** правила, при которых результат A виден в B (lock, volatile, start, join, final).
- **`final`-поля:** корректно видны после конструктора (если `this` не «утекает»).
- **Race condition:** неверный результат из-за чередования; лечится атомарностью.
- **Deadlock:** циклическое ожидание; условия Коффмана; лечение — единый порядок захвата, `tryLock`; ищите через `jstack`.
- **Livelock:** активны, но нет прогресса; лечение — backoff/рандомизация.
- **Starvation:** голодание из-за приоритетов/нечестности; лечение — fair-локи.
- **Semaphore:** разрешения; **CountDownLatch:** одноразовый вниз; **CyclicBarrier:** многоразовый вверх; **Phaser:** динамика; **Exchanger:** парный обмен; **LockSupport:** park/unpark.
- **ConcurrentHashMap:** CAS + `synchronized` на корзине, без `null`, атомарные `computeIfAbsent`/`merge`.
- **CopyOnWriteArrayList:** снимок при записи; много чтений, мало записей.
- **BlockingQueue:** `put/take` блокируют, `offer/poll` с таймаутом, `add/remove` бросают.
- **CAS:** compare-and-swap; lock-free; **ABA** лечится `AtomicStampedReference`.
- **LongAdder** лучше `AtomicLong` при высокой конкуренции; **VarHandle** — современный доступ.
- **Пул:** создавайте явно через `new ThreadPoolExecutor(...)` с ограниченной очередью и `RejectedExecutionHandler`.
- **ForkJoinPool:** work-stealing; **CompletableFuture:** `thenApply`/`thenCompose`/`thenCombine`/`allOf`/`exceptionally`.
- **ThreadLocal:** своя копия у потока; всегда `remove()` в `finally`; `InheritableThreadLocal` копирует при создании потока.

## 11. Частые вопросы на собеседовании с короткими ответами

1. **Чем `Lock` лучше `synchronized`?**
   `tryLock`, таймауты, прерываемое ожидание, fairness, несколько `Condition`, `ReadWriteLock`. Скорость в Java 6+ сопоставима.

2. **Почему `unlock()` в `finally`?**
   Чтобы освободить замок даже при исключении, иначе поток зависнет навсегда.

3. **Что такое реентерабельность?**
   Возможность потока повторно захватить уже удерживаемый им замок; ведётся счётчик удержаний.

4. **`Condition` вместо `wait/notify` — зачем?**
   Несколько независимых очередей ожидания и точные сигналы.

5. **Когда `ReadWriteLock` полезен?**
   Когда чтений заметно больше записей и читатели могут идти параллельно.

6. **Что такое optimistic read в `StampedLock`?**
   Чтение без блокировки + `validate(stamp)`; если была запись — перечитать под read lock.

7. **Что гарантирует `volatile`?**
   Видимость и запрет переупорядочивания. Не атомарность.

8. **Почему `count++` не атомарен?**
   Это read + increment + write; два потока могут потерять обновления.

9. **Что такое happens-before?**
   Отношение, при котором результат A гарантированно виден в B.

10. **Зачем `volatile` в double-checked locking?**
    Чтобы другой поток не увидел частично сконструированный объект.

11. **Четыре условия дедлока?**
    Взаимное исключение, удержание-и-ожидание, отсутствие вытеснения, циклическое ожидание.

12. **Как предотвратить дедлок?**
    Единый порядок захвата, `tryLock` с таймаутом, минимум замков.

13. **Как найти дедлок?**
    `jstack <pid>` («Found one Java-level deadlock»), `jconsole`/`jvisualvm`.

14. **Livelock vs deadlock?**
    В livelock потоки активны, но не продвигаются; в deadlock — заблокированы.

15. **`CountDownLatch` vs `CyclicBarrier`?**
    Одноразовый счёт вниз vs многоразовый счёт вверх с ожиданием друг друга.

16. **Зачем `Semaphore`?**
    Ограничить число одновременных доступов (пул соединений, rate limiting).

17. **Как устроен `ConcurrentHashMap` в Java 8?**
    CAS + `synchronized` на корзине, без сегментов; запрещены `null`.

18. **Почему `ConcurrentHashMap` запрещает `null`?**
    Нельзя отличить отсутствие ключа от значения `null` в конкурентном коде.

19. **Когда `CopyOnWriteArrayList`?**
    Много чтений и мало записей.

20. **`put` vs `offer` в `BlockingQueue`?**
    `put` блокируется, `offer` возвращает `false`/ждёт с таймаутом.

21. **Что такое CAS?**
    Атомарная инструкция «сравнить и заменить», основа lock-free.

22. **Что такое ABA-проблема?**
    Значение вернулось к исходному; лечится версией (`AtomicStampedReference`).

23. **`AtomicLong` vs `LongAdder`?**
    Точность vs масштабируемость под высокой конкуренцией.

24. **Чем опасен `newFixedThreadPool`?**
    Неограниченная очередь → `OutOfMemoryError`; лучше `ThreadPoolExecutor` явно.

25. **`shutdown` vs `shutdownNow`?**
    Доделать текущие задачи vs прервать и вернуть невыполненные.

26. **Что такое work-stealing?**
    Простаивающий поток крадёт задачи у занятого (ForkJoinPool).

27. **`thenApply` vs `thenCompose`?**
    map vs flatMap (разворачивание вложенного future).

28. **Что такое `ThreadLocal`?**
    Своя копия переменной у каждого потока.

29. **Почему `ThreadLocal` течёт в пуле?**
    Ключ — слабая ссылка, значение — сильная; долгоживущий поток держит значение. Лечится `remove()`.

30. **`ThreadLocal` vs `InheritableThreadLocal`?**
    Второй копирует значение родителя при создании дочернего потока.
