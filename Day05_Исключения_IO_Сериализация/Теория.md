## 1. Иерархия исключений

### 1.1. Зачем вообще исключения

Представь, что ты едешь на машине и вдруг загорелась лампочка «проверьте двигатель». У тебя есть два мира:

- **Мир кодов возврата** (как в C): каждая функция возвращает число — 0 всё ок, −1 ошибка. Тебе нужно после каждого вызова писать `if (result < 0) ...`, и легко забыть. Ошибка «размазана» по коду.
- **Мир исключений** (как в Java): при проблеме «взрывается сигнальная ракета» — объект-исключение летит вверх по стеку вызовов, пока кто-то его не поймает. Нормальная логика остаётся чистой, без проверок на каждом шаге.

Исключение в Java — это **объект**. Обычный объект класса, унаследованного от `Throwable`. Его можно создать (`new IOException("файл не найден")`), хранить в переменной, передавать, класть в коллекции. Бросают его оператором `throw`, ловят блоком `catch`.

### 1.2. Дерево классов

Вся иерархия начинается с одного корня — `java.lang.Throwable`:

```
Throwable
 ├── Error                         (не восстанавливаемые проблемы JVM, не ловим)
 │    ├── OutOfMemoryError
 │    ├── StackOverflowError
 │    ├── NoClassDefFoundError
 │    ├── LinkageError
 │    │    └── ExceptionInInitializerError
 │    └── AssertionError
 │
 └── Exception                     (прикладные ошибки)
      ├── RuntimeException          (unchecked)
      │    ├── NullPointerException
      │    ├── IllegalArgumentException
      │    │    └── NumberFormatException
      │    ├── IllegalStateException
      │    ├── IndexOutOfBoundsException
      │    │    └── ArrayIndexOutOfBoundsException
      │    ├── ClassCastException
      │    ├── ArithmeticException
      │    ├── UnsupportedOperationException
      │    └── ConcurrentModificationException
      │
      └── (checked — всё, что не RuntimeException и не Error)
           ├── IOException
           │    ├── FileNotFoundException
           │    └── EOFException
           ├── SQLException
           ├── ReflectiveOperationException
           │    ├── ClassNotFoundException
           │    └── NoSuchMethodException
           ├── InterruptedException
           └── CloneNotSupportedException
```

**Аналогия.** `Throwable` — это «тревожный сигнал» вообще. `Error` — пожар в здании (ты не можешь его потушить, надо эвакуироваться). `Exception` — это, например, «заклинило дверь»: неприятно, но можно открыть другую или починить. `RuntimeException` — это «ты сам неправильно повернул ключ» (ошибка программиста), `checked` — «на улице ливень» (внешнее обстоятельство, от тебя не зависящее, но которое нужно предусмотреть).

### 1.3. Три ветки крупным планом

| Ветка | Что означает | Ловить? | Примеры |
|---|---|---|---|
| `Error` | Сбой самой JVM/среды, состояние неопределено | Обычно нет | `OutOfMemoryError`, `StackOverflowError` |
| `Exception` (checked) | Внешняя восстанавливаемая ситуация | Обязательно (компилятор заставит) | `IOException`, `SQLException` |
| `RuntimeException` (unchecked) | Ошибка программиста / нарушение контракта | По желанию | `NullPointerException`, `IllegalArgumentException` |

Важно понимать: `RuntimeException` — это **не** синоним «unchecked». Unchecked = `RuntimeException` + `Error`. Но на практике под «unchecked» почти всегда имеют в виду `RuntimeException`.

### 1.4. Методы класса Throwable

`Throwable` — не просто маркер, у него есть полезные методы. Разберём каждый.

```java
public class ThrowableDemo {
    public static void main(String[] args) {
        try {
            methodA();
        } catch (Exception e) {
            // 1. getMessage() — текст, переданный в конструктор
            System.out.println("message: " + e.getMessage());

            // 2. getCause() — первопричина (то, что передали в super(cause) / initCause)
            Throwable cause = e.getCause();
            System.out.println("cause: " + (cause == null ? "нет" : cause.getMessage()));

            // 3. getStackTrace() — массив кадров стека
            StackTraceElement[] frames = e.getStackTrace();
            System.out.println("глубина стека: " + frames.length);
            System.out.println("верхний кадр: " + frames[0]); // где брошено

            // 4. toString() — класс + сообщение
            System.out.println("toString: " + e);

            // 5. printStackTrace() — печатает всё в stderr
            // e.printStackTrace();

            // 6. addSuppressed()/getSuppressed() — "подавленные" исключения
            System.out.println("suppressed: " + e.getSuppressed().length);
        }
    }

    static void methodA() {
        methodB();
    }

    static void methodB() {
        throw new IllegalStateException("что-то пошло не так");
    }
}
```

Ожидаемый вывод (примерно):

```
message: что-то пошло не так
cause: нет
глубина стека: 3
верхний кадр: ThrowableDemo.methodB(ThrowableDemo.java:...)
toString: java.lang.IllegalStateException: что-то пошло не так
suppressed: 0
```

Сводная таблица методов `Throwable`:

| Метод | Что делает |
|---|---|
| `getMessage()` | Возвращает текст сообщения (может быть `null`) |
| `getLocalizedMessage()` | Локализованное сообщение (по умолчанию = `getMessage()`) |
| `getCause()` | Возвращает причину (`Throwable`) или `null` |
| `initCause(Throwable)` | Установить причину, если она ещё не задана (вызывается один раз) |
| `getStackTrace()` | Массив `StackTraceElement` — кадры стека |
| `setStackTrace(...)` | Заменить стек (используется фреймворками/сериализацией) |
| `printStackTrace()` | Напечатать класс, сообщение и стек в `System.err` |
| `toString()` | `имя_класса: сообщение` |
| `addSuppressed(Throwable)` | Добавить «подавленное» исключение (для try-with-resources) |
| `getSuppressed()` | Получить массив подавленных исключений |
| `fillInStackTrace()` | Заполнить стек текущим состоянием (дорого!) |

> **Важный нюанс производительности.** Создание исключения и вызов `fillInStackTrace()` — дорогая операция, потому что JVM обходит стек и запоминает кадры. Если исключение используется для управления потоком (например, в цикле), это сильно бьёт по производительности. Поэтому не бросай исключения «на каждый чих».

### 1.5. Конструкторы Throwable

Все исключения обычно имеют четыре конструктора:

```java
new IOException();                          // без сообщения
new IOException("файл не найден");          // только сообщение
new IOException(cause);                     // только причина
new IOException("файл не найден", cause);   // сообщение + причина
```

Четвёртый вариант — золотой стандарт при оборачивании исключений.

### Типичные ошибки

- Ловить `Throwable` или `Exception` «на всякий случай» и глотать (пустой `catch`). Это скрывает баги.
- Путать `getMessage()` и `toString()`: `getMessage()` не содержит имя класса.
- Считать, что `Error` можно «починить» в `catch` и продолжить нормально. Чаще всего нельзя.

### Часто спрашивают на собеседовании

- **Чем `Error` отличается от `Exception`?** `Error` — сбой JVM, не предполагает восстановления; `Exception` — прикладная ситуация.
- **Что такое checked-исключение?** Наследник `Exception`, но не `RuntimeException`; компилятор требует обработки.
- **Можно ли поймать `Throwable`?** Синтаксически да, но не надо: поймаешь и `Error`-ы.
- **Где хранится стек исключения?** В самом объекте (`StackTraceElement[]`), заполняется при создании.

## 2. Checked vs Unchecked

### 2.1. Суть различия

**Checked** (проверяемые) — компилятор **требует**, чтобы ты либо обернул вызов в `try/catch`, либо объявил `throws` в сигнатуре. Если не сделаешь — программа не скомпилируется.

**Unchecked** (непроверяемые) — компилятор не следит. Ошибка проявится только в рантайме.

```java
// CHECKED: без try/catch или throws — ошибка компиляции
void read() {
    throw new IOException("..."); // compile error: unreported exception
}

// правильно:
void readOk() throws IOException {
    throw new IOException("...");
}

// UNCHECKED: компилируется всегда
void bad() {
    throw new IllegalArgumentException("..."); // ок
}
```

### 2.2. Таблица сравнения

| | Checked | Unchecked |
|---|---|---|
| Наследник | `Exception`, кроме `RuntimeException` | `RuntimeException` и `Error` |
| Когда проверяется | во время компиляции | во время выполнения |
| Нужен `try/catch` или `throws` | **да, обязательно** | нет |
| Философия | внешние восстанавливаемые ситуации | программные ошибки, нарушение контракта |
| Примеры | `IOException`, `SQLException`, `InterruptedException`, `ClassNotFoundException` | `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`, `ArithmeticException` |
| Кто виноват | среда/внешний мир | программист |

### 2.3. Философия: почему вообще так сделали

Аналогия: ты отправляешь посылку.

- **Checked** — это «получатель может отсутствовать». Это внешнее обстоятельство. Логично заставить отправителя заранее подумать: что делать, если дома никого? Поэтому компилятор бьёт по рукам: обработай или предупреди.
- **Unchecked** — это «ты написал неверный адрес» или «положил в посылку кирпич вместо документов». Это твоя ошибка в коде. Заставлять обрабатывать каждую свою ошибку бессмысленно — правильнее её исправить.

Отсюда правило проектирования:

- Если ошибку **можно осмысленно обработать** на уровне вызывающего (повторить, спросить другой путь, показать сообщение) — делай checked.
- Если ошибка означает **баг в коде** (передали `null`, неверный аргумент, вызов в неправильном состоянии) — делай unchecked, чтобы программа упала и ты её починил.

### 2.4. Проблема checked-исключений (почему их часто критикуют)

1. **Загрязняют сигнатуры.** `throws IOException` протекает по всему стеку: метод A → B → C. Если C кидает checked, либо все наверху объявляют `throws`, либо кто-то оборачивает.
2. **Провоцируют плохие практики.** Программисты пишут `catch (Exception e) {}` или `e.printStackTrace()`, лишь бы скомпилировалось.
3. **Не работают с лямбдами/Stream API.** Функциональные интерфейсы (`Function`, `Supplier`) не объявляют checked-исключений, поэтому приходится оборачивать в unchecked вручную.
4. **Ломают инкапсуляцию.** Детали реализации (что там файл) протекают наружу.

Поэтому в современном Java-коде (особенно в Spring, Hibernate) часто предпочитают unchecked-исключения, оборачивая checked в своё runtime-исключение.

### 2.5. Как создавать свои исключения

**Checked-исключение:**

```java
public class InsufficientFundsException extends Exception {
    private final double deficit;

    public InsufficientFundsException(String message, double deficit) {
        super(message);
        this.deficit = deficit;
    }

    public double getDeficit() {
        return deficit;
    }
}
```

**Unchecked-исключение:**

```java
public class InvalidOrderException extends RuntimeException {
    public InvalidOrderException(String message) {
        super(message);
    }

    public InvalidOrderException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

Правила хорошего тона при создании своего исключения:

1. Наследуйся от `Exception` (checked) или `RuntimeException` (unchecked).
2. Добавляй конструкторы: `()`, `(String)`, `(String, Throwable)`, `(Throwable)`.
3. Не наследуйся напрямую от `Throwable` — это плохая практика.
4. Давай осмысленное имя, оканчивающееся на `Exception`.
5. Передавай `cause`, если оборачиваешь другое исключение.
6. При необходимости добавляй поля с контекстом (например, `deficit`).

### 2.6. Полный пример: оборачивание checked в unchecked

```java
import java.io.*;

public class WrappingDemo {

    // Низкоуровневый метод кидает checked
    static String load(String path) throws IOException {
        try (var in = new FileInputStream(path)) {
            return new String(in.readAllBytes());
        }
    }

    // Верхний слой не хочет тащить checked — оборачивает
    static String loadOrThrow(String path) {
        try {
            return load(path);
        } catch (IOException e) {
            throw new DataLoadException("Не удалось загрузить: " + path, e);
        }
    }

    public static void main(String[] args) {
        try {
            System.out.println(loadOrThrow("нет-такого-файла.txt"));
        } catch (DataLoadException e) {
            System.out.println("Поймали: " + e.getMessage());
            System.out.println("Причина: " + e.getCause());
        }
    }
}

class DataLoadException extends RuntimeException {
    public DataLoadException(String msg, Throwable cause) {
        super(msg, cause);
    }
}
```

Ожидаемый вывод:

```
Поймали: Не удалось загрузить: нет-такого-файла.txt
Причина: java.io.FileNotFoundException: нет-такого-файла.txt (Не удается найти указанный файл)
```

### Типичные ошибки

- Делать **всё** checked. Тогда сигнатуры обрастают `throws`, и код становится неудобным.
- Делать **всё** unchecked, включая ситуации, которые вызывающий реально может обработать (например, «неверный пароль» при логине).
- Терять `cause`: `throw new MyException("ошибка")` вместо `throw new MyException("ошибка", e)`. Тогда стек-трейс обрывается, и отладка усложняется.
- Объявлять `throws Exception` — слишком широко, скрывает детали.

### Часто спрашивают на собеседовании

- **Почему `NumberFormatException` unchecked, хотя это про ввод пользователя?** Потому что это чаще следствие бага (не проверили формат), и обработку удобнее делать явно, чем заставлять ловить.
- **Можно ли кинуть checked из `main`?** Да: `public static void main(String[] args) throws Exception`.
- **Когда создавать свой тип исключения?** Когда нужен свой контекст/поля или чтобы отличать свою ошибку от чужой.
- **Почему `InterruptedException` checked?** Чтобы программист не забыл корректно обработать прерывание (восстановить флаг `Thread.currentThread().interrupt()`).

## 3. try-catch-finally

### 3.1. Базовая анатомия

```java
try {
    // код, который может бросить исключение
} catch (SpecificException e) {
    // обработка конкретного исключения
} catch (OtherException e) {
    // обработка другого
} finally {
    // выполнится всегда
}
```

Аналогия: `try` — «попробуй зайти в дом». `catch` — «если дверь заперта, залезь в окно». `finally` — «в любом случае закрой за собой калитку».

### 3.2. Порядок catch: от конкретного к общему

Компилятор проверяет достижимость. Если сначала поймать `Exception`, то следующий `catch (IOException)` станет недостижимым — ошибка компиляции.

```java
try {
    risky();
} catch (FileNotFoundException e) {   // самое конкретное
    System.out.println("файл не найден");
} catch (IOException e) {              // более общее
    System.out.println("ошибка ввода-вывода");
} catch (Exception e) {                // самое общее — последним
    System.out.println("что-то ещё");
}
```

Если поменять порядок — компилятор скажет: `exception IOException has already been caught`.

### 3.3. Multi-catch (Java 7+)

Когда для нескольких исключений обработка одинаковая, их можно объединить через `|`:

```java
try {
    process();
} catch (IOException | SQLException e) {
    log.error("Сбой: {}", e.getMessage());
    throw new ServiceException(e);
}
```

Правила multi-catch:

- Типы не должны быть связаны наследованием (нельзя `IOException | FileNotFoundException`).
- Переменная `e` неявно `final` — переприсвоить нельзя.
- Тип переменной — общий супертип перечисленных.

```java
catch (IOException | SQLException e) {
    e = new IOException(); // compile error: e is effectively final
}
```

### 3.4. finally выполняется всегда (почти)

```java
public class FinallyDemo {
    public static void main(String[] args) {
        System.out.println(test());
    }

    static int test() {
        try {
            System.out.println("try");
            return 1;
        } finally {
            System.out.println("finally");
        }
    }
}
```

Вывод:

```
try
finally
1
```

`finally` выполняется даже при `return`, даже при пробросе исключения. Исключения-исключения:

- `System.exit(0)` / `Runtime.getRuntime().halt(0)` — JVM умирает.
- Краш JVM (например, `SIGKILL`, segmentation fault).
- Бесконечный цикл или взаимная блокировка внутри `try` (до `finally` просто не дойдёт).
- Переопределение `finalize` тут ни при чём — не путать.

### 3.5. `return` в finally — зло

```java
static int bad() {
    try {
        return 1;
    } finally {
        return 2; // перекрывает return из try!
    }
}
// bad() вернёт 2
```

Почему плохо:

1. **Перекрывает** нормальный результат и даже проброшенное исключение.
2. Скрывает ошибки: исключение «проглатывается».
3. Тяжело читать и отлаживать.

```java
static int worse() {
    try {
        throw new RuntimeException("boom");
    } finally {
        return 42; // исключение ПОТЕРЯЕТСЯ, вернётся 42
    }
}
// worse() вернёт 42, исключения не будет!
```

Вывод: никогда не пиши `return` в `finally`.

### 3.6. try без catch (с finally)

Допустимо, если есть `finally`:

```java
try {
    lock.lock();
    // ...
} finally {
    lock.unlock();
}
```

Но `try` **без** `catch` и **без** `finally` — ошибка компиляции. Также нельзя `try` без ресурсов и без `catch`/`finally`.

### 3.7. Вложенные try

Вложенные блоки нужны, когда разные этапы могут падать независимо:

```java
try {
    openConnection();
    try {
        sendData();
    } catch (IOException e) {
        log.warn("не удалось отправить, повторяем", e);
        resend();
    }
} finally {
    closeConnection();
}
```

Внутренний `catch` обрабатывает локальную проблему, внешний `finally` гарантирует закрытие ресурса.

### 3.8. Wrapping и cause — почему важно

Плохо:

```java
try {
    parseConfig();
} catch (IOException e) {
    throw new ConfigException("Ошибка конфигурации"); // cause потерян!
}
```

Хорошо:

```java
try {
    parseConfig();
} catch (IOException e) {
    throw new ConfigException("Ошибка конфигурации", e); // cause сохранён
}
```

С `cause` в стек-трейсе будет строка `Caused by: java.io.IOException: ...`, и ты увидишь первопричину. Без неё — только верхний уровень.

### 3.9. Полный разбор с выводом

```java
public class Order {
    static void process() throws Exception {
        System.out.println("A: начало");
        try {
            System.out.println("B: в try");
            throw new IllegalStateException("сбой обработки");
        } catch (IllegalStateException e) {
            System.out.println("C: catch -> " + e.getMessage());
            throw new Exception("обёртка", e);
        } finally {
            System.out.println("D: finally");
        }
    }

    public static void main(String[] args) {
        try {
            process();
        } catch (Exception e) {
            System.out.println("E: main -> " + e.getMessage());
            System.out.println("F: cause -> " + e.getCause().getMessage());
        }
    }
}
```

Вывод:

```
A: начало
B: в try
C: catch -> сбой обработки
D: finally
E: main -> обёртка
F: cause -> сбой обработки
```

Порядок: `try` → `catch` → `finally` (перед выходом) → проброс наверх.

### Типичные ошибки

- Пустой `catch` — «проглотить» исключение.
- `catch (Exception e) { e.printStackTrace(); }` вместо нормальной обработки/логирования.
- `return` в `finally`.
- Ловить слишком общий тип и терять конкретику.
- Забыть `cause`.
- Писать `finally` там, где нужен try-with-resources.

### Часто спрашивают на собеседовании

- **Выполнится ли `finally`, если в `try` `return`?** Да.
- **Что если `finally` тоже бросает исключение?** Оно заменит исходное (исходное потеряется). Поэтому `finally` должен быть максимально безопасным.
- **Можно ли `try` без `catch`?** Да, если есть `finally` или ресурсы.
- **Что будет с исключением из `try`, если в `finally` `return`?** Исключение потеряется.
- **Порядок catch?** От частного к общему.

## 4. try-with-resources

### 4.1. Проблема, которую решает

Классический код с ручным закрытием многословен и опасен:

```java
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("data.txt"));
    return br.readLine();
} finally {
    if (br != null) {
        try {
            br.close(); // close() сам кидает IOException!
        } catch (IOException e) {
            log.error("не закрылось", e);
        }
    }
}
```

Легко забыть закрыть, легко потерять исключение при закрытии. Java 7 добавила конструкцию **try-with-resources**.

### 4.2. Синтаксис

```java
try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {
    return br.readLine();
} // close() вызовется автоматически
```

Несколько ресурсов:

```java
try (var in = new FileInputStream("in.txt");
     var out = new FileOutputStream("out.txt")) {
    in.transferTo(out);
} // закрываются в ОБРАТНОМ порядке: сначала out, потом in
```

### 4.3. AutoCloseable vs Closeable

| Интерфейс | Пакет | Метод | Может кидать | С какого Java |
|---|---|---|---|---|
| `AutoCloseable` | `java.lang` | `close() throws Exception` | `Exception` | Java 7 |
| `Closeable` | `java.io` | `close() throws IOException` | `IOException` | Java 5 |

`Closeable extends AutoCloseable`. Для потоков используй `Closeable` (уже́ по исключению), для общих ресурсов — `AutoCloseable`.

```java
public class Connection implements AutoCloseable {
    public Connection() {
        System.out.println("открыли соединение");
    }

    public void send(String msg) {
        System.out.println("отправили: " + msg);
    }

    @Override
    public void close() {
        System.out.println("закрыли соединение");
    }
}

// использование
try (var c = new Connection()) {
    c.send("привет");
}
```

Вывод:

```
открыли соединение
отправили: привет
закрыли соединение
```

### 4.4. Порядок закрытия

Ресурсы закрываются в порядке, **обратном** объявлению. Это логично: если `out` зависит от `in`, сначала надо закрыть «верхний» ресурс.

```java
try (A a = new A(); B b = new B()) { } // close: b, затем a
```

### 4.5. Suppressed exceptions (подавленные исключения)

Что, если и тело `try` бросило исключение, и `close()` бросил? Java сохраняет **оба**: основное — «главное», исключение из `close()` — «подавленное» (suppressed).

```java
public class SuppressDemo {
    static class Broken implements AutoCloseable {
        @Override
        public void close() {
            throw new RuntimeException("ошибка при закрытии");
        }
    }

    public static void main(String[] args) {
        try (var b = new Broken()) {
            throw new RuntimeException("ошибка в теле");
        } catch (Exception e) {
            System.out.println("основное: " + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                System.out.println("подавленное: " + s.getMessage());
            }
        }
    }
}
```

Вывод:

```
основное: ошибка в теле
подавленное: ошибка при закрытии
```

Если тело не бросало, а `close()` бросил — это исключение станет основным.

### 4.6. Java 9: effectively final ресурсы

С Java 9 можно использовать уже объявленную переменную, если она `final` или effectively final:

```java
var br = new BufferedReader(new FileReader("data.txt")); // Java 10 var
try (br) {                 // Java 9: ресурс без объявления
    System.out.println(br.readLine());
}
```

Ограничения: переменная должна быть effectively final и не может быть `null` (иначе `NullPointerException` при попытке `close`).

### 4.7. try-with-resources vs finally

| | try-with-resources | try-finally |
|---|---|---|
| Краткость | высокая | низкая |
| Порядок закрытия | автоматически, обратный | вручную |
| Suppressed-исключения | поддерживаются | теряются |
| Требование | `AutoCloseable` | любой код |
| Риск забыть закрыть | нет | есть |

**Правило:** если ресурс реализует `AutoCloseable` — всегда try-with-resources.

### Типичные ошибки

- Использовать `finally` для закрытия `AutoCloseable` — теряются suppressed-исключения.
- Считать, что `close()` не бросает исключений. Бросает!
- Пытаться передать в `try (...)` `null` — при выходе будет `NullPointerException`.
- Открывать ресурс вне try и забывать закрыть при исключении в конструкторе.

### Часто спрашивают на собеседовании

- **В каком порядке закрываются ресурсы?** В обратном порядку объявления.
- **Что такое suppressed exception?** Исключение из `close()`, прикреплённое к основному через `addSuppressed`.
- **Чем `AutoCloseable` отличается от `Closeable`?** Широтой `throws`; `Closeable` — для I/O.
- **Можно ли использовать `var`/локальную переменную в ресурсах?** Да, с Java 9, если effectively final.

## 5. Error, OutOfMemoryError, StackOverflowError

### 5.1. Error — что это

`Error` — подкласс `Throwable`, обозначающий серьёзные проблемы, которые **приложение не должно пытаться обработать**. Это сбой среды исполнения.

Аналогия: `Exception` — «спустило колесо, поставь запаску». `Error` — «загорелся двигатель на трассе»: останавливайся и вызывай эвакуатор, а не пытайся ехать дальше.

Типичные `Error`:

| Error | Причина |
|---|---|
| `OutOfMemoryError` | не хватило памяти |
| `StackOverflowError` | переполнен стек |
| `NoClassDefFoundError` | класс был при компиляции, но отсутствует в рантайме |
| `ExceptionInInitializerError` | упал статический инициализатор |
| `AssertionError` | провалился `assert` |
| `LinkageError` | проблемы связывания классов |

### 5.2. Почему `Error` не ловят

Состояние JVM после `Error` неопределено. Поймав `OutOfMemoryError`, ты не знаешь, какие объекты успели создаться, а какие нет; дальнейшая работа может давать странные результаты. Иногда `OutOfMemoryError` логируют в самом верхнем уровне (чтобы записать факт) и завершают процесс — но не «восстанавливаются».

### 5.3. OutOfMemoryError: разновидности

`OutOfMemoryError` — не одно исключение, а семейство с разными сообщениями:

| Сообщение | Область | Типичная причина |
|---|---|---|
| `Java heap space` | куча (heap) | утечка, слишком много объектов, большой объём данных |
| `Metaspace` | метаданные классов | утечка ClassLoader, генерация классов |
| `GC overhead limit exceeded` | куча | GC тратит >98% времени, освобождая <2% |
| `Direct buffer memory` | off-heap (прямые буферы) | много `ByteBuffer.allocateDirect` |
| `unable to create native thread` | потоки ОС | слишком много потоков, мало памяти ОС |
| `Requested array size exceeds VM limit` | массив | попытка создать массив слишком большого размера |

**Аналогия с кучей.** Куча — это склад. Ты приносишь коробки, часть выбрасываешь. Если приносишь быстрее, чем уборщик (GC) успевает уносить, склад переполняется — `Java heap space`.

Пример утечки:

```java
import java.util.*;

public class LeakDemo {
    static final List<byte[]> LEAK = new ArrayList<>();

    public static void main(String[] args) {
        while (true) {
            LEAK.add(new byte[1024 * 1024]); // держим ссылки, GC не может собрать
        }
    }
}
// Обычно падает с: java.lang.OutOfMemoryError: Java heap space
```

### 5.4. StackOverflowError

Стек — это область памяти для кадров вызовов методов и локальных переменных. Каждый вызов метода добавляет кадр. Слишком глубокая (или бесконечная) рекурсия переполняет стек.

```java
public class StackDemo {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse(); // никогда не останавливается
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("Глубина: " + depth);
        }
    }
}
```

Вывод (число зависит от JVM/ОС):

```
Глубина: 12xxx
```

> Да, `StackOverflowError` в примере пойман — чтобы показать. В продакшене так делать не стоит; обычно это признак бага.

### 5.5. Как избежать OOM и StackOverflow

**Против `Java heap space`:**

1. Увеличить кучу: `-Xmx2g` (максимум), `-Xms512m` (стартовый).
2. Найти утечку профилировщиком (VisualVM, JProfiler, async-profiler, MAT).
3. Не держать лишние ссылки: чистить коллекции, не использовать статические коллекции как «вечный кэш».
4. Стримить данные вместо загрузки всего в память: `Files.lines`, `BufferedReader`, пагинация.
5. Использовать слабые ссылки (`WeakHashMap`) для кэшей.

**Против `StackOverflowError`:**

1. Заменить рекурсию на цикл/явный стек.
2. Увеличить размер стека: `-Xss512k` (или больше).
3. Сократить локальные переменные в методе (они тоже занимают место в кадре).
4. Осторожно с глубокими структурами (глубокие JSON/XML) — используй итеративные парсеры.
5. Помни: JVM **не** делает оптимизацию хвостовой рекурсии (tail call optimization) для обычных методов.

**Таблица флагов JVM:**

| Флаг | Что задаёт | Пример |
|---|---|---|
| `-Xms` | начальный размер heap | `-Xms512m` |
| `-Xmx` | максимальный размер heap | `-Xmx2g` |
| `-Xss` | размер стека потока | `-Xss512k` |
| `-XX:MaxMetaspaceSize` | максимум Metaspace | `-XX:MaxMetaspaceSize=256m` |
| `-XX:+HeapDumpOnOutOfMemoryError` | дамп кучи при OOM | |
| `-XX:HeapDumpPath` | куда сохранять дамп | `-XX:HeapDumpPath=/dumps` |

### 5.6. `NoClassDefFoundError` vs `ClassNotFoundException`

Важное различие:

- `ClassNotFoundException` — **checked** `Exception`. Возникает при явной попытке загрузить класс (`Class.forName`, `ClassLoader.loadClass`), которого нет.
- `NoClassDefFoundError` — **Error**. Класс был при компиляции, но в рантайме его нет (или он не смог инициализироваться). Часто это «вторая попытка» после `ExceptionInInitializerError`.

### Типичные ошибки

- Ловить `OutOfMemoryError` и продолжать работу — состояние неопределено.
- Держать статические `Map`/`List` как кэш без ограничения размера.
- Читать огромный файл целиком (`Files.readAllBytes`) вместо стрима.
- Увеличивать `-Xmx` вместо устранения утечки.
- Путать `-Xmx` (heap) и `-Xss` (stack).

### Часто спрашивают на собеседовании

- **Что такое `OutOfMemoryError` и какие бывают виды?** Переполнение памяти; heap, Metaspace, direct buffer и др.
- **Чем `StackOverflowError` отличается от OOM?** Первый — стек, второй — куча/метаданные.
- **Можно ли поймать `Error`?** Да синтаксически, но обычно не нужно.
- **Как найти утечку?** Heap dump + анализатор (MAT), профилировщик.
- **Что делает `-Xmx`?** Максимальный размер heap.

## 6. throw, throws, assert

### 6.1. `throw`

Оператор `throw` бросает объект исключения и немедленно прерывает текущий метод:

```java
if (amount < 0) {
    throw new IllegalArgumentException("Сумма не может быть отрицательной: " + amount);
}
```

Можно бросать только `Throwable` и его наследников. Строку бросить нельзя:

```java
throw "ошибка"; // compile error
```

### 6.2. `throws`

Объявляет в сигнатуре, какие checked-исключения метод может пробросить:

```java
public void save(String path) throws IOException, SQLException {
    // ...
}
```

`throws` — это **контракт**: «я могу выбросить вот это, будь готов». Unchecked-исключения объявлять не обязательно (но можно, для документации).

### 6.3. `throw` vs `throws`

| | `throw` | `throws` |
|---|---|---|
| Что делает | бросает исключение | объявляет возможные исключения |
| Где | внутри тела метода | в сигнатуре метода |
| Сколько | один объект | список через запятую |
| Время | рантайм | компиляция (контракт) |

### 6.4. Переброс и сохранение стека

Если поймать и бросить **тот же** объект — стек сохраняется:

```java
try {
    parse();
} catch (ParseException e) {
    log.error("не распарсили", e);
    throw e; // стек остаётся исходным
}
```

Если создать **новое** — исходный стек теряется (если не передать cause):

```java
catch (ParseException e) {
    throw new RuntimeException("ошибка парсинга"); // стек обрезан
}
```

### 6.5. `assert`

Синтаксис:

```java
assert condition;                 // без сообщения
assert condition : message;       // с сообщением (может быть выражением)
```

Если условие ложно — бросается `AssertionError` (с сообщением, если задано).

```java
public int divide(int a, int b) {
    assert b != 0 : "делитель не должен быть нулём";
    return a / b;
}
```

### 6.6. Почему assert отключён по умолчанию

Ассерты **выключены** по умолчанию и включаются флагом `-ea` (enable assertions):

```bash
java -ea Main
java -ea:com.example... Main   // только для пакета
java -da:com.example... Main   // выключить для пакета
```

Это сделано специально: ассерты — для проверок во время **разработки и тестирования**, а не в проде. Отключённые ассерты не несут накладных расходов.

### 6.7. Почему assert нельзя использовать для валидации

Ключевая причина: в продакшене ассерты **выключены**, значит проверка не выполнится. Если ты валидируешь входные данные через `assert`, в проде туда спокойно пройдут неверные значения.

Плохо:

```java
public void withdraw(double amount) {
    assert amount > 0;   // в проде не сработает!
    balance -= amount;
}
```

Хорошо:

```java
public void withdraw(double amount) {
    if (amount <= 0) {
        throw new IllegalArgumentException("amount должен быть > 0, получено: " + amount);
    }
    balance -= amount;
}
```

Также в проде часто используют `Objects.requireNonNull`, `Objects.checkIndex`, `Objects.checkFromToIndex`.

```java
import java.util.Objects;

public void setName(String name) {
    this.name = Objects.requireNonNull(name, "name не может быть null");
}
```

### 6.8. Полный пример

```java
public class AssertVsValidation {
    public static void main(String[] args) {
        // Валидация — всегда:
        try {
            withdraw(-5);
        } catch (IllegalArgumentException e) {
            System.out.println("Ошибка: " + e.getMessage());
        }

        // Ассерт — только для внутренних инвариантов (запускать с -ea):
        try {
            internal(-1);
        } catch (AssertionError e) {
            System.out.println("AssertionError: " + e.getMessage());
        }
    }

    static void withdraw(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount должен быть > 0");
        }
        System.out.println("сняли " + amount);
    }

    static void internal(int x) {
        assert x >= 0 : "x отрицательный: " + x;
        System.out.println("x = " + x);
    }
}
```

Запуск с `-ea`:

```
Ошибка: amount должен быть > 0
AssertionError: x отрицательный: -1
```

Запуск без `-ea`:

```
Ошибка: amount должен быть > 0
x = -1
```

### Типичные ошибки

- Валидировать пользовательский ввод через `assert`.
- Забыть, что assert выключен, и удивляться, почему проверка не сработала.
- Использовать `assert` с побочными эффектами: `assert list.remove(x);` — при выключенных ассертах эффекта не будет.
- Объявлять `throws` для unchecked-исключений без необходимости (не ошибка, но шум).
- Терять стек, создавая новое исключение без cause.

### Часто спрашивают на собеседовании

- **В чём разница `throw` и `throws`?** Одно бросает, другое объявляет.
- **Как включить assert?** Флагом `-ea`.
- **Почему assert не для валидации?** В проде выключен.
- **Что бросает assert при провале?** `AssertionError`.
- **Можно ли в assert писать выражение с побочным эффектом?** Технически да, но это баг: при `-da` эффект исчезнет.

## 7. Потоки ввода-вывода (I/O)

### 7.1. Зачем потоки

Поток (stream) — абстракция «источник/приёмник данных, из которого/в который можно последовательно читать/писать». Источником может быть файл, сеть, память, консоль.

Аналогия: байтовый поток — это **труба с водой**, по которой течёт что угодно (байты). Символьный поток — это **труба с текстом**, где на выходе гарантированно буквы (символы), а не «сырые» капли.

### 7.2. Байтовые vs символьные

| | Байтовые | Символьные |
|---|---|---|
| Базовые классы | `InputStream` / `OutputStream` | `Reader` / `Writer` |
| Единица | байт (8 бит) | символ (16 бит, `char`) |
| Для чего | бинарные данные: изображения, zip, аудио | текст |
| Кодировка | не важна | учитывается (UTF-8 и т.п.) |
| Примеры | `FileInputStream`, `BufferedInputStream` | `FileReader`, `BufferedReader` |

**Правило:** текст — символьные потоки; всё остальное — байтовые. Никогда не читай текст байтами без учёта кодировки.

### 7.3. Иерархия потоков

```
InputStream (abstract)
 ├── FileInputStream
 ├── ByteArrayInputStream
 ├── PipedInputStream
 ├── FilterInputStream (abstract)
 │    ├── BufferedInputStream
 │    ├── DataInputStream
 │    └── PushbackInputStream
 └── ObjectInputStream

OutputStream (abstract)
 ├── FileOutputStream
 ├── ByteArrayOutputStream
 ├── PipedOutputStream
 ├── FilterOutputStream (abstract)
 │    ├── BufferedOutputStream
 │    ├── DataOutputStream
 │    └── PrintStream
 └── ObjectOutputStream

Reader (abstract)
 ├── InputStreamReader        (байты -> символы, с кодировкой)
 │    └── FileReader
 ├── BufferedReader
 ├── CharArrayReader
 ├── StringReader
 └── FilterReader

Writer (abstract)
 ├── OutputStreamWriter       (символы -> байты, с кодировкой)
 │    └── FileWriter
 ├── BufferedWriter
 ├── CharArrayWriter
 ├── StringWriter
 └── PrintWriter
```

### 7.4. Decorator pattern (шаблон «Декоратор»)

Потоки оборачивают друг друга, добавляя поведение. Это классический **Decorator pattern**: базовый компонент + обёртки с тем же интерфейсом.

```java
BufferedReader br = new BufferedReader(
        new InputStreamReader(
                new FileInputStream("file.txt"),
                StandardCharsets.UTF_8));
```

Читаем «изнутри наружу»:

1. `FileInputStream` — открывает файл, читает байты.
2. `InputStreamReader` — декодирует байты в символы (UTF-8).
3. `BufferedReader` — буферизует и даёт удобный `readLine()`.

Закрытие внешнего (`br.close()`) автоматически закроет внутренние.

Зачем нужны декораторы:

| Обёртка | Что добавляет |
|---|---|
| `Buffered*` | буферизация (сильное ускорение мелких операций) |
| `Data*` | чтение/запись примитивов и строк (`readInt`, `writeUTF`) |
| `Object*` | сериализация объектов |
| `PrintStream`/`PrintWriter` | удобные `print`/`println`, не кидают `IOException` |
| `InputStreamReader`/`OutputStreamWriter` | мост байты ↔ символы + кодировка |

### 7.5. Буферизация: почему это важно

Без буфера каждый `read()` — это системный вызов. Представь, что за каждой ложкой супа ты бегаешь в магазин. Буфер — это кастрюля: набрал и ешь.

```java
// медленно: много системных вызовов
try (var in = new FileInputStream("big.bin")) {
    int b;
    while ((b = in.read()) != -1) { /* ... */ }
}

// быстро: читаем блоками
try (var in = new BufferedInputStream(new FileInputStream("big.bin"))) {
    int b;
    while ((b = in.read()) != -1) { /* ... */ }
}
```

### 7.6. Чтение и запись файла (примеры с выводом)

**Чтение текста построчно:**

```java

```

Вывод:
```

```

**Запись текста:**

```java

    bw.newLine();
```

### 7.8. Кодировки

Кодировка — правило «символ ↔ байты». Ошибки с кодировками — классика.

```java
byte[] bytes = "Привет".getBytes(StandardCharsets.UTF_8); // 12 байт (2 на букву)
String s = new String(bytes, StandardCharsets.UTF_8);      // обратно
```

Проблема «кракозябр» (`ÐŸÑ€Ð¸Ð²ÐµÑ‚`) — когда байты декодировали не той кодировкой.

> В Java 18+ кодировка по умолчанию — UTF-8 (`file.encoding=UTF-8`). До этого зависела от ОС (на Windows часто `windows-1251`/`Cp1251`). **Всегда указывай кодировку явно**, чтобы поведение не зависело от платформы.

| Кодировка | Особенность |
|---|---|
| `UTF-8` | переменная длина, совместим с ASCII, стандарт |
| `UTF-16` | 2 или 4 байта, есть BOM-варианты |
| `ISO-8859-1` | 1 байт, только западноевропейские символы |
| `windows-1251` | 1 байт, кириллица (Windows) |
| `US-ASCII` | 7 бит, только английский |

### 7.9. NIO и NIO.2

**NIO (Java 1.4):** `java.nio` — каналы (`Channel`), буферы (`ByteBuffer`), селекторы. Позволяет неблокирующий ввод-вывод.

**NIO.2 (Java 7):** `java.nio.file` — новый файловый API: `Path`, `Files`, `Paths`.

**Path вместо File:**

```java
import java.nio.file.*;

Path p = Paths.get("dir", "file.txt");     // dir/file.txt
Path abs = p.toAbsolutePath();
Path parent = p.getParent();               // dir
Path name = p.getFileName();               // file.txt
Path norm = Paths.get("a/./b/../c").normalize(); // a/c
```

**Files — главный рабочий инструмент:**

```java
Path p = Paths.get("data.txt");

// запись/чтение
Files.writeString(p, "привет");                 // Java 11+
String content = Files.readString(p);           // Java 11+

// построчно
List<String> lines = Files.readAllLines(p);
Files.write(p, List.of("a", "b"), StandardCharsets.UTF_8);

// копирование/перемещение/удаление
Files.copy(src, dst, StandardCopyOption.REPLACE_EXISTING);
Files.move(src, dst, StandardCopyOption.ATOMIC_MOVE);
Files.deleteIfExists(p);

// проверки
Files.exists(p);
Files.isDirectory(p);
Files.size(p);
Files.createDirectories(Paths.get("a/b/c"));

// обход дерева
try (var stream = Files.walk(dir)) {            // Stream<Path>, ленивый
    stream.filter(Files::isRegularFile).forEach(System.out::println);
}
```

### 7.10. Чтение больших файлов

Нельзя грузить гигабайтный файл в память целиком (`Files.readAllBytes`, `readAllLines`). Варианты:

**1. `Files.lines` — ленивый Stream:**

```java
try (var lines = Files.lines(Paths.get("huge.log"))) {
    lines.filter(l -> l.contains("ERROR")).forEach(System.out::println);
}
```

**2. `BufferedReader`:**

```java
try (var br = Files.newBufferedReader(Paths.get("huge.log"), StandardCharsets.UTF_8)) {
    String line;
    while ((line = br.readLine()) != null) {
        // обработка
    }
}
```

**3. `FileChannel` + `ByteBuffer` — для бинарных файлов:**

```java
try (var channel = FileChannel.open(Paths.get("big.bin"), StandardOpenOption.READ)) {
    var buffer = ByteBuffer.allocate(8192);
    while (channel.read(buffer) != -1) {
        buffer.flip();       // переключились на чтение из буфера
        while (buffer.hasRemaining()) {
            byte b = buffer.get();
            // обработка
        }
        buffer.clear();      // готовы к следующей порции
    }
}
```

**4. Memory-mapped файл (для больших бинарных):**

```java
try (var channel = FileChannel.open(Paths.get("big.bin"), StandardOpenOption.READ)) {
    MappedByteBuffer mmap = channel.map(FileChannel.MapMode.READ_ONLY, 0, channel.size());
    // читаем как массив
}
```

Сравнение:

| Способ | Когда использовать |
|---|---|
| `Files.readAllBytes`/`readAllLines` | маленькие файлы |
| `Files.lines` | текстовые, построчная обработка |
| `BufferedReader` | текстовые, нужен контроль |
| `FileChannel` + `ByteBuffer` | бинарные, большой объём |
| Memory-mapped | очень большие бинарные, случайный доступ |

### 7.11. `ByteBuffer` подробно

Три ключевых состояния: `position` (текущая позиция), `limit` (граница), `capacity` (ёмкость).

```java
ByteBuffer buf = ByteBuffer.allocate(10); // capacity=10, position=0, limit=10

buf.put((byte) 1);        // position=1
buf.put((byte) 2);        // position=2

buf.flip();               // limit=2, position=0 — переходим к чтению
while (buf.hasRemaining()) {
    System.out.println(buf.get());
}
// 1
// 2

buf.clear();              // position=0, limit=capacity — снова пишем
```

| Метод | Что делает |
|---|---|
| `allocate(n)` | создать буфер в heap |
| `allocateDirect(n)` | прямой (off-heap) буфер |
| `put/get` | записать/прочитать байт |
| `flip()` | limit = position, position = 0 (режим чтения) |
| `clear()` | position = 0, limit = capacity (режим записи) |
| `rewind()` | position = 0 (перечитать) |
| `compact()` | переносит непрочитанное в начало |
| `hasRemaining()` | есть ли ещё данные |

### Типичные ошибки

- Читать текст байтовыми потоками без кодировки → «кракозябры».
- Забывать `flip()` у `ByteBuffer` → читаешь пустоту.
- Не закрывать потоки (нужен try-with-resources).
- Использовать `FileReader`/`FileWriter` без указания кодировки (используют платформенную).
- Загружать большие файлы через `readAllLines`.
- Писать в `PrintWriter` и не проверять `checkError()`.
- Смешивать буферизованный и небуферизованный доступ к тому же файлу.

### Часто спрашивают на собеседовании

- **Байтовые и символьные потоки — разница?** Байты для бинарных, символы для текста с кодировкой.
- **Зачем нужен Decorator?** Гибко комбинировать поведение без взрыва классов.
- **Почему `BufferedReader` быстрее?** Меньше системных вызовов.
- **`Path` vs `File`?** `Path` — современный NIO.2 API, богаче и удобнее.
- **Как прочитать большой файл?** Стрим/построчно/через каналы, не целиком.
- **`Files.lines` нужно закрывать?** Да, он держит открытый файл, поэтому try-with-resources.

## 8. Сериализация

### 8.1. Что это

**Сериализация** — превращение объекта в поток байт. **Десериализация** — обратное превращение байт в объект.

Аналогия: сериализация — «упаковать мебель в коробки для переезда». Десериализация — «распаковать и собрать обратно». Но есть нюанс: при распаковке **сборщики мебели (конструктор) не приходят** — JVM собирает объект сама.

Зачем нужно: сохранение состояния, передача по сети, кэширование, RMI, кластеризация сессий.

### 8.2. Базовый пример

```java
import java.io.*;

public class SerializationDemo {
    public static void main(String[] args) throws Exception {
        User user = new User("Алиса", "secret123", 30);

        // сериализация
        try (var out = new ObjectOutputStream(new FileOutputStream("user.ser"))) {
            out.writeObject(user);
        }

        // десериализация
        try (var in = new ObjectInputStream(new FileInputStream("user.ser"))) {
            User restored = (User) in.readObject();
            System.out.println(restored);
        }
    }
}

class User implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private transient String password;  // не сохраняется
    private static int counter;         // статическое — не сериализуется
    private int age;

    User(String name, String password, int age) {
        this.name = name;
        this.password = password;
        this.age = age;
        counter++;
    }

    @Override
    public String toString() {
        return "User{name=" + name + ", password=" + password + ", age=" + age + "}";
    }
}
```

Вывод:

```
User{name=Алиса, password=null, age=30}
```

`password` стал `null`, потому что `transient`.

### 8.3. Правила сериализации

1. Класс должен реализовать маркерный интерфейс `java.io.Serializable`. Иначе — `NotSerializableException`.
2. **Все** нестатические, нетранзиентные поля должны быть либо примитивами, либо `Serializable`. Иначе — `NotSerializableException`.
3. `serialVersionUID` желательно задавать явно.
4. `transient`-поля пропускаются.
5. `static`-поля не сериализуются (они принадлежат классу, а не объекту).
6. Конструктор при десериализации **не вызывается**.
7. Сериализуются и родительские поля, если родитель `Serializable`.

### 8.4. serialVersionUID

`serialVersionUID` — версия класса. При десериализации JVM сравнивает UID в байтах с UID текущего класса.

- Если совпадает — ок.
- Если не совпадает — `InvalidClassException: local class incompatible`.

Если не задать явно, компилятор генерирует UID из структуры класса (поля, методы, интерфейсы). Тогда **любое** изменение класса (даже добавление метода) меняет UID, и старые данные не читаются.

```java
class Account implements Serializable {
    private static final long serialVersionUID = 42L; // задавай явно!
}
```

> Совет: всегда пиши `private static final long serialVersionUID = 1L;` и меняй осознанно.

### 8.5. transient и static

```java
class Session implements Serializable {
    private static final long serialVersionUID = 1L;

    private String user;
    private transient String token;   // не сохранится, станет null
    private transient int cachedHash; // не сохранится, станет 0
    private static int totalSessions; // НЕ сериализуется
}
```

| Модификатор | Сериализуется? | После десериализации |
|---|---|---|
| обычное поле | да | восстановленное значение |
| `transient` | нет | значение по умолчанию (`null`/`0`/`false`) |
| `static` | нет | берётся текущее значение класса |

> Хитрость: если хочется, чтобы `transient`-поле восстановилось, используй `readObject`.

### 8.6. Конструктор не вызывается

Это важный факт для собеседования. При десериализации объект создаётся «в обход» обычного конструирования — JVM выделяет память и заполняет поля из потока. Конструктор класса **не выполняется**.

```java
class Person implements Serializable {
    private static final long serialVersionUID = 1L;
    private String name;

    Person() {
        System.out.println("конструктор вызван!");
        this.name = "по умолчанию";
    }
}

// При десериализации "конструктор вызван!" НЕ напечатается.
```

Следствие: инварианты, устанавливаемые в конструкторе, могут нарушиться. Проверяй данные в `readObject`.

### 8.7. readObject / writeObject

Для кастомизации объявляют приватные методы с точными сигнатурами:

```java
import java.io.*;

class SecureUser implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private transient String password;

    private void writeObject(ObjectOutputStream out) throws IOException {
        out.defaultWriteObject();                       // сначала стандартные поля
        out.writeUTF(encrypt(password));                // потом своё
    }

    private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        in.defaultReadObject();
        this.password = decrypt(in.readUTF());
        if (name == null) {                             // валидация инвариантов
            throw new InvalidObjectException("name обязателен");
        }
    }

    private static String encrypt(String s) { return "enc:" + s; }
    private static String decrypt(String s) { return s.substring(4); }
}
```

`defaultWriteObject()` / `defaultReadObject()` обрабатывают обычные поля, а ты добавляешь своё.

### 8.8. readResolve

Позволяет подменить объект при десериализации — например, для singleton или enum-подобного поведения:

```java
import java.io.*;

class Singleton implements Serializable {
    private static final long serialVersionUID = 1L;

    public static final Singleton INSTANCE = new Singleton();

    private Singleton() { }

    // вызывается после readObject — возвращает существующий экземпляр
    private Object readResolve() {
        return INSTANCE;
    }
}
```

Без `readResolve` десериализация singleton создаст **второй** экземпляр, ломая singleton.

### 8.9. Externalizable

`Externalizable extends Serializable` — полный ручной контроль:

```java
import java.io.*;

class Point implements Externalizable {
    private int x, y;

    public Point() { }   // ОБЯЗАТЕЛЬНО public no-arg!

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public void writeExternal(ObjectOutput out) throws IOException {
        out.writeInt(x);
        out.writeInt(y);
    }

    @Override
    public void readExternal(ObjectInput in) throws IOException {
        this.x = in.readInt();
        this.y = in.readInt();
    }

    @Override
    public String toString() {
        return "Point(" + x + ", " + y + ")";
    }
}
```

Отличия `Externalizable` от `Serializable`:

| | `Serializable` | `Externalizable` |
|---|---|---|
| Управление | автоматическое | полностью ручное |
| Конструктор при десериализации | не вызывается | **вызывается** public no-arg |
| Скорость | медленнее | быстрее |
| Реализация | маркер | два метода |
| Родительские поля | автоматически | нужно писать вручную |

### 8.10. Наследование и сериализация

Правило: сериализуются поля **всех** родителей, которые сами `Serializable`.

Если родитель **не** `Serializable`:

- его поля **не** сериализуются;
- при десериализации вызывается **его no-arg конструктор**, чтобы инициализировать эти поля.

```java
class Parent {                     // НЕ Serializable
    int parentField = 100;
    Parent() {
        System.out.println("Parent конструктор");
    }
}

class Child extends Parent implements Serializable {
    private static final long serialVersionUID = 1L;
    int childField = 200;
}

// При десериализации Child: напечатается "Parent конструктор",
// parentField = 100 (из конструктора), childField восстановится из потока.
```

> Если у не-сериализуемого родителя нет no-arg конструктора — десериализация упадёт с `InvalidClassException`.

### 8.11. NotSerializableException

Возникает, когда:
- класс не реализует `Serializable`;
- поле не `Serializable` и не `transient`.

```java
class Order implements Serializable {
    private static final long serialVersionUID = 1L;
    private Thread thread; // Thread не Serializable -> NotSerializableException
}
```

Лечение: сделать поле `transient` или заменить тип.

### 8.12. Безопасность: gadget chains

Десериализация недоверенных данных — **критическая уязвимость**. Атакующий может подсунуть байты, которые при `readObject` вызовут опасные методы (цепочка «гаджетов») и выполнят произвольный код. Знаменитые примеры: Apache Commons Collections, Spring, WebLogic.

Меры:

1. **Не десериализуй недоверенные данные.** Лучшее решение.
2. `ObjectInputFilter` (Java 9+) — белый/чёрный список классов:

```java
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "com.example.*;java.base/*;!*");
try (var in = new ObjectInputStream(new FileInputStream("data.ser"))) {
    in.setObjectInputFilter(filter);
    Object obj = in.readObject();
}
```

3. JEP 290 (Java 9) — глобальные фильтры через `jdk.serialFilter`.
4. Использовать JSON/Protobuf вместо Java-сериализации.

### 8.13. Производительность и альтернативы

Java-сериализация:

- медленная (рефлексия, метаданные);
- объёмная (пишет имена классов, метаданные);
- несовместима между версиями;
- небезопасна.

Альтернативы:

| Формат | Плюсы | Минусы |
|---|---|---|
| JSON (Jackson) | читаемый, кроссплатформенный | больше размер, медленнее парсинг |
| Protobuf | компактный, быстрый, схема | нужна `.proto`, бинарный |
| Avro | схема, эволюция | сложнее |
| Kryo | быстрый | не кроссплатформенный |
| MessagePack | компактный | менее распространён |

### 8.14. Полный пример с наследованием и transient

```java
import java.io.*;

public class InheritanceDemo {
    public static void main(String[] args) throws Exception {
        var child = new Child();
        child.childField = 777;
        child.parentField = 555;

        byte[] data;
        try (var bos = new ByteArrayOutputStream();
             var out = new ObjectOutputStream(bos)) {
            out.writeObject(child);
            data = bos.toByteArray();
        }

        try (var in = new ObjectInputStream(new ByteArrayInputStream(data))) {
            var restored = (Child) in.readObject();
            System.out.println("childField = " + restored.childField);
            System.out.println("parentField = " + restored.parentField);
        }
    }
}

class Parent {
    int parentField = 100;
    Parent() {
        System.out.println("Parent конструктор вызван");
    }
}

class Child extends Parent implements Serializable {
    private static final long serialVersionUID = 1L;
    int childField = 200;
}
```

Вывод:

```
Parent конструктор вызван
childField = 777
parentField = 100
```

Обрати внимание: `parentField` **не** сохранился (стал 100 из конструктора), а `childField` — сохранился.

### Типичные ошибки

- Забыть `serialVersionUID` → проблемы при эволюции класса.
- Ожидать, что `transient`/`static` сохранятся.
- Думать, что конструктор вызывается при десериализации.
- Десериализовать данные из сети без фильтра.
- Хранить `Serializable` объекты в кэше надолго (несовместимость версий).
- Использовать Java-сериализацию для API/хранения вместо JSON.

### Часто спрашивают на собеседовании

- **Что такое `serialVersionUID` и зачем?** Версия класса; несовпадение → `InvalidClassException`.
- **Сериализуются ли `static` поля?** Нет.
- **Что делает `transient`?** Исключает поле из сериализации.
- **Вызывается ли конструктор?** Нет (кроме `Externalizable` и не-сериализуемого родителя).
- **`Serializable` vs `Externalizable`?** Автоматически vs вручную.
- **Опасна ли десериализация?** Да, gadget chains; нужны фильтры/отказ от неё.
- **Как сделать singleton сериализуемым?** `readResolve` или `enum`.

## 9. Сериализация в XML/JSON

### 9.1. Зачем альтернативы

Java-сериализация бинарна и нечитаема. Для обмена данными с другими системами нужны текстовые/кроссплатформенные форматы: XML и JSON.

### 9.2. JAXB

**JAXB** (Java Architecture for XML Binding) — стандарт привязки Java-объектов к XML. Входил в JDK до Java 8. С Java 11 **удалён** из JDK (JEP 320), потому что был частью Java EE. Теперь подключается отдельной зависимостью (`jakarta.xml.bind`).

Пример аннотаций:

```java
import jakarta.xml.bind.annotation.*;

@XmlRootElement(name = "user")
@XmlAccessorType(XmlAccessType.FIELD)
public class User {
    @XmlElement
    private String name;

    @XmlElement
    private int age;

    // getters/setters
}
```

Маршалинг/демаршалинг:

```java
import jakarta.xml.bind.*;
import java.io.StringReader;
import java.io.StringWriter;

public class JaxbDemo {
    public static void main(String[] args) throws Exception {
        JAXBContext ctx = JAXBContext.newInstance(User.class);

        User user = new User();
        user.setName("Алиса");
        user.setAge(30);

        // marshal: объект -> XML
        Marshaller marshaller = ctx.createMarshaller();
        marshaller.setProperty(Marshaller.JAXB_FORMATTED_OUTPUT, true);
        StringWriter sw = new StringWriter();
        marshaller.marshal(user, sw);
        System.out.println(sw);

        // unmarshal: XML -> объект
        Unmarshaller unmarshaller = ctx.createUnmarshaller();
        User parsed = (User) unmarshaller.unmarshal(new StringReader(sw.toString()));
        System.out.println(parsed.getName() + ", " + parsed.getAge());
    }
}
```

> Почему удалён: Java EE-модули вынесли из JDK, чтобы уменьшить размер и дать развиваться отдельно (перешли под `jakarta.*`). Также у JAXB были проблемы с безопасностью (XXE-атаки).

### 9.3. Jackson

**Jackson** — самая популярная библиотека для JSON в Java (и XML). Основные компоненты: `ObjectMapper`, аннотации.

```java
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.annotation.*;

public class JacksonDemo {
    public static void main(String[] args) throws Exception {
        ObjectMapper mapper = new ObjectMapper();

        User user = new User("Алиса", 30, "secret");

        // объект -> JSON
        String json = mapper.writeValueAsString(user);
        System.out.println(json);
        // {"name":"Алиса","age":30}

        // JSON -> объект
        User parsed = mapper.readValue(json, User.class);
        System.out.println(parsed.getName() + ", " + parsed.getAge());
    }
}

class User {
    private String name;
    private int age;

    @JsonProperty("password")
    @JsonIgnore                       // не выводить в JSON
    private String password;

    @JsonCreator
    public User(@JsonProperty("name") String name,
                @JsonProperty("age") int age,
                @JsonProperty("password") String password) {
        this.name = name;
        this.age = age;
        this.password = password;
    }

    public String getName() { return name; }
    public int getAge() { return age; }
}
```

Вывод:

```
{"name":"Алиса","age":30}
Алиса, 30
```

Полезные аннотации Jackson:

| Аннотация | Назначение |
|---|---|
| `@JsonProperty` | связать поле/параметр с именем в JSON |
| `@JsonIgnore` | исключить из (де)сериализации |
| `@JsonCreator` | указать конструктор для десериализации |
| `@JsonInclude` | включать только не-null поля и т.п. |
| `@JsonFormat` | формат дат/чисел |
| `@JsonAlias` | альтернативные имена при чтении |
| `@JsonTypeInfo` | полиморфизм |

Jackson умеет и XML — через модуль `jackson-dataformat-xml` и `XmlMapper`:

```java
XmlMapper xmlMapper = new XmlMapper();
String xml = xmlMapper.writeValueAsString(user);
```

### 9.4. Сравнение

| Формат | Библиотека | Читаемость | Размер | Скорость | Кроссплатформ. |
|---|---|---|---|---|---|
| Java binary | встроено | нет | средний | медленно | нет |
| XML | JAXB/Jackson | высокая | большой | медленно | да |
| JSON | Jackson/Gson | высокая | средний | быстро | да |
| Protobuf | protobuf | нет | минимальный | очень быстро | да |

### Типичные ошибки

- Ожидать JAXB «из коробки» в Java 11+ — его там нет.
- Забыть `@JsonIgnore` для чувствительных полей (пароль утечёт в JSON).
- Не указывать кодировку при записи XML/JSON в файл.
- Использовать небезопасный XML-парсер (XXE): отключай DTD/external entities.
- Путать маршалинг (объект→формат) и демаршалинг (формат→объект).

### Часто спрашивают на собеседовании

- **Почему JAXB убрали из JDK?** Часть Java EE, вынесена отдельно (JEP 320).
- **Что такое маршалинг/демаршалинг?** Преобразование объект↔XML/JSON.
- **Как исключить поле из JSON?** `@JsonIgnore` или `transient` (для Jackson).
- **Что используешь на практике?** Обычно Jackson для JSON.

## 10. ClassLoader

### 10.1. Что это и зачем

`ClassLoader` — компонент JVM, который **загружает байт-код классов** (`.class`) в память и превращает его в объект `Class`.

Аналогия: ClassLoader — это **библиотекарь**. Ты просишь книгу «java.lang.String»; библиотекарь сначала смотрит в главное хранилище (родительский загрузчик), и только если там нет — идёт в свой зал (classpath) и достаёт. Так библиотекарь не даёт подсунуть подделку вместо оригинала.

### 10.2. Три фазы загрузки класса

1. **Loading (загрузка).** ClassLoader находит `.class`, читает байты, создаёт `Class`-объект.
2. **Linking (связывание):**
   - **Verification** — проверка байт-кода (корректность, безопасность).
   - **Preparation** — выделение памяти под статические поля и значения по умолчанию (`0`, `null`).
   - **Resolution** — разрешение символьных ссылок на реальные (может быть ленивым).
3. **Initialization (инициализация).** Выполняется статический инициализатор (`static {}`), присваиваются реальные значения статическим полям.

> `ClassNotFoundException` (checked) — на этапе loading. `NoClassDefFoundError` (Error) — если класс был, но инициализация не удалась/класс пропал.

### 10.3. Иерархия ClassLoader (Java 9+)

```
Bootstrap ClassLoader   (нативный, java.base и др. модули платформы)
        ↑
Platform ClassLoader    (бывший Extension, модули платформы)
        ↑
Application/System      (classpath: твои классы и библиотеки)
        ↑
Custom ClassLoaders     (Tomcat, OSGi, плагины, hot-reload)
```

| Загрузчик | Что грузит | Виден через |
|---|---|---|
| Bootstrap | `java.base`, ядро JDK | `null` (реализован нативно) |
| Platform | модули платформы | `ClassLoader.getPlatformClassLoader()` |
| Application | classpath, модульный путь | `ClassLoader.getSystemClassLoader()` |
| Custom | своё | ты сам создаёшь |

```java
public class LoaderDemo {
    public static void main(String[] args) {
        // Bootstrap -> null
        System.out.println(String.class.getClassLoader());
        // Platform
        System.out.println(java.sql.Driver.class.getClassLoader());
        // Application
        System.out.println(LoaderDemo.class.getClassLoader());
    }
}
```

Примерный вывод:

```
null
jdk.internal.loader.ClassLoaders$PlatformClassLoader@...
jdk.internal.loader.ClassLoaders$AppClassLoader@...
```

### 10.4. Parent delegation (делегирование родителю)

Правило: получив запрос на класс, загрузчик **сначала делегирует** его родителю. Только если родитель не нашёл — грузит сам.

Алгоритм `loadClass`:

```
1. Проверить кэш уже загруженных классов.
2. Делегировать родителю (recursively до Bootstrap).
3. Если родитель не нашёл — попытаться найти класс самому (findClass).
4. Если не нашёл — ClassNotFoundException.
```

Зачем:

1. **Безопасность.** Нельзя подменить `java.lang.String` своим классом: Bootstrap найдёт настоящий раньше.
2. **Уникальность.** Один и тот же класс загружается один раз.
3. **Консистентность.** Все части системы видят одинаковые базовые классы.

### 10.5. Идентификация класса парой (ClassLoader, имя)

Класс определяется **не только** полным именем, но и загрузчиком. Один и тот же `.class`, загруженный двумя разными ClassLoader-ами, даёт **два разных** объекта `Class`, несовместимых между собой.

```java
// Псевдокод: загружаем один и тот же класс двумя загрузчиками
Class<?> a = loader1.loadClass("com.example.Foo");
Class<?> b = loader2.loadClass("com.example.Foo");
System.out.println(a == b);              // false
System.out.println(a.equals(b));         // false
```

Попытка привести объект одного к «тому же» классу из другого загрузчика:

```java
Object objFromLoader1 = a.getDeclaredConstructor().newInstance();
Object objFromLoader2 = b.getDeclaredConstructor().newInstance();
// (Foo из loader2) objFromLoader1  ->  ClassCastException
```

### 10.6. Статические переменные у каждого загрузчика свои

Раз классы разные, то и `static`-поля у них **отдельные копии**:

```java
class Counter {
    static int count = 0;
}

// loader1 и loader2 загрузили Counter по отдельности:
Class<?> c1 = loader1.loadClass("Counter");
Class<?> c2 = loader2.loadClass("Counter");

// Field f1 = c1.getField("count");
// f1.setInt(null, 10);   // изменили только "Counter из loader1"
// c2.getField("count").getInt(null) -> 0
```

Это частая причина загадочных багов: «я поменял static, а он не изменился» — потому что это другая копия класса.

### 10.7. Своя реализация ClassLoader

Достаточно переопределить `findClass`:

```java
import java.io.IOException;
import java.nio.file.*;

public class MyClassLoader extends ClassLoader {
    private final Path baseDir;

    public MyClassLoader(Path baseDir, ClassLoader parent) {
        super(parent);
        this.baseDir = baseDir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] bytes = Files.readAllBytes(
                    baseDir.resolve(name.replace('.', '/') + ".class"));
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

Применение: загрузка классов из нестандартного места, шифрование байт-кода, изоляция плагинов.

### 10.8. Context ClassLoader

Каждый поток имеет **context class loader** (`Thread.currentThread().getContextClassLoader()`). Он позволяет коду, загруженному родителем, загружать классы, видимые потомку (актуально для SPI, JDBC-драйверов, фреймворков).

### 10.9. Утечки Metaspace

ClassLoader (и все загруженные им `Class`-объекты) не собираются GC, пока живы ссылки. Классические утечки:

- **Веб-приложения в Tomcat.** При reload приложение создаёт новый ClassLoader, старый должен умереть. Если что-то (статический ThreadLocal, поток, кэш) держит ссылку — старый ClassLoader не собирается → `OutOfMemoryError: Metaspace`.
- **Динамическая генерация классов** (CGLIB, Groovy, JSP) — классы копятся.
- **ThreadLocal**, статические поля, незакрытые потоки.

Диагностика: heap dump + поиск «доминирующих» ClassLoader, `-XX:MaxMetaspaceSize`, `-verbose:class`.

### 10.10. Применение ClassLoader

| Сценарий | Зачем свой загрузчик |
|---|---|
| Tomcat/Jetty | изоляция веб-приложений друг от друга |
| OSGi | модульность, версии библиотек |
| Плагины (IDE, CI) | динамическая подгрузка/выгрузка |
| Hot reload / devtools | перезагрузка изменённых классов |
| Шифрование кода | расшифровка `.class` при загрузке |
| Разные версии библиотек | каждый загрузчик видит свою версию |

### 10.11. Пример: загрузка одного класса двумя загрузчиками

```java
import java.net.*;

public class TwoLoaders {
    public static void main(String[] args) throws Exception {
        URL[] urls = { Paths.get("build/classes").toUri().toURL() };

        var l1 = new URLClassLoader(urls, null); // parent = bootstrap
        var l2 = new URLClassLoader(urls, null);

        Class<?> c1 = l1.loadClass("com.example.Foo");
        Class<?> c2 = l2.loadClass("com.example.Foo");

        System.out.println("c1 == c2: " + (c1 == c2));           // false
        System.out.println("loader1: " + c1.getClassLoader());
        System.out.println("loader2: " + c2.getClassLoader());
    }
}
```

Вывод:

```
c1 == c2: false
loader1: java.net.URLClassLoader@...
loader2: java.net.URLClassLoader@...
```

### Типичные ошибки

- Думать, что класс определяется только именем (нет — парой loader+name).
- Создавать загрузчики и не освобождать ссылки → утечка Metaspace.
- Ломать parent delegation без понимания последствий (например, child-first загрузка может сломать типы).
- Хранить `Class`-объекты/ThreadLocal от старого загрузчика после reload.
- Ожидать, что `static`-поля «общие» между разными загрузчиками.

### Часто спрашивают на собеседовании

- **Какие ClassLoader есть в JVM?** Bootstrap, Platform, Application, Custom.
- **Что такое parent delegation и зачем?** Сначала родителю — для безопасности и уникальности.
- **Как JVM идентифицирует класс?** Парой (ClassLoader, fully-qualified name).
- **Почему `static` поля не общие между загрузчиками?** Потому что это разные `Class`-объекты.
- **Что такое `ClassCastException` при разных загрузчиках?** Попытка привести объект класса из другого загрузчика к «такому же» классу.
- **Почему утекает Metaspace?** ClassLoader остаётся достижимым (ThreadLocal, потоки, кэши).
- **Где используют свои ClassLoader?** Tomcat, OSGi, плагины, hot-deploy.

## 11. Шпаргалка

**Исключения**

- `Throwable` → `Error` (не ловим) и `Exception`.
- `Exception` → checked + `RuntimeException` (unchecked).
- Методы: `getMessage`, `getCause`, `printStackTrace`, `getStackTrace`, `addSuppressed`.
- Checked проверяет компилятор; unchecked — нет.
- Своё: `extends Exception` (checked) / `extends RuntimeException` (unchecked).

**try-catch-finally**

- Catch — от конкретного к общему.
- Multi-catch: `catch (A | B e)`, `e` effectively final.
- `finally` выполняется всегда (кроме `System.exit`, краха JVM, бесконечного цикла).
- `return` в `finally` — зло (перекрывает результат/исключение).
- Оборачивая, всегда передавай `cause`.

**try-with-resources**

- Ресурс должен быть `AutoCloseable`/`Closeable`.
- Закрытие — в обратном порядке объявления.
- Исключения из `close()` → suppressed.
- Java 9: можно `try (existingVar)` для effectively final.

**Error**

- `OutOfMemoryError`: heap, Metaspace, GC overhead, direct buffer, native thread.
- `StackOverflowError` — глубокая рекурсия; `-Xss`.
- Heap: `-Xms`/`-Xmx`; Metaspace: `-XX:MaxMetaspaceSize`.
- `ClassNotFoundException` (checked) vs `NoClassDefFoundError` (Error).

**throw/throws/assert**

- `throw` — бросает; `throws` — объявляет.
- `assert` включён только с `-ea`; при провале `AssertionError`.
- Для валидации — `IllegalArgumentException`/`Objects.requireNonNull`, не `assert`.

**I/O**

- Байтовые: `InputStream`/`OutputStream`; символьные: `Reader`/`Writer`.
- Декораторы: `Buffered*`, `Data*`, `Object*`, `Print*`, `*StreamReader`.
- Всегда указывай кодировку (`StandardCharsets.UTF_8`).
- NIO.2: `Path`, `Files`, `Paths`; каналы: `FileChannel` + `ByteBuffer` (`flip`!).
- Большие файлы: `Files.lines`, `BufferedReader`, каналы — не целиком.

**Сериализация**

- `Serializable` — маркер; задавай `serialVersionUID`.
- `transient` и `static` не сериализуются.
- Конструктор при десериализации не вызывается (кроме `Externalizable`).
- `readObject`/`writeObject` — кастомизация; `readResolve` — подмена.
- Не-`Serializable` родитель: поля не сохраняются, вызывается no-arg конструктор.
- Небезопасно: gadget chains; `ObjectInputFilter`; лучше JSON/Protobuf.

**XML/JSON**

- JAXB удалён из JDK с Java 11 (JEP 320); подключается отдельно.
- Jackson — стандарт для JSON; `ObjectMapper`, `@JsonProperty`, `@JsonIgnore`.

**ClassLoader**

- Bootstrap → Platform → Application → Custom.
- Parent delegation: сначала родителю.
- Класс = (ClassLoader, имя); static-поля у каждого загрузчика свои.
- Утечка ClassLoader → `OutOfMemoryError: Metaspace`.

## 12. Частые вопросы на собеседовании с короткими ответами

**1. Чем `Error` отличается от `Exception`?**
`Error` — сбой JVM (не восстанавливаемый), `Exception` — прикладная ошибка.

**2. Что такое checked-исключение?**
Наследник `Exception`, не `RuntimeException`; компилятор требует `try/catch` или `throws`.

**3. Почему `finally` иногда не выполняется?**
`System.exit`, `Runtime.halt`, крах JVM, бесконечный цикл/блокировка в `try`.

**4. Что делает `return` в `finally`?**
Перекрывает `return` из `try` и «проглатывает» исключения. Плохая практика.

**5. В каком порядке закрываются ресурсы try-with-resources?**
В обратном порядку объявления.

**6. Что такое suppressed-исключение?**
Исключение из `close()`, прикреплённое к основному через `addSuppressed`.

**7. Чем `Closeable` отличается от `AutoCloseable`?**
`Closeable` (java.io) кидает `IOException`; `AutoCloseable` (java.lang) — `Exception`. `Closeable extends AutoCloseable`.

**8. Разница байтовых и символьных потоков?**
Байтовые — для бинарных данных; символьные — для текста с учётом кодировки.

**9. Что такое Decorator pattern в I/O?**
Обёртывание потоков друг в друга для добавления поведения (`Buffered`, `Data`, ...).

**10. Как прочитать большой файл?**
Построчно/ленивым стримом (`Files.lines`, `BufferedReader`) или каналами; не грузить целиком.

**11. Что такое `serialVersionUID`?**
Версия сериализуемого класса; несовпадение → `InvalidClassException`. Задавать явно.

**12. Сериализуются ли `static`/`transient` поля?**
Нет. `transient` станет значением по умолчанию, `static` — берётся из класса.

**13. Вызывается ли конструктор при десериализации?**
Нет (кроме `Externalizable` и не-`Serializable` родителя).

**14. `Serializable` vs `Externalizable`?**
Автоматическая сериализация vs полностью ручная (нужен public no-arg конструктор).

**15. Как сделать singleton сериализуемым?**
`readResolve` (или `enum`).

**16. Почему десериализация опасна?**
Gadget chains → RCE. Нельзя десериализовать недоверенные данные; используй `ObjectInputFilter`.

**17. Почему JAXB убрали из JDK?**
Это часть Java EE, вынесена отдельно (JEP 320), с Java 11 нет в JDK.

**18. Какие ClassLoader есть в JVM?**
Bootstrap, Platform, Application (System), Custom.

**19. Что такое parent delegation?**
Загрузчик сначала просит родителя; если тот не нашёл — грузит сам. Защита от подмены ядра.

**20. Как JVM идентифицирует класс?**
Парой (ClassLoader, fully-qualified name). Один класс у разных загрузчиков — разные `Class`.

**21. Почему `static`-поля у разных загрузчиков разные?**
Потому что это разные `Class`-объекты, у каждого своя копия статики.

**22. Что такое `ClassCastException` при нескольких загрузчиках?**
Попытка привести объект класса из загрузчика A к «такому же» классу из загрузчика B.

**23. Почему утекает Metaspace?**
ClassLoader остаётся достижимым (ThreadLocal, потоки, кэши), классы не выгружаются.

**24. Зачем `-Xss` и `-Xmx`?**
`-Xss` — размер стека потока, `-Xmx` — максимум heap.

**25. Когда использовать `assert`?**
Только для внутренних инвариантов в тестах/разработке (`-ea`). Не для валидации входа.

**26. Что будет, если `close()` бросит исключение, а тело `try` тоже?**
Основным будет исключение из тела, а из `close()` — suppressed.

**27. Можно ли использовать `try` без `catch`?**
Да, если есть `finally` или ресурсы.

**28. Как избежать `StackOverflowError`?**
Заменить рекурсию циклом, увеличить `-Xss`, уменьшить локальные переменные.

**29. `Files.readAllLines` vs `Files.lines`?**
Первый грузит всё в память, второй — ленивый `Stream` (закрывать!).

**30. Что такое `ByteBuffer.flip()`?**
Переключение буфера в режим чтения: `limit = position`, `position = 0`.
