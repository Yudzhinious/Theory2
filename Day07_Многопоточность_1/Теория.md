## 0. Зачем вообще многопоточность? (введение для новичка)

Представьте завод. Раньше на нём стоял **один рабочий** — процессор с одним ядром. Он делал всё сам: точил деталь, потом упаковывал, потом отвечал по телефону. Пока он точит — телефон звонит впустую, упаковка стоит.

Потом завод расширили: поставили **несколько рабочих** (ядер), и наняли **бригаду** (потоки), которая работает параллельно в одном цехе. Теперь один рабочий точит, другой упаковывает, третий отвечает на звонки — всё одновременно.

Именно за это мы платим сложностью многопоточности.

**Плюсы:**
- **Использование многоядерности.** Одно ядро физически не может выполнять два машинных кода одновременно; несколько ядер — могут.
- **Отзывчивость.** В интерфейсе «тяжёлая» операция (загрузка файла) не должна морозить кнопки. Её уводят в отдельный поток.
- **Совмещение ожидания и работы.** Пока поток ждёт ответа по сети, другой поток считает.
- **Структурирование.** Сервер на каждого клиента выделяет поток — код получается понятнее, чем один большой конечный автомат.

**Минусы:**
- **Гонки (race conditions).** Два потока лезут в одни данные и портят результат.
- **Дедлоки (deadlock).** Два потока навечно ждут друг друга.
- **Проблемы видимости.** Один поток записал, другой не видит (кэши, оптимизации компилятора).
- **Сложная отладка.** Ошибка может проявляться раз в тысячу запусков, только на 8-ядерной машине, только в проде.

> **Главная мысль всего дня:** многопоточность — это не «бесплатный ускоритель». Это инструмент, у которого есть цена — необходимость синхронизации.

## 1. Процесс и поток

### 1.1 Аналогия

- **Процесс** — это отдельный **цех завода** со своей стеной, своими станками, своим складом. Никто снаружи в него не залезет. У каждого цеха свой номер (PID).
- **Поток** — это **рабочий внутри цеха**. Все рабочие одного цеха стоят в одном помещении и пользуются **общим складом** (Heap), но у каждого — **своя тумбочка с инструментами** (стек), свой **журнал текущего задания** (PC-регистр) и свои **закладки** (регистры CPU).

### 1.2 Формальное определение

| Признак | Процесс | Поток |
|---|---|---|
| Что это | Запущенная программа | Единица выполнения внутри процесса |
| Адресное пространство | **Своё, изолированное** | **Общее** с другими потоками процесса |
| Память | Своя Heap | Общая Heap, **свой стек** |
| Что ещё своё | PID, дескрипторы файлов, права | Стек, PC, регистры, состояние, приоритет |
| Стоимость создания | Дорого (миллисекунды) | Дешевле (микросекунды) |
| Стоимость переключения | Дорого (смена адресного пространства, TLB flush) | Дешевле (общая память) |
| Изоляция | Полная | Отсутствует (общая память — источник багов) |
| Общение | IPC: сокеты, pipe, shared memory | Просто общая память (и это опасно!) |

### 1.3 Что потоки делят, а что — нет

**Делят (общее):**
- **Heap** — все объекты `new ...` лежат здесь. Если два потока видят ссылку на один объект, они видят одни и те же поля.
- **Metaspace** (в старых JVM — PermGen) — метаданные классов, статические поля.
- **Открытые файлы, сокеты, дескрипторы.**
- **Сам код класса** (байт-код).

**Не делят (личное):**
- **Стек** — локальные переменные и кадры вызовов. У каждого потока свой стек (размер задаётся `-Xss`, по умолчанию ~512 КБ–1 МБ).
- **Program Counter (PC)** — какой байт-код выполняется сейчас.
- **Регистры процессора** (при переключении сохраняются/восстанавливаются).
- **Состояние потока** (`Thread.State`), приоритет, флаг daemon, флаг прерывания.

```java
public class SharedVsLocal {
    static int shared = 0;            // в Heap, общая для всех потоков

    public static void main(String[] args) {
        Runnable task = () -> {
            int local = 100;          // в стеке ЭТОГО потока, у каждого своя
            shared++;                 // работа с общей памятью — опасно!
            System.out.println(Thread.currentThread().getName()
                    + ": local=" + local + ", shared=" + shared);
        };
        new Thread(task, "A").start();
        new Thread(task, "B").start();
    }
}
```

Возможный вывод (порядок и значения `shared` не гарантированы!):

```
A: local=100, shared=1
B: local=100, shared=2
```

или

```
A: local=100, shared=2
B: local=100, shared=2   // потерянное обновление: оба прочитали 1 и записали 2
```

`local` всегда `100`, потому что у каждого потока **свой стек**. А `shared++` — гонка (разберём в разделе 7).

### 1.4 Переключение контекста (context switch)

Процессор в каждый момент выполняет **один** поток на **одном** ядре. Чтобы «казалось», что всё параллельно, планировщик ОС быстро переключает потоки. Переключение — это:
1. Сохранить состояние текущего потока (PC, регистры) в его блок управления.
2. Выбрать следующий поток.
3. Восстановить его состояние.

Это занимает время (сотни наносекунд — микросекунды). Чем больше потоков на одном ядре, тем больше накладных расходов на переключение и меньше полезной работы. Отсюда правило: **не создавайте тысячи «тяжёлых» потоков** — используйте пулы.

При переключении **между процессами** дополнительно меняется адресное пространство (и сбрасывается TLB — кэш трансляции адресов), поэтому это заметно дороже, чем между потоками одного процесса.

### 1.5 Платформенные vs виртуальные потоки (Java 21)

**Платформенный поток (platform thread)** — «толстая» обёртка над потоком ОС. Соотношение **1:1**: один Java-поток = один поток ОС. Именно так было всегда до Java 21. Минус: поток ОС дорог (память на стек, стоимость создания), а их количество ограничено (десятки тысяч — уже много).

**Виртуальный поток (virtual thread)** — появился в **Java 21** (Project Loom, JEP 444). Это лёгкий поток, которым управляет **JVM**, а не ОС. Соотношение **M:N**: много виртуальных потоков «катаются» на небольшом пуле платформенных потоков (carrier threads).

```java
// Java 21: запустить 1 000 000 виртуальных потоков — реально
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        int id = i;
        executor.submit(() -> {
            Thread.sleep(1000);       // блокировка НЕ занимает поток ОС
            return id;
        });
    }
} // автоматический close() дождётся завершения
```

**Как это работает:** когда виртуальный поток делает блокирующую операцию (`sleep`, `wait`, I/O), JVM **снимает** его с потока-носителя (unmount), а носитель берётся за другой виртуальный поток. Поток ОС не простаивает.

| | Платформенный | Виртуальный (Java 21) |
|---|---|---|
| Кто управляет | ОС | JVM |
| Модель | 1:1 | M:N |
| Стек | Фиксированный, «толстый» | Гибкий, в куче, «тонкий» |
| Создать миллион | Невозможно | Легко |
| Блокировки | Занимают поток ОС | Освобождают носитель |
| CPU-bound задачи | Хорошо | **Плохо** (нет выгоды) |
| `Thread.currentThread()` | `Thread` | `VirtualThread` |
| `isVirtual()` | `false` | `true` |

> **Важно:** виртуальные потоки — для задач, которые **много ждут** (I/O). Для тяжёлых вычислений (CPU-bound) они не дают ускорения, потому что носителей столько же, сколько ядер.

> **Осторожно:** внутри `synchronized` виртуальный поток **прилипает** (pinning) к носителю, и польза теряется. С Java 21 рекомендуется использовать `ReentrantLock` вместо `synchronized` в коде для виртуальных потоков. (В более новых версиях pinning из-за `synchronized` устранён, но привычка полезна.)

### 1.6 Типичные ошибки темы 1

- Считать, что потоки делят всё. Нет — стек у каждого свой.
- Думать, что `static`-поля «в каждом потоке свои». Нет, они общие (лежат в Metaspace/Heap).
- Создавать поток на каждую мелкую задачу — накладные расходы съедят выгоду.
- Ждать ускорения от виртуальных потоков на CPU-bound задачах.

### 1.7 Часто спрашивают на собеседовании (тема 1)

1. **Чем поток отличается от процесса?** Поток — единица внутри процесса; делит адресное пространство, имеет свой стек и PC. Процесс изолирован.
2. **Что общего у потоков одного процесса?** Heap, Metaspace/статика, открытые ресурсы, код.
3. **Что у потока своё?** Стек, PC, регистры, состояние, приоритет, флаг прерывания.
4. **Что дороже переключить — процесс или поток?** Процесс (смена адресного пространства, TLB).
5. **Что такое виртуальные потоки?** Лёгкие потоки JVM, Java 21, M:N, для I/O.

## 2. Состояния потока (`Thread.State`)

### 2.1 Зачем это знать

Состояние — это «что поток делает прямо сейчас». По нему диагностируют: поток завис в `BLOCKED` — кто-то держит монитор; в `WAITING` — ждёт `notify`, которого может не быть. `jstack` показывает состояния — это первое, что смотрят при разборе зависаний.

### 2.2 Диаграмма переходов

```
                     start()
        NEW ───────────────────────► RUNNABLE
                                        │  ▲
                     ждёт монитор       │  │ получил монитор
                     synchronized       ▼  │
                                   BLOCKED──┘
                                        │
                     wait() / join()    │   sleep(ms) / wait(ms)
                     park() (без тайма) ▼   join(ms) / parkNanos()
                                  WAITING   TIMED_WAITING
                                        │        │
                     notify/notifyAll ──┘        │ таймаут / notify
                     (снова в BLOCKED,           │
                      затем RUNNABLE)             │
                                                  ▼
        RUNNABLE ────────── завершение run() ──► TERMINATED
```

### 2.3 Разбор каждого состояния

**NEW** — объект `Thread` создан (`new Thread(...)`), но `start()` ещё не вызван. Это ещё не «живой» поток ОС, а просто Java-объект. Вызов `run()` в этом состоянии выполнит код в текущем потоке, а `start()` переведёт в RUNNABLE.

**RUNNABLE** — поток либо **выполняется** на CPU, либо **готов** выполняться и ждёт планировщика. В Java в это состояние входит и ожидание ввода-вывода/сетевых операций (JVM не различает «работаю» и «жду данные от ОС»). Поэтому RUNNABLE ≠ «гарантированно жрёт CPU».

**BLOCKED** — поток **ждёт освобождения монитора**, чтобы войти в `synchronized`-блок/метод или вернуться в него после `wait()`. Это состояние **только** про встроенные мониторы (`synchronized`).

**WAITING** — поток ждёт **бессрочно**, пока другой поток его не разбудит явно:
- `Object.wait()` (без таймаута),
- `Thread.join()` (без таймаута),
- `LockSupport.park()` (без таймаута).

**TIMED_WAITING** — поток ждёт **с таймаутом**, сам проснётся по истечении:
- `Thread.sleep(ms)`,
- `Object.wait(ms)`,
- `Thread.join(ms)`,
- `LockSupport.parkNanos()/parkUntil()`.

**TERMINATED** — метод `run()` завершился (нормально или через исключение). Поток **нельзя** перезапустить: повторный `start()` бросит `IllegalThreadStateException`.

### 2.4 Ключевая разница BLOCKED vs WAITING

Это любимый вопрос собеседований.

| | BLOCKED | WAITING |
|---|---|---|
| Чего ждёт | **Монитора** `synchronized` | **Сигнала** (`notify`, `join`-потока, `unpark`) |
| Кто «виноват» | Другой поток держит монитор | Программная логика: ждём события |
| Выйти из состояния | Когда монитор освободится | Когда придут `notify/notifyAll/unpark` |
| Таймаут | Нет | Нет (это WAITING), с таймаутом — TIMED_WAITING |
| `ReentrantLock.lock()` | **НЕ BLOCKED** → WAITING/TIMED_WAITING | — |

**Запомните:** `BLOCKED` — это «стою в очереди к двери с замком». `WAITING` — это «сижу в комнате ожидания и жду, когда позовут по имени».

> Ожидание в `ReentrantLock` (и вообще в `java.util.concurrent`) не отображается как `BLOCKED`, потому что это не монитор JVM, а своя реализация на `LockSupport.park()`.

### 2.5 Пример: наблюдаем состояния

```java
public class StateDemo {
    public static void main(String[] args) throws InterruptedException {
        Object lock = new Object();

        Thread waiting = new Thread(() -> {
            synchronized (lock) {
                try {
                    lock.wait();          // уйдёт в WAITING
                } catch (InterruptedException ignored) { }
            }
        });
        waiting.start();

        Thread sleeping = new Thread(() -> {
            try { Thread.sleep(10_000); } catch (InterruptedException ignored) { } // TIMED_WAITING
        });
        sleeping.start();

        Thread blocked = new Thread(() -> {
            synchronized (lock) {          // застрянет в BLOCKED, пока waiting держит lock? нет:
                // waiting освободил lock внутри wait(), поэтому blocked войдёт и сразу выйдет
            }
        });
        blocked.start();

        Thread.sleep(300);                 // дать потокам дойти до нужных состояний
        System.out.println("waiting: " + waiting.getState());   // WAITING
        System.out.println("sleeping: " + sleeping.getState()); // TIMED_WAITING

        synchronized (lock) {
            lock.notifyAll();              // разбудить waiting
        }
        waiting.join();
        System.out.println("waiting: " + waiting.getState());   // TERMINATED
        sleeping.interrupt();
    }
}
```

Ожидаемый вывод:

```
waiting: WAITING
sleeping: TIMED_WAITING
waiting: TERMINATED
```

### 2.6 Типичные ошибки темы 2

- Путать `BLOCKED` и `WAITING`.
- Считать, что `RUNNABLE` всегда означает «работает на CPU» (может ждать I/O).
- Пытаться перезапустить завершённый поток.
- Считать, что `ReentrantLock` даёт `BLOCKED` — нет, там `WAITING`/`TIMED_WAITING`.

### 2.7 Часто спрашивают (тема 2)

1. **Перечислите состояния потока.** NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
2. **BLOCKED vs WAITING?** BLOCKED — ждёт монитор; WAITING — ждёт сигнал.
3. **Как перевести поток в TIMED_WAITING?** `sleep(ms)`, `wait(ms)`, `join(ms)`, `parkNanos`.
4. **Можно ли из TERMINATED вернуть поток в RUNNABLE?** Нет, только создать новый.

## 3. Способы создания потока

### 3.1 Аналогия

Рабочего на завод можно нанять по-разному:
1. **Вырастить внутри компании** — сделать подкласс бригадира (`extends Thread`). Жёстко, занимает единственное «место наследования».
2. **Нанять по контракту на конкретную работу** — `Runnable`. Гибко, рабочий не обязан быть «бригадиром».
3. **Нанять и ждать результат его работы** — `Callable` + `Future`.
4. **Не нанимать вручную, а отдать задачи кадровому агентству** — `ExecutorService` (пул).
5. **Отдать задачу и «повесить обработчик» на результат** — `CompletableFuture`.

### 3.2 Способ 1: `extends Thread`

```java
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Работает поток: " + getName());
    }
}

public class Demo1 {
    public static void main(String[] args) {
        MyThread t = new MyThread();
        t.start();                       // создаёт новый поток ОС и вызывает run() в нём
        System.out.println("Работает поток: " + Thread.currentThread().getName());
    }
}
```

Возможный вывод (порядок не гарантирован):

```
Работает поток: main
Работает поток: Thread-0
```

**Минус:** Java не поддерживает множественное наследование классов. Если класс уже наследует что-то (например, `JFrame`), `extends Thread` невозможен. Плюс ты «примешиваешь» логику задачи к инфраструктуре потока — нарушение разделения ответственности.

### 3.3 Способ 2: `implements Runnable` (предпочтительный)

```java
public class Demo2 {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println("hi from " + Thread.currentThread().getName());
        Thread t = new Thread(task, "worker-1");
        t.start();
    }
}
```

Ожидаемый вывод:

```
hi from worker-1
```

Почему лучше:
- Класс свободен наследовать что угодно.
- Задачу можно передать в любой пул, а не только в `Thread`.
- Один и тот же `Runnable` можно запустить в нескольких потоках.
- Чистое разделение: *что делать* (`Runnable`) vs *как исполнять* (`Thread`/`Executor`).

### 3.4 Способ 3: `Callable<V>` + `Future<V>`

`Callable` — как `Runnable`, но **возвращает результат** и **может бросать checked-исключения**.

```java
import java.util.concurrent.*;

public class Demo3 {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        Callable<Integer> sum = () -> {
            int s = 0;
            for (int i = 1; i <= 100; i++) s += i;
            return s;                     // возвращаем результат
        };

        Future<Integer> future = pool.submit(sum);
        System.out.println("Делаем что-то ещё, пока считают...");
        int result = future.get();        // БЛОКИРУЕТ до готовности
        System.out.println("Сумма = " + result);

        pool.shutdown();
    }
}
```

Ожидаемый вывод:

```
Делаем что-то ещё, пока считают...
Сумма = 5050
```

Методы `Future`:

| Метод | Что делает |
|---|---|
| `get()` | Ждёт результат (блокирует), бросает `ExecutionException` |
| `get(timeout, unit)` | Ждёт с таймаутом → `TimeoutException` |
| `isDone()` | Готово ли (успех/ошибка/отмена) |
| `isCancelled()` | Отменено ли |
| `cancel(mayInterrupt)` | Попытка отменить |

Если задача бросила исключение, `get()` обернёт его в `ExecutionException`, а причина — внутри `getCause()`.

```java
Future<Integer> bad = pool.submit(() -> { throw new RuntimeException("boom"); });
try {
    bad.get();
} catch (ExecutionException e) {
    System.out.println("Причина: " + e.getCause().getMessage()); // boom
}
```

### 3.5 Способ 4: `ExecutorService` (пул потоков) — как надо в реальном коде

Создавать `new Thread(...)` на каждую задачу — плохо: дорого и неконтролируемо. Пул переиспользует потоки.

```java
import java.util.concurrent.*;

public class Demo4 {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(3);

        for (int i = 1; i <= 5; i++) {
            int id = i;
            pool.submit(() ->
                System.out.println("Задача " + id + " в " + Thread.currentThread().getName()));
        }

        pool.shutdown();                          // не принимает новые, доделывает текущие
        pool.awaitTermination(1, TimeUnit.MINUTES); // дождаться завершения
    }
}
```

Возможный вывод (номера потоков повторяются, т.к. пул из 3):

```
Задача 1 в pool-1-thread-1
Задача 2 в pool-1-thread-2
Задача 3 в pool-1-thread-3
Задача 4 в pool-1-thread-1
Задача 5 в pool-1-thread-2
```

Типы пулов (кратко; подробно — в следующих днях):

| Фабрика | Особенность |
|---|---|
| `newFixedThreadPool(n)` | Фиксированное число потоков |
| `newCachedThreadPool()` | Создаёт по необходимости, переиспользует |
| `newSingleThreadExecutor()` | Один поток, задачи по порядку |
| `newScheduledThreadPool(n)` | Отложенные/периодические задачи |
| `newVirtualThreadPerTaskExecutor()` | Виртуальный поток на задачу (Java 21) |

### 3.6 Способ 5: `CompletableFuture` (высокоуровневый)

Позволяет строить цепочки асинхронных операций без ручной блокировки.

```java
import java.util.concurrent.CompletableFuture;

public class Demo5 {
    public static void main(String[] args) {
        CompletableFuture.supplyAsync(() -> 21)       // асинхронно получить 21
                .thenApply(x -> x * 2)                // преобразовать: 42
                .thenAccept(x -> System.out.println("Результат: " + x))
                .join();                              // дождаться (не блокирует checked)
    }
}
```

Ожидаемый вывод:

```
Результат: 42
```

### 3.7 `start()` vs `run()` — критично!

```java
public class StartVsRun {
    public static void main(String[] args) {
        Thread t = new Thread(() ->
                System.out.println("Выполняется в: " + Thread.currentThread().getName()));

        System.out.println("--- вызываем run() ---");
        t.run();      // это ОБЫЧНЫЙ вызов метода: работает в потоке main, НОВЫЙ поток не создаётся

        System.out.println("--- вызываем start() ---");
        t.start();    // создаёт НОВЫЙ поток и вызывает run() в нём
    }
}
```

Ожидаемый вывод:

```
--- вызываем run() ---
Выполняется в: main
--- вызываем start() ---
Выполняется в: Thread-0
```

**Правило:** `start()` — «нанять рабочего», `run()` — «самому сделать его работу».

Нельзя вызвать `start()` дважды:

```java
Thread t = new Thread(() -> {});
t.start();
t.start(); // IllegalThreadStateException: поток уже запущен/завершён
```

### 3.8 Сравнительная таблица способов

| Способ | Возвращает результат | Бросает checked | Пул | Когда использовать |
|---|---|---|---|---|
| `extends Thread` | Нет | Нет | Нет | Учебные примеры |
| `Runnable` | Нет | Нет | Да | Обычные задачи |
| `Callable`+`Future` | **Да** | **Да** | Да | Нужен результат/исключение |
| `ExecutorService` | Через Future | Через Future | **Да** | Реальный код |
| `CompletableFuture` | Да (асинхронно) | Нет (unchecked) | Да | Цепочки, композиция |

### 3.9 Типичные ошибки темы 3

- Вызвать `run()` вместо `start()` — код выполнится в текущем потоке, а не в новом.
- `extends Thread` там, где достаточно `Runnable`.
- Забыть `shutdown()` у пула — приложение не завершится (потоки не-daemon).
- Создавать `new Thread` в цикле на тысячи задач.
- Дважды вызвать `start()`.

### 3.10 Часто спрашивают (тема 3)

1. **`start()` vs `run()`?** `start()` создаёт поток; `run()` — обычный метод.
2. **Почему `Runnable` лучше `Thread`?** Не занимает наследование, гибче, разделяет задачу и исполнение.
3. **`Runnable` vs `Callable`?** `Callable` возвращает результат и бросает checked.
4. **Как получить результат задачи?** `Callable` + `Future.get()`.
5. **Можно ли вызвать `start()` дважды?** Нет, `IllegalThreadStateException`.

## 4. Корректное завершение потока

### 4.1 Почему нельзя «просто убить» поток

Представьте рабочего, который посреди работы с инструментом. Если вырвать инструмент из рук (`stop()`), он может уронить деталь, испортить станок, оставить кран открытым. То же с потоком: он может держать монитор, писать в файл, менять несколько связанных полей — и остановится на середине.

**`Thread.stop()`** (deprecated):
- Разблокирует все мониторы, которые держал поток → другой поток увидит объект в **несогласованном** состоянии.
- Может бросить `ThreadDeath` в произвольной точке.
- Может «сломать» инварианты объектов.

**`Thread.suspend()` / `resume()`** (deprecated):
- `suspend()` останавливает поток, **не освобождая** удерживаемые мониторы.
- Если приостановленный поток держал монитор, нужный потоку, который должен его разбудить через `resume()` → **дедлок**.

> Вывод: поток должен останавливаться **сам**, по своей воле, получив сигнал. Это называется **кооперативным** завершением.

### 4.2 Способ 1: volatile-флаг

Самый простой и понятный. Поток сам проверяет флаг в цикле.

```java
public class FlagStop implements Runnable {
    private volatile boolean running = true;   // volatile обязателен!

    @Override
    public void run() {
        while (running) {
            // полезная работа
            System.out.println("Работаю...");
            try { Thread.sleep(500); } catch (InterruptedException e) {
                Thread.currentThread().interrupt(); // см. ниже
                break;
            }
        }
        System.out.println("Аккуратно завершился");
    }

    public void shutdown() {
        running = false;   // другой поток может это сделать
    }

    public static void main(String[] args) throws InterruptedException {
        FlagStop task = new FlagStop();
        Thread t = new Thread(task);
        t.start();
        Thread.sleep(2000);
        task.shutdown();     // просим остановиться
        t.join();            // ждём фактического завершения
    }
}
```

Почему `volatile`? Без него компилятор/JIT может **закешировать** `running` в регистре и цикл станет бесконечным — поток никогда не увидит изменение из другого потока. `volatile` гарантирует видимость (подробно — раздел 8 и День 8).

### 4.3 Способ 2: `interrupt()` + `InterruptedException`

`interrupt()` — это **не** «убить поток». Это вежливая просьба: «остановись, когда сможешь». Он **устанавливает флаг прерывания**.

Поведение зависит от состояния потока:
- Поток **выполняется** → просто выставляется флаг; поток должен сам его проверять (`isInterrupted()`).
- Поток в `sleep/wait/join` → эти методы **немедленно бросают** `InterruptedException` и **сбрасывают** флаг.

```java
public class InterruptDemo implements Runnable {
    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {   // проверяем флаг
            System.out.println("Тик...");
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                // sleep бросил исключение и СБРОСИЛ флаг
                System.out.println("Меня прервали во сне!");
                Thread.currentThread().interrupt();  // ВОССТАНАВЛИВАЕМ флаг
                break;                               // выходим из цикла
            }
        }
        System.out.println("Поток завершился");
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(new InterruptDemo());
        t.start();
        Thread.sleep(2500);
        t.interrupt();     // просим остановиться
        t.join();
    }
}
```

Ожидаемый вывод:

```
Тик...
Тик...
Тик...
Меня прервали во сне!
Поток завершился
```

### 4.4 Почему важно восстанавливать флаг

`InterruptedException` **сбрасывает** флаг прерывания. Если вы поймали исключение и просто `break`/проглотили, информация «меня просили прерваться» **теряется**. Если вызов выше по стеку тоже ждёт прерывания, он его не увидит.

**Три корректных варианта:**

```java
// 1. Пробросить дальше (лучший вариант, если сигнатура позволяет)
void doWork() throws InterruptedException {
    Thread.sleep(1000);
}

// 2. Восстановить флаг и завершиться/вернуть управление
void doWork() {
    try {
        Thread.sleep(1000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // "я знаю, что меня прервали"
        return;
    }
}

// 3. Сохранить и перевести в unchecked (если checked нельзя)
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new RuntimeException(e);
}
```

**Плохо:** `catch (InterruptedException e) { }` — «проглотить» исключение. Это классический баг.

### 4.5 `interrupt()` vs `isInterrupted()` vs `Thread.interrupted()`

| Метод | Тип | Что делает |
|---|---|---|
| `t.interrupt()` | instance | Устанавливает флаг у потока `t`; если тот спит — бросает ему `InterruptedException` |
| `t.isInterrupted()` | instance | Возвращает флаг, **не сбрасывая** |
| `Thread.interrupted()` | **static** | Возвращает флаг **текущего** потока и **сбрасывает** его |

### 4.6 Daemon-потоки

**Daemon-поток** — «фоновый слуга». JVM завершается, когда остаются только daemon-потоки. Примеры: сборщик мусора, служебные потоки.

```java
Thread t = new Thread(() -> {
    while (true) {
        // вечный фоновый мониторинг
    }
});
t.setDaemon(true);   // ОБЯЗАТЕЛЬНО до start(), иначе IllegalThreadStateException
t.start();
// когда main закончится, JVM не будет ждать этот поток
```

- `setDaemon(true)` только **до** `start()`.
- Поток наследует daemon-статус от создателя.
- Daemon-поток не должен держать ресурсы, требующие аккуратного закрытия (JVM его не ждёт).
- `main` — не daemon.

### 4.7 `shutdown()` vs `shutdownNow()`

Для `ExecutorService`:

| | `shutdown()` | `shutdownNow()` |
|---|---|---|
| Новые задачи | Отклоняются | Отклоняются |
| Текущие задачи | **Досчитываются** | Пытается прервать (`interrupt`) |
| Очередь задач | Обрабатывается | **Возвращается** как `List<Runnable>` |
| Возврат | `void` | `List<Runnable>` — невыполненные |
| Применение | Плановое завершение | Аварийное |

```java
ExecutorService pool = Executors.newFixedThreadPool(2);
pool.submit(() -> { while (!Thread.currentThread().isInterrupted()) { /* ... */ } });

pool.shutdown();                                  // мягко
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    List<Runnable> notRun = pool.shutdownNow();   // жёстко
    System.out.println("Не выполнено задач: " + notRun.size());
}
```

> `shutdownNow()` **не гарантирует** мгновенную остановку: он лишь посылает `interrupt`. Задача должна корректно на него реагировать.

### 4.8 Типичные ошибки темы 4

- Использовать `stop()`/`suspend()`/`resume()`.
- Забыть `volatile` у флага — бесконечный цикл.
- Проглотить `InterruptedException` без восстановления флага.
- Считать, что `interrupt()` сразу убивает поток.
- Вызвать `setDaemon` после `start()`.
- Ждать, что daemon-поток аккуратно закроет файлы.

### 4.9 Часто спрашивают (тема 4)

1. **Почему `stop()` deprecated?** Оставляет объекты в несогласованном состоянии, разблокирует мониторы.
2. **Как корректно остановить поток?** `volatile`-флаг или `interrupt()` с обработкой.
3. **Что делает `interrupt()`?** Ставит флаг; если поток спит — бросает `InterruptedException`.
4. **Зачем восстанавливать флаг?** `InterruptedException` сбрасывает его; иначе сигнал теряется.
5. **Daemon-поток?** Не мешает JVM завершиться.

## 5. `wait` / `notify` / `notifyAll`

### 5.1 Аналогия

Представьте переговорную с **одним ключом** (монитор). Внутри сидит рабочий. Если ему нужны детали, которых пока нет, он **выходит из комнаты**, **отдаёт ключ** и **ждёт в коридоре** (`wait`). Когда поставщик приносит детали, он **кричит в коридор**: «детали есть!» (`notify`/`notifyAll`). Рабочий возвращается, **снова берёт ключ** и продолжает.

### 5.2 Главное про эти методы

- Это методы класса **`Object`**, а **не** `Thread`. Любой объект может быть монитором.
- Вызывать можно **только** когда текущий поток **владеет монитором** этого объекта (внутри `synchronized(obj)` или `synchronized`-метода на `this`).
- Иначе — **`IllegalMonitorStateException`**.

```java
Object lock = new Object();
lock.wait();   // IllegalMonitorStateException — мы не в synchronized(lock)!

synchronized (lock) {
    lock.wait();   // ок
}
```

### 5.3 Что делают методы

| Метод | Действие |
|---|---|
| `wait()` | Освобождает монитор и ждёт **бессрочно** (до `notify`/`notifyAll`/`interrupt`) |
| `wait(ms)`, `wait(ms, ns)` | То же, но с таймаутом (сам проснётся) |
| `notify()` | Будит **один** случайный ожидающий поток |
| `notifyAll()` | Будит **все** ожидающие потоки |

**Ключевой факт:** `wait()` **освобождает монитор** (в отличие от `sleep`). Иначе никто не смог бы войти в `synchronized` и разбудить ждущего — получился бы дедлок.

### 5.4 Цикл `while`, а не `if` — почему?

**Spurious wakeup** (ложное пробуждение) — поток может проснуться без `notify`. Это разрешено спецификацией. Плюс бывает «не моя очередь»: разбудили всех (`notifyAll`), но условие для конкретного потока ещё не выполнено.

Поэтому **всегда** так:

```java
synchronized (lock) {
    while (!condition) {      // while, НЕ if!
        lock.wait();
    }
    // только теперь condition истинно — можно действовать
}
```

Если написать `if`, поток может проснуться, условие ещё ложно, а он уже полезет делать работу → баг.

### 5.5 Классический пример: Producer-Consumer

Один поток кладёт товар (producer), другой забирает (consumer). Буфер ограничен.

```java
import java.util.LinkedList;
import java.util.Queue;

public class ProducerConsumer {
    static class Buffer {
        private final Queue<Integer> q = new LinkedList<>();
        private final int capacity;

        Buffer(int capacity) { this.capacity = capacity; }

        // Производитель
        synchronized void put(int x) throws InterruptedException {
            while (q.size() == capacity) {   // пока полон — ждём
                wait();
            }
            q.add(x);
            System.out.println(Thread.currentThread().getName() + " положил " + x + ", размер=" + q.size());
            notifyAll();                     // разбудить потребителя
        }

        // Потребитель
        synchronized int get() throws InterruptedException {
            while (q.isEmpty()) {            // пока пуст — ждём
                wait();
            }
            int x = q.poll();
            System.out.println(Thread.currentThread().getName() + " забрал " + x + ", размер=" + q.size());
            notifyAll();                     // разбудить производителя
            return x;
        }
    }

    public static void main(String[] args) {
        Buffer buffer = new Buffer(3);

        Thread producer = new Thread(() -> {
            for (int i = 1; i <= 6; i++) {
                try { buffer.put(i); Thread.sleep(100); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            for (int i = 1; i <= 6; i++) {
                try { buffer.get(); Thread.sleep(200); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Consumer");

        producer.start();
        consumer.start();
    }
}
```

Возможный вывод:

```
Producer положил 1, размер=1
Consumer забрал 1, размер=0
Producer положил 2, размер=1
Producer положил 3, размер=2
Consumer забрал 2, размер=1
Producer положил 4, размер=2
Producer положил 5, размер=3
Consumer забрал 3, размер=2
Producer положил 6, размер=3
Consumer забрал 4, размер=2
Consumer забрал 5, размер=1
Consumer забрал 6, размер=0
```

### 5.6 `notify` vs `notifyAll`

| | `notify()` | `notifyAll()` |
|---|---|---|
| Кого будит | Одного случайного | Всех |
| Проблема | Может разбудить «не того», полезный поток продолжит спать → дедлок/зависание | Больше переключений |
| Безопасность | Опасен, если ждут разные условия | Безопасен по умолчанию |
| Совет | Используйте только если точно один вид ждущих | **Предпочитайте** `notifyAll()` |

**Почему `notify()` опасен:** если на одном мониторе ждут потоки с **разными** условиями (например, «буфер полон» и «буфер пуст»), `notify()` может разбудить производителя, когда буфер всё ещё полон, а нужный потребитель так и останется спать.

### 5.7 Правила безопасности

1. Всегда `while`, не `if`.
2. Вызывать `wait/notify` только под тем же монитором.
3. Один монитор — один набор связанных условий.
4. Предпочитайте `notifyAll()`.
5. В современном коде вместо ручных `wait/notify` берите `BlockingQueue`, `Condition`, `SynchronousQueue` и т.п.

### 5.8 Типичные ошибки темы 5

- `wait()` без `synchronized` → `IllegalMonitorStateException`.
- `if` вместо `while` (spurious wakeup).
- `notify()` там, где ждут разные условия.
- Держать блокировку во время долгих операций после пробуждения.
- Путать `wait()` (Object, освобождает монитор) и `sleep()` (Thread, не освобождает).

### 5.9 Часто спрашивают (тема 5)

1. **Почему `wait/notify` у `Object`, а не у `Thread`?** Монитор — это любой объект; ждать можно на любом объекте.
2. **Почему `wait` только в `synchronized`?** Иначе нечего освобождать; нужна атомарность проверки условия и ожидания.
3. **Почему `while`, а не `if`?** Spurious wakeup и ложные пробуждения.
4. **`notify` vs `notifyAll`?** Один случайный vs все; `notifyAll` безопаснее.
5. **Освобождает ли `wait` монитор?** Да.

## 6. `sleep`, `yield`, `join`

### 6.1 Аналогия

- **`sleep`** — рабочий ставит будильник и дремлет прямо за станком (станок/ключ не отдаёт).
- **`yield`** — рабочий говорит: «я могу и подождать, дай другим поработать» (но начальник может проигнорировать).
- **`join`** — вы ждёте, пока конкретный рабочий закончит, прежде чем идти дальше.

### 6.2 `Thread.sleep(ms)`

- Усыпляет **текущий** поток на указанное время.
- **Не освобождает** монитор.
- Может бросить `InterruptedException`.
- Точность не гарантирована (минимум — указанное время, может больше).

```java
System.out.println("Старт: " + System.currentTimeMillis());
Thread.sleep(1000);
System.out.println("Прошла ~1 секунда");
```

### 6.3 `Thread.yield()`

- Подсказка планировщику: «готов уступить CPU».
- **Без гарантий** — может быть проигнорирована.
- Монитор не освобождает.
- Используется редко; в реальном коде почти не нужен.

### 6.4 `join()`

Текущий поток ждёт завершения другого.

```java
Thread t = new Thread(() -> {
    try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    System.out.println("Поток t завершился");
});

t.start();
t.join();                 // main ждёт, пока t закончит
System.out.println("main продолжил после t");

// с таймаутом
Thread t2 = new Thread(() -> { /* долго */ });
t2.start();
t2.join(500);             // ждать максимум 500 мс
System.out.println("Ждали максимум 500 мс, isAlive=" + t2.isAlive());
```

Ожидаемый вывод:

```
Поток t завершился
main продолжил после t
Ждали максимум 500 мс, isAlive=true
```

`join()` внутри устроен как `wait()` на объекте потока, поэтому может бросить `InterruptedException` и переводит вызывающий поток в `WAITING`/`TIMED_WAITING`.

### 6.5 Таблица `sleep` vs `wait`

| Критерий | `Thread.sleep` | `Object.wait` |
|---|---|---|
| Класс | `Thread` (static) | `Object` |
| Освобождает монитор | **Нет** | **Да** |
| Требует `synchronized` | Нет | **Да** |
| Пробуждение | Таймер или `interrupt` | `notify`/`notifyAll`, таймаут или `interrupt` |
| Состояние потока | `TIMED_WAITING` | `WAITING`/`TIMED_WAITING` |
| Возвращает монитор | — | Обязательно заново захватывает |
| Типичное применение | Пауза, polling | Ожидание условия |

### 6.6 Типичные ошибки темы 6

- Думать, что `sleep` освобождает монитор (нет!).
- Использовать `sleep` для синхронизации («подожду 100 мс, наверное, успеет») — хрупко.
- Забыть, что `sleep`/`join` бросают `InterruptedException`.
- Полагаться на `yield` в логике.

### 6.7 Часто спрашивают (тема 6)

1. **`sleep` vs `wait`?** `sleep` не освобождает монитор и не требует `synchronized`; `wait` освобождает и требует.
2. **Что делает `join`?** Ждёт завершения другого потока.
3. **Есть ли гарантии у `yield`?** Нет.

## 7. Синхронизация: `synchronized`

### 7.1 Гонка (race condition) — корень зла

**Гонка** — когда результат зависит от того, в каком порядке потоки выполнили операции. Пример: два кассира одновременно считают выручку на одном счётчике.

```java
public class RaceDemo {
    static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter++;      // НЕ атомарно!
            }
        };

        Thread a = new Thread(inc);
        Thread b = new Thread(inc);
        a.start(); b.start();
        a.join();  b.join();

        System.out.println("Ожидали 200000, получили: " + counter);
    }
}
```

Возможный вывод:

```
Ожидали 200000, получили: 174823
```

Почему меньше? `counter++` — это три шага:
1. **read** — прочитать `counter` в регистр;
2. **modify** — прибавить 1;
3. **write** — записать обратно.

Если поток A прочитал 5, поток B тоже прочитал 5, оба записали 6 — одно обновление **потеряно**.

### 7.2 Критическая секция

**Критическая секция** — участок кода, который должен выполняться **атомарно** (как единое целое) относительно других потоков. `counter++` — критическая секция. Её надо защитить.

### 7.3 `synchronized` — что даёт

`synchronized` даёт **два** эффекта:
1. **Взаимное исключение (mutual exclusion)** — только один поток одновременно внутри.
2. **Видимость (visibility)** — изменения, сделанные до выхода из блока, видны тому, кто войдёт в блок с тем же монитором. Это гарантия **happens-before**: «выход из synchronized → вход в synchronized на том же мониторе».

### 7.4 Синтаксис

```java
// 1. synchronized-метод — монитор = this (для нестатического)
public synchronized void inc() {
    counter++;
}

// 2. synchronized-блок — монитор = указанный объект
private final Object lock = new Object();
public void inc() {
    synchronized (lock) {
        counter++;
    }
}

// 3. static synchronized — монитор = MyClass.class
public static synchronized void incStatic() {
    counter++;
}
```

Исправленный пример:

```java
public class SyncDemo {
    static int counter = 0;
    static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> {
            for (int i = 0; i < 100_000; i++) {
                synchronized (lock) {
                    counter++;
                }
            }
        };
        Thread a = new Thread(inc);
        Thread b = new Thread(inc);
        a.start(); b.start();
        a.join();  b.join();
        System.out.println("Получили: " + counter);   // всегда 200000
    }
}
```

Ожидаемый вывод:

```
Получили: 200000
```

### 7.5 Монитор

**Монитор** — это «замок», связанный с каждым объектом. В JVM у объекта есть заголовок (mark word), где хранится информация о блокировке (и о том, какой поток её держит). Когда поток входит в `synchronized(obj)`, он захватывает монитор `obj`; выходит — освобождает.

> Важно: **блокировка привязана к объекту**, а не к коду. Два разных потока, синхронизированные на **разных** объектах, не мешают друг другу, даже если код один и тот же.

### 7.6 Реентерабельность

Блокировка **реентерабельна**: поток, уже владеющий монитором, может войти в него повторно.

```java
public class Reentrant {
    public synchronized void a() {
        System.out.println("a");
        b();      // тот же поток снова входит в свой монитор — ОК
    }
    public synchronized void b() {
        System.out.println("b");
    }
    public static void main(String[] args) {
        new Reentrant().a();   // выведет a, b — дедлока нет
    }
}
```

JVM считает «глубину» входа. Если бы блокировка не была реентерабельной, `a()` вызвал бы дедлок на `b()`.

### 7.7 `happens-before` и видимость

Без синхронизации изменение может «застрять» в кэше ядра:

```java
public class VisibilityProblem {
    static boolean ready = false;    // нет volatile/synchronized
    static int value = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread writer = new Thread(() -> {
            value = 42;
            ready = true;
        });
        Thread reader = new Thread(() -> {
            while (!ready) { /* ждём */ }   // может не увидеть true → бесконечный цикл
            System.out.println("value = " + value); // может вывести 0
        });
        reader.start();
        Thread.sleep(100);
        writer.start();
    }
}
```

`ready` может быть закеширован, и `reader` зациклится навсегда. Лечится `volatile` или `synchronized`:

```java
static volatile boolean ready = false;
```

`volatile` гарантирует: запись `value=42` произойдёт **до** записи `ready=true` (запрет переупорядочивания), а `reader`, увидев `ready=true`, увидит и `value=42`.

### 7.8 Атомарность: почему `count++` не спасает `volatile`

`volatile` даёт видимость, но **не** атомарность. `count++` всё ещё read-modify-write из трёх шагов, и `volatile` от гонки не спасает.

Решения:

```java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.LongAdder;

// 1. synchronized
synchronized (lock) { count++; }

// 2. AtomicInteger — CAS (compare-and-swap)
AtomicInteger atomicCount = new AtomicInteger(0);
atomicCount.incrementAndGet();     // атомарно

// 3. LongAdder — быстрее при высокой конкуренции (разбивает счётчик на ячейки)
LongAdder adder = new LongAdder();
adder.increment();
```

Пример с `AtomicInteger`:

```java
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicDemo {
    static AtomicInteger counter = new AtomicInteger(0);
    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> { for (int i = 0; i < 100_000; i++) counter.incrementAndGet(); };
        Thread a = new Thread(inc), b = new Thread(inc);
        a.start(); b.start(); a.join(); b.join();
        System.out.println("Получили: " + counter.get()); // всегда 200000
    }
}
```

### 7.9 Почему нельзя синхронизироваться на `String`/`Integer`/`this`

**`String`-литералы и `Integer` кэшируются** JVM. Если вы блокируетесь на `"LOCK"` или `Integer.valueOf(1)`, другой, никак не связанный код может блокироваться на **том же самом объекте** из кэша → непредсказуемые дедлоки.

```java
// ПЛОХО: литерал интернируется, все "LOCK" — один объект
synchronized ("LOCK") { ... }

// ПЛОХО: Integer от -128 до 127 кэшируется
synchronized (Integer.valueOf(100)) { ... }
```

**`this`** как монитор тоже опасен, если ссылку на объект можно получить извне: посторонний код может захватить монитор и заблокировать вас. Лучше — приватный `final`-объект:

```java
private final Object lock = new Object();   // ХОРОШО
```

> Для статических блокировок используйте выделенный `static final Object LOCK = new Object();`, а не `MyClass.class` (хотя `MyClass.class` технически корректно, приватный объект безопаснее).

### 7.10 Типичные ошибки темы 7

- Синхронизироваться на изменяемой/кэшируемой ссылке (`String`, `Integer`).
- Разные потоки используют **разные** объекты-замки и удивляются, что гонка осталась.
- Считать, что `volatile` делает `count++` атомарным.
- Слишком широкая критическая секция → падение производительности.
- Синхронизация на `this`, доступном извне.
- Дедлок при захвате двух мониторов в разном порядке.

### 7.11 Часто спрашивают (тема 7)

1. **Что гарантирует `synchronized`?** Взаимное исключение + видимость.
2. **Что такое монитор?** Замок, связанный с объектом.
3. **Реентерабельность?** Поток может повторно войти в свой монитор.
4. **Почему `count++` не атомарен?** Это read-modify-write.
5. **Можно ли синхронизироваться на `String`?** Нельзя/не рекомендуется из-за интернирования.
6. **`volatile` vs `synchronized`?** `volatile` — видимость, без атомарности; `synchronized` — и то, и другое.

## 8. Статические vs нестатические `synchronized` методы

### 8.1 Разные мониторы!

Это частая ловушка. Монитор зависит от того, какой метод:

| Метод | Монитор |
|---|---|
| `public synchronized void m()` (instance) | `this` — конкретный объект |
| `public static synchronized void m()` (static) | `MyClass.class` — объект класса |

**Они не блокируют друг друга**, потому что замки разные.

### 8.2 Пример-доказательство

```java
public class StaticVsInstance {
    // нестатический — монитор this
    public synchronized void instanceMethod() {
        System.out.println(Thread.currentThread().getName() + " вошёл в instanceMethod");
        sleep(1000);
        System.out.println(Thread.currentThread().getName() + " вышел из instanceMethod");
    }

    // статический — монитор StaticVsInstance.class
    public static synchronized void staticMethod() {
        System.out.println(Thread.currentThread().getName() + " вошёл в staticMethod");
        sleep(1000);
        System.out.println(Thread.currentThread().getName() + " вышел из staticMethod");
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) {
        StaticVsInstance obj = new StaticVsInstance();

        new Thread(obj::instanceMethod, "T1").start();
        new Thread(StaticVsInstance::staticMethod, "T2").start();
    }
}
```

Ожидаемый вывод (оба работают **одновременно**, ~1 секунда):

```
T1 вошёл в instanceMethod
T2 вошёл в staticMethod
T1 вышел из instanceMethod
T2 вышел из staticMethod
```

Если бы мониторы совпадали, второй вошёл бы только после выхода первого.

### 8.3 Как синхронизировать вместе

Если нужно, чтобы static и instance методы были взаимоисключающими, используйте **общий** замок:

```java
public class Together {
    private static final Object LOCK = new Object();

    public void instanceMethod() {
        synchronized (LOCK) { /* ... */ }
    }
    public static void staticMethod() {
        synchronized (LOCK) { /* ... */ }
    }
}
```

### 8.4 Типичные ошибки темы 8

- Думать, что `static synchronized` и `synchronized` на экземпляре блокируют друг друга.
- Синхронизировать статический и instance код на разных объектах и ждать корректности.

### 8.5 Часто спрашивают (тема 8)

1. **Какой монитор у `static synchronized`?** Объект `Class` (`MyClass.class`).
2. **Блокируют ли друг друга static и instance методы?** Нет, разные мониторы.

## 9. Практические примеры

### 9.1 Потокобезопасный счётчик: три варианта

**Вариант 1 — `synchronized`:**

```java
public class SyncCounter {
    private int count = 0;
    public synchronized void increment() { count++; }
    public synchronized int get() { return count; }
}
```

**Вариант 2 — `AtomicInteger`:**

```java
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounter {
    private final AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); }
    public int get() { return count.get(); }
}
```

**Вариант 3 — `LongAdder` (для высокой конкуренции):**

```java
import java.util.concurrent.atomic.LongAdder;

public class AdderCounter {
    private final LongAdder count = new LongAdder();
    public void increment() { count.increment(); }
    public long get() { return count.sum(); }
}
```

Сравнение:

| Подход | Атомарность | Производительность | Когда |
|---|---|---|---|
| `synchronized` | Да | Ниже | Просто, общий случай |
| `AtomicInteger` | Да (CAS) | Высокая | Один счётчик |
| `LongAdder` | Да | Очень высокая | Много потоков, редкое чтение |

Проверка корректности:

```java
public class CounterTest {
    public static void main(String[] args) throws InterruptedException {
        SyncCounter c = new SyncCounter();
        Runnable r = () -> { for (int i = 0; i < 100_000; i++) c.increment(); };
        Thread a = new Thread(r), b = new Thread(r);
        a.start(); b.start(); a.join(); b.join();
        System.out.println("Итог: " + c.get()); // 200000
    }
}
```

### 9.2 Producer-Consumer через `BlockingQueue` (современный способ)

Ручные `wait/notify` — учебные. В проде берут `BlockingQueue`.

```java
import java.util.concurrent.*;

public class BlockingQueueDemo {
    public static void main(String[] args) {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 6; i++) {
                    queue.put(i);                       // блокируется, если полна
                    System.out.println("Положил " + i);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            try {
                for (int i = 1; i <= 6; i++) {
                    int x = queue.take();               // блокируется, если пуста
                    System.out.println("Забрал " + x);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "Consumer");

        producer.start();
        consumer.start();
    }
}
```

Возможный вывод:

```
Положил 1
Забрал 1
Положил 2
Положил 3
Забрал 2
...
```

`BlockingQueue` сама реализует `wait/notify` внутри — вам не нужно думать о цикле и spurious wakeup.

### 9.3 Типичные ошибки темы 9

- Использовать `int`-счётчик с `volatile` и думать, что он потокобезопасен.
- Писать свой producer-consumer на `wait/notify`, когда есть `BlockingQueue`.
- Читать счётчик `LongAdder` слишком часто (дорого `sum()`).

### 9.4 Часто спрашивают (тема 9)

1. **Как сделать потокобезопасный счётчик?** `synchronized`, `AtomicInteger`, `LongAdder`.
2. **Чем `LongAdder` лучше `AtomicInteger`?** Меньше конкуренции при записи.
3. **Как организовать producer-consumer?** `BlockingQueue`.

## 10. Шпаргалка

- **Процесс** — изолированное адресное пространство. **Поток** — единица внутри процесса, делит Heap, имеет свой стек и PC.
- До Java 21 поток = поток ОС (1:1). В Java 21 — **виртуальные потоки** (M:N), для I/O, не для CPU-bound.
- **Состояния:** NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
- **BLOCKED** — ждёт монитор; **WAITING** — ждёт сигнал.
- **Создание:** `extends Thread` (нет), `implements Runnable` (да), `Callable`+`Future` (результат), `ExecutorService` (пул), `CompletableFuture` (цепочки).
- **`start()`** создаёт поток; **`run()`** — обычный метод.
- **Остановка:** `volatile`-флаг или `interrupt()`; `stop()/suspend()/resume()` deprecated.
- `interrupt()` ставит флаг; `sleep/wait/join` бросают `InterruptedException` и **сбрасывают** флаг → восстанавливайте `Thread.currentThread().interrupt()`.
- **Daemon** — не мешает JVM завершиться; `setDaemon(true)` до `start()`.
- **`wait/notify`** — методы `Object`, только в `synchronized`, в цикле `while`, предпочитайте `notifyAll()`.
- **`sleep`** монитор не освобождает; **`wait`** — освобождает.
- **`synchronized`** = взаимоисключение + видимость. Реентерабельно.
- Instance `synchronized` → монитор `this`; static `synchronized` → монитор `MyClass.class`.
- **`count++` не атомарен.** `volatile` не спасает от гонки. Нужны `synchronized`/`AtomicInteger`/`LongAdder`.
- Не синхронизируйтесь на `String`/`Integer` (кэш) и на `this` (доступен извне). Лучше приватный `final Object lock`.

## 11. Частые вопросы на собеседовании с короткими ответами

1. **Процесс vs поток?** Процесс изолирован, поток делит память процесса, но имеет свой стек.
2. **Что потоки делят?** Heap, статику, ресурсы, код. **Не делят:** стек, регистры, PC.
3. **Платформенный vs виртуальный поток?** 1:1 с ОС vs M:N в JVM; виртуальные — для I/O.
4. **Перечислите состояния потока.** NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
5. **BLOCKED vs WAITING?** Ждёт монитор vs ждёт сигнал.
6. **`start()` vs `run()`?** Новый поток vs обычный вызов метода.
7. **`Runnable` vs `Callable`?** `Callable` возвращает результат и бросает checked.
8. **Почему `Runnable` предпочтительнее `Thread`?** Не занимает наследование, гибче.
9. **Почему `stop()` deprecated?** Оставляет объекты в несогласованном состоянии.
10. **Как корректно остановить поток?** `volatile`-флаг или `interrupt()`.
11. **Что делает `interrupt()`?** Ставит флаг; при `sleep/wait/join` бросает `InterruptedException`.
12. **Зачем восстанавливать флаг прерывания?** Исключение его сбрасывает.
13. **Что такое daemon-поток?** Поток, не мешающий JVM завершиться.
14. **`shutdown()` vs `shutdownNow()`?** Досчитать текущие vs прервать и вернуть очередь.
15. **Почему `wait/notify` у `Object`?** Монитором может быть любой объект.
16. **Почему `wait` в цикле `while`?** Spurious wakeup.
17. **`notify` vs `notifyAll`?** Один случайный vs все; `notifyAll` безопаснее.
18. **Освобождает ли `wait` монитор?** Да. `sleep` — нет.
19. **`sleep` vs `wait`?** Класс, освобождение монитора, необходимость `synchronized`.
20. **Что гарантирует `synchronized`?** Взаимное исключение и видимость.
21. **Что такое монитор?** Замок, связанный с объектом.
22. **Что такое реентерабельность?** Повторный вход потока в свой монитор.
23. **Почему `count++` не атомарен?** Read-modify-write из трёх операций.
24. **`volatile` vs `synchronized`?** Видимость без атомарности vs и видимость, и атомарность.
25. **Можно ли синхронизироваться на `String`/`Integer`?** Нельзя — интернирование/кэш.
26. **Монитор static `synchronized` метода?** `MyClass.class`.
27. **Как сделать потокобезопасный счётчик?** `synchronized`, `AtomicInteger`, `LongAdder`.
28. **Как реализовать producer-consumer?** `BlockingQueue` или `wait/notify` в цикле.
29. **Почему `RUNNABLE` не значит «на CPU»?** Включает ожидание I/O.
30. **Что такое happens-before?** Гарантия видимости: выход из `synchronized` → вход в него.
