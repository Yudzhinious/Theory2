# Часть A. Тестирование

## A.0. Зачем вообще тестировать?

Представь, что ты собираешь шкаф из IKEA. Можно собрать «на глаз» и надеяться, что он не развалится. А можно:
1. Проверить, что все детали на месте (проверка входа).
2. Собрать по инструкции.
3. Подёргать — не шатается ли (проверка результата).

**Тесты — это твоя автоматическая инструкция и проверка.** Ты один раз пишешь проверку, а дальше компьютер прогоняет её тысячи раз за секунды.

Зачем это нужно на практике:
- **Ловим регрессии.** Поменял код в одном месте — тесты показывают, не сломал ли ты другое. Как датчик дыма: он не тушит пожар, но предупреждает.
- **Документация.** Тест `shouldThrowWhenDivideByZero` читается как «вот как этот метод должен себя вести».
- **Смелость рефакторинга.** Есть сетка безопасности — не страшно переписать код.
- **Проектирование.** Код, который тяжело тестировать, обычно плохо спроектирован (много связей, скрытые зависимости).

> **Аналогия.** Тесты — это как примеры в учебнике математики. Ты решаешь задачу, но чтобы убедиться, что правило работает, проверяешь его на конкретных числах. Тест — это проверка правила на конкретном примере.

## A.1. JUnit 5: платформа, Jupiter, Vintage

**JUnit** — самый популярный фреймворк модульного (unit) тестирования в Java.

JUnit 5 — это не один кусок, а **три отдельные части** (это частый вопрос):

| Компонент | Что это | Роль |
|---|---|---|
| **JUnit Platform** | движок (test engine) | Запускает тесты, соединяет IDE/сборочные системы с фреймворками тестирования |
| **JUnit Jupiter** | новый API (`org.junit.jupiter.api.*`) | Аннотации и assertions JUnit 5, которыми ты пишешь тесты |
| **JUnit Vintage** | движок совместимости | Позволяет запускать старые тесты JUnit 3/4 внутри JUnit 5 |

**Аналогия:** Platform — это «розетка» (стандарт подключения), Jupiter — новый «прибор» (новый синтаксис тестов), Vintage — переходник для старых приборов (JUnit 4).

Почему так сделали? Чтобы можно было подключать разные движки (JUnit, Spock, Cucumber) к одному стандартному запускателю. JUnit 5 не ломает старые тесты — их запускает Vintage.

**Зависимости Maven (пример):**

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>
</dependency>
<!-- Опционально: запуск старых тестов JUnit 4 -->
<dependency>
    <groupId>org.junit.vintage</groupId>
    <artifactId>junit-vintage-engine</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>
</dependency>
```

> **Важно.** Аннотации JUnit 5 лежат в пакете `org.junit.jupiter.api.*`, а не `org.junit.*`. Классическая ошибка новичка — импортировать старый `org.junit.Test` (JUnit 4) и удивляться, почему тест не виден.

## A.2. Принципы FIRST и паттерн AAA

### FIRST — каким должен быть хороший тест

| Буква | Расшифровка | Что означает | Аналогия |
|---|---|---|---|
| **F** | Fast | Быстрый | Тест за миллисекунды; медленные тесты никто не запускает |
| **I** | Independent | Независимый | Тесты не влияют друг на друга и не зависят от порядка |
| **R** | Repeatable | Повторяемый | Одинаковый результат в любой среде, в любой день |
| **S** | Self-validating | Самопроверяющийся | Тест сам говорит «прошёл/упал», без ручного анализа |
| **T** | Timely | Своевременный | Пишется вместе с кодом, а не «когда-нибудь потом» |

Дополнительно к этому часто добавляют:
- **Один тест — один сценарий.** Упал тест — сразу понятно, что сломалось.
- **Имя теста описывает поведение:** `shouldThrowWhenDivideByZero`, а не `test1`.
- **Тестируй поведение, а не реализацию.** Если тест ломается от безобидного рефакторинга — он плохой.
- **Тест детерминированный.** Никаких `Thread.sleep`, случайных чисел без seed, зависимости от текущего времени.

### AAA — как писать тело теста

**Arrange — Act — Assert** («Подготовь — Действуй — Проверь»):

```java
@Test
void shouldReturnFullName() {
    // Arrange (подготовка)
    var user = new User("Ivan", "Petrov");

    // Act (действие)
    String fullName = user.getFullName();

    // Assert (проверка)
    assertEquals("Ivan Petrov", fullName);
}
```

**Аналогия AAA:** научный эксперимент. Сначала готовим приборы (Arrange), затем проводим опыт (Act), затем измеряем результат и сверяем с ожиданием (Assert).

> **Почему AAA важен.** Он делает тест линейным и читаемым сверху вниз. Если у тебя в тесте 5 блоков Act и 10 Assert — скорее всего, ты тестируешь слишком много за раз, разбей на несколько тестов.

**Given-When-Then** — та же идея в BDD-терминах: Given (дано) — When (когда) — Then (тогда). Встречается в Cucumber и описаниях.

## A.3. Аннотации JUnit 5 (подробно)

| Аннотация | Назначение | Нюанс |
|---|---|---|
| `@Test` | помечает тестовый метод | метод должен быть не-static, обычно void, без параметров |
| `@BeforeEach` | выполняется **перед каждым** тестом | подготовка свежих данных |
| `@AfterEach` | выполняется **после каждого** теста | очистка ресурсов |
| `@BeforeAll` | выполняется **один раз перед всеми** тестами | метод **static** (в JUnit 5 можно и не-static при `@TestInstance(PER_CLASS)`) |
| `@AfterAll` | один раз после всех | обычно `static` |
| `@DisplayName` | человекочитаемое имя теста | можно эмодзи и пробелы |
| `@Disabled` | отключить тест/класс | с указанием причины |
| `@Nested` | вложенный класс тестов | группировка по сценариям |
| `@ParameterizedTest` | тест с параметрами | + `@ValueSource`/`@MethodSource`/`@CsvSource` |
| `@Tag` | метка категории | для запуска подмножества тестов |
| `@ExtendWith` | подключить расширение | например, `MockitoExtension` |
| `@TestInstance` | жизненный цикл экземпляра | `PER_CLASS` — один объект на все тесты |
| `@Timeout` | ограничение по времени | защита от «зависших» тестов |
| `@RepeatedTest` | повторить N раз | для проверки нестабильности |

**Пример со всеми основными аннотациями:**

```java
@DisplayName("Калькулятор")
class CalculatorTest {

    private Calculator calc;

    @BeforeAll
    static void beforeAll() {
        System.out.println("Один раз до всех тестов");
    }

    @BeforeEach
    void setUp() {
        calc = new Calculator(); // свежий объект перед каждым тестом
    }

    @AfterEach
    void tearDown() {
        System.out.println("После каждого теста");
    }

    @AfterAll
    static void afterAll() {
        System.out.println("Один раз после всех тестов");
    }

    @Test
    @DisplayName("Сложение 2 + 3 даёт 5")
    void shouldAdd() {
        assertEquals(5, calc.add(2, 3));
    }

    @Test
    @Disabled("Пока не реализовано деление")
    void division() {
        // будет пропущен
    }

    @Nested
    @DisplayName("Когда делитель ноль")
    class WhenZero {
        @Test
        void throwsException() {
            assertThrows(ArithmeticException.class, () -> calc.divide(1, 0));
        }
    }
}
```

**Порядок выполнения:** `@BeforeAll` → для каждого теста (`@BeforeEach` → `@Test` → `@AfterEach`) → `@AfterAll`.

> **Аналогия жизненного цикла.** `@BeforeAll` — построить сцену. `@BeforeEach` — выставить декорации для конкретной сцены. `@Test` — сыграть сцену. `@AfterEach` — убрать декорации. `@AfterAll` — разобрать сцену.

### `@Nested` — зачем?

Позволяет группировать тесты по контексту и разделять общий `@BeforeEach` для группы:

```java
class UserServiceTest {
    @Nested
    class WhenUserExists {
        @BeforeEach void setUpExisting() { /* ... */ }
        @Test void returnsUser() { /* ... */ }
    }
    @Nested
    class WhenUserMissing {
        @BeforeEach void setUpMissing() { /* ... */ }
        @Test void throwsNotFound() { /* ... */ }
    }
}
```

Так тест-класс читается как оглавление: «Когда пользователь есть → …; когда нет → …».

## A.4. Утверждения (assertions)

Assertions — это проверки. Если проверка не прошла — тест падает с понятным сообщением.

| Метод | Что проверяет |
|---|---|
| `assertEquals(expected, actual)` | равенство (использует `equals`) |
| `assertNotEquals(a, b)` | неравенство |
| `assertTrue(condition)` / `assertFalse` | истинность |
| `assertNull(x)` / `assertNotNull(x)` | null / не null |
| `assertSame(a, b)` | ссылочное равенство (`==`) |
| `assertArrayEquals(a, b)` | поэлементное равенство массивов |
| `assertThrows(Exception.class, executable)` | что исключение брошено |
| `assertDoesNotThrow(executable)` | что исключение НЕ брошено |
| `assertTimeout(...)` | уложился ли в лимит времени |
| `assertAll(...)` | выполнить все проверки, даже если часть упала |
| `assertIterableEquals` | равенство коллекций по порядку |

**Пример `assertThrows`:**

```java
@Test
void divideThrowsOnZero() {
    var ex = assertThrows(ArithmeticException.class,
                          () -> calc.divide(1, 0));
    assertEquals("/ by zero", ex.getMessage());
}
```

**Пример `assertAll`** — выполняет все проверки и показывает сразу все ошибки, а не только первую:

```java
@Test
void userFieldsAreValid() {
    var user = new User("Ivan", 25);
    assertAll(
        () -> assertEquals("Ivan", user.getName()),
        () -> assertEquals(25, user.getAge()),
        () -> assertNotNull(user.getCreatedAt())
    );
}
```

**Почему `assertAll` полезен?** Если проверять по одному, тест упадёт на первой ошибке, и ты не увидишь остальные. `assertAll` даёт полную картину.

**Порядок аргументов:** в JUnit 5 сначала **expected** (ожидаемое), потом **actual** (фактическое). Это важно для сообщения об ошибке.

**Типичные ошибки (assertions):**
- Перепутан порядок expected/actual — сообщение вводит в заблуждение.
- Сравнение `double` без delta: `assertEquals(0.3, 0.1 + 0.2)` упадёт. Нужно `assertEquals(0.3, 0.1 + 0.2, 0.0001)`.
- Проверка на исключение через `try/catch` вместо `assertThrows` — легко забыть `fail()`.
- `assertTrue(a == b)` для объектов вместо `assertSame`/`assertEquals`.

**Часто спрашивают:**
- *Чем `assertEquals` отличается от `assertSame`?* — `assertEquals` использует `equals()`, `assertSame` сравнивает ссылки (`==`).
- *Как проверить, что метод бросает исключение?* — `assertThrows`, он же возвращает пойманное исключение для дальнейших проверок.

## A.5. Параметризация тестов

Когда одна логика проверяется на многих данных, не надо копировать тест. Используем `@ParameterizedTest`.

**`@ValueSource`** — простые значения:

```java
@ParameterizedTest
@ValueSource(ints = {1, 2, 3, 5, 100})
void isPositive(int number) {
    assertTrue(number > 0);
}
```

**`@CsvSource`** — несколько аргументов в строке:

```java
@ParameterizedTest
@CsvSource({
    "1, 1, 2",
    "2, 3, 5",
    "10, 20, 30"
})
void adds(int a, int b, int expected) {
    assertEquals(expected, calc.add(a, b));
}
```

**`@MethodSource`** — данные из метода (в том числе сложные объекты):

```java
@ParameterizedTest
@MethodSource("userProvider")
void validatesUser(User user, boolean expected) {
    assertEquals(expected, validator.isValid(user));
}

static Stream<Arguments> userProvider() {
    return Stream.of(
        Arguments.of(new User("Ivan", 25), true),
        Arguments.of(new User("", -1), false)
    );
}
```

**`@EnumSource`** — прогон по всем значениям enum:

```java
@ParameterizedTest
@EnumSource(Role.class)
void roleHasName(Role role) {
    assertNotNull(role.getDisplayName());
}
```

**`@NullAndEmptySource`** — проверить `null` и пустую строку:

```java
@ParameterizedTest
@NullAndEmptySource
void rejectsBlank(String input) {
    assertFalse(validator.isNotBlank(input));
}
```

> **Аналогия.** Параметризованный тест — это конвейер: одна и та же проверка прогоняется по ленте входных данных. Вместо 20 почти одинаковых методов — один.

**Типичные ошибки:**
- Забыли, что `@ParameterizedTest` заменяет `@Test` (нельзя ставить оба).
- Метод-провайдер должен быть `static`, иначе не найдётся (без `PER_CLASS`).
- Слишком много данных в одном параметризованном тесте — тяжело понять, какой кейс упал. Используй `name` в `@ParameterizedTest`.

## A.6. Stub vs Mock vs Fake vs Spy

Это четыре способа подменить зависимость в тесте. Разница — **что мы проверяем**: состояние или взаимодействие.

| Тип | Что это | Что проверяем | Пример |
|---|---|---|---|
| **Stub** | Заранее заданные ответы на вызовы | **Состояние** (результат) | Заглушка репозитория, всегда возвращающая фиксированного пользователя |
| **Mock** | Объект, записывающий вызовы | **Взаимодействие** (какие методы вызваны) | Проверить, что `emailService.send()` был вызван |
| **Fake** | Рабочая, но упрощённая реализация | Поведение | In-memory репозиторий на `HashMap` вместо реальной БД |
| **Spy** | Реальный объект, часть методов подменена | Смешанно | Реальный сервис, но один метод возвращает фиксированное значение |

**Простыми словами: stub отвечает, mock проверяет.**

**Аналогия.** Ты репетируешь пьесу:
- **Stub** — суфлёр, который всегда подсказывает одну и ту же реплику. Ты проверяешь, правильно ли ты играешь дальше.
- **Mock** — режиссёр, который записывает, вышел ли ты на сцену и сказал ли нужную реплику. Ты проверяешь, что действие произошло.
- **Fake** — дублёр-актёр: играет по-настоящему, но по упрощённому сценарию.
- **Spy** — настоящий актёр, которому в одной сцене подсказали реплику.

> **Важно:** в Mockito граница между stub и mock размыта — один и тот же объект-мок может и возвращать значения (`when`), и записывать вызовы (`verify`). Термины — про **цель использования**, а не про класс.

**Когда что использовать:**
- Не хочу ходить в БД/сеть → **stub/fake**.
- Проверяю, что сервис вызвал нужный метод с нужным аргументом → **mock**.
- Нужна быстрая «почти настоящая» реализация → **fake** (часто для репозиториев).
- Тестирую реальный класс, но один метод опасный/медленный → **spy**.

**Пример Fake:**

```java
class InMemoryUserRepository implements UserRepository {
    private final Map<Long, User> store = new HashMap<>();

    @Override public Optional<User> findById(Long id) {
        return Optional.ofNullable(store.get(id));
    }
    @Override public void save(User user) {
        store.put(user.getId(), user);
    }
}
```

Fake-репозиторий реально работает, но без БД — тест быстрый и детерминированный.

## A.7. Mockito: полный разбор

**Mockito** — самая популярная библиотека для моков в Java.

### Основные аннотации

| Аннотация | Что делает |
|---|---|
| `@Mock` | Создаёт мок-объект. Все методы возвращают дефолты (`null`, `0`, `false`, пустой `Optional`/коллекция) |
| `@Spy` | Оборачивает **реальный** объект. По умолчанию вызываются реальные методы |
| `@InjectMocks` | Создаёт тестируемый объект и внедряет в него моки (`@Mock`/`@Spy`) |
| `@Captor` | Создаёт `ArgumentCaptor` |

**Дефолтные значения моков:**

| Тип возврата | Дефолт |
|---|---|
| объект | `null` |
| `int`/`long` | `0` |
| `boolean` | `false` |
| `Optional` | `Optional.empty()` |
| коллекция/`Stream` | пустая |

### Базовый пример

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    UserRepository repo;               // пустой мок

    @Spy
    EmailService email = new EmailService(); // реальный объект

    @InjectMocks
    UserService service;               // сюда внедряются моки

    @Test
    void findsUserAndSendsEmail() {
        // Arrange
        when(repo.findById(1L)).thenReturn(Optional.of(new User("A")));

        // Act
        User user = service.get(1L);

        // Assert
        assertEquals("A", user.getName());

        // Проверка взаимодействия
        verify(repo).findById(1L);
        verify(repo, times(1)).findById(1L);
        verify(email).send("A");
        verifyNoMoreInteractions(repo);
    }
}
```

### `when(...).thenReturn/thenThrow/thenAnswer`

```java
when(repo.findById(1L)).thenReturn(Optional.of(user));       // вернуть значение
when(repo.save(any())).thenThrow(new RuntimeException("db")); // бросить исключение
when(repo.count()).thenReturn(1L, 2L, 3L);                    // последовательные ответы
when(repo.findById(anyLong())).thenAnswer(inv -> {            // вычисляемый ответ
    Long id = inv.getArgument(0);
    return Optional.of(new User("user-" + id));
});
```

### `doReturn` / `doThrow` — когда `when` не работает

Проблема: `when(spy.method())` **сначала вызывает реальный метод** (чтобы получить объект для мока), а это может быть опасно или бросить исключение.

Для spy и `void`-методов используют `doReturn`/`doThrow`/`doNothing`/`doAnswer`:

```java
doReturn("fixed").when(spy).getName();        // не вызывает реальный getName
doThrow(new IllegalStateException()).when(spy).dangerousMethod();
doNothing().when(spy).voidMethod();           // подавить реальный void-метод
```

> **Запомни правило:** для **void**-методов и **spy** используй `doXxx().when(...)`. Для обычных моков — `when(...).thenXxx(...)`.

### `verify`: times, never, atLeast, atMost

```java
verify(repo).save(user);                       // ровно 1 раз (times(1))
verify(repo, times(2)).findById(anyLong());
verify(repo, never()).delete(any());
verify(repo, atLeastOnce()).findAll();
verify(repo, atLeast(2)).findAll();
verify(repo, atMost(3)).findAll();
verifyNoInteractions(repo);                    // вообще не вызывался
verifyNoMoreInteractions(repo);                // после проверенных вызовов больше ничего
```

**`verifyNoMoreInteractions`** — проверяет, что **не было лишних** вызовов, кроме уже проверенных. Часто признак хорошего теста: тестируемый код не делает «мусорных» вызовов.

### `ArgumentCaptor` — захват аргументов

Когда важно не просто «метод вызван», а **с каким именно аргументом**:

```java
@Captor
ArgumentCaptor<User> userCaptor;

@Test
void savesNormalizedName() {
    service.create("  ivan  ");

    verify(repo).save(userCaptor.capture());
    User saved = userCaptor.getValue();
    assertEquals("Ivan", saved.getName()); // проверяем нормализацию
}
```

Аналог «более простого» способа — `verify(repo).save(eq(expectedUser))`, но он требует точного объекта. `ArgumentCaptor` удобнее, когда объект создаётся внутри и ты хочешь заглянуть в него.

### `ArgumentMatchers`: any, eq, anyLong

```java
verify(repo).save(any(User.class));
verify(repo).findById(eq(1L));
when(repo.findById(anyLong())).thenReturn(Optional.empty());
```

> **Правило:** если используешь хотя бы один matcher (`any`, `eq`), то **все** аргументы должны быть matcher-ами. Нельзя `verify(repo).save(user, anyLong())` — смешение «сырого» значения и matcher бросит `InvalidUseOfMatchersException`.

### MockitoExtension и без него

**С расширением (рекомендуется):**

```java
@ExtendWith(MockitoExtension.class)
class MyTest {
    @Mock Repo repo;
    @InjectMocks Service service;
}
```

Расширение само инициализирует аннотации и **сбрасывает моки перед каждым тестом**.

**Без расширения (вручную):**

```java
class MyTest {
    @Mock Repo repo;
    AutoCloseable mocks;

    @BeforeEach
    void init() {
        mocks = MockitoAnnotations.openMocks(this);
    }

    @AfterEach
    void close() throws Exception {
        mocks.close();
    }
}
```

### Строгость моков (strictness)

По умолчанию `MockitoExtension` работает в режиме **STRICT_STUBS**: лишние стабы (те, что не были использованы) вызывают ошибку. Это ловит «мёртвые» заглушки.

Ослабить можно точечно:

```java
lenient().when(repo.count()).thenReturn(0L); // не будет ругаться, если не вызвано
```

Или на класс:

```java
@MockitoSettings(strictness = Strictness.LENIENT)
class MyTest { ... }
```

Дополнительные настройки мока:

```java
@Mock(answer = Answers.RETURNS_DEEP_STUBS) // repo.find().get().getName() не падает
Repo repo;
```

> **Совет:** не злоупотребляй `RETURNS_DEEP_STUBS` и `lenient()` — обычно это признак плохого дизайна (нарушение закона Деметры).

### `@MockBean` (Spring Boot)

`@MockBean` — аннотация Spring Boot Test. Она **заменяет бин в Spring-контексте** моком (или добавляет, если не было). Контекст пересоздаётся при разных наборах моков — это дорого, поэтому злоупотреблять не стоит.

```java
@SpringBootTest
class OrderServiceIT {
    @MockBean PaymentClient paymentClient; // реальный бин заменён моком
    @Autowired OrderService orderService;

    @Test
    void paysOrder() {
        when(paymentClient.pay(any())).thenReturn(true);
        assertTrue(orderService.process(order));
    }
}
```

**Разница `@Mock` vs `@MockBean`:**

| | `@Mock` | `@MockBean` |
|---|---|---|
| Кто создаёт | Mockito | Spring Test |
| Где живёт | в тестовом классе | в Spring-контексте (заменяет бин) |
| Требует | `MockitoExtension` | `@SpringBootTest`/срез |
| Когда | чистый unit-тест | интеграционный тест со Spring |

**Типичные ошибки (Mockito):**
- Смешение matcher и сырых аргументов.
- `when(spy.voidMethod())` — не компилируется/не работает, нужно `doNothing().when(spy).voidMethod()`.
- Забыли `@ExtendWith(MockitoExtension.class)` — моки остаются `null`.
- Проверяют не то, что нужно: `verify` на внутренние детали, ломающиеся при рефакторинге.
- Стабят методы, которых нет у реального мока, или стабят лишнее (STRICT_STUBS ругается).
- Мокают value-объекты/DTO — обычно не нужно, это не зависимости.

**Часто спрашивают:**
- *Чем `@Mock` отличается от `@Spy`?* — мок полностью подменён, spy вызывает реальные методы (кроме подменённых).
- *Зачем `ArgumentCaptor`?* — захватить аргумент, с которым вызван метод, и проверить его.
- *Что делает `@InjectMocks`?* — создаёт объект и внедряет в него моки через конструктор/setter/поле.
- *`when` vs `doReturn`?* — `when` вызывает метод при настройке (плохо для spy/void), `doReturn` — нет.

## A.8. Пирамида тестирования

```
        /\
       /E2E\          мало, медленные, дорогие, хрупкие
      /------\
     /Integration\    среднее количество
    /------------\
   /   Unit tests  \ много, быстрые, дешёвые, стабильные
  /----------------\
```

| Уровень | Что проверяет | Скорость | Количество | Моки |
|---|---|---|---|---|
| **Unit** | один класс/метод в изоляции | мс | много | да, всё внешнее |
| **Integration** | взаимодействие компонентов (БД, HTTP, Spring) | секунды | средне | частично |
| **E2E/UI** | вся система целиком через UI/API | минуты | мало | нет |

**Почему пирамида, а не «много всего»?**
- Unit-тесты быстрые → запускаешь постоянно, ловишь ошибки рано.
- E2E медленные и хрупкие → их много не сделать, они падают по «внешним» причинам.
- **Антипаттерн «мороженое» (ice-cream cone):** перевёрнутая пирамида — много E2E, мало unit. Приводит к долгим, нестабильным сборкам.

**Тестовая «трофей» (Testing Trophy, Kent C. Dodds):** для фронтенда/приложений акцент на интеграционные тесты, потому что они дают больше уверенности за разумное время. Пирамида и трофей — не догма, а ориентир.

> **Аналогия.** Пирамида — как проверка самолёта: сначала проверяют отдельные детали на стенде (unit), затем узлы в сборе (integration), и лишь потом — полёт целиком (E2E). Проверять каждый полёт слишком дорого.

## A.9. Интеграционные тесты и Testcontainers

**Интеграционный тест** проверяет, что компоненты работают **вместе**: сервис + БД, сервис + очередь, Spring-контекст.

Проблемы «настоящих» интеграционных тестов:
- Нужна реальная БД, настроенная одинаково у всех.
- H2 (in-memory) не всегда ведёт себя как PostgreSQL/MySQL (разный SQL, транзакции).
- Тесты должны быть изолированы и воспроизводимы.

**Testcontainers** — библиотека, которая **поднимает реальную БД (и не только) в Docker-контейнере** прямо во время теста и удаляет после. Это решает проблему «H2 не как прод».

```java
@Testcontainers
@SpringBootTest
class UserRepositoryIT {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", postgres::getJdbcUrl);
        r.add("spring.datasource.username", postgres::getUsername);
        r.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired UserRepository repo;

    @Test
    void savesAndFinds() {
        repo.save(new User("Ivan"));
        assertTrue(repo.findByName("Ivan").isPresent());
    }
}
```

**Плюсы Testcontainers:** реальная СУБД, идентичная прод-версии; автоматическое управление контейнером; одинаково у всех.
**Минусы:** нужен Docker; старт контейнера занимает секунды; чуть сложнее настройка.

**Когда что:**
- Быстрая проверка логики без БД → unit с fake-репозиторием.
- Проверка SQL/маппингов/транзакций → integration с Testcontainers (реальная БД).
- Проверка всего сценария → E2E.

**Типичные ошибки (тестирование):**
- Тесты зависят от порядка (`@BeforeAll` мутирует общее состояние).
- Общая БД между тестами без очистки → «мигающие» тесты.
- `Thread.sleep` вместо ожидания условия.
- Тест проверяет реализацию (private-методы через рефлексию), а не поведение.
- Один гигантский тест на 500 строк — невозможно понять, что упало.

**Часто спрашивают:**
- *Чем unit отличается от integration?* — unit изолирует один компонент (моки), integration проверяет связку реальных компонентов.
- *Почему H2 не всегда подходит?* — другое поведение SQL/типов/транзакций, чем у реальной СУБД.
- *Что такое Testcontainers?* — запуск реальных сервисов в Docker на время теста.

# Часть B. JDBC

## B.0. Что такое JDBC и зачем он нужен

**JDBC (Java Database Connectivity)** — стандартный низкоуровневый API Java для работы с реляционными базами данных.

**Аналогия.** JDBC — это как **розетка стандарта**. Вилка (твой Java-код) одинаковая, а в розетку можно включить любой прибор (PostgreSQL, MySQL, Oracle) через соответствующий драйвер-«переходник». Драйвер — это как переходник для конкретной страны.

Зачем JDBC, если есть Hibernate/JPA? Потому что все ORM и `JdbcTemplate` работают **поверх JDBC**. Понимание JDBC = понимание того, что происходит «под капотом» (и что спросят на собеседовании).

**Архитектура:**
```
Java-приложение
      |
   JDBC API  (java.sql.*)
      |
  JDBC Driver (реализация, напр. org.postgresql.Driver)
      |
   База данных
```

---

## B.1. Шаги подключения к базе данных

1. **Загрузить драйвер.** В современных JDBC (4.0+) драйвер подхватывается автоматически через `ServiceLoader` (файл `META-INF/services/java.sql.Driver`). Явная загрузка `Class.forName("org.postgresql.Driver")` нужна только для очень старых драйверов.
2. **Получить `Connection`.** Напрямую через `DriverManager` (просто, но без пула) или через `DataSource` (рекомендуется, работает с пулами).
3. **Создать `Statement`/`PreparedStatement`.**
4. **Выполнить запрос, обработать `ResultSet`.**
5. **Закрыть ресурсы.** Всегда — через try-with-resources.

**JDBC URL:**
```
jdbc:postgresql://localhost:5432/mydb
jdbc:mysql://localhost:3306/mydb
jdbc:h2:mem:testdb
```
Формат: `jdbc:<подпротокол>://<хост>:<порт>/<база>`.

**Полный пример:**

```java
String url  = "jdbc:postgresql://localhost:5432/mydb";
String user = "app";
String pass = "secret";

String sql = "SELECT id, name FROM users WHERE id = ?";

try (Connection conn = DriverManager.getConnection(url, user, pass);
     PreparedStatement ps = conn.prepareStatement(sql)) {

    ps.setLong(1, id);

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            long userId = rs.getLong("id");
            String name = rs.getString("name");
            System.out.println(userId + " -> " + name);
        }
    }
} catch (SQLException e) {
    throw new RuntimeException("Ошибка запроса", e);
}
```

> **Почему try-with-resources?** `Connection`, `Statement`, `ResultSet` — это ресурсы ОС (сокеты, курсоры). Если не закрыть — утечка соединений и исчерпание пула. try-with-resources закрывает автоматически в обратном порядке, даже при исключении.

**Почему не `DriverManager` в проде?** Он создаёт **новое** физическое соединение на каждый вызов — дорого (TCP + handshake + auth). В проде используют пул.

---

## B.2. `Connection`, `DataSource` и пулы (HikariCP)

**`Connection`** — сессия с БД: через неё создаются statements и управляются транзакции.

**`DataSource`** — интерфейс-фабрика соединений. Ключевое преимущество: может отдавать соединения из **пула**.

**Пул соединений** — заранее открытый набор соединений, которые переиспользуются. Взял → поработал → вернул в пул (а не закрыл физически).

**Аналогия.** Пул соединений — как парковка такси. Держать 10 такси наготове дешевле, чем заказывать новую машину под каждого клиента. Клиент пришёл — взял такси, доехал — вернул на стоянку.

**HikariCP** — самый популярный и быстрый пул (по умолчанию в Spring Boot).

```java
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:postgresql://localhost:5432/mydb");
config.setUsername("app");
config.setPassword("secret");
config.setMaximumPoolSize(10);       // максимум соединений
config.setMinimumIdle(2);            // минимум «горячих»
config.setConnectionTimeout(30_000); // мс ожидания соединения
config.setIdleTimeout(600_000);

DataSource ds = new HikariDataSource(config);

try (Connection conn = ds.getConnection()) {
    // соединение взято из пула; при закрытии вернётся обратно
}
```

**Важные параметры:**

| Параметр | Смысл |
|---|---|
| `maximumPoolSize` | Максимум соединений. Обычно `(число ядер * 2) + число дисков` |
| `minimumIdle` | Сколько соединений держать открытыми в простое |
| `connectionTimeout` | Сколько ждать свободное соединение, иначе исключение |
| `idleTimeout` | Через сколько закрывать простаивающее соединение |
| `maxLifetime` | Максимальное время жизни соединения (меньше лимита БД) |

> **Частая ошибка:** ставить `maximumPoolSize` огромным «чтобы точно хватило». Это вредит: БД тратит ресурсы на лишние соединения, а переключение контекста растёт. Пул должен соответствовать нагрузке.

**Типичные ошибки (пулы):**
- Забыли вернуть соединение (не закрыли) → пул исчерпался, приложение «зависло».
- Держат соединение во время долгой операции без БД → пул блокируется.
- `maxLifetime` больше таймаута БД → БД рвёт соединение, приложение получает ошибку.

## B.3. Statement vs PreparedStatement vs CallableStatement

| Критерий | `Statement` | `PreparedStatement` | `CallableStatement` |
|---|---|---|---|
| SQL | Статический, без параметров | С `?`-параметрами | Вызов процедур/функций |
| Компиляция | Каждый раз заново | **Один раз**, план кэшируется | Один раз |
| SQL-инъекции | **Уязвим** | **Защищён** | Защищён |
| Производительность при повторах | Ниже | **Выше** (предкомпиляция) | — |
| Типобезопасность | Нет | `setInt/setString/...` | `registerOutParameter` |
| Когда использовать | DDL, динамический SQL без параметров | **По умолчанию — почти всегда** | Вызов хранимых процедур |

### Почему `PreparedStatement` безопаснее

`PreparedStatement` отправляет SQL-шаблон и параметры **отдельно**. БД сначала компилирует шаблон, а затем подставляет значения как **данные**, а не как часть SQL-кода. Поэтому строка `' OR '1'='1` останется просто значением, а не оператором.

### Почему быстрее

Шаблон компилируется один раз и кэшируется. При повторных вызовах с разными параметрами БД переиспользует план. Особенно заметно в цикле/батче.

```java
// Плохо: конкатенация — инъекция + повторная компиляция
String sql = "SELECT * FROM users WHERE name = '" + name + "'";

// Хорошо: параметр — безопасно и быстро
String sql = "SELECT * FROM users WHERE name = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);
    try (ResultSet rs = ps.executeQuery()) { ... }
}
```

### `CallableStatement` — вызов процедур

```sql
CREATE PROCEDURE get_user_count(IN min_age INT, OUT cnt INT)
BEGIN
    SELECT COUNT(*) INTO cnt FROM users WHERE age >= min_age;
END;
```

```java
String call = "{ call get_user_count(?, ?) }";
try (CallableStatement cs = conn.prepareCall(call)) {
    cs.setInt(1, 18);
    cs.registerOutParameter(2, Types.INTEGER); // выходной параметр
    cs.execute();
    int count = cs.getInt(2);
}
```

**Часто спрашивают:**
- *Почему `PreparedStatement` защищает от инъекций?* — Параметры передаются отдельно от SQL и не интерпретируются как код.
- *Когда использовать `Statement`?* — Для DDL и запросов без параметров; в остальном — `PreparedStatement`.
- *Что такое предкомпиляция?* — БД один раз строит план для шаблона и переиспользует его.

## B.4. executeQuery vs executeUpdate vs execute

| Метод | Для чего | Что возвращает |
|---|---|---|
| `executeQuery()` | `SELECT` (чтение) | `ResultSet` |
| `executeUpdate()` | `INSERT`/`UPDATE`/`DELETE`/DDL | `int` — число затронутых строк (для DDL — `0`) |
| `execute()` | Любой запрос (общий) | `boolean`: `true`, если результат — `ResultSet` |

**`execute()`** нужен редко — когда тип запроса заранее неизвестен (например, пользователь ввёл произвольный SQL). После него:

```java
boolean hasResultSet = stmt.execute(sql);
if (hasResultSet) {
    try (ResultSet rs = stmt.getResultSet()) { ... }
} else {
    int updated = stmt.getUpdateCount();
}
```

```java
// SELECT
try (ResultSet rs = ps.executeQuery()) { ... }

// INSERT/UPDATE/DELETE
int rows = ps.executeUpdate();
System.out.println("Затронуто строк: " + rows);
```

> **Частая ошибка:** вызвать `executeQuery()` для `UPDATE` или `executeUpdate()` для `SELECT` — получишь `SQLException`.

## B.5. ResultSet и его обработка

**`ResultSet`** — курсор по строкам результата. Изначально стоит **до** первой строки.

- `rs.next()` — перейти к следующей строке; `true`, если строка есть.
- `rs.getXxx("column")` / `rs.getXxx(index)` — получить значение.
- `rs.wasNull()` — проверить, было ли последнее прочитанное значение `NULL`.
- `rs.getObject("col", LocalDate.class)` — современное получение типов.

```java
try (ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        long id = rs.getLong("id");
        String name = rs.getString("name");
        LocalDate born = rs.getObject("birth_date", LocalDate.class);

        int age = rs.getInt("age");
        if (rs.wasNull()) {          // важно для примитивов: NULL -> 0
            System.out.println("Возраст неизвестен");
        }
    }
}
```

**Важные нюансы:**
- Колонки нумеруются **с 1**, не с 0.
- `getInt` на `NULL` вернёт `0`; проверяй `wasNull()`.
- `getObject(col, Class)` предпочтительнее для дат/`BigDecimal`.
- Курсор по умолчанию `TYPE_FORWARD_ONLY` — только вперёд.

**Аналогия.** `ResultSet` — как лента конвейера с ящиками. `next()` двигает ленту к следующему ящику, `getXxx()` достаёт из него конкретную деталь.

## B.6. Batch (пакетная обработка)

**Batch** — отправка нескольких запросов одним «пакетом» вместо N отдельных походов в БД. Огромный выигрыш по сети.

**Аналогия.** Вместо того чтобы бегать в магазин за каждым продуктом отдельно, ты составляешь список и идёшь один раз.

```java
String sql = "INSERT INTO users(name, age) VALUES (?, ?)";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    conn.setAutoCommit(false);

    for (User u : users) {
        ps.setString(1, u.getName());
        ps.setInt(2, u.getAge());
        ps.addBatch();               // накапливаем
    }

    int[] results = ps.executeBatch(); // выполняем пакетом
    conn.commit();
}
```

**Правила и нюансы:**
- Batch эффективнее с `PreparedStatement` (шаблон компилируется один раз).
- Работает для `INSERT/UPDATE/DELETE`, **не** для `SELECT`.
- `executeBatch()` возвращает массив чисел затронутых строк.
- Обязательно в транзакции: если упадёт посередине — `rollback`.
- Слишком большой batch (сотни тысяч) может съесть память — делай порциями.

---

## B.7. Метаданные

**`DatabaseMetaData`** — информация о БД (версия, поддержка возможностей).

```java
DatabaseMetaData md = conn.getMetaData();
System.out.println(md.getDatabaseProductName());
System.out.println(md.getDatabaseProductVersion());
System.out.println(md.supportsBatchUpdates());
```

**`ResultSetMetaData`** — информация о колонках результата: имена, типы, количество.

```java
try (ResultSet rs = ps.executeQuery()) {
    ResultSetMetaData meta = rs.getMetaData();
    int columns = meta.getColumnCount();
    for (int i = 1; i <= columns; i++) {
        System.out.println(meta.getColumnName(i) + " : " + meta.getColumnTypeName(i));
    }
}
```

**Зачем нужно?** Для универсальных утилит (маппинг строк в объекты без знания схемы), генерации отчётов, ORM — Hibernate внутри использует метаданные, чтобы сопоставить колонки и поля.

## B.8. Транзакции и ACID

**Транзакция** — логическая единица работы, которая выполняется по принципу «всё или ничего».

**Аналогия.** Перевод денег другу: списать у тебя и зачислить ему — это **одна** транзакция. Если списание прошло, а зачисление нет — деньги исчезли. Транзакция гарантирует, что либо оба действия, либо ни одного.

**ACID** — четыре свойства надёжной транзакции:

| Свойство | Что означает | Аналогия |
|---|---|---|
| **A — Atomicity** (атомарность) | Всё или ничего | Нельзя перевести «половину» денег |
| **C — Consistency** (согласованность) | Переход из одного валидного состояния в другое; ограничения соблюдены | Сумма балансов до и после одинакова |
| **I — Isolation** (изолированность) | Параллельные транзакции не видят «полуготовых» данных друг друга | Два кассира не перепутают деньги |
| **D — Durability** (долговечность) | После commit данные сохранятся даже при сбое | Чек распечатан — деньги списаны навсегда |

> **Как СУБД обеспечивает ACID:** журнал (WAL — write-ahead log) для durability, блокировки/MVCC для isolation, механизм commit/rollback для atomicity.

## B.9. Управление транзакцией: setAutoCommit / commit / rollback / savepoint

По умолчанию JDBC работает в режиме **autocommit = true**: каждый запрос сразу фиксируется. Для группы операций автокоммит выключают.

**Классический паттерн:**

```java
Connection conn = dataSource.getConnection();
try {
    conn.setAutoCommit(false);           // начало транзакции
    try {
        // ... несколько операций ...
        conn.commit();                   // фиксируем
    } catch (SQLException e) {
        conn.rollback();                 // откатываем всё
        throw e;
    } finally {
        conn.setAutoCommit(true);        // возвращаем режим
    }
} finally {
    conn.close();                        // вернуть соединение в пул
}
```

**Ключевые методы:**

| Метод | Назначение |
|---|---|
| `setAutoCommit(false)` | Выключить автокоммит — начать управлять транзакцией вручную |
| `commit()` | Зафиксировать изменения |
| `rollback()` | Откатить всю текущую транзакцию |
| `setSavepoint("name")` | Создать промежуточную точку |
| `rollback(savepoint)` | Откатить только до savepoint |
| `releaseSavepoint(sp)` | Удалить savepoint |
| `setTransactionIsolation(level)` | Установить уровень изоляции |

**Savepoint** — промежуточная «точка сохранения»:

```java
conn.setAutoCommit(false);
Savepoint sp = conn.setSavepoint("afterStep1");

try {
    step2(); // может упасть
} catch (SQLException e) {
    conn.rollback(sp); // откатили только step2, step1 сохранён
}
conn.commit(); // фиксируем step1 + успешный step3
```

**Аналогия savepoint.** Ты играешь в игру и сохраняешься перед сложным боссом. Если проиграл — возвращаешься к сохранению, а не начинаешь игру заново.

**Типичные ошибки (транзакции):**
- Забыли `commit()` — изменения не сохранились (а соединение вернулось в пул).
- `rollback` без `setAutoCommit(false)` — ничего не откатится.
- Долгая транзакция с сетевыми вызовами внутри → блокировки держатся долго.
- Не вернули `autoCommit = true` перед возвратом соединения в пул.
- `try/catch`, который «съедает» исключение и всё равно делает `commit`.

**Часто спрашивают:**
- *Что такое транзакция?* — Набор операций как единое целое: либо все, либо ни одна.
- *Что произойдёт без commit?* — Изменения будут потеряны при закрытии/откате.
- *Зачем savepoint?* — Частичный откат внутри транзакции.
- *Что такое ACID?* — Atomicity, Consistency, Isolation, Durability.

## B.10. Аномалии чтения и уровни изоляции

При параллельном доступе возможны аномалии:

| Аномалия | Суть | Аналогия |
|---|---|---|
| **Dirty read** (грязное чтение) | Читаем данные, которые другая транзакция ещё **не закоммитила** (и может откатить) | Ты прочитал черновик письма, а автор его порвал |
| **Non-repeatable read** (неповторяющееся чтение) | Читаем строку дважды — значение изменилось, потому что кто-то обновил и закоммитил | Перечитал цену — она стала другой |
| **Phantom read** (фантомное чтение) | Повторный запрос возвращает **новые строки**, появившиеся от другой транзакции | Пересчитал товары — появились новые |

**Уровни изоляции** (от слабого к строгому):

| Уровень | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| **READ UNCOMMITTED** | Возможен | Возможен | Возможен |
| **READ COMMITTED** | Нет | Возможен | Возможен |
| **REPEATABLE READ** | Нет | Нет | Возможен* |
| **SERIALIZABLE** | Нет | Нет | Нет |

\* В **MySQL/InnoDB** уровень `REPEATABLE READ` предотвращает и phantom read благодаря MVCC + gap locks. Это важный нюанс.

**Чем выше уровень — тем меньше аномалий, но больше блокировок и ниже параллелизм.**

```java
conn.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
```

**Дефолтные уровни:**

| СУБД | Уровень по умолчанию |
|---|---|
| **PostgreSQL** | `READ COMMITTED` |
| **MySQL (InnoDB)** | `REPEATABLE READ` |
| Oracle | `READ COMMITTED` |
| SQL Server | `READ COMMITTED` |

> **Почему PostgreSQL по умолчанию READ COMMITTED?** Это хороший баланс: нет грязных чтений, но высокая параллельность. `SERIALIZABLE` в PostgreSQL реализован через SSI (Serializable Snapshot Isolation) и может давать ошибки сериализации, требующие повтора.

**MVCC (Multi-Version Concurrency Control)** — многоверсионность. СУБД хранит несколько версий строки, поэтому:
- **Чтение не блокирует запись**, а запись не блокирует чтение.
- Транзакция видит согласованный «снимок» данных на момент старта (в зависимости от уровня).
- Старые версии удаляются сборщиком мусора (`VACUUM` в PostgreSQL).

**Аналогия MVCC.** Вместо того чтобы запрещать читать документ, пока кто-то его редактирует, система даёт читателю копию-снимок. Все довольны, никто не ждёт.

**Часто спрашивают:**
- *Чем dirty read отличается от non-repeatable read?* — Dirty — чтение незакоммиченного; non-repeatable — данные изменились между двумя чтениями уже закоммиченной транзакцией.
- *Что такое phantom read?* — Появление новых строк при повторном запросе диапазона.
- *Какой уровень изоляции по умолчанию в PostgreSQL/MySQL?* — READ COMMITTED / REPEATABLE READ.
- *Что такое MVCC?* — Многоверсионность: чтение не блокирует запись.

## B.11. SQL-инъекции и способы защиты

**SQL-инъекция** — атака, при которой пользовательский ввод попадает в SQL-код как **исполняемая часть**, а не как данные.

**Уязвимый код:**

```java
String input = request.getParameter("name");
String sql = "SELECT * FROM users WHERE name = '" + input + "'";
// input = "' OR '1'='1"  ->
// SELECT * FROM users WHERE name = '' OR '1'='1'  -> вернёт ВСЕХ пользователей
```

Ещё опаснее, если ввод попадает в `UPDATE`/`DELETE`:
```java
// input = "'; DROP TABLE users; --"
// SELECT * FROM users WHERE name = ''; DROP TABLE users; --'
```

**Способы защиты (по приоритету):**

| Способ | Суть |
|---|---|
| **1. PreparedStatement с `?`** | Главный способ. Параметры передаются отдельно от SQL |
| **2. Хранимые процедуры с параметрами** | Логика в БД, ввод передаётся как параметр |
| **3. Валидация / whitelist** | Разрешаем только ожидаемые значения/формат |
| **4. Наименьшие привилегии** | У пользователя БД нет прав на DROP/лишние таблицы |
| **5. Экранирование** | Крайняя мера; легко ошибиться, используй только как дополнение |

**Безопасный вариант:**

```java
String sql = "SELECT * FROM users WHERE name = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, input); // input = "' OR '1'='1" — просто строка, не код
    try (ResultSet rs = ps.executeQuery()) { ... }
}
```

**Почему параметры защищают?** БД получает **шаблон** и **значения отдельно**. Значение не может изменить структуру запроса.

> **Важно:** `PreparedStatement` не спасает, если ты подставляешь пользовательский ввод в **имена таблиц/колонок** или в `ORDER BY` через конкатенацию (параметры `?` там не работают). Такие случаи закрывают **whitelist**-проверкой.

**Типичные ошибки (инъекции):**
- Думать, что `PreparedStatement` решает всё: он не покрывает динамические имена таблиц/колонок и `ORDER BY`.
- Валидировать ввод на клиенте — обходится.
- Прятать ошибки БД от пользователя, но писать их в лог с вводом — утечка.
- Использовать конкатенацию «только для чисел», а потом передать строку.

**Часто спрашивают:**
- *Что такое SQL-инъекция?* — Внедрение SQL-кода через пользовательский ввод.
- *Как защититься?* — PreparedStatement с параметрами, валидация, наименьшие привилегии.
- *Почему параметры безопасны?* — Они передаются как данные и не могут изменить структуру запроса.

# Часть C. SQL и проектирование баз данных

## C.1. Нормализация: 1NF, 2NF, 3NF, BCNF и денормализация

**Нормализация** — процесс разбиения таблиц так, чтобы убрать дублирование и аномалии обновления/вставки/удаления.

**Зачем?** Если одни и те же данные хранятся в нескольких местах, при обновлении легко забыть одно из них → рассогласованность.

**Аномалии без нормализации:**
- **Аномалия вставки:** нельзя добавить данные, не добавив лишние.
- **Аномалия обновления:** обновил в одном месте — в другом осталось старое.
- **Аномалия удаления:** удалил запись — потерял нужную информацию.

### 1NF — первая нормальная форма

**Правила:** все значения **атомарны** (неделимы), нет повторяющихся групп/списков в ячейке, есть первичный ключ, строки уникальны.

**Плохо** (список телефонов в одной ячейке):

| id | name | phones |
|---|---|---|
| 1 | Ivan | +7-111, +7-222 |

**Хорошо** (вынести в отдельную таблицу):

| id | name |
|---|---|
| 1 | Ivan |

| user_id | phone |
|---|---|
| 1 | +7-111 |
| 1 | +7-222 |

### 2NF — вторая нормальная форма

**Правило:** 1NF + **нет частичной зависимости** неключевого атрибута от **части составного** ключа.

**Плохо** (ключ `(order_id, product_id)`, а `product_name` зависит только от `product_id` — части ключа):

| order_id | product_id | product_name | quantity |
|---|---|---|---|
| 1 | 10 | Milk | 2 |

**Хорошо** — вынести название товара в таблицу `products`.

### 3NF — третья нормальная форма

**Правило:** 2NF + **нет транзитивных зависимостей** (неключевой атрибут не зависит от другого неключевого).

**Плохо** (`zip` зависит от `city`, а `city` — от `id`):

| id | name | city | zip |
|---|---|---|---|
| 1 | Ivan | Moscow | 101000 |

`zip` транзитивно зависит от `id` через `city`.

**Хорошо** — вынести `city → zip` в отдельную таблицу.

### BCNF — нормальная форма Бойса-Кодда

**Правило:** усиленная 3NF: для **каждой** функциональной зависимости `X → Y` детерминант `X` должен быть **суперключом**.

Нарушение BCNF возможно, когда в таблице несколько перекрывающихся составных ключей.

**Пример:** таблица бронирования аудиторий с ключом `(student, subject)` и зависимостями:
- `(student, subject) → room`
- `room → subject` (каждая аудитория — под один предмет)

Здесь `room → subject`, но `room` — не суперключ → нарушение BCNF. Разбивают на две таблицы.

**Кратко:**

| НФ | Условие |
|---|---|
| 1NF | Атомарные значения, нет повторяющихся групп |
| 2NF | 1NF + нет частичной зависимости от составного ключа |
| 3NF | 2NF + нет транзитивных зависимостей |
| BCNF | 3NF + каждый детерминант — суперключ |

### Денормализация

**Денормализация** — намеренное нарушение нормальных форм ради **производительности чтения**: меньше JOIN-ов, быстрее запросы.

**Когда применяют:**
- Частые сложные отчёты/аналитика.
- Чтение преобладает над записью (read-heavy).
- JOIN-ы слишком дороги.

**Цена:** дублирование, риск рассогласованности, усложнение записи (нужно обновлять несколько мест).

> **Аналогия.** Нормализация — как аккуратно разложить инструменты по отдельным ящикам. Денормализация — как положить самые нужные инструменты в один ящик под рукой: быстрее достать, но при поломке сложнее синхронизировать наборы.

**Часто спрашивают:**
- *Зачем нормализация?* — Убрать дублирование и аномалии обновления/вставки/удаления.
- *Что нарушает 3NF?* — Транзитивная зависимость неключевого атрибута.
- *Когда денормализовать?* — Когда чтение критично и JOIN-ы дороги, осознанно принимая дублирование.

## C.2. Типы связей: 1:1, 1:N, M:N

| Связь | Как реализовать | Пример |
|---|---|---|
| **1:1** | FK с `UNIQUE` в одной из таблиц, либо общий PK | `user` ↔ `user_profile` |
| **1:N** | FK на стороне «многих» | `user` → `orders` (`orders.user_id`) |
| **M:N** | Промежуточная (junction) таблица с двумя FK | `students` ↔ `courses` через `enrollments` |

**1:1** — FK с ограничением уникальности, чтобы у пользователя был максимум один профиль:

```sql
CREATE TABLE user_profile (
    id        BIGINT PRIMARY KEY,
    user_id   BIGINT UNIQUE NOT NULL REFERENCES users(id),
    bio       TEXT
);
```

**1:N** — FK у «многих»:

```sql
CREATE TABLE orders (
    id      BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    total   NUMERIC(12,2)
);
```

**M:N** — junction-таблица:

```sql
CREATE TABLE students (
    id   BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE courses (
    id    BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL
);

CREATE TABLE enrollments (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id  BIGINT NOT NULL REFERENCES courses(id),
    grade      INT,
    PRIMARY KEY (student_id, course_id) -- составной PK запрещает дубли
);
```

> **Почему junction-таблица, а не два FK в одной из основных таблиц?** Потому что студент может быть на многих курсах, а курс — у многих студентов. Одним FK это не выразить. Промежуточная таблица моделирует сами «связи» и может хранить их атрибуты (оценку, дату зачисления).

**Часто спрашивают:**
- *Как реализовать M:N?* — Через junction-таблицу с двумя FK и составным PK.
- *Где хранить FK при 1:N?* — На стороне «многих».

## C.3. Ключи: PK, UNIQUE, FK и surrogate/natural

| Ключ | Назначение | NULL | Индекс |
|---|---|---|---|
| **Primary Key (PK)** | Уникально идентифицирует строку | Нет (`NOT NULL`) | Да, уникальный |
| **Unique key** | Гарантирует уникальность | Допускает (в большинстве СУБД) | Да, уникальный |
| **Foreign Key (FK)** | Ссылка на PK/unique другой таблицы | Может (если не `NOT NULL`) | Нет автоматически* |

\* В PostgreSQL/MySQL индекс по FK **не создаётся автоматически** — часто создают вручную для производительности JOIN-ов и проверок целостности.

**PK:**
- Один на таблицу (может быть **составным** — из нескольких колонок).
- Создаёт уникальный индекс.
- Не может быть `NULL`.

**Unique:**
- Может быть несколько на таблицу.
- Обычно допускает `NULL` (в PostgreSQL — сколько угодно `NULL`, так как `NULL != NULL`).
- Используется, например, для email/логина.

**Foreign Key:**
- Обеспечивает **ссылочную целостность**: нельзя вставить `orders.user_id`, которого нет в `users`.
- Поведение при удалении/обновлении родителя задаётся `ON DELETE`/`ON UPDATE`:

| Опция | Что делает |
|---|---|
| `CASCADE` | Удалить/обновить и дочерние строки |
| `SET NULL` | Установить FK в `NULL` |
| `SET DEFAULT` | Установить значение по умолчанию |
| `RESTRICT` / `NO ACTION` | Запретить, если есть ссылки (обычно по умолчанию) |

```sql
CREATE TABLE orders (
    id      BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL
        REFERENCES users(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

**Surrogate vs Natural key:**

| | Surrogate (суррогатный) | Natural (естественный) |
|---|---|---|
| Что это | Искусственный id (`BIGSERIAL`, UUID) | Реальное бизнес-поле (email, ИНН, паспорт) |
| Плюсы | Стабильный, компактный, не меняется | Имеет смысл, не нужен лишний id |
| Минусы | Нет бизнес-смысла | Может измениться, длиннее, иногда не уникален |

**Практика:** почти всегда используют **суррогатный PK** (id) + `UNIQUE` на естественный ключ (email). Это даёт стабильные ссылки и защиту от дублей.

**Аналогия.** Суррогатный ключ — как номер заказа в ресторане: короткий, уникальный, не меняется. Естественный ключ — как описание блюда: осмысленно, но может измениться (переименовали блюдо).

**Часто спрашивают:**
- *PK vs unique?* — PK один, `NOT NULL`, идентифицирует строку; unique может быть много и допускает `NULL`.
- *Что делает ON DELETE CASCADE?* — Удаляет дочерние строки вместе с родительской.
- *Surrogate vs natural key?* — Искусственный стабильный id vs бизнес-поле.

## C.4. Индексы

**Индекс** — структура данных (обычно B-tree), ускоряющая поиск, сортировку и JOIN. Это как алфавитный указатель в книге: не листаешь всё, а сразу находишь страницу.

**Зачем:** без индекса СУБД делает **Seq Scan** — читает всю таблицу. С индексом — **Index Scan** — сразу идёт к нужным строкам.

**Цена индексов:**
- Замедляют `INSERT`/`UPDATE`/`DELETE` (индекс нужно обновлять).
- Занимают место на диске.
- Требуют обслуживания (в PostgreSQL — `VACUUM`, `REINDEX`).

**Виды индексов:**

| Тип | Когда использовать |
|---|---|
| **B-tree** | По умолчанию; `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префикс `LIKE 'abc%'` |
| **Hash** | Только равенство `=` (редко) |
| **GIN** | Массивы, JSONB, полнотекстовый поиск (PostgreSQL) |
| **GiST** | Геоданные, диапазоны, полнотекст (PostgreSQL) |
| **BRIN** | Огромные таблицы с естественной сортировкой (время) |
| **Full-text** | Поиск по тексту |

**Составной индекс** — по нескольким колонкам. **Порядок колонок критичен** (префиксное правило): индекс `(last_name, first_name)` помогает запросам по `last_name` и по `(last_name, first_name)`, но **не** по одному `first_name`.

```sql
CREATE INDEX idx_users_name ON users(last_name, first_name);
-- использует: WHERE last_name = 'Ivan'  и  WHERE last_name='Ivan' AND first_name='P'
-- НЕ использует: WHERE first_name = 'P'
```

**Уникальный индекс** — гарантирует уникальность (лежит в основе `UNIQUE`/PK).

**Покрывающий индекс (covering index)** — содержит **все** колонки, нужные запросу, включая `SELECT`. Тогда СУБД отвечает из индекса без обращения к таблице (**index-only scan**).

```sql
CREATE INDEX idx_cover ON users(city) INCLUDE (name, age);
-- SELECT name, age FROM users WHERE city = 'Moscow'; -- index-only scan
```

**Когда индекс НЕ работает / бесполезен:**
- **Низкая селективность** (мало уникальных значений, например `boolean` пол): сканировать таблицу дешевле.
- **Функция над колонкой:** `WHERE LOWER(email) = ...` — обычный индекс не применяется (нужен функциональный индекс).
- **`LIKE '%...'`** с ведущим `%` — индекс по B-tree не помогает.
- **Неявное приведение типов:** `WHERE id = '1'` (строка vs число) может отключить индекс.
- **Маленькая таблица** — Seq Scan может быть быстрее.
- **`OR`** по разным колонкам без индексов на обе.
- **`NOT`, `!=`** часто не используют индекс.

**Когда создавать индекс:** колонки в `WHERE`, `JOIN ... ON`, `ORDER BY`, `GROUP BY`; FK (вручную); часто используемые высокоселективные колонки.

> **Аналогия.** Индекс — как оглавление. Если книга на 10 страниц — листать быстрее, чем искать в оглавлении. Если книга на 1000 — оглавление спасает. И если оглавление содержит всё содержание (покрывающий индекс) — саму книгу открывать не надо.

**Часто спрашивают:**
- *Плюсы и минусы индексов?* — Ускоряют чтение, замедляют запись и занимают место.
- *Что такое составной индекс и почему важен порядок?* — Индекс по нескольким колонкам; работает по префиксу слева направо.
- *Почему `LIKE '%x'` не использует индекс?* — Неизвестно начало строки, B-tree не может искать по префиксу.
- *Что такое покрывающий индекс?* — Содержит все нужные запросу колонки, позволяет index-only scan.

## C.5. JOIN: соединение таблиц

**JOIN** соединяет строки из двух таблиц по условию.

| Тип | Результат |
|---|---|
| **INNER JOIN** | Только совпадающие строки в обеих таблицах |
| **LEFT (OUTER) JOIN** | Все строки левой + совпадения справа (`NULL`, если нет) |
| **RIGHT JOIN** | Зеркало LEFT |
| **FULL OUTER JOIN** | Все строки обеих таблиц |
| **CROSS JOIN** | Декартово произведение (каждая с каждой) |
| **SELF JOIN** | Таблица соединяется с собой |

**Данные для примеров:**

`users`:

| id | name |
|---|---|
| 1 | Ivan |
| 2 | Anna |
| 3 | Oleg |

`orders`:

| id | user_id | total |
|---|---|---|
| 100 | 1 | 500 |
| 101 | 1 | 300 |
| 102 | 2 | 700 |

**INNER JOIN** — только пользователи с заказами:

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;
-- Ivan 500, Ivan 300, Anna 700 (Oleg отсутствует)
```

**LEFT JOIN** — все пользователи, даже без заказов:

```sql
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
-- Ivan 500, Ivan 300, Anna 700, Oleg NULL
```

**RIGHT JOIN** — все заказы и их пользователи (здесь эквивалент INNER, если FK валиден):

```sql
SELECT u.name, o.total
FROM users u
RIGHT JOIN orders o ON o.user_id = u.id;
```

**FULL OUTER JOIN** — все пользователи и все заказы:

```sql
SELECT u.name, o.total
FROM users u
FULL OUTER JOIN orders o ON o.user_id = u.id;
```

**CROSS JOIN** — все комбинации (осторожно: `N × M` строк):

```sql
SELECT u.name, c.title
FROM users u
CROSS JOIN courses c;
```

**SELF JOIN** — например, найти сотрудников и их менеджеров в одной таблице:

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**Поиск «сирот»** — пользователей без заказов:

```sql
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

**Частая ошибка:** `WHERE o.total > 100` в `LEFT JOIN` **превращает** его в `INNER JOIN` (отсекает строки с `NULL`). Условие по правой таблице нужно ставить в `ON`, если хочешь сохранить несовпадающие строки:

```sql
LEFT JOIN orders o ON o.user_id = u.id AND o.total > 100
```

**Часто спрашивают:**
- *Разница INNER и LEFT JOIN?* — INNER только совпадения, LEFT сохраняет все строки левой таблицы.
- *Как найти записи без связей?* — `LEFT JOIN ... WHERE правая.id IS NULL`.
- *Что такое CROSS JOIN?* — Декартово произведение.

## C.6. WHERE vs HAVING и GROUP BY

**Порядок выполнения логики запроса** (упрощённо):

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

- **`WHERE`** фильтрует **строки до** группировки. Агрегаты в `WHERE` **нельзя**.
- **`GROUP BY`** группирует строки по значениям колонок.
- **`HAVING`** фильтрует **группы после** группировки. Агрегаты в `HAVING` **можно**.

```sql
SELECT city, COUNT(*) AS cnt
FROM users
WHERE age > 18            -- фильтр строк ДО группировки
GROUP BY city
HAVING COUNT(*) > 10      -- фильтр групп ПОСЛЕ
ORDER BY cnt DESC;
```

**Почему нельзя агрегаты в WHERE?** На момент `WHERE` группы ещё не сформированы — считать нечего. `HAVING` работает уже с готовыми группами.

**Аналогия.** `WHERE` — фейс-контроль перед входом в клуб (проверяем каждого гостя). `GROUP BY` — рассаживаем по столам. `HAVING` — проверяем, что за столом набралось достаточно людей, и только такие столы оставляем.

**Правило:** всё, что можно отфильтровать в `WHERE`, фильтруй в `WHERE` — это раньше уменьшает данные и быстрее.

**Типичные ошибки:**
- Агрегат в `WHERE` → ошибка.
- `SELECT` колонки, которой нет в `GROUP BY` и не под агрегатом (в строгом SQL — ошибка; в MySQL зависит от `ONLY_FULL_GROUP_BY`).
- `HAVING` вместо `WHERE` для обычных условий — работает, но медленнее.

## C.7. View vs Materialized View

**View (представление)** — именованный сохранённый запрос. Выглядит как таблица, но **данные не хранит** — выполняет запрос при каждом обращении.

```sql
CREATE VIEW active_users AS
SELECT id, name, email
FROM users
WHERE active = true;

SELECT * FROM active_users WHERE name LIKE 'I%';
```

**Плюсы View:**
- Инкапсуляция сложной логики (JOIN-ы в одном месте).
- Безопасность: можно дать доступ к view, скрыв чувствительные колонки/таблицы.
- Упрощение запросов для приложений.
- Абстракция: изменил схему — поправил view, приложение не тронул.

**Materialized View** — **физически хранит** результат запроса на диске.

```sql
CREATE MATERIALIZED VIEW sales_summary AS
SELECT city, SUM(total) AS revenue
FROM orders
GROUP BY city;

REFRESH MATERIALIZED VIEW sales_summary; -- обновить вручную
```

| | View | Materialized View |
|---|---|---|
| Хранит данные | Нет | Да |
| Актуальность | Всегда свежие | На момент `REFRESH` |
| Скорость чтения | Зависит от запроса | Очень быстрая |
| Обновление | Автоматически | Вручную/по расписанию |
| Место | Не занимает | Занимает |
| Индексы | Нельзя | Можно |

> **Аналогия.** View — как «живой» перевод валют по текущему курсу: всегда актуален, но считается каждый раз. Materialized View — как распечатанная сводка: читается мгновенно, но данные на момент печати.

**Когда что:** часто меняющиеся данные и нужна актуальность → View. Тяжёлая аналитика, допустима задержка → Materialized View.

## C.8. Агрегатные функции

| Функция | Что делает |
|---|---|
| `COUNT(*)` | Считает **все** строки (включая `NULL`) |
| `COUNT(col)` | Считает строки, где `col` **не NULL** |
| `COUNT(DISTINCT col)` | Число уникальных не-NULL значений |
| `SUM(col)` | Сумма |
| `AVG(col)` | Среднее (игнорирует `NULL`) |
| `MIN(col)` / `MAX(col)` | Минимум/максимум |
| `STRING_AGG` / `GROUP_CONCAT` | Склейка строк |
| `ARRAY_AGG` | Массив значений (PostgreSQL) |

```sql
SELECT department, AVG(salary) AS avg_salary
FROM employees
GROUP BY department;
```

**`COUNT(*)` vs `COUNT(col)`:**

| Запрос | Что считает |
|---|---|
| `COUNT(*)` | Все строки |
| `COUNT(email)` | Только строки, где `email IS NOT NULL` |
| `COUNT(DISTINCT email)` | Уникальные непустые email |

```sql
SELECT
    COUNT(*)                     AS total,
    COUNT(email)                 AS with_email,
    COUNT(DISTINCT email)        AS unique_email
FROM users;
```

> **Важно:** `SUM`/`AVG`/`MIN`/`MAX` **игнорируют `NULL`**, а `COUNT(*)` — нет. Отсюда классическая разница результатов.

**Агрегат без `GROUP BY`** сворачивает всю таблицу в одну строку:

```sql
SELECT COUNT(*), AVG(salary) FROM employees;
```

**Часто спрашивают:**
- *Чем COUNT(*) отличается от COUNT(col)?* — Первый считает все строки, второй только не-NULL значения.
- *Как агрегаты обрабатывают NULL?* — Игнорируют (кроме `COUNT(*)`).

## C.9. Query Execution Plan (план выполнения запроса)

**План выполнения** — то, как СУБД собирается выполнить запрос: в каком порядке соединять таблицы, какие индексы использовать, сколько строк ожидает. Это главный инструмент оптимизации.

**Как получить:**

| СУБД | Команда |
|---|---|
| PostgreSQL | `EXPLAIN <query>`, `EXPLAIN ANALYZE <query>` |
| MySQL | `EXPLAIN <query>`, `EXPLAIN FORMAT=JSON` |
| SQL Server | `SET SHOWPLAN_TEXT ON` / Actual Execution Plan |
| Oracle | `EXPLAIN PLAN FOR ...`, `DBMS_XPLAN.DISPLAY` |

**`EXPLAIN` vs `EXPLAIN ANALYZE`:**

| | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| Выполняет запрос | Нет | **Да** |
| Показывает план | Да | Да |
| Показывает реальное время/строки | Нет | Да |
| Оценки стоимости | Да | Да |

```sql
EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id)
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.city = 'Moscow'
GROUP BY u.name;
```

**Ключевые операторы:**

| Оператор | Что значит | Хорошо/плохо |
|---|---|---|
| **Seq Scan** | Полное сканирование таблицы | Плохо на больших таблицах, нормально на маленьких |
| **Index Scan** | Поиск по индексу + обращение к таблице | Хорошо при высокой селективности |
| **Index Only Scan** | Ответ только из индекса | Отлично (покрывающий индекс) |
| **Nested Loop** | Для каждой строки одной таблицы ищет в другой | Хорошо при малых объёмах/индексе |
| **Hash Join** | Строит хэш-таблицу и соединяет | Хорошо для больших объёмов без индекса |
| **Merge Join** | Сортирует обе таблицы и сливает | Хорошо, если данные уже отсортированы |
| **Sort** | Сортировка | Дорого на больших объёмах |
| **Aggregate** | Группировка/агрегация | Нормально |
| **Bitmap Heap Scan** | Битовая карта по индексу | Хорошо для средних выборок |

**Как читать план (упрощённо):**
1. Читаем **снизу вверх** и **изнутри наружу** — вложенные узлы выполняются первыми.
2. Ищем **`Seq Scan`** на больших таблицах — кандидат на индекс.
3. Сравниваем **оценку** (`rows=...`) с **реальным** числом строк в `ANALYZE` — большое расхождение значит устаревшую статистику (`ANALYZE`/`VACUUM`).
4. Смотрим самые «дорогие» узлы по времени.
5. Ищем лишние `Sort`, повторные сканирования, `Nested Loop` с большим числом итераций.

**Пример плана (PostgreSQL):**

```
HashAggregate  (cost=25.10..25.20 rows=10 width=40) (actual time=0.150..0.155 rows=3 loops=1)
  ->  Hash Join  (cost=12.30..24.80 rows=60 width=36) (actual time=0.050..0.120 rows=50 loops=1)
        Hash Cond: (o.user_id = u.id)
        ->  Seq Scan on orders o  (cost=0.00..10.00 rows=100 width=12)
        ->  Hash  (cost=11.00..11.00 rows=5 width=28)
              ->  Index Scan using idx_users_city on users u (cost=0.00..11.00 rows=5 width=28)
                    Index Cond: (city = 'Moscow'::text)
```

Читаем: сначала `Index Scan` по индексу города (5 пользователей), затем `Hash` и `Hash Join` с `orders`, затем `HashAggregate` для `GROUP BY`. `orders` сканируется целиком (`Seq Scan`) — при росте таблицы стоит подумать об индексе по `user_id`.

**Что оптимизировать:**
- Добавить индекс по колонкам в `WHERE`/`JOIN`.
- Переписать запрос (убрать функции над колонками в `WHERE`, уменьшить `SELECT *`).
- Обновить статистику (`ANALYZE`).
- Избежать лишних `Sort` (индекс под `ORDER BY`).
- Разбить сложный запрос или использовать materialized view.

**Типичные ошибки (планы):**
- Смотреть только `cost`, не проверяя реальные строки.
- Забыть `ANALYZE` (без него `EXPLAIN` даёт только оценки, без времени).
- Делать вывод по плану на пустой таблице.
- Игнорировать расхождение оценок кардинальности — часто это причина плохого плана.

**Часто спрашивают:**
- *Чем EXPLAIN отличается от EXPLAIN ANALYZE?* — ANALYZE реально выполняет запрос и показывает фактические метрики.
- *Что такое Seq Scan?* — Полное сканирование таблицы; плохо на больших таблицах.
- *Что такое Nested Loop / Hash Join?* — Способы соединения таблиц; Nested Loop хорош для малых объёмов, Hash Join — для больших.
- *Как понять, что индекс не используется?* — В плане стоит `Seq Scan` вместо `Index Scan`.

# Шпаргалка

## Тестирование

- **JUnit 5 = Platform + Jupiter + Vintage.** Jupiter — API (`org.junit.jupiter.api.*`).
- **FIRST:** Fast, Independent, Repeatable, Self-validating, Timely.
- **AAA:** Arrange → Act → Assert.
- **`@BeforeEach`/`@AfterEach`** — вокруг каждого теста; **`@BeforeAll`/`@AfterAll`** — один раз (обычно `static`).
- **Assertions:** `assertEquals` (equals), `assertSame` (==), `assertThrows`, `assertAll`.
- **Stub отвечает, mock проверяет.** Fake — рабочая упрощённая реализация. Spy — реальный объект с подменой.
- **Mockito:** `@Mock`, `@Spy`, `@InjectMocks`; `when/thenReturn/thenThrow`; `doReturn/doThrow` для spy/void; `verify(times/never)`; `ArgumentCaptor`; `@ExtendWith(MockitoExtension.class)`; `@MockBean` — Spring-бин.
- **Пирамида:** много unit, средне integration, мало E2E. Testcontainers — реальная БД в Docker.

## JDBC

- Шаги: драйвер (авто) → `Connection` (лучше пул/`DataSource`) → `Statement` → `ResultSet` → закрыть (try-with-resources).
- **HikariCP** — популярный пул; `maximumPoolSize`, `connectionTimeout`.
- **PreparedStatement:** предкомпиляция + параметры → быстрее и защита от инъекций. `Statement` — для DDL/динамики.
- `executeQuery` → `ResultSet`; `executeUpdate` → `int`; `execute` → `boolean`.
- **ACID:** Atomicity, Consistency, Isolation, Durability.
- `setAutoCommit(false)` → `commit()`/`rollback()`; **savepoint** — частичный откат.
- **Аномалии:** dirty, non-repeatable, phantom. Уровни: RU → RC → RR → Serializable.
- Дефолты: PostgreSQL — READ COMMITTED, MySQL — REPEATABLE READ. **MVCC** — чтение не блокирует запись.
- **SQL-инъекция:** защита — PreparedStatement с `?`, whitelist, наименьшие привилегии.

## SQL/БД

- **Нормализация:** 1NF (атомарность) → 2NF (нет частичной зависимости) → 3NF (нет транзитивной) → BCNF. **Денормализация** — ради скорости чтения.
- **Связи:** 1:1 (unique FK), 1:N (FK у многих), M:N (junction-таблица).
- **PK** — один, `NOT NULL`, индекс; **UNIQUE** — много, допускает `NULL`; **FK** — ссылочная целостность + `ON DELETE CASCADE/SET NULL/RESTRICT`.
- **Surrogate key** (id) — обычно; **natural key** (email) — как unique.
- **Индексы:** ускоряют чтение, замедляют запись; составной (порядок колонок!), покрывающий (index-only scan). Не работают: низкая селективность, функция над колонкой, `LIKE '%x'`, неявное приведение.
- **JOIN:** INNER, LEFT, RIGHT, FULL, CROSS, SELF. Поиск «сирот»: `LEFT JOIN ... WHERE right.id IS NULL`.
- **WHERE до GROUP BY, HAVING после.** Агрегаты — только в `HAVING`.
- **View** — не хранит данные; **Materialized View** — хранит, требует `REFRESH`.
- **COUNT(*)** — все строки; **COUNT(col)** — не-NULL.
- **EXPLAIN** — план, **EXPLAIN ANALYZE** — план + реальные метрики. Seq Scan плохо, Index Scan хорошо; Nested Loop — малые объёмы, Hash Join — большие.

# Частые вопросы на собеседовании с короткими ответами

**Тестирование**

1. **Что такое JUnit 5 и из чего состоит?** — Фреймворк тестирования; Platform (движок запуска), Jupiter (API), Vintage (запуск JUnit 4).
2. **Что такое принципы FIRST?** — Fast, Independent, Repeatable, Self-validating, Timely.
3. **Что такое AAA?** — Arrange (подготовка), Act (действие), Assert (проверка).
4. **`@BeforeEach` vs `@BeforeAll`?** — Первый перед каждым тестом, второй один раз до всех (обычно `static`).
5. **`assertEquals` vs `assertSame`?** — `equals()` vs сравнение ссылок (`==`).
6. **Как проверить исключение?** — `assertThrows(Exception.class, () -> ...)`.
7. **Stub vs Mock?** — Stub возвращает заготовленные данные (проверяем состояние), mock проверяет взаимодействия (какие методы вызваны).
8. **Fake vs Spy?** — Fake — упрощённая рабочая реализация; spy — реальный объект с частичной подменой.
9. **`@Mock` vs `@Spy`?** — Мок полностью подменён (дефолты), spy вызывает реальные методы.
10. **Что делает `@InjectMocks`?** — Создаёт объект и внедряет в него моки.
11. **`when` vs `doReturn`?** — `when` вызывает метод при настройке (плохо для spy/void), `doReturn` — нет.
12. **Зачем `ArgumentCaptor`?** — Захватить аргумент вызова и проверить его.
13. **`verifyNoMoreInteractions`?** — Что после проверенных вызовов других не было.
14. **`@Mock` vs `@MockBean`?** — `@Mock` создаёт Mockito-мок в тесте, `@MockBean` заменяет бин в Spring-контексте.
15. **Пирамида тестирования?** — Много unit, средне integration, мало E2E.
16. **Что такое Testcontainers?** — Реальные сервисы (БД) в Docker-контейнере на время теста.
17. **Почему не H2 для интеграционных тестов?** — Поведение SQL/типов/транзакций отличается от реальной СУБД.

**JDBC**

18. **Что такое JDBC?** — Низкоуровневый API Java для работы с реляционными БД; все ORM работают поверх него.
19. **Шаги подключения?** — Драйвер → Connection (пул) → Statement → выполнить → ResultSet → закрыть.
20. **Зачем пул соединений?** — Создание соединения дорого; пул переиспользует готовые.
21. **Что такое HikariCP?** — Быстрый популярный пул соединений (дефолт Spring Boot).
22. **Statement vs PreparedStatement?** — Последний с параметрами, предкомпилирован и защищён от инъекций.
23. **Почему PreparedStatement защищает от инъекций?** — Параметры передаются отдельно от SQL как данные.
24. **executeQuery vs executeUpdate?** — Первый для SELECT → ResultSet; второй для INSERT/UPDATE/DELETE → число строк.
25. **Зачем batch?** — Отправить много запросов одним пакетом — меньше сетевых обходов.
26. **Что такое транзакция?** — Набор операций «всё или ничего».
27. **ACID?** — Atomicity, Consistency, Isolation, Durability.
28. **Как управлять транзакцией в JDBC?** — `setAutoCommit(false)`, затем `commit()`/`rollback()`.
29. **Что такое savepoint?** — Промежуточная точка для частичного отката.
30. **Dirty vs non-repeatable vs phantom read?** — Чтение незакоммиченного / изменение значения между чтениями / появление новых строк.
31. **Уровни изоляции?** — READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE.
32. **Дефолтные уровни?** — PostgreSQL — READ COMMITTED, MySQL InnoDB — REPEATABLE READ.
33. **Что такое MVCC?** — Многоверсионность: чтение не блокирует запись.
34. **Как защититься от SQL-инъекции?** — PreparedStatement с параметрами, whitelist, наименьшие привилегии.
35. **PreparedStatement защищает везде?** — Нет: имена таблиц/колонок и `ORDER BY` параметризовать нельзя, нужен whitelist.

**SQL/БД**

36. **Зачем нормализация?** — Убрать дублирование и аномалии обновления/вставки/удаления.
37. **1NF/2NF/3NF?** — Атомарность / нет частичной зависимости / нет транзитивной зависимости.
38. **BCNF?** — Усиленная 3NF: каждый детерминант — суперключ.
39. **Что такое денормализация?** — Намеренное нарушение НФ ради скорости чтения.
40. **Как реализовать M:N?** — Через junction-таблицу с двумя FK и составным PK.
41. **PK vs UNIQUE?** — PK один, `NOT NULL`, идентифицирует строку; UNIQUE может быть много, допускает `NULL`.
42. **ON DELETE CASCADE?** — Удаляет дочерние строки при удалении родителя.
43. **Surrogate vs natural key?** — Искусственный стабильный id vs реальное бизнес-поле.
44. **Зачем индексы и в чём минус?** — Ускоряют чтение, но замедляют запись и занимают место.
45. **Составной индекс и порядок колонок?** — Работает по префиксу слева направо; `(a,b)` не помогает для `b` отдельно.
46. **Покрывающий индекс?** — Содержит все нужные запросу колонки → index-only scan.
47. **Когда индекс не работает?** — Низкая селективность, функция над колонкой, `LIKE '%x'`, неявное приведение, маленькая таблица.
48. **INNER vs LEFT JOIN?** — INNER только совпадения; LEFT сохраняет все строки левой таблицы.
49. **Как найти записи без связей?** — `LEFT JOIN ... WHERE right.id IS NULL`.
50. **WHERE vs HAVING?** — WHERE фильтрует строки до группировки, HAVING — группы после; агрегаты только в HAVING.
51. **COUNT(*) vs COUNT(col)?** — Все строки vs только не-NULL.
52. **View vs Materialized View?** — View не хранит данные (всегда свежий), materialized хранит и требует REFRESH.
53. **EXPLAIN vs EXPLAIN ANALYZE?** — ANALYZE реально выполняет запрос и показывает фактические метрики.
54. **Seq Scan vs Index Scan?** — Полное сканирование таблицы vs поиск по индексу.
55. **Nested Loop vs Hash Join?** — Nested Loop хорош для малых объёмов, Hash Join — для больших без индекса.
