## 1. Абстрактный класс vs интерфейс

### 1.1. Аналогия из жизни

Представь, что ты проектируешь зоопарк.

- **Интерфейс** — это табличка «Умеет плавать». Её можно повесить на дельфина, на утку и на подводную лодку. Она ничего не говорит о том, *как* плавать, — только *что* умеет.
- **Абстрактный класс** — это «Млекопитающее». У всех млекопитающих уже есть общий «движок»: сердце, лёгкие, теплокровность (общее состояние и код). А конкретное «мяукать» или «лаять» каждый доопределяет сам.

Один объект может иметь **много** табличек (интерфейсов), но родитель-«млекопитающее» у него **один** (одиночное наследование).

### 1.2. Что это такое формально

- **Абстрактный класс** — класс, который нельзя инстанцировать (`new`). Может содержать абстрактные методы (без тела) и обычные методы с реализацией, а также **поля и состояние**.
- **Интерфейс** — чистый контракт (набор требований к классу). С Java 8+ в нём можно писать `default` и `static` методы, с Java 9 — `private`.

### 1.3. Большая сравнительная таблица

| Критерий | Абстрактный класс | Интерфейс |
|---|---|---|
| Ключевое слово | `abstract class` | `interface` |
| Как наследуется | `extends` (только **один** родитель) | `implements` (**много** интерфейсов) |
| Поля экземпляра (состояние) | да, любые (private, non-static) | нет; только `public static final` константы |
| Конструктор | есть (вызывается через `super()`) | нет |
| Абстрактные методы | да | да |
| Обычные методы с телом | да | `default` и `static` (Java 8+), `private` (Java 9+) |
| Модификаторы методов | любые (`public`, `protected`, `private`…) | методы `public` по умолчанию; `private` только в Java 9+ |
| Множественное наследование реализации | нет | да (через `default`-методы) |
| Изменение состояния | да | нет (нельзя хранить изменяемое состояние) |
| Скорость | чуть быстрее | чуть медленнее, но гибче |
| Когда выбирать | общая реализация + общее состояние, тесная иерархия | контракт/роль, слабая связанность |
| Пример из JDK | `AbstractList`, `InputStream` | `List`, `Comparable`, `Runnable` |

### 1.4. Конструктор в абстрактном классе

Да, у абстрактного класса **есть** конструктор, хотя сам класс нельзя создать. Он нужен, чтобы наследник через `super(...)` проинициализировал общие поля родителя.

```java
abstract class Animal {
    protected final String name;

    protected Animal(String name) {   // конструктор абстрактного класса
        this.name = name;
        System.out.println("Animal создан: " + name);
    }

    abstract void makeSound();
}

class Dog extends Animal {
    Dog(String name) {
        super(name);                  // обязательно проинициализировать родителя
        System.out.println("Dog создан: " + name);
    }
    @Override void makeSound() { System.out.println(name + " гав"); }
}

// ВЫВОД:
// Animal создан: Рекс
// Dog создан: Рекс
// Рекс гав
```

### 1.5. Поля в абстрактном классе vs интерфейсе

```java
abstract class Base {
    private int counter = 0;          // состояние конкретного объекта
    protected String shared = "A";    // доступно наследникам
    public int getCounter() { return counter; }
}

interface Config {
    int MAX = 100;                    // неявно public static final — константа!
    // int x = 0; x = 5;             // ОШИБКА: константу нельзя менять
}
```

> В интерфейсе **любое** поле — это `public static final` константа. Оно одно на всех и его нельзя изменить. Хранить в интерфейсе изменяемое состояние нельзя.

### 1.6. default, static и private методы интерфейса

**default-метод (Java 8)** позволяет добавить реализацию, не ломая уже существующие классы-наследники. Это спасало при добавлении `stream()` в `Collection`.

```java
interface Greeter {
    void greet(String name);

    default void greetAll(String... names) {   // реализация по умолчанию
        for (String n : names) greet(n);
    }
}

class Friendly implements Greeter {
    public void greet(String name) { System.out.println("Привет, " + name); }
}

new Friendly().greetAll("Аня", "Боб");
// ВЫВОД:
// Привет, Аня
// Привет, Боб
```

**static-метод** в интерфейсе не наследуется классом и вызывается только через имя интерфейса:

```java
interface MathUtil {
    static int square(int x) { return x * x; }
}
int r = MathUtil.square(5);   // 25
// new Friendly().square(5);  // ОШИБКА: static не наследуется
```

**private-метод (Java 9)** — чтобы не дублировать код между `default`-методами:

```java
interface Validator {
    default boolean validName(String s) { return check(s, 3); }
    default boolean validCity(String s) { return check(s, 2); }

    private boolean check(String s, int min) {   // помощник, наружу не виден
        return s != null && s.trim().length() >= min;
    }
}
```

**Конфликт default-методов.** Если два интерфейса дают разные `default` с одной сигнатурой, класс обязан разрешить конфликт вручную:

```java
interface A { default String hi() { return "A"; } }
interface B { default String hi() { return "B"; } }

class C implements A, B {
    @Override public String hi() { return A.super.hi() + B.super.hi(); }
}
// new C().hi() -> "AB"
```

Если конфликт не разрешить — **ошибка компиляции**.

### 1.7. Маркерные интерфейсы

**Маркерный интерфейс** — интерфейс без методов, который «помечает» класс свойством:

- `Serializable` — объект можно сериализовать.
- `Cloneable` — объект поддерживает `clone()` (иначе `CloneNotSupportedException`).
- `RandomAccess` — список поддерживает быстрый доступ по индексу (для `ArrayList`), алгоритмы выбирают стратегию.

```java
class Token implements Serializable {   // помечен — можно сохранять в поток
    private String value;
}
```

> Аналогия: маркерный интерфейс — как наклейка «хрупкое» на коробке. Она не меняет содержимое, но курьер знает, как обращаться.

### 1.8. Функциональные интерфейсы

**Функциональный интерфейс** — интерфейс ровно с **одним абстрактным методом** (SAM — Single Abstract Method). Такие интерфейсы можно реализовать лямбдой. Помечают `@FunctionalInterface` (необязательно, но полезно — компилятор проверит).

```java
@FunctionalInterface
interface Calculator {
    int apply(int a, int b);          // один абстрактный метод
    default int twice(int a) { return apply(a, a); }  // default не считается
}

Calculator add = (a, b) -> a + b;    // лямбда вместо анонимного класса
System.out.println(add.apply(2, 3)); // 5
```

Примеры из JDK: `Runnable`, `Callable`, `Comparator`, `Function`, `Predicate`, `Supplier`, `Consumer`.

### 1.9. Когда что выбирать — пошаговое правило

1. Нужен только **контракт** («умеет X»), состояние не нужно → **интерфейс**.
2. Нужно **общее состояние/реализация** у родственных классов → **абстрактный класс**.
3. Нужна гибкость и множественное наследование типа → **интерфейс**.
4. Хочешь дать дефолтную реализацию, но не хранить состояние → **интерфейс с `default`**.
5. Класс должен наследовать что-то другое → **интерфейс** (абстрактный класс занял бы единственный слот `extends`).
6. **Правило большого пальца:** начинай с интерфейса; абстрактный класс добавляй, только если реально нужна общая реализация/состояние.

### 1.10. Типичные ошибки

- Пытаются создать `new AbstractClass()` или `new Interface()` — нельзя.
- Думают, что в интерфейсе можно хранить изменяемое поле — нет, только константы.
- Забывают про `super(...)` в конструкторе наследника абстрактного класса.
- Не разрешают конфликт `default`-методов → ошибка компиляции.
- Делают «толстые» интерфейсы с 20 методами — нарушение Interface Segregation.
- Считают, что `static`-метод интерфейса наследуется — он вызывается только через интерфейс.

### 1.11. Часто спрашивают на собеседовании

- *Может ли интерфейс иметь конструктор?* — Нет. Абстрактный класс — да.
- *Можно ли в интерфейсе объявить поле?* — Да, но оно всегда `public static final`.
- *Зачем `default`-методы?* — Чтобы расширять интерфейс без ломания существующих реализаций.
- *Сколько родителей можно наследовать?* — Класс — один (`extends`), интерфейсов — много (`implements`).
- *Что такое функциональный интерфейс?* — Ровно один абстрактный метод; можно заменить лямбдой.

## 2. Перегрузка (overloading) vs переопределение (overriding)

### 2.1. Аналогия из жизни

- **Перегрузка** — как слово «ключ»: ключ от двери, гаечный ключ, ключ-родник. Одно имя, но разные смыслы в зависимости от контекста (типов аргументов). Решается **заранее**, при компиляции.
- **Переопределение** — как «говорить»: животное издаёт звук, но собака лает, а кошка мяукает. Метод с тем же именем ведёт себя по-разному у разных классов. Решается **в рантайме** по реальному типу объекта.

### 2.2. Сравнительная таблица

| Критерий | Overloading (перегрузка) | Overriding (переопределение) |
|---|---|---|
| Где происходит | в одном классе (или иерархии) | родитель → наследник |
| Сигнатура | имя то же, **параметры разные** | сигнатура **та же** |
| Возвращаемый тип | любой | **ковариантный** (уже, но не примитив) |
| Модификатор доступа | любой | **не уже**, чем у родителя |
| Исключения | любые | **не шире** (можно уже/меньше/убрать) |
| Тип связывания | compile-time (static binding) | runtime (dynamic binding) |
| `static`/`private`/`final` | можно перегружать | **нельзя** переопределять |
| Полиморфизм | нет | да |
| Аннотация | не нужна | `@Override` (рекомендуется) |

### 2.3. Перегрузка: пошаговый разбор

Перегружать можно по:

- **числу** параметров,
- **типу** параметров,
- **порядку** параметров.

**Нельзя** перегружать только по возвращаемому типу или только по имени параметра.

```java
class Printer {
    void print(int x)     { System.out.println("int: " + x); }
    void print(String s)  { System.out.println("String: " + s); }
    void print(int a, int b) { System.out.println("two ints: " + a + "," + b); }
}

Printer p = new Printer();
p.print(5);        // int: 5
p.print("hi");     // String: hi
p.print(1, 2);     // two ints: 1,2
```

Как компилятор выбирает перегрузку? Идёт от **самого точного** совпадения к расширениям:

```java
void f(long x)  { System.out.println("long"); }
void f(int x)   { System.out.println("int"); }

f(5);        // int  — точное совпадение
f(5L);       // long
f((short)5); // int  — short расширяется до int (ближайший)
```

> Важно: если точного совпадения нет, компилятор ищет **расширение примитива** (widening), затем **автоупаковку** (boxing), затем **varargs**. Это порядок предпочтения.

### 2.4. Переопределение: пошаговый разбор

```java
class Animal {
    public String speak() { return "..."; }
}

class Dog extends Animal {
    @Override
    public String speak() { return "Гав"; }   // та же сигнатура
}

Animal a = new Dog();       // тип ссылки Animal, объект Dog
System.out.println(a.speak()); // Гав — вызов решён в рантайме (dynamic binding)
```

Компилятор смотрит на **тип ссылки** (`Animal`), а виртуальная машина вызывает метод по **реальному типу объекта** (`Dog`).

### 2.5. Ковариантный возвращаемый тип

Наследник может вернуть **более конкретный** (подтип) тип:

```java
class Parent {
    Number get() { return 1; }
}
class Child extends Parent {
    @Override
    Integer get() { return 2; }   // Integer — подтип Number: допустимо
}
```

Для примитивов ковариантности нет: `int` → `long` при переопределении **нельзя**.

### 2.6. Модификаторы доступа при переопределении

Правило: **нельзя сужать** видимость. Порядок: `public` > `protected` > package-private > `private`.

```java
class A {
    protected void m() {}
}
class B extends A {
    @Override public void m() {}       // OK: расширили
    // @Override private void m() {}   // ОШИБКА: сузили
}
```

### 2.7. Исключения при переопределении

- **Checked-исключения:** нельзя объявлять **шире**, чем родитель. Можно уже или не объявлять вовсе.
- **Unchecked (RuntimeException):** можно добавлять свободно.

```java
class A {
    void m() throws IOException {}
}
class B extends A {
    @Override void m() throws FileNotFoundException {}  // уже — OK
    // @Override void m() throws Exception {}           // шире — ОШИБКА
}
```

### 2.8. static, private, final

- `private`-метод **не переопределяется** (он не виден наследнику) — можно лишь объявить свой метод с тем же именем.
- `static`-метод **скрывается** (hiding), а не переопределяется. Вызов зависит от типа ссылки, а не объекта.
- `final`-метод **запрещено** переопределять.

```java
class A { static void s() { System.out.println("A"); } }
class B extends A { static void s() { System.out.println("B"); } }

A a = new B();
a.s();   // A — static binding по типу ссылки!
B b = new B();
b.s();   // B
```

### 2.9. `@Override`

Аннотация `@Override` не обязательна, но крайне полезна: компилятор проверит, что ты действительно переопределяешь, и поймает опечатку.

```java
class Dog extends Animal {
    // @Override
    public String speek() { ... }   // с @Override это ОШИБКА компиляции — опечатка!
}
```

### 2.10. Типичные ошибки

- Пытаются перегрузить, меняя только возвращаемый тип → ошибка компиляции.
- Переопределяют `static`/`private`/`final` метод, думая, что это полиморфизм.
- Сужают доступ при переопределении → ошибка.
- Расширяют checked-исключения при переопределении → ошибка.
- Забывают `@Override` и получают «тихую» перегрузку вместо переопределения.
- Путают hiding (`static`) и overriding (instance).

### 2.11. Часто спрашивают на собеседовании

- *Чем overload отличается от override?* — Разные параметры / та же сигнатура; compile-time / runtime.
- *Можно ли переопределить `static`-метод?* — Нет, только скрыть.
- *Что такое ковариантный возврат?* — Наследник возвращает подтип.
- *Можно ли сузить доступ при override?* — Нет.
- *Можно ли расширить исключения?* — Checked — нет, unchecked — да.

## 3. Передача параметров: только по значению

### 3.1. Главная мысль

Java **всегда** передаёт **копию значения**. Никакой «передачи по ссылке» в Java нет.

- Если значение — **примитив** → копируется само число.
- Если значение — **объект** → копируется **ссылка** на объект (сам объект общий!).

### 3.2. Аналогия из жизни

Представь, что ты даёшь другу **копию адреса** своего дома. Друг может поехать по этому адресу и переставить мебель (объект меняется). Но если друг напишет на копии бумажки **другой адрес**, твоя оригинальная бумажка не изменится (переприсваивание ссылки не влияет).

### 3.3. Примитивы

```java
void modify(int x) {
    x = 100;                 // меняем локальную копию
}
int a = 5;
modify(a);
System.out.println(a);       // ВЫВОД: 5 — оригинал не изменился
```

### 3.4. Объекты: изменение содержимого

```java
class Person { String name; Person(String n){ name = n; } }

void rename(Person p) {
    p.name = "Боб";          // меняем поле по скопированной ссылке — объект общий
}
Person person = new Person("Аня");
rename(person);
System.out.println(person.name);   // ВЫВОД: Боб
```

### 3.5. Объекты: переприсваивание ссылки

```java
void replace(Person p) {
    p = new Person("Карл");  // меняем только локальную копию ссылки
}
Person person = new Person("Аня");
replace(person);
System.out.println(person.name);   // ВЫВОД: Аня — оригинальная ссылка не изменилась
```

### 3.6. Массивы (тоже объекты)

```java
void changeArray(int[] arr) {
    arr[0] = 99;             // меняем элемент — видно снаружи
}
void reassignArray(int[] arr) {
    arr = new int[]{7, 7};   // меняем локальную ссылку — не видно
}
int[] data = {1, 2, 3};
changeArray(data);           // data = [99, 2, 3]
reassignArray(data);         // data остаётся [99, 2, 3]
```

### 3.7. Сводная таблица

| Что передаём | Что копируется | Изменится ли снаружи? |
|---|---|---|
| Примитив | число | Нет |
| Поле объекта (`p.field = x`) | ссылка | **Да** (общий объект) |
| Переприсваивание (`p = new ...`) | ссылка | Нет |
| Элемент массива | ссылка | **Да** |
| `String` (immutable) | ссылка | Нет (создаётся новый объект) |

### 3.8. `String` — особый случай

`String` неизменяема, поэтому «изменение» строки внутри метода создаёт новый объект, а внешняя ссылка остаётся старой:

```java
void addSuffix(String s) { s = s + "!"; }
String str = "hi";
addSuffix(str);
System.out.println(str);     // ВЫВОД: hi
```

### 3.9. Типичные ошибки

- Говорить «Java передаёт объекты по ссылке» — неверно; передаётся **копия ссылки**.
- Ожидать, что метод изменит объект, если внутри переприсвоить параметр.
- Забывать, что мутирующие методы (например `list.add`) изменяют общий объект.
- Думать, что `String` изменится как `StringBuilder`.

### 3.10. Часто спрашивают на собеседовании

- *Java передаёт по значению или по ссылке?* — Всегда по значению; для объектов значение = ссылка.
- *Изменит ли метод объект?* — Содержимое — да, переприсваивание ссылки — нет.
- *Почему `String` не меняется?* — Она immutable.

## 4. Конструкторы

### 4.1. Что такое конструктор

Конструктор — специальный блок, вызываемый при `new`. Он:

- имеет **имя класса** и **нет возвращаемого типа** (даже `void`);
- **не наследуется**;
- вызывается ровно один раз на объект.

```java
class User {
    String name;
    User(String name) { this.name = name; }   // конструктор
}
User u = new User("Аня");
```

### 4.2. Конструктор по умолчанию (default)

Если **не объявлен ни один** конструктор, компилятор сам добавит конструктор без параметров:

```java
class Empty { }                 // компилятор добавит Empty() {}
new Empty();                    // OK
```

Но если объявить **хотя бы один** конструктор, default **исчезает**:

```java
class WithCtor {
    WithCtor(int x) {}
}
// new WithCtor();   // ОШИБКА: нет конструктора без параметров
```

> Тонкость: `record` и `enum` — исключения со своими правилами.

### 4.3. `this(...)` и `super(...)`

- `super(...)` — вызов конструктора **родителя**.
- `this(...)` — вызов **другого конструктора** того же класса.
- Оба должны быть **первой строкой** и **взаимоисключающи**.
- Если не написать ни то, ни другое — компилятор неявно вставит `super()` (без параметров).

```java
class Point {
    int x, y;
    Point() { this(0, 0); }          // делегирование
    Point(int x) { this(x, 0); }
    Point(int x, int y) { this.x = x; this.y = y; }
}
```

Если у родителя нет конструктора без параметров, а ты не вызываешь `super(...)` явно — **ошибка компиляции**.

```java
class A { A(int x) {} }
class B extends A {
    B() { super(5); }   // обязательно, иначе ошибка
}
```

### 4.4. private-конструктор

Используется, когда создавать объекты снаружи не нужно:

```java
class MathUtils {
    private MathUtils() {}           // запрет на создание; только static-методы
    static int square(int x) { return x * x; }
}

class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}           // защита от new снаружи
    public static Singleton getInstance() { return INSTANCE; }
}
```

### 4.5. Copy constructor (конструктор копирования)

Копирует поля из другого объекта того же типа:

```java
class Person {
    String name;
    int age;
    Person(String name, int age) { this.name = name; this.age = age; }
    Person(Person other) { this.name = other.name; this.age = other.age; }  // copy
}
Person a = new Person("Аня", 30);
Person b = new Person(a);        // копия
b.name = "Боб";
System.out.println(a.name);      // Аня — оригинал не затронут
```

> Для изменяемых полей делай **глубокую копию** (см. раздел 6).

### 4.6. Чего не может быть

Конструктор **не может** быть: `final`, `static`, `abstract`, `synchronized`. Может быть `private`, `public`, `protected`, package-private.

### 4.7. Порядок инициализации с наследованием — подробно по шагам

Рассмотрим:

```java
class Parent {
    static { System.out.println("1. static Parent"); }
    int pf = initP();                       // поле родителя
    { System.out.println("3. instance-блок Parent"); }
    Parent() { System.out.println("4. конструктор Parent"); }
    int initP() { System.out.println("2. поле Parent"); return 10; }
}

class Child extends Parent {
    static { System.out.println("A. static Child"); }
    int cf = initC();                       // поле ребёнка
    { System.out.println("C. instance-блок Child"); }
    Child() { super(); System.out.println("D. конструктор Child"); }
    int initC() { System.out.println("B. поле Child"); return 20; }
}

new Child();
```

**Порядок выполнения:**

1. **Загрузка классов** (один раз): `static`-поля и `static`-блоки — сначала родителя, потом ребёнка. Вывод: `1. static Parent`, затем `A. static Child`.
2. `new Child()` → выделяется память, все поля = дефолты (`0`, `null`).
3. Вызывается `Child()` → неявно `super()` → вызывается `Parent()`.
4. **Перед** телом конструктора `Parent`: инициализаторы полей и instance-блоки `Parent` **в порядке объявления** → `2. поле Parent`, затем `3. instance-блок Parent`.
5. Тело конструктора `Parent` → `4. конструктор Parent`.
6. Возврат в `Child`: **перед** телом его конструктора — поля и instance-блоки `Child` → `B. поле Child`, затем `C. instance-блок Child`.
7. Тело конструктора `Child` → `D. конструктор Child`.

**Итоговый вывод:**

```
1. static Parent
A. static Child
2. поле Parent
3. instance-блок Parent
4. конструктор Parent
B. поле Child
C. instance-блок Child
D. конструктор Child
```

> Ключевая мысль: **сначала полностью инициализируется родитель** (поля + блок + конструктор), и только потом инициализаторы и конструктор ребёнка.

### 4.8. Опасность: вызов переопределённого метода из конструктора

Если конструктор родителя вызывает метод, переопределённый в ребёнке, а поля ребёнка ещё не инициализированы — получишь `null`/`0`:

```java
class Parent {
    Parent() { print(); }            // вызывается ДО инициализации полей Child
    void print() { System.out.println("Parent"); }
}
class Child extends Parent {
    String value = "готово";
    @Override void print() { System.out.println("Child: " + value); }
}
new Child();   // ВЫВОД: Child: null  — ловушка!
```

### 4.9. Типичные ошибки

- Думать, что конструкторы наследуются.
- Вызывать `this()`/`super()` не первой строкой.
- Забывать, что при наличии своего конструктора default пропадает.
- Вызывать переопределяемые методы из конструктора.
- Копировать изменяемые поля поверхностно (shared mutable state).

### 4.10. Часто спрашивают на собеседовании

- *Можно ли сделать конструктор private?* — Да (singleton, utility).
- *Что делает `this()`?* — Вызывает другой конструктор того же класса.
- *Наследуются ли конструкторы?* — Нет.
- *Порядок инициализации?* — static → родитель (поля/блоки/конструктор) → ребёнок.

## 5. Блоки инициализации

### 5.1. Два вида блоков

- **static-блок** `static { ... }` — выполняется **один раз** при загрузке класса.
- **instance-блок** `{ ... }` — выполняется **при создании каждого объекта**, перед телом конструктора (после `super()`).

### 5.2. Аналогия

- static-блок — как подготовка сцены перед первым спектаклем: делается один раз.
- instance-блок — как гримёрка перед каждым выходом актёра: повторяется каждый раз.

### 5.3. Пример порядка

```java
class Init {
    static { System.out.print("1 "); }   // при загрузке класса
    { System.out.print("2 "); }          // при каждом new
    Init() { System.out.print("3 "); }
}
new Init();   // ВЫВОД: 1 2 3
new Init();   // ВЫВОД: 1 2 3  (static "1" больше не печатается)
```

### 5.4. Порядок внутри класса

И static-поля, и static-блоки выполняются **в порядке объявления** сверху вниз. То же для instance-полей и instance-блоков.

```java
class Order {
    static int a = print("static a");
    static { print("static block"); }
    int b = print("instance b");
    { print("instance block"); }
    Order() { print("ctor"); }

    static int print(String s) { System.out.println(s); return 0; }
}
new Order();
// ВЫВОД:
// static a
// static block
// instance b
// instance block
// ctor
```

> Если поменять местами `b` и блок — изменится порядок. **Правило: сверху вниз, как написано.**

### 5.5. Зачем instance-блок

Чтобы не дублировать общий код в нескольких конструкторах:

```java
class Config {
    List<String> items = new ArrayList<>();
    {                                 // общий код для всех конструкторов
        items.add("default");
    }
    Config() {}
    Config(String extra) { items.add(extra); }
}
```

### 5.6. `ExceptionInInitializerError`

Если static-блок бросает исключение, класс не может быть загружен — JVM оборачивает ошибку в `ExceptionInInitializerError`. Повторная попытка использования класса снова выбросит `NoClassDefFoundError`.

```java
class Bad {
    static int x = 1 / 0;   // ArithmeticException внутри инициализации
}
// При первом обращении: ExceptionInInitializerError
// При повторном: NoClassDefFoundError
```

### 5.7. Типичные ошибки

- Путают порядок static и instance-блоков.
- Ожидают, что static-блок выполнится при каждом `new`.
- Тяжёлая логика в static-блоке → медленная загрузка, сложно отлаживать.
- Исключение в static-блоке делает класс «навсегда» неиспользуемым.

### 5.8. Часто спрашивают на собеседовании

- *Когда выполняется static-блок?* — Один раз при загрузке класса.
- *Когда instance-блок?* — Перед каждым телом конструктора.
- *Что если static-блок бросит исключение?* — `ExceptionInInitializerError`.

## 6. Mutable и Immutable классы

### 6.1. Определения

- **Immutable (неизменяемый)** — состояние нельзя изменить после создания. Все «изменения» создают новый объект.
- **Mutable (изменяемый)** — состояние можно менять после создания.

### 6.2. Аналогия

- Immutable — как напечатанный документ: чтобы что-то поменять, печатаешь новый.
- Mutable — как доска с маркером: стирай и пиши поверх.

### 6.3. Как создать immutable-класс — 5 шагов

1. Сделать класс `final` (запретить наследование, чтобы подкласс не добавил мутабельность).
2. Все поля `private final`.
3. Не делать сеттеров.
4. В конструкторе и геттерах делать **защитную копию** (defensive copy) изменяемых полей.
5. Не возвращать наружу ссылки на изменяемые поля.

```java
public final class Person {                         // 1. final
    private final String name;                      // 2. private final
    private final List<String> hobbies;

    public Person(String name, List<String> hobbies) {
        this.name = name;
        this.hobbies = List.copyOf(hobbies);        // 4. копия на входе
    }

    public String getName() { return name; }        // 3. без сеттеров

    public List<String> getHobbies() {
        return hobbies;                             // 5. список уже immutable (copyOf)
    }
}
```

### 6.4. Defensive copy подробно

**Проблема:** если сохранить или вернуть ссылку на изменяемую коллекцию, её можно изменить в обход класса.

```java
public final class Bad {
    private final List<String> list;
    public Bad(List<String> list) { this.list = list; }   // БЕДА: внешняя ссылка
    public List<String> getList() { return list; }        // БЕДА: отдаём ссылку
}

List<String> src = new ArrayList<>(List.of("a"));
Bad bad = new Bad(src);
src.add("b");                 // меняем извне — bad.list тоже изменился!
bad.getList().add("c");       // и так можно!
System.out.println(bad.getList());   // [a, b, c]
```

**Решение:**

```java
public final class Good {
    private final List<String> list;
    public Good(List<String> list) { this.list = new ArrayList<>(list); }  // копия входа
    public List<String> getList() { return Collections.unmodifiableList(list); } // защита выхода
}
```

Современные удобные варианты: `List.copyOf(list)`, `Set.copyOf(...)`, `Map.copyOf(...)` — возвращают **неизменяемые** копии (и не допускают `null`).

### 6.5. Immutable-примеры из Java Core

| Класс | Почему immutable |
|---|---|
| `String` | Любая «модификация» создаёт новую строку |
| Примитивные обёртки (`Integer`, `Long`, `Boolean`) | Значение внутри `final` |
| `BigInteger`, `BigDecimal` | Арифметика возвращает новый объект |
| `java.time.*` (`LocalDate`, `Instant`) | Современный API даты/времени |
| `record` (Java 16+) | Поля неявно `final` |
| `List.of(...)`, `Map.of(...)` | Неизменяемые фабрики коллекций |

> `java.util.Date` — классический **плохой mutable** класс (методы меняют объект). Именно поэтому появился `java.time`.

### 6.6. Плюсы immutable

- **Потокобезопасность** — нечего синхронизировать.
- **Кэшируемость** — можно переиспользовать (например, `Integer.valueOf` кэширует -128..127).
- **Безопасные ключи `Map`** — `hashCode` не меняется.
- **Проще рассуждать** — объект не «потечёт» под ногами.
- **Хорошо для value-объектов** — деньги, даты, координаты.

### 6.7. Минусы immutable

- Новый объект при каждом изменении → нагрузка на GC.
- Иногда неудобно писать «цепочки» изменений.
- Нужно аккуратно делать defensive copy (накладные расходы).

### 6.8. `record` как быстрый immutable

```java
public record Point(int x, int y) {}   // поля final, нет сеттеров
Point p = new Point(1, 2);
// p.x = 5;   // ОШИБКА: поле final
```

### 6.9. Mutable-классы

`ArrayList`, `HashMap`, `StringBuilder`, `Date`, `Calendar`. Их нормально использовать локально; проблема начинается, когда изменяемый объект «утекает» наружу из immutable-класса.

### 6.10. Типичные ошибки

- Не сделать класс `final` → подкласс добавляет сеттер.
- Забыть defensive copy → утечка изменяемого состояния.
- Возвращать внутренний `ArrayList` напрямую.
- Считать `record` полным immutable, если внутри изменяемое поле (например `int[]`) — массив всё ещё можно менять!

```java
record Bad(int[] data) {}
int[] arr = {1, 2};
Bad b = new Bad(arr);
b.data()[0] = 99;   // изменили содержимое record!
```

### 6.11. Часто спрашивают на собеседовании

- *Как сделать immutable класс?* — 5 шагов выше.
- *Почему `String` immutable?* — Безопасность, кэш `hashCode`, потокобезопасность, String pool.
- *Что такое defensive copy?* — Копирование изменяемых данных на границах класса.
- *Immutable всегда потокобезопасен?* — Да, если внутри нет утечки мутабельных ссылок.

## 7. `static`

### 7.1. Смысл

`static` означает «принадлежит **классу**, а не экземпляру». Общий для всех объектов, существует в единственном экземпляре.

### 7.2. static-поле

Одно на класс. Живёт в области `Metaspace` (память классов), а не в куче объекта.

```java
class Counter {
    static int total = 0;       // общее для всех
    int id;
    Counter() { id = ++total; }
}
new Counter(); new Counter();
System.out.println(Counter.total);   // 2
```

### 7.3. static-метод

- Вызывается без объекта.
- **Нет `this`** → не может обращаться к нестатическим полям/методам напрямую.
- Не может быть переопределён (только **скрыт**).
- Не может использовать `super`/`this`.

```java
class Utils {
    static int max(int a, int b) { return a > b ? a : b; }
}
Utils.max(3, 5);   // 5
```

### 7.4. static-блок

Один раз при загрузке класса (см. раздел 5). Удобен для сложной инициализации статики:

```java
class Config {
    static final Map<String, String> DEFAULTS;
    static {
        Map<String, String> m = new HashMap<>();
        m.put("lang", "ru");
        DEFAULTS = Collections.unmodifiableMap(m);
    }
}
```

### 7.5. static-вложенный класс

Не имеет ссылки на внешний экземпляр, создаётся как `Outer.Nested` (см. раздел 8).

### 7.6. static-импорт

Позволяет использовать статические члены без имени класса:

```java
import static java.lang.Math.*;

double r = sqrt(16) + PI;   // вместо Math.sqrt, Math.PI
```

> Умеренно: частый static-import ухудшает читаемость.

### 7.7. Изменение static через объект

```java
class A { static int x = 0; }
A a = new A();
a.x = 5;                 // компилятор предупредит, но это меняет ОБЩИЙ static
System.out.println(A.x); // 5
```

Работает, но считается плохим стилем — обращайся через `A.x`.

### 7.8. Почему static-метод нельзя переопределить

Потому что привязка происходит **на этапе компиляции** по типу ссылки (static binding). Полиморфизм (runtime) для `static` невозможен — JVM не смотрит на реальный объект.

```java
class A { static void m() { System.out.println("A"); } }
class B extends A { static void m() { System.out.println("B"); } }
A a = new B();
a.m();   // A — тип ссылки, не объекта
```

### 7.9. static в интерфейсах

- `static`-методы интерфейса не наследуются и вызываются через имя интерфейса.
- Поля интерфейса всегда `public static final`.

```java
interface I {
    int VERSION = 1;                       // public static final
    static I create() { return null; }     // вызывается как I.create()
}
```

### 7.10. Типичные ошибки

- Обращаться из static-метода к нестатическому полю → ошибка компиляции.
- Думать, что static-поле своё у каждого объекта.
- Менять static через объект (`obj.x = ...`).
- Ожидать полиморфизма от static-метода.
- Хранить в static глобальное изменяемое состояние (проблемы с тестами и потоками).

### 7.11. Часто спрашивают на собеседовании

- *Можно ли переопределить static?* — Нет, только скрыть.
- *Где живёт static-поле?* — В памяти классов (Metaspace), а не в куче объекта.
- *Почему static-метод не имеет `this`?* — Он не привязан к объекту.
- *Наследуются ли static-методы интерфейса?* — Нет.

## 8. Вложенные классы

### 8.1. Зачем нужны вложенные классы

- **Логическая группировка**: класс нужен только внутри другого.
- **Инкапсуляция**: вложенный класс видит `private` внешнего.
- **Удобство**: «умный» доступ к состоянию внешнего (у inner-классов).

### 8.2. Четыре вида — таблица

| Тип | Синтаксис | Ссылка на внешний экземпляр | Особенности |
|---|---|---|---|
| **Static nested** | `static class N` | нет | как обычный класс внутри другого; доступ к `private` внешнего |
| **Inner (non-static)** | `class I` | да (`Outer.this`) | нельзя создать без экземпляра внешнего; до Java 16 не мог иметь static-члены |
| **Local** | класс внутри метода | да, если метод нестатический | виден только внутри метода |
| **Anonymous** | `new Interface(){...}` | да | без имени, один экземпляр |

### 8.3. Static nested

```java
class Outer {
    private static int secret = 42;
    static class Nested {
        int read() { return secret; }     // доступ к private внешнего
    }
}
Outer.Nested n = new Outer.Nested();      // без объекта Outer
System.out.println(n.read());             // 42
```

### 8.4. Inner (non-static)

```java
class Outer {
    private int x = 1;
    class Inner {
        int read() { return x; }          // Outer.this.x
    }
}
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();    // нужен объект Outer
System.out.println(inner.read());         // 1
```

> Inner-класс хранит **синтетическую ссылку** на внешний объект (`Outer.this`). Это скрытое поле может мешать сериализации и держать внешний объект в памяти (утечки).

### 8.5. Local

```java
void method() {
    class Local {                         // объявлен внутри метода
        void hello() { System.out.println("hi"); }
    }
    new Local().hello();
}
```

Local-класс виден только в пределах метода и может захватывать effectively final локальные переменные.

### 8.6. Anonymous

```java
Runnable r = new Runnable() {            // без имени
    @Override public void run() {
        System.out.println("бегу");
    }
};
r.run();
```

### 8.7. Доступ к private

Все вложенные классы (включая static nested) имеют доступ к `private`-членам внешнего класса — компилятор генерирует синтетические методы-мостики (`access$...`).

### 8.8. Синтетические ссылки

- Inner-класс неявно содержит поле `this$0` — ссылку на внешний объект.
- Компилятор создаёт методы `access$000` для доступа к private.
- Из-за `this$0` inner-класс нельзя создать без внешнего объекта.

```java
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();    // синтаксис создания inner
```

### 8.9. Выбор типа

- Нужен независимый от экземпляра класс → **static nested**.
- Нужен доступ к состоянию конкретного внешнего объекта → **inner**.
- Класс нужен только в одном методе → **local**.
- Реализация «на один раз» → **anonymous** (или лямбда).

### 8.10. Типичные ошибки

- Пытаются создать inner без внешнего объекта.
- Делают inner вместо static nested без необходимости → лишняя ссылка, риск утечки.
- Сериализуют inner-классы → внешний объект тоже должен быть сериализуем.
- Объявляют static-члены в inner-классе (запрещено до Java 16).

### 8.11. Часто спрашивают на собеседовании

- *Разница static nested и inner?* — Inner держит ссылку на внешний объект, static — нет.
- *Зачем вложенные классы?* — Группировка, инкапсуляция, доступ к private.
- *Как создать inner-объект?* — `outer.new Inner()`.

## 9. Анонимные классы

### 9.1. Что это

Анонимный класс — класс **без имени**, объявляемый и создаваемый в одном выражении. Обычно реализует интерфейс или наследует класс «на месте».

### 9.2. Синтаксис

```java
Интерфейс/Класс ссылка = new Интерфейс/Класс(аргументы) {
    // поля, методы, реализация
};
```

Пример с Comparator:

```java
List<String> names = new ArrayList<>(List.of("Боб", "Аня", "Вика"));
names.sort(new Comparator<String>() {
    @Override public int compare(String a, String b) {
        return a.length() - b.length();
    }
});
System.out.println(names);   // [Боб, Аня, Вика]
```

### 9.3. Ограничения

- **Нет конструктора** (класс без имени). Вместо него — instance-блок инициализации.
- Нельзя `extends` и `implements` одновременно — только один тип.
- Может обращаться к `private`-членам внешнего класса.
- Компилируется в файл `Outer$1.class`, `Outer$2.class`, …

```java
Runnable r = new Runnable() {
    { System.out.println("init-блок вместо конструктора"); }
    @Override public void run() { }
};
```

### 9.4. Захват переменных

Анонимный класс может использовать **effectively final** локальные переменные (не изменяемые после инициализации) и любые поля внешнего класса.

```java
String prefix = "-> ";                 // effectively final
Runnable r = new Runnable() {
    @Override public void run() {
        System.out.println(prefix + "run");
    }
};
// prefix = "!!";                       // тогда capture был бы запрещён
```

> Почему effectively final? Локальная переменная живёт в стеке, а объект анонимного класса — в куче. Значение копируется в поле сгенерированного класса, поэтому должно быть неизменным, иначе было бы неясно, какое значение «зафиксировать».

### 9.5. Замена лямбдами (Java 8+)

Если интерфейс функциональный, анонимный класс можно заменить лямбдой:

```java
// было
Comparator<String> byLen = new Comparator<String>() {
    @Override public int compare(String a, String b) { return a.length() - b.length(); }
};
// стало
Comparator<String> byLen2 = (a, b) -> a.length() - b.length();
```

Ещё короче — `Comparator.comparingInt(String::length)`.

### 9.6. Где реально применяют

- Обработчики событий (listeners) в GUI.
- Реализация `Comparator`, `Runnable`, `Callable` «на месте».
- Быстрые тестовые заглушки (mocks) в старом коде.
- Инициализация, требующая состояния до Java 8.

### 9.7. Типичные ошибки

- Пытаются написать конструктор в анонимном классе.
- Меняют захваченную локальную переменную → ошибка компиляции.
- Плодят `$1`, `$2`, `$3` классы, теряя читаемость.
- Используют анонимный класс там, где хватило бы лямбды.

### 9.8. Часто спрашивают на собеседовании

- *Есть ли у анонимного класса конструктор?* — Нет, но есть init-блок.
- *Какие переменные можно захватить?* — effectively final и поля внешнего класса.
- *Как заменить лямбдой?* — Если интерфейс функциональный.
- *В какой файл компилируется?* — `Outer$1.class`.

## 10. Generics

### 10.1. Зачем generics

До Java 5 коллекции хранили `Object`, и приходилось приводить типы вручную — ошибки всплывали в рантайме. Generics (Java 5) дают **типобезопасность на этапе компиляции** и переиспользование кода.

```java
// без generics: ClassCastException в рантайме
List list = new ArrayList();
list.add("hi");
Integer x = (Integer) list.get(0);   // падение

// с generics: ошибка поймана компилятором
List<String> list2 = new ArrayList<>();
list2.add("hi");
// list2.add(5);                      // ошибка компиляции
String s = list2.get(0);              // без приведения
```

### 10.2. Синтаксис

```java
class Box<T> { T value; void set(T v){ value = v; } T get(){ return value; } }

Box<String> b = new Box<>();   // diamond-оператор <>
b.set("hi");
String s = b.get();
```

Можно несколько параметров: `Map<K, V>`, `Pair<A, B>`.

### 10.3. Type erasure (стирание типов)

Компилятор **удаляет** информацию о типе-параметре. В байт-коде `T` превращается в `Object` (или в верхнюю границу, если есть `extends`).

```java
Box<String> и Box<Integer> в рантайме — один и тот же класс Box.
```

**Последствия:**

- Нельзя `new T()` — неизвестно, что создавать.
- Нельзя `new T[]`.
- Нельзя `instanceof T` и `instanceof List<String>` (только `instanceof List`).
- Нельзя перегружать `m(Box<String>)` и `m(Box<Integer>)` — одинаковая стёртая сигнатура.
- Нельзя статическое поле типа `T`.
- Нельзя ловить `catch (T e)`.
- Мосты (bridge methods) генерируются, чтобы полиморфизм работал после стирания.

```java
// Не компилируется:
// class Gen<T> { T instance = new T(); }
// class Gen<T> { static T value; }
// if (x instanceof T) {}
```

### 10.4. Ограничения (bounds)

Ограничение сверху задаёт максимально общий тип:

```java
class NumberBox<T extends Number> {       // T — Number или подтип
    double half(T v) { return v.doubleValue() / 2; }
}
NumberBox<Integer> b = new NumberBox<>();   // OK
// NumberBox<String> s = new NumberBox<>(); // ошибка
```

Несколько границ (только первая может быть классом, остальные — интерфейсы):

```java
<T extends Number & Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
```

### 10.5. Wildcards

- `?` — любой тип.
- `? extends T` — T или **подтип** (ковариантность) — **читаем**.
- `? super T` — T или **надтип** (контравариантность) — **пишем**.

```java
List<? extends Number> src;   // можно читать как Number, писать нельзя (кроме null)
List<? super Integer> dst;    // можно писать Integer, читать только как Object
```

### 10.6. PECS

**P**roducer **E**xtends, **C**onsumer **S**uper:

- Если коллекция **отдаёт** значения (producer) → `? extends T`.
- Если коллекция **принимает** значения (consumer) → `? super T`.

```java
static void copy(List<? extends Number> src, List<? super Number> dst) {
    for (Number n : src) {
        dst.add(n);            // src читаем, dst пишем
    }
}

List<Integer> ints = List.of(1, 2, 3);
List<Number> nums = new ArrayList<>();
copy(ints, nums);
System.out.println(nums);      // [1, 2, 3]
```

Классика — `Collections.copy(dest, src)`.

### 10.7. Инвариантность generics

`List<Object>` **не** является родителем `List<String>`, хотя `Object` — родитель `String`. Generics **инвариантны**.

```java
List<String> strings = new ArrayList<>();
// List<Object> objects = strings;   // ОШИБКА компиляции — это защита!
```

Если бы это разрешили, в список строк можно было бы положить `Integer` и сломать типы. Ковариантность даётся явно через wildcard `? extends`.

### 10.8. Generic-методы

Тип-параметр объявляется перед возвращаемым типом:

```java
static <T> T first(List<T> list) { return list.get(0); }
static <T extends Comparable<T>> T max(List<T> list) { /* ... */ }
```

### 10.9. Типичные ошибки

- `new T()`, `new T[]`, `instanceof T` — не компилируется из-за erasure.
- Путают `? extends` и `? super` (запомни PECS).
- Думают, что `List<String>` можно присвоить в `List<Object>`.
- Перегружают методы, отличающиеся только параметром generic-типа.
- Сырые типы (`List` без параметра) → теряется типобезопасность.

### 10.10. Часто спрашивают на собеседовании

- *Что такое type erasure?* — Стирание типов на компиляции; в рантайме параметр → `Object`/граница.
- *Что такое PECS?* — Producer Extends, Consumer Super.
- *Почему нельзя `new T()`?* — Информация о типе стёрта.
- *Инвариантны ли generics?* — Да; ковариантность через `? extends`.
- *Что такое мостовой метод?* — Синтетический метод для полиморфизма после erasure.

## 11. `enum`

### 11.1. Что это

`enum` — перечисление: класс с **фиксированным** набором констант. Каждая константа — `public static final` экземпляр этого класса.

```java
public enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }
```

### 11.2. Аналогия

Как список дней недели: их ровно семь, других быть не может. Компилятор не даст написать опечатку.

### 11.3. Поля, конструктор, методы

```java
public enum Planet {
    EARTH(5.976e+24, 6.37814e6),
    MARS(6.421e+23, 3.3972e6);

    private final double mass;
    private final double radius;

    Planet(double mass, double radius) {   // конструктор ВСЕГДА private
        this.mass = mass;
        this.radius = radius;
    }

    public double surfaceGravity() {
        return 6.67300E-11 * mass / (radius * radius);
    }
}
System.out.println(Planet.EARTH.surfaceGravity());
```

Конструктор `enum` неявно `private`; указать `public` нельзя.

### 11.4. Что наследует и реализует

- Наследует `java.lang.Enum<E>` (поэтому **нельзя** наследовать другой класс).
- Реализует `Comparable` (порядок по `ordinal()`), `Serializable`.
- Может реализовывать интерфейсы, иметь поля, методы, статические члены.

```java
enum Operation implements Runnable {
    PLUS, MINUS;
    @Override public void run() { System.out.println(name()); }
}
```

### 11.5. Основные методы

| Метод | Что делает |
|---|---|
| `values()` | Массив всех констант (в порядке объявления) |
| `valueOf(String)` | Константа по имени; `IllegalArgumentException`, если нет |
| `name()` | Имя константы как в коде |
| `ordinal()` | Индекс (0-based) |
| `compareTo(...)` | Сравнение по `ordinal()` |

```java
Day[] days = Day.values();               // все 7
Day d = Day.valueOf("MON");              // Day.MON
System.out.println(d.name());            // MON
System.out.println(d.ordinal());         // 0
```

### 11.6. enum как Singleton

Лучший способ реализовать одиночку: JVM гарантирует один экземпляр даже при рефлексии и сериализации.

```java
public enum Singleton {
    INSTANCE;
    public void doWork() { System.out.println("work"); }
}
Singleton.INSTANCE.doWork();
```

### 11.7. EnumSet и EnumMap

Специализированные коллекции на битовых масках — очень быстрые и компактные.

```java
EnumSet<Day> weekend = EnumSet.of(Day.SAT, Day.SUN);
EnumMap<Day, String> plan = new EnumMap<>(Day.class);
plan.put(Day.MON, "работа");
```

### 11.8. enum в switch

```java
switch (day) {
    case MON:
    case TUE: System.out.println("начало недели"); break;
    case SAT:
    case SUN: System.out.println("выходной"); break;
    default:  System.out.println("середина");
}
```

В `switch` по enum имена пишутся **без** `Day.` (`case MON:`), это типобезопасно.

### 11.9. enum с абстрактным методом

Каждая константа реализует метод по-своему:

```java
enum Op {
    ADD { int apply(int a, int b) { return a + b; } },
    MUL { int apply(int a, int b) { return a * b; } };
    abstract int apply(int a, int b);
}
System.out.println(Op.ADD.apply(2, 3));   // 5
```

### 11.10. Типичные ошибки

- Используют `ordinal()` для хранения в БД — при переупорядочивании значения «съедут». Используй `name()` или явный код.
- Пытаются наследовать enum от другого класса — нельзя.
- Пытаются сделать конструктор `public`.
- Забывают, что `valueOf` бросает `IllegalArgumentException` на неизвестное имя.
- Считают, что `values()` возвращает `List` — возвращает **массив**.

### 11.11. Часто спрашивают на собеседовании

- *Можно ли у enum иметь конструктор?* — Да, всегда private.
- *Чем `name()` отличается от `ordinal()`?* — Имя / индекс.
- *Почему enum — лучший singleton?* — Защита от рефлексии и сериализации.
- *Чем EnumMap лучше HashMap?* — Быстрее, компактнее, использует ordinal.

## 12. Comparable vs Comparator

### 12.1. Идея

- **Comparable** — «я знаю, как сравнивать себя с другими» (естественный порядок внутри класса).
- **Comparator** — «внешний судья» сравнивает два объекта (можно много разных порядков, не меняя класс).

### 12.2. Аналогия

- Comparable — рост человека на медосмотре: сравнивается «сам с собой» по встроенному правилу.
- Comparator — разные судьи: один оценивает по росту, другой по весу, третий по имени.

### 12.3. Таблица

| | Comparable | Comparator |
|---|---|---|
| Пакет | `java.lang` | `java.util` |
| Метод | `compareTo(T o)` | `compare(T a, T b)` |
| Где | внутри класса | снаружи |
| Порядков | один (естественный) | сколько угодно |
| Менять класс | нужно | не нужно |
| Сортировка | `Collections.sort(list)` / `list.sort(null)` | `list.sort(cmp)` |
| Когда | «природный» порядок | альтернативные порядки |

### 12.4. Comparable

```java
class Person implements Comparable<Person> {
    String name; int age;
    Person(String name, int age) { this.name = name; this.age = age; }

    @Override
    public int compareTo(Person o) {
        return Integer.compare(this.age, o.age);   // по возрасту
    }
}
List<Person> people = new ArrayList<>(List.of(new Person("Боб", 40), new Person("Аня", 20)));
Collections.sort(people);
```

Возврат: отрицательное (меньше), `0` (равно), положительное (больше).

### 12.5. Comparator и цепочки

```java
Comparator<Person> byName = Comparator
        .comparing(Person::getName)
        .thenComparingInt(Person::getAge)
        .reversed();

people.sort(byName);
```

- `Comparator.comparing(keyExtractor)` — по ключу.
- `thenComparing(...)` — вторичный критерий при равенстве.
- `reversed()` — обратный порядок.
- `Comparator.nullsFirst(...)` / `nullsLast(...)` — обработка `null`.
- `Comparator.naturalOrder()` / `reverseOrder()`.

### 12.6. `Integer.compare` вместо `a - b`

Разность может **переполниться** и дать неверный знак:

```java
int a = Integer.MAX_VALUE, b = -1;
System.out.println(a - b);            // -2147483648 (переполнение!)
System.out.println(Integer.compare(a, b));   // 1 (правильно)
```

Всегда используй `Integer.compare`, `Long.compare`, `Double.compare` (или методы `Comparator`).

### 12.7. Согласованность с `equals`

Сильно рекомендуется: `compareTo == 0` ⇔ `equals == true`. Иначе `TreeSet`/`TreeMap` будут считать «равными» объекты, которые `equals` считает разными (потеря элементов!).

```java
class Bad implements Comparable<Bad> {
    int id;
    @Override public int compareTo(Bad o) { return 0; }   // все «равны»!
}
// TreeSet<Bad> оставит только один элемент
```

### 12.8. Типичные ошибки

- `a - b` вместо `Integer.compare`.
- `compareTo` не согласован с `equals` → баги в `TreeMap`/`TreeSet`.
- Изменяют класс ради второго порядка вместо `Comparator`.
- Забывают про `null` при сортировке.
- Используют вычитание для `long`/`double`.

### 12.9. Часто спрашивают на собеседовании

- *Разница Comparable и Comparator?* — Внутренний/естественный vs внешний/множественный.
- *Почему не `a - b`?* — Переполнение.
- *Обязателен ли Comparator для `Collections.sort`?* — Нет, если класс реализует Comparable.
- *Что будет при несогласованности с equals?* — Проблемы в TreeSet/TreeMap.

## 13. Optional

### 13.1. Зачем

`Optional<T>` — контейнер, который содержит значение или пуст. Его цель — **явно** показать «значение может отсутствовать» и уменьшить число `NullPointerException`.

### 13.2. Аналогия

Как коробка: внутри может быть подарок, а может быть пусто. Прежде чем «достать» — проверяешь, есть ли содержимое. Но не стоит заворачивать в коробки всё подряд.

### 13.3. Создание

```java
Optional<String> full = Optional.of("значение");        // значение обязательно
Optional<String> nullable = Optional.ofNullable(maybeNull); // null → empty
Optional<String> empty = Optional.empty();              // пусто
```

> `Optional.of(null)` → `NullPointerException`.

### 13.4. Основные методы

| Метод | Назначение |
|---|---|
| `isPresent()` / `isEmpty()` | Проверка наличия (Java 11+) |
| `get()` | Достать значение (опасно!) |
| `orElse(T)` | Значение или запасное (запасное вычисляется **всегда**) |
| `orElseGet(Supplier)` | Значение или ленивое запасное |
| `orElseThrow(Supplier)` | Значение или исключение |
| `ifPresent(Consumer)` | Действие, если есть |
| `ifPresentOrElse(...)` | Действие или альтернатива (Java 9+) |
| `map(Function)` | Преобразовать значение |
| `flatMap(Function)` | Преобразовать в другой Optional без вложенности |
| `filter(Predicate)` | Оставить, если подходит |
| `stream()` | Превратить в поток (0 или 1 элемент) |

```java
Optional<User> user = repo.findById(id);
String name = user.map(User::getName).orElse("unknown");
user.ifPresent(u -> System.out.println("Привет, " + u.getName()));
user.orElseThrow(() -> new NotFoundException("нет пользователя"));
```

### 13.5. `map` vs `flatMap`

```java
Optional<String> opt = Optional.of("hi");
Optional<Integer> len = opt.map(String::length);          // Optional<Integer>

Optional<Optional<Integer>> nested = opt.map(s -> Optional.of(s.length()));  // вложенность
Optional<Integer> flat = opt.flatMap(s -> Optional.of(s.length()));          // плоско
```

`flatMap` нужен, когда функция сама возвращает `Optional`.

### 13.6. `orElse` vs `orElseGet`

```java
String a = opt.orElse(expensive());        // expensive() вызывается ВСЕГДА
String b = opt.orElseGet(() -> expensive()); // вызывается только если пусто
```

Если `opt` непустой, `orElse` всё равно выполнит аргумент — иногда это дорого или с побочным эффектом.

### 13.7. Антипаттерны

```java
// 1. get() без проверки
String s = opt.get();                    // риск NoSuchElementException

// 2. isPresent + get — просто вернули null обратно
if (opt.isPresent()) return opt.get();
else return null;

// 3. Optional как поле класса (не Serializable, лишняя обёртка)
class User { Optional<String> name; }    // плохо

// 4. Optional как параметр метода
void save(Optional<String> name) {}      // плохо

// 5. Optional в коллекциях
List<Optional<String>> list;             // плохо
```

Правильно: `Optional` — **только как возвращаемое значение**.

### 13.8. Где нельзя применять

- Поля классов (особенно сериализуемые) — не `Serializable`.
- Параметры методов — усложняет вызов.
- Элементы коллекций.
- Для примитивов в горячем коде без нужды (есть `OptionalInt`, `OptionalLong`, `OptionalDouble`).

### 13.9. Типичные ошибки

- Вызов `get()` без проверки.
- `Optional.of(null)` → NPE.
- Возврат `null` из метода, возвращающего `Optional` (надо `Optional.empty()`).
- Использование `orElse` с дорогим аргументом вместо `orElseGet`.
- Применение `Optional` везде, где достаточно простого `null` внутри приватного метода.

### 13.10. Часто спрашивают на собеседовании

- *Зачем Optional?* — Явно выразить возможное отсутствие значения.
- *Разница `orElse` и `orElseGet`?* — Жадное vs ленивое вычисление.
- *Можно ли хранить Optional в поле?* — Не рекомендуется.
- *Что делает `flatMap`?* — Убирает вложенность `Optional<Optional<T>>`.

## 14. SOLID, YAGNI, KISS, DRY

### 14.1. Зачем принципы

Это «правила гигиены» проектирования: код проще менять, тестировать и понимать. Это не законы, а ориентиры.

### 14.2. SRP — Single Responsibility Principle

**Один класс — одна причина для изменения** (одна ответственность).

Нарушение:

```java
class Report {
    void calculate() { /* бизнес-логика */ }
    void saveToFile() { /* запись в файл */ }
    void print() { /* печать */ }
}
```

Три причины меняться: изменится расчёт, формат файла или способ печати.

Исправление:

```java
class Report { void calculate() { } }
class ReportSaver { void save(Report r) { } }
class ReportPrinter { void print(Report r) { } }
```

### 14.3. OCP — Open/Closed Principle

**Открыт для расширения, закрыт для изменения.** Добавляй поведение новыми классами, а не правкой существующих `if/else`.

Нарушение:

```java
double area(Shape s) {
    if (s.type == CIRCLE) return ...;
    else if (s.type == SQUARE) return ...;   // правка при каждом новом типе
    return 0;
}
```

Исправление:

```java
interface Shape { double area(); }
class Circle implements Shape { public double area() { return Math.PI * r * r; } }
class Square implements Shape { public double area() { return side * side; } }
// новый тип = новый класс, старый код не трогаем
```

### 14.4. LSP — Liskov Substitution Principle

**Наследник должен заменять родителя без сюрпризов.** Не усиливать предусловия, не ослаблять постусловия, не бросать неожиданные исключения.

Нарушение (классика):

```java
class Bird { void fly() { } }
class Penguin extends Bird {
    @Override void fly() { throw new UnsupportedOperationException(); }  // сюрприз!
}
```

Исправление — правильная иерархия:

```java
interface Bird { }
interface FlyingBird extends Bird { void fly(); }
class Sparrow implements FlyingBird { public void fly() { } }
class Penguin implements Bird { }
```

### 14.5. ISP — Interface Segregation Principle

**Много маленьких интерфейсов лучше одного «толстого».** Клиент не должен зависеть от методов, которые не использует.

Нарушение:

```java
interface Worker { void work(); void eat(); void sleep(); }
class Robot implements Worker {
    public void work() {}
    public void eat() {}    // робот не ест — вынужден реализовать заглушку
    public void sleep() {}
}
```

Исправление:

```java
interface Workable { void work(); }
interface Feedable { void eat(); }
interface Sleepable { void sleep(); }
class Robot implements Workable { public void work() {} }
```

### 14.6. DIP — Dependency Inversion Principle

**Зависеть от абстракций, а не от реализаций.** Высокоуровневый код не должен знать конкретные детали.

Нарушение:

```java
class OrderService {
    private MySQLDatabase db = new MySQLDatabase();   // жёсткая привязка
}
```

Исправление:

```java
interface Database { void save(Order o); }
class OrderService {
    private final Database db;
    OrderService(Database db) { this.db = db; }        // внедрение зависимости (DI)
}
```

### 14.7. YAGNI — You Aren't Gonna Need It

**Не пиши функциональность «на будущее».** Она может не понадобиться, а поддерживать её придётся.

Нарушение: метод `saveWithRetryAndCacheAndAudit()`, хотя нужен только `save()`.
Исправление: делай минимум, добавляй по мере реальной необходимости.

### 14.8. KISS — Keep It Simple, Stupid

**Простейшее рабочее решение — лучше.** Сложность — враг сопровождения.

Нарушение: рекурсивная функция с рефлексией для суммирования списка.
Исправление:

```java
int sum = list.stream().mapToInt(Integer::intValue).sum();
```

### 14.9. DRY — Don't Repeat Yourself

**Избегай дублирования знаний.** Одна логика — в одном месте.

Нарушение: одинаковый расчёт налога скопирован в трёх местах; при изменении забудут один.
Исправление: вынеси в метод/класс и вызывай.

> Осторожно: **DRY не про «любой повтор».** Две похожие, но независимые вещи — не дублирование. Преждевременная абстракция хуже копипасты (см. правило трёх).

### 14.10. Как принципы сочетаются

- SOLID — про архитектуру и границы.
- YAGNI/KISS — про объём и сложность.
- DRY — про устранение дублирования знаний.

Часто конфликтуют: DRY тянет к абстракции, KISS — к простоте. Выбор — инженерный компромисс.

### 14.11. Типичные ошибки

- Преждевременная абстракция «на будущее» (YAGNI).
- «Толстые» интерфейсы (ISP).
- Наследование там, где нужно композиция.
- `if/else` вместо полиморфизма (OCP).
- Фанатичный DRY, склеивающий несвязанные вещи.

### 14.12. Часто спрашивают на собеседовании

- *Расшифруй SOLID.* — SRP, OCP, LSP, ISP, DIP.
- *Приведи пример нарушения LSP.* — Квадрат/прямоугольник, пингвин-птица.
- *Что такое DIP?* — Зависимость от абстракций + внедрение зависимостей.
- *Когда DRY вреден?* — Когда объединяет случайно похожий, но независимый код.

## 15. Records (Java 16+)

### 15.1. Что это

`record` — краткий способ объявить **неизменяемый** value-класс. Компилятор сам генерирует весь boilerplate.

```java
public record Point(int x, int y) {}
Point p = new Point(1, 2);
System.out.println(p.x());          // 1 — геттер без get
System.out.println(p);              // Point[x=1, y=2]
```

### 15.2. Что генерирует компилятор

Для `record Point(int x, int y)` автоматически:

- `private final` поля `x`, `y`;
- канонический конструктор `Point(int x, int y)`;
- геттеры `x()` и `y()` (без префикса `get`);
- `equals()` и `hashCode()` (по всем полям);
- `toString()` вида `Point[x=1, y=2]`.

```java
Point a = new Point(1, 2);
Point b = new Point(1, 2);
System.out.println(a.equals(b));   // true
System.out.println(a.hashCode() == b.hashCode()); // true
```

### 15.3. Компактный конструктор

Для валидации/нормализации:

```java
public record Range(int low, int high) {
    Range {                              // компактная форма — без параметров
        if (low > high) {
            throw new IllegalArgumentException("low > high");
        }
    }
}
// new Range(5, 1) -> IllegalArgumentException
```

Присваивание полей компилятор делает сам; можно лишь менять параметры:

```java
public record User(String name) {
    User {
        name = name == null ? "guest" : name.trim();   // нормализация
    }
}
```

### 15.4. Дополнительные методы и статические члены

```java
public record Point(int x, int y) {
    public int sum() { return x + y; }            // обычный метод
    public static Point origin() { return new Point(0, 0); }  // static
}
```

### 15.5. Ограничения

- Поля **всегда final** (immutable-скелет).
- **Нельзя** наследовать класс (record неявно `extends Record`).
- **Можно** реализовывать интерфейсы.
- Нельзя объявлять дополнительные поля экземпляра (только статические).
- Нет сеттеров.
- Нельзя сделать `abstract`.
- Можно переопределить `equals/hashCode/toString` вручную.

```java
public record Named(String name) implements Comparable<Named> {
    public int compareTo(Named o) { return name.compareTo(o.name); }
}
```

### 15.6. `record` и `enum` — неявно final

И `record`, и `enum` нельзя наследовать (они `final` по факту).

### 15.7. Типичные ошибки

- Ждут геттеры `getX()` — у record они называются `x()`.
- Пытаются изменить поле — `final`.
- Пытаются унаследоваться от record.
- Хранят изменяемый объект (`int[]`, `List`) и думают, что record полностью immutable (нужна defensive copy).
- Добавляют поле экземпляра вне заголовка.

### 15.8. Часто спрашивают на собеседовании

- *Что генерирует record?* — Конструктор, геттеры, `equals`, `hashCode`, `toString`.
- *Можно ли наследовать record?* — Нет.
- *Можно ли реализовать интерфейс?* — Да.
- *Что такое компактный конструктор?* — Форма для валидации без повтора параметров.

## 16. Шпаргалка

- **Абстрактный класс** = общая реализация + состояние + конструктор; **интерфейс** = контракт (можно `default`/`static`/`private`, много интерфейсов, но нет состояния).
- **Overload** — compile-time, разные параметры; **override** — runtime, та же сигнатура, ковариантный возврат, доступ не уже, checked-исключения не шире.
- **Java передаёт всё по значению**: примитив — число, объект — копию ссылки (содержимое меняется, переприсваивание — нет).
- **Конструкторы** не наследуются; default появляется только без других; `this()`/`super()` — первой строкой.
- **Порядок инициализации**: static (родитель → ребёнок) → родитель (поля/блоки → конструктор) → ребёнок (поля/блоки → конструктор).
- **Блоки**: static — один раз при загрузке; instance — перед каждым конструктором; ошибка в static → `ExceptionInInitializerError`.
- **Immutable**: final класс, private final поля, без сеттеров, defensive copy, не отдавать изменяемые ссылки.
- **static** — принадлежит классу; не переопределяется, только скрывается; static-метод не имеет `this`.
- **Вложенные**: static nested (без ссылки), inner (`Outer.this`), local (в методе), anonymous (один раз).
- **Анонимные классы** — без имени и конструктора, захват effectively final, заменяются лямбдами.
- **Generics**: type erasure (нельзя `new T()`, `instanceof T`), PECS, инвариантность.
- **enum**: фиксированные константы, private-конструктор, `values`/`valueOf`/`name`/`ordinal`, лучший singleton, `EnumSet`/`EnumMap`.
- **Comparable** — внутри класса, один порядок; **Comparator** — снаружи, много порядков; `Integer.compare` вместо `a-b`.
- **Optional** — только для возврата; `ofNullable`, `map`/`flatMap`, `orElse`/`orElseGet`, `orElseThrow`; не хранить в полях.
- **SOLID**: SRP, OCP, LSP, ISP, DIP; **YAGNI** — не делай лишнего; **KISS** — проще; **DRY** — без дублей (но не фанатично).
- **record**: конструктор, геттеры без `get`, `equals`/`hashCode`/`toString`; final, не наследуется, реализует интерфейсы, компактный конструктор для валидации.

## 17. Частые вопросы на собеседовании с короткими ответами

**ООП и наследование**

1. *Абстрактный класс или интерфейс — что выбрать?* — Интерфейс для контракта/роли; абстрактный класс при общем состоянии и реализации.
2. *Можно ли создать объект абстрактного класса?* — Нет, только наследника.
3. *Есть ли конструктор у абстрактного класса?* — Да, вызывается через `super()`.
4. *Может ли интерфейс иметь поля?* — Только `public static final` константы.
5. *Зачем default-методы?* — Расширять интерфейс, не ломая реализации.

**Overload/override**

6. *Overload vs override?* — Разные параметры/compile-time vs та же сигнатура/runtime.
7. *Можно ли переопределить static?* — Нет, только скрыть.
8. *Что такое ковариантный возврат?* — Наследник возвращает подтип.
9. *Можно ли сузить доступ?* — Нет.
10. *Можно ли расширить checked-исключения?* — Нет.

**Параметры и инициализация**

11. *Java передаёт по ссылке?* — Нет, всегда по значению; объекты — копия ссылки.
12. *Изменит ли метод объект?* — Содержимое да, ссылку — нет.
13. *Порядок инициализации?* — static → родитель → ребёнок.
14. *Когда static-блок?* — Один раз при загрузке класса.
15. *Что если static-блок бросит исключение?* — `ExceptionInInitializerError`.

**Immutable/static/вложенные**

16. *Как сделать immutable?* — final класс, private final поля, без сеттеров, defensive copy.
17. *Почему String immutable?* — Безопасность, кэш hashCode, потокобезопасность.
18. *Можно ли переопределить static-метод?* — Нет.
19. *Разница inner и static nested?* — Inner держит ссылку на внешний объект.
20. *Как создать inner-объект?* — `outer.new Inner()`.

**Generics/enum/сортировка**

21. *Что такое type erasure?* — Стирание типов; в рантайме `T` → `Object`/граница.
22. *Что такое PECS?* — Producer Extends, Consumer Super.
23. *Почему нельзя `new T()`?* — Тип стёрт.
24. *Почему enum — лучший singleton?* — Защита от рефлексии и сериализации.
25. *Comparable vs Comparator?* — Внутри/один порядок vs снаружи/много.
26. *Почему не `a - b`?* — Переполнение; используй `Integer.compare`.

**Optional/принципы/records**

27. *Зачем Optional?* — Явно выразить отсутствие значения.
28. *orElse vs orElseGet?* — Жадное vs ленивое.
29. *Можно ли Optional в поле?* — Не рекомендуется.
30. *Расшифруй SOLID?* — SRP, OCP, LSP, ISP, DIP.
31. *Что такое YAGNI/KISS/DRY?* — Не делай лишнего / проще / без дублей.
32. *Что генерирует record?* — Конструктор, геттеры, `equals`, `hashCode`, `toString`.
33. *Можно ли наследовать record?* — Нет; реализовывать интерфейсы — да.
