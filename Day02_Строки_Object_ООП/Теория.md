## 1. Строки: литерал vs `new String()`, String Pool, `intern()`

### Аналогия из жизни

Представьте библиотеку редких книг. Если вы просите книгу «Война и мир», библиотекарь сначала смотрит в **каталог** (пул): если такая книга уже есть, он выдаёт вам **ту же самую** книгу. Только если её нет — заказывает новую. Так экономится место.

`String Pool` — это и есть такой каталог уникальных строк.

### Что происходит при создании строки

```java
String s1 = "hello";              // литерал -> кладётся в String Pool
String s2 = "hello";              // уже есть в пуле -> та же ссылка
String s3 = new String("hello");  // всегда НОВЫЙ объект в обычной куче (Heap)
String s4 = s3.intern();          // взять канонический объект из пула

System.out.println(s1 == s2);      // true  (одна и та же ссылка)
System.out.println(s1 == s3);      // false (разные объекты)
System.out.println(s1 == s4);      // true  (intern вернул строку из пула)
System.out.println(s1.equals(s3)); // true  (одинаковое содержимое)
```

**Ожидаемый вывод:**
```text
true
false
true
true
```

### Разбор по шагам

1. `String s1 = "hello";` — компилятор кладёт литерал в **пул строк** и возвращает ссылку на него.
2. `String s2 = "hello";` — литерал уже в пуле, поэтому `s2` ссылается на **тот же** объект.
3. `new String("hello")` — принудительно создаёт **новый** объект в куче, даже если такой же уже есть в пуле. Причём сначала создаётся литерал `"hello"` в пуле (он идёт в конструктор), а потом новый объект.
4. `intern()` — метод, который возвращает ссылку из пула. Если строки там нет — добавляет.

### `==` против `equals`

| Оператор | Что сравнивает | Когда использовать |
|---|---|---|
| `==` | **ссылки** (адреса в памяти), для примитивов — значения | только для примитивов и проверки «это тот же объект» |
| `equals` | **содержимое** (логическое равенство) | для всех объектов, включая `String` |

```java
String a = "abc";
String b = new String("abc");

System.out.println(a == b);       // false — разные объекты
System.out.println(a.equals(b));  // true  — одинаковое содержимое
```

> **Правило на всю жизнь:** строки (и любые объекты) сравнивай через `equals`, а не через `==`. Для строк принято писать `"const".equals(variable)`, чтобы не получить `NullPointerException`.

```java
String userInput = null;
// System.out.println(userInput.equals("yes")); // NPE!
System.out.println("yes".equals(userInput));     // false, безопасно
```

### String Pool: важные факты

- Пул строк находится в **Heap** (до Java 7 — в PermGen, с Java 7+ — в обычной куче).
- Литералы интернируются **автоматически** при загрузке класса.
- Строки, полученные во время выполнения (конкатенация, `substring`, чтение файла), **не** попадают в пул автоматически.
- `intern()` можно вызвать вручную, но это стоит денег: поиск/вставка в пул.

```java
String runtime = "he" + "llo"; // это compile-time константа -> "hello" из пула
String dynamic = "he" + new String("llo"); // runtime -> новый объект
System.out.println(runtime == "hello");    // true  (компилятор свернул константы)
System.out.println(dynamic == "hello");    // false (вычислено в runtime)
```

### Когда создаётся объект

| Выражение | Сколько объектов | Где |
|---|---|---|
| `String s = "hi";` | 1 (или 0, если уже был) | Pool |
| `new String("hi");` | 1 новый + литерал в пуле | Heap + Pool |
| `"a" + "b" + "c";` | 1 (компилятор сворачивает) | Pool |
| `s1 + s2` (переменные) | несколько через `StringBuilder` | Heap |

### Типичные ошибки

- ❌ Сравнивать строки через `==`. Работает «случайно» для литералов, ломается для `new` и runtime-строк.
- ❌ Думать, что `intern()` всегда быстрый — на больших объёмах может тормозить.
- ❌ Полагаться, что все строки попадают в пул автоматически.
- ❌ Вызывать `equals` на переменной, которая может быть `null`.

### Часто спрашивают на собеседовании

- **Сколько объектов создаст `String s = new String("abc");`?** — До двух: `"abc"` в пуле (если ещё нет) и новый объект в куче.
- **Зачем нужен `intern()`?** — Чтобы получить единственный канонический экземпляр и сэкономить память / ускорить сравнение ссылок.
- **Где живёт String Pool?** — В куче (Heap); до Java 7 был в PermGen.

## 2. Почему `String` неизменяемый (immutable)

### Аналогия из жизни

Immutable-объект — это как **заламинированный документ**: сколько бы людей ни получили копию ссылки на него, никто не может переписать текст. Значит, все, кто на него смотрит, видят одно и то же.

### Как реализована неизменяемость

1. Класс объявлен `final` — от `String` нельзя унаследоваться и подменить поведение.
2. Массив символов/байтов внутри объявлен `private final` — ссылку нельзя переназначить, доступ снаружи закрыт.
3. Нет методов, меняющих содержимое (все «изменяющие» методы вроде `substring`, `toUpperCase` возвращают **новую** строку).
4. Конструктор копирует входные данные (защитное копирование), чтобы внешний массив нельзя было изменить после создания.

```java
public final class String implements java.io.Serializable,
        Comparable<String>, CharSequence {
    private final byte[] value; // Java 9+
    private final byte coder;   // Java 9+
    private int hash;           // кэш hashCode, ленивый
    // ...
}
```

### 5+ причин неизменяемости

| № | Причина | Пояснение |
|---|---|---|
| 1 | **Безопасность** | Строки используются в путях к файлам, SQL-запросах, загрузке классов, сетевых адресах. Если бы строку можно было изменить после проверки, это была бы дыра в безопасности. |
| 2 | **Кэширование `hashCode`** | Хэш можно посчитать один раз и хранить. `String` — идеальный ключ `HashMap`. |
| 3 | **Потокобезопасность** | Неизменяемый объект можно безопасно разделять между потоками без синхронизации. |
| 4 | **String Pool** | Интернирование возможно только для неизменяемых строк — иначе один поток поменял бы строку у всех. |
| 5 | **Безопасные ключи коллекций** | Если бы ключ менялся, его нельзя было бы найти в `HashMap` после изменения. |
| 6 | **Удобство кэширования и повторного использования** | Один объект можно отдавать во множество мест. |

### Что значит «неизменяемый» на практике

```java
String s = "Hello";
String upper = s.toUpperCase();

System.out.println(s);      // Hello  — оригинал не изменился
System.out.println(upper);  // HELLO  — это новый объект
System.out.println(s == upper); // false
```

### Ловушка: `final` ссылка ≠ immutable объект

```java
final int[] arr = {1, 2, 3};
arr[0] = 99;            // так можно! final запрещает менять ссылку, не содержимое
// arr = new int[5];    // а вот это нельзя — ошибка компиляции

final List<String> list = new ArrayList<>();
list.add("a");          // можно менять содержимое
// list = new ArrayList<>(); // нельзя переприсвоить
```

`String` неизменяем **не только** из-за `final`, а потому что у него нет методов изменения и массив скрыт.

### Типичные ошибки

- ❌ Думать, что `final String` делает строку ещё «более неизменяемой» — она и так неизменяема.
- ❌ Считать, что `final` на массиве/коллекции защищает содержимое.
- ❌ Ожидать, что `s.concat("x")` изменит `s` — он возвращает новый объект.

### Часто спрашивают на собеседовании

- **Почему `String` сделан immutable?** — Безопасность, кэш хэша, потокобезопасность, пул строк, надёжные ключи Map.
- **Можно ли изменить строку через reflection?** — Формально можно (`setAccessible`), но это ломает инварианты и запрещено в Java 17+ для JDK-классов.

## 3. Как устроен `String` внутри: Java 8 vs Java 9+

### Java 8 и раньше

```java
public final class String {
    private final char[] value; // 2 байта на каждый символ (UTF-16)
    private int hash;           // кэш хэш-кода
}
```

`char` в Java — это 2 байта. Значит, даже строка `"abc"` занимала `3 × 2 = 6` байт только под данные. Для латиницы это расточительно.

### Java 9+ (Compact Strings, JEP 254)

```java
public final class String {
    private final byte[] value; // 1 или 2 байта на символ
    private final byte coder;   // LATIN1 или UTF16
    private int hash;
}
```

| Константа | Значение | Когда используется |
|---|---|---|
| `LATIN1` | 0 | все символы ≤ U+00FF (латиница, многие европейские) |
| `UTF16` | 1 | есть хотя бы один символ > U+00FF |

### Аналогия

Раньше под каждый товар выдавали большую коробку (2 байта), даже если товар крошечный. Теперь коробку подбирают по размеру: маленькую (1 байт) или большую (2 байта).

### Выигрыш

- Строки из латиницы занимают **до 2 раз меньше** памяти.
- Меньше памяти → меньше работы GC → быстрее приложение.
- Проверяется кодировка: `coder() == LATIN1`.

### Почему `serialVersionUID` менялся

Внутреннее представление изменилось (`char[]` → `byte[]` + `coder`), поэтому сериализованные в Java 8 строки несовместимы с Java 9+. Это одна из причин, почему сериализацию в Java считают хрупкой.

### Типичные ошибки

- ❌ Считать, что `String` всегда занимает 2 байта на символ — с Java 9 это не так.
- ❌ Полагаться на `value` через reflection — внутренний API может измениться.

### Часто спрашивают на собеседовании

- **Что такое Compact Strings?** — Оптимизация Java 9: `byte[]` + `coder`, латиница хранится по 1 байту.
- **Почему изменился формат сериализации?** — Из-за смены внутреннего представления `String`.

## 4. Unicode, ASCII, code point, UTF-8 и UTF-16

### Аналогия из жизни

- **Unicode** — это как **всемирная телефонная книга символов**: каждому символу дан уникальный номер (code point).
- **Кодировка (UTF-8, UTF-16)** — это **способ записать этот номер в память/файл**.

Один и тот же номер можно записать по-разному. Unicode — «что», кодировка — «как».

### Основные понятия

| Термин | Что это |
|---|---|
| **ASCII** | Старая таблица: 7 бит, 128 символов (латиница, цифры, управляющие). |
| **Unicode** | Стандарт, где каждому символу присвоен **code point** (U+0000 … U+10FFFF). |
| **Code point** | Абстрактный номер символа, например U+0416 = «Ж». |
| **Code unit** | Минимальная единица кодировки: в UTF-8 — 1 байт, в UTF-16 — 2 байта. |
| **BMP** | Basic Multilingual Plane, символы до U+FFFF (влезают в один `char`). |
| **Суррогатная пара** | Два `char` в UTF-16 для символов выше U+FFFF (эмодзи, редкие иероглифы). |

### UTF-8 vs UTF-16

| Параметр | UTF-8 | UTF-16 |
|---|---|---|
| Размер code unit | 1 байт | 2 байта |
| Длина символа | 1–4 байта | 2 или 4 байта |
| ASCII-совместимость | ✅ да | ❌ нет |
| Где используется | веб, файлы, сети | внутреннее представление Java, Windows API |
| Кириллица | 2 байта | 2 байта |

### Суррогатные пары

Символы выше U+FFFF не влезают в один `char` (2 байта). Их кодируют двумя `char`:

```java
String emoji = "😀";                       // U+1F600
System.out.println(emoji.length());         // 2  (два code unit!)
System.out.println(emoji.codePointCount(0, emoji.length())); // 1 (один символ)
System.out.println(emoji.codePointAt(0));   // 128512 (0x1F600)
```

**Ожидаемый вывод:**
```text
2
1
128512
```

### `length()` vs `codePointCount()`

```java
String s = "Привет😀";

System.out.println(s.length());                       // 8 (7 букв + 2 code unit эмодзи = 9? см. ниже)
System.out.println(s.codePointCount(0, s.length()));  // число реальных символов
```

Разбор: `"Привет"` — 6 символов, каждый по 1 code unit в UTF-16, плюс эмодзи = 2 code unit. Итого `length()` = 8, а `codePointCount()` = 7.

> **Правило:** для подсчёта «видимых» символов используй `codePointCount`, а не `length`, если могут быть эмодзи/редкие иероглифы.

### Кодировки при чтении файлов

Никогда не полагайся на «кодировку по умолчанию» — она зависит от системы.

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.io.*;

// Плохо: кодировка по умолчанию
String bad = Files.readString(Path.of("file.txt"));

// Хорошо: явно указываем UTF-8
String good = Files.readString(Path.of("file.txt"), StandardCharsets.UTF_8);

// Чтение через поток с явной кодировкой
try (BufferedReader r = new BufferedReader(
        new InputStreamReader(new FileInputStream("file.txt"), StandardCharsets.UTF_8))) {
    System.out.println(r.readLine());
}
```

### Как не превратить текст в «кракозябры»

1. Читай и пиши **одной и той же** кодировкой (обычно UTF-8).
2. Явно передавай `StandardCharsets.UTF_8`.
3. При работе с консолью Windows учитывай, что по умолчанию может быть cp1251.
4. Строки в Java всегда внутри UTF-16 — проблема только на границе ввода/вывода.

### Типичные ошибки

- ❌ Использовать `length()` для подсчёта символов в тексте с эмодзи.
- ❌ Полагаться на `FileReader` без указания кодировки.
- ❌ Путать Unicode (набор символов) и UTF-8/UTF-16 (кодировки).
- ❌ Обрезать строку по `length()` вслепую — можно разрезать суррогатную пару и получить битый символ.

### Часто спрашивают на собеседовании

- **Сколько байт занимает `char`?** — 2 байта.
- **Почему `"😀".length() == 2`?** — Из-за суррогатной пары: символ вне BMP.
- **Чем Unicode отличается от UTF-8?** — Unicode — стандарт символов, UTF-8 — кодировка.

## 5. `String` vs `StringBuilder` vs `StringBuffer`

### Аналогия из жизни

- **`String`** — бумажный документ: чтобы «дописать» слово, нужно перепечатать весь лист.
- **`StringBuilder`** — блокнот одного автора: пишешь и стираешь быстро, но если два человека пишут одновременно — каша.
- **`StringBuffer`** — блокнот с замком: писать может только один за раз (медленнее, но безопасно).

### Сравнительная таблица

| | `String` | `StringBuilder` | `StringBuffer` |
|---|---|---|---|
| Изменяемость | immutable | mutable | mutable |
| Потокобезопасность | ✅ (immutable) | ❌ нет | ✅ `synchronized` |
| Скорость конкатенации | медленно (новый объект) | быстро | медленнее из-за локов |
| Появился в | Java 1.0 | Java 1.5 | Java 1.0 |
| Наследник | `Object` | `AbstractStringBuilder` | `AbstractStringBuilder` |
| Когда использовать | константы, ключи | однопоточная сборка | многопоточная (редко) |

### Почему конкатенация в цикле — O(n²)

```java
String result = "";
for (int i = 0; i < 10_000; i++) {
    result += i; // каждый раз создаётся НОВАЯ строка и копируется старая
}
```

На шаге `i` копируется `i` символов. Сумма `1 + 2 + ... + n = n²/2` → **O(n²)**.

Правильно:

```java
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10_000; i++) {
    sb.append(i);
}
String result = sb.toString(); // O(n)
```

### Что делает компилятор

Для **простого** выражения компилятор сам подставляет `StringBuilder`:

```java
String s = a + b + c;
// компилятор превращает в:
// String s = new StringBuilder().append(a).append(b).append(c).toString();
```

Но **внутри цикла** каждая итерация получает свой `StringBuilder`, поэтому выигрыша нет — нужно создавать его вручную вне цикла.

### `capacity` и рост буфера

- `StringBuilder` хранит внутренний `char[]`/`byte[]` с запасом — `capacity`.
- По умолчанию `capacity = 16`.
- При переполнении новый размер: `newCapacity = oldCapacity * 2 + 2`.
- `ensureCapacity(n)` заранее расширяет буфер, чтобы избежать лишних копирований.

```java
StringBuilder sb = new StringBuilder();       // capacity = 16
System.out.println(sb.capacity());            // 16
sb.append("1234567890123456");                // ровно 16
System.out.println(sb.capacity());            // 16
sb.append("x");                               // переполнение
System.out.println(sb.capacity());            // 34 = 16*2 + 2

StringBuilder big = new StringBuilder(1000);  // заранее capacity = 1000
```

### `StringBuilder` и `StringBuffer` не `final`

Их можно наследовать, но методы не рассчитаны на переопределение (внутренние вызовы не виртуальные для производительности). Практически наследовать их не нужно.

### Почему `String` final

- Чтобы гарантировать неизменяемость (наследник мог бы добавить изменяющее поведение).
- Чтобы работал String Pool.
- Чтобы кэш `hashCode` был корректным.
- Безопасность.

### Типичные ошибки

- ❌ Конкатенировать строки в цикле через `+=`.
- ❌ Использовать `StringBuffer` там, где нет многопоточности (лишние локи).
- ❌ Забывать `toString()` у `StringBuilder` и удивляться выводу.
- ❌ Создавать `StringBuilder` внутри цикла.

### Часто спрашивают на собеседовании

- **Почему `StringBuilder` быстрее `StringBuffer`?** — Методы `StringBuffer` синхронизированы, `StringBuilder` — нет.
- **Как растёт capacity?** — `old * 2 + 2`.
- **Почему конкатенация в цикле медленная?** — Каждая операция создаёт новый неизменяемый объект → O(n²).

<a id="6"></a>
## 6. Класс `Object` и все его методы

### Аналогия из жизни

`Object` — это **«прародитель всего»** в Java. Каждый класс, даже если вы не пишете `extends`, неявно наследует `Object`. Как у всех людей есть общий предок, так у всех классов есть общие методы.

### Полный список методов `Object`

| Метод | Модификатор | Назначение |
|---|---|---|
| `equals(Object)` | public | Логическое равенство (по умолчанию — сравнение ссылок). |
| `hashCode()` | public native | Хэш-код (по умолчанию — на основе идентичности). |
| `toString()` | public | Строковое представление (`ИмяКласса@hexHash`). |
| `getClass()` | public final native | Возвращает `Class<?>`; **нельзя переопределить**. |
| `clone()` | protected native | Поверхностное копирование. |
| `finalize()` | protected | Вызывается GC перед удалением; **deprecated** с Java 9. |
| `wait()` | public final | Ждать на мониторе; **final**. |
| `wait(long)` | public final | Ждать с таймаутом. |
| `wait(long, int)` | public final | Ждать с таймаутом (нано). |
| `notify()` | public final native | Разбудить один поток; **final**. |
| `notifyAll()` | public final native | Разбудить все потоки; **final**. |
| `registerNatives()` | private static native | Внутренний. |

### `getClass()` — final

```java
class A {}
A a = new A();
System.out.println(a.getClass());        // class A
System.out.println(a.getClass().getName()); // A
```

Переопределить нельзя, потому что это фундамент рефлексии и динамической диспетчеризации.

### `toString()`

По умолчанию:

```java
class User { int id = 1; String name = "Ann"; }

User u = new User();
System.out.println(u); // User@1b6d3586 (примерно)
```

Переопределяем для читаемых логов:

```java
@Override
public String toString() {
    return "User{id=" + id + ", name='" + name + "'}";
}
// Вывод: User{id=1, name='Ann'}
```

### `wait` / `notify` / `notifyAll`

- Все объявлены `final` — их нельзя переопределить.
- Вызывать можно **только** внутри блока `synchronized` на том же объекте, иначе `IllegalMonitorStateException`.

```java
final Object lock = new Object();

Thread waiter = new Thread(() -> {
    synchronized (lock) {
        try {
            lock.wait(); // освобождает монитор и ждёт сигнала
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        System.out.println("Проснулся!");
    }
});

Thread notifier = new Thread(() -> {
    synchronized (lock) {
        lock.notifyAll(); // будим ждущих
    }
});
```

### `finalize()` — устарел

- Не гарантируется, что вызовется.
- Замедляет GC.
- Может «оживить» объект.
- Замены: `try-with-resources`, `java.lang.ref.Cleaner` (Java 9+).

### Зачем переопределять методы `Object`

| Метод | Зачем переопределять |
|---|---|
| `equals` | Сравнение по значению, а не по ссылке. |
| `hashCode` | Чтобы объект корректно работал в `HashMap`/`HashSet`. |
| `toString` | Читаемые логи и отладка. |
| `clone` | Если нужна поддержка копирования. |

### Типичные ошибки

- ❌ Переопределить `equals`, но забыть `hashCode`.
- ❌ Пытаться переопределить `getClass`, `wait`, `notify`.
- ❌ Использовать `finalize` для освобождения ресурсов.

### Часто спрашивают на собеседовании

- **Какие методы `Object` нельзя переопределить?** — `getClass`, `wait`, `notify`, `notifyAll` (они `final`).
- **Что печатает `toString` по умолчанию?** — `ИмяКласса@шестнадцатеричныйХэш`.

<a id="7"></a>
## 7. 4 принципа ООП

### 1. Инкапсуляция

**Аналогия:** банкомат. Вы нажимаете кнопки (публичный интерфейс), но не имеете доступа к сейфу напрямую (приватное состояние).

**Суть:** скрыть внутреннее состояние за публичным интерфейсом, чтобы защитить данные и упростить изменение реализации.

```java
public class BankAccount {
    private long balance; // скрыто

    public long getBalance() { return balance; }

    public void deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount <= 0");
        balance += amount; // контролируемое изменение
    }
}
```

**Что даёт:** целостность данных, возможность менять реализацию без ломания клиентов, читаемость.

### 2. Наследование

**Аналогия:** кот наследует признаки кошачьих (усы, хвост), но добавляет своё.

**Суть:** иерархия «is-a», повторное использование кода.

```java
class Animal {
    void eat() { System.out.println("eat"); }
}

class Dog extends Animal {
    void bark() { System.out.println("woof"); }
}

Dog d = new Dog();
d.eat();   // унаследовано
d.bark();  // своё
```

> **Осторожно:** наследование создаёт сильную связанность. Часто лучше композиция (см. раздел 13).

### 3. Полиморфизм

**Аналогия:** слово «открыть» работает для двери, банки, файла — один интерфейс, разное поведение.

**Виды:**

| Вид | Механизм | Когда решается | Пример |
|---|---|---|---|
| **Compile-time** (статический) | Перегрузка методов (overloading) | на этапе компиляции | `print(int)`, `print(String)` |
| **Runtime** (динамический) | Переопределение (overriding) | во время выполнения | `Animal a = new Dog(); a.speak();` |

```java
class Animal {
    void speak() { System.out.println("..."); }
}
class Cat extends Animal {
    @Override void speak() { System.out.println("meow"); }
}
class Dog extends Animal {
    @Override void speak() { System.out.println("woof"); }
}

Animal a = new Cat();
a.speak(); // meow — решение в runtime
a = new Dog();
a.speak(); // woof
```

**Как работает runtime-полиморфизм:** у каждого объекта есть ссылка на таблицу виртуальных методов (**vtable**). Вызов `a.speak()` идёт по этой таблице и выбирает реализацию фактического типа объекта. Это **dynamic dispatch**.

### 4. Абстракция

**Аналогия:** руль автомобиля. Вы знаете, что поворот руля поворачивает колёса, но не знаете (и не должны) как устроен механизм.

**Суть:** выделить существенное и скрыть сложность. Достигается интерфейсами и абстрактными классами.

```java
interface PaymentMethod {
    void pay(double amount);
}

class CardPayment implements PaymentMethod {
    public void pay(double amount) { System.out.println("Оплата картой: " + amount); }
}

class CashPayment implements PaymentMethod {
    public void pay(double amount) { System.out.println("Оплата наличными: " + amount); }
}
```

Клиенту не важно, как именно проходит оплата — важен контракт `pay`.

### Абстракция vs Инкапсуляция

| | Абстракция | Инкапсуляция |
|---|---|---|
| Что скрывает | сложность, детали предметной области | реализацию и данные |
| Цель | модель «что делает» | защита «как устроено» |
| Инструмент | интерфейсы, абстрактные классы | `private`, геттеры/сеттеры |
| Пример | `List` без знания о `ArrayList` | `private balance` + `deposit()` |

### Типичные ошибки

- ❌ Путать абстракцию и инкапсуляцию.
- ❌ Использовать наследование там, где достаточно композиции.
- ❌ Думать, что перегрузка (overload) — это runtime-полиморфизм (это compile-time).

### Часто спрашивают на собеседовании

- **Чем перегрузка отличается от переопределения?** — Overload — один класс, разные параметры, compile-time; override — иерархия, одинаковая сигнатура, runtime.
- **Как JVM реализует полиморфизм?** — Через vtable и dynamic dispatch.
- **Абстракция и инкапсуляция — одно и то же?** — Нет: первая скрывает сложность, вторая — реализацию/данные.

<a id="8"></a>
## 8. Контракт `equals`

### Аналогия из жизни

`equals` — это вопрос «эти два паспорта описывают одного человека?». `==` — «это физически один и тот же документ?».

### 5 правил контракта (из JavaDoc)

1. **Рефлексивность:** `x.equals(x)` всегда `true`.
2. **Симметричность:** `x.equals(y) == y.equals(x)`.
3. **Транзитивность:** если `x.equals(y)` и `y.equals(z)`, то `x.equals(z)`.
4. **Согласованность:** повторные вызовы дают одинаковый результат, пока объекты не менялись.
5. **Сравнение с `null`:** `x.equals(null)` == `false` и не бросает `NullPointerException`.

### Канонический шаблон

```java
import java.util.Objects;

public class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                          // 1. быстрый путь
        if (o == null || getClass() != o.getClass()) return false; // 2. null и тип
        Person that = (Person) o;                            // 3. приведение
        return age == that.age && Objects.equals(name, that.name); // 4. поля
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, age);
    }
}
```

### `getClass()` vs `instanceof`

| | `getClass() != o.getClass()` | `instanceof` |
|---|---|---|
| Симметричность при наследовании | ✅ сохраняется | ❌ может нарушиться |
| Работа с прокси (Hibernate) | ❌ может сломаться | ✅ обычно работает |
| Стиль | строгий | гибкий |

**Почему `instanceof` может нарушить симметричность:**

```java
class Point { int x, y; /* equals через instanceof */ }
class ColorPoint extends Point { String color; }
```

Если `ColorPoint.equals(Point)` использует `instanceof` и игнорирует цвет, а `Point.equals(ColorPoint)` — тоже, то получим `p.equals(cp) == true`, но `cp.equals(p)` может быть `false`. Симметрия нарушена.

**Вывод:** для классов, которые могут наследоваться, используй `getClass()`. Для `final` value-объектов `instanceof` допустим и удобен.

### Java 16+: pattern matching

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Person p)) return false; // сразу приводим тип
    return age == p.age && Objects.equals(name, p.name);
}
```

### `Objects.equals` и `Objects.hash`

```java
Objects.equals(a, b); // null-safe: если оба null -> true; один null -> false
Objects.hash(name, age); // строит hashCode по полям
```

### Проблема наследования и `equals`

Правило: **нельзя** добавлять значимое поле в подкласс и при этом сохранить контракт `equals`, если родитель уже переопределил `equals` через `instanceof`. Рекомендации:
- предпочитай **композицию** наследованию;
- делай value-классы `final`;
- используй `record` (Java 16+) — `equals`/`hashCode` генерируются автоматически.

### Типичные ошибки

- ❌ Переопределить `equals` без `hashCode`.
- ❌ Использовать `==` внутри `equals` для ссылочных полей.
- ❌ Не проверять `null`.
- ❌ Делать `equals` на изменяемых полях.
- ❌ Использовать `instanceof` там, где нужно `getClass`.

### Часто спрашивают на собеседовании

- **Назовите 5 правил `equals`.** — Рефлексивность, симметричность, транзитивность, согласованность, `false` для `null`.
- **Почему `getClass`, а не `instanceof`?** — Чтобы не нарушить симметричность при наследовании.
- **Что будет, если `equals` вернуть `true` всегда?** — Сломается логика коллекций; контракт рефлексивности формально выполнится, но объекты станут «равны» всем.

<a id="9"></a>
## 9. `hashCode` и его связь с `equals`

### Аналогия из жизни

`hashCode` — это **номер шкафчика** в раздевалке, а `equals` — проверка содержимого. Чтобы найти свою вещь, вы сначала идёте к нужному шкафчику (хэш), затем сверяете содержимое (`equals`). Если два человека с одинаковыми вещами положат их в разные шкафчики — вы найдёте не всё.

### Контракт `hashCode`

1. Если `a.equals(b)`, то `a.hashCode() == b.hashCode()` — **обязательно**.
2. Если `a.equals(b)` ложно, хэши **могут** совпадать (коллизия) — это допустимо.
3. При неизменных данных и одном запуске JVM `hashCode` стабилен.
4. `hashCode` не обязан быть одинаковым между запусками JVM.

### Зачем переопределять вместе

`HashMap`/`HashSet` работают так:
1. По `hashCode` находят «корзину» (bucket).
2. Внутри корзины сравнивают через `equals`.

Если переопределить только `equals`:
- Два «равных» объекта с разными хэшами попадут в разные корзины → `HashSet` будет считать их разными → **дубликаты**.
- `map.get(equalKey)` может не найти значение.

### Пример

```java
import java.util.*;

class BadKey {
    String id;
    BadKey(String id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof BadKey b && Objects.equals(id, b.id);
    }
    // hashCode НЕ переопределён!
}

Set<BadKey> set = new HashSet<>();
set.add(new BadKey("1"));
System.out.println(set.contains(new BadKey("1"))); // false — ОШИБКА!
```

Если добавить `hashCode`, всё заработает:

```java
@Override public int hashCode() { return Objects.hash(id); }
// contains(new BadKey("1")) -> true
```

### Канонический `hashCode`

```java
@Override
public int hashCode() {
    int result = 17;
    result = 31 * result + (name != null ? name.hashCode() : 0);
    result = 31 * result + age;
    return result;
}
```

Или короче:

```java
@Override
public int hashCode() {
    return Objects.hash(name, age);
}
```

### Почему множитель 31

- 31 — **простое** число.
- Нечётное.
- `31 * i == (i << 5) - i` — JVM может оптимизировать умножение на сдвиг и вычитание.
- Исторически даёт хорошее распределение и мало коллизий.

### Можно ли вернуть константу

```java
@Override public int hashCode() { return 42; }
```

Формально контракт выполнен (равные объекты дают равный хэш), **но** все объекты попадают в одну корзину. В `HashMap` Java 8+ при большой цепочке список превращается в дерево (O(log n)), но производительность всё равно сильно падает. Так делать **нельзя**.

### Влияние на `HashMap`/`HashSet`

| Ситуация | Последствие |
|---|---|
| `equals` есть, `hashCode` нет | Дубликаты, «не находится» ключ |
| `hashCode` есть, `equals` нет | Коллизии, но объекты всё равно разные |
| Оба переопределены | Корректная работа |

### Типичные ошибки

- ❌ Изменять поля, участвующие в `hashCode`, после добавления в `HashSet`/`HashMap` — объект «теряется».
- ❌ Возвращать константу.
- ❌ Использовать `hashCode` для сравнения вместо `equals`.
- ❌ Забывать, что `hashCode` не уникален.

### Часто спрашивают на собеседовании

- **Могут ли разные объекты иметь одинаковый `hashCode`?** — Да, это коллизия, она допустима.
- **Почему 31?** — Простое, нечётное, оптимизируется как сдвиг.
- **Что будет, если вернуть константу?** — Все в одну корзину, резкое падение производительности.
- **Почему нельзя менять поля-участники хэша после вставки в Map?** — Хэш изменится, и объект станет ненаходимым.

## 10. `clone()`: поверхностное и глубокое копирование

### Аналогия из жизни

- **Shallow (поверхностное) копирование** — сфотографировать дом снаружи: у копии и оригинала общий подвал (ссылочные поля указывают на один объект).
- **Deep (глубокое) копирование** — построить полностью отдельный дом, включая свой подвал.

### `Object.clone()`

```java
protected native Object clone() throws CloneNotSupportedException;
```

- `protected` — снаружи не вызвать.
- `native` — реализован в JVM.
- Копирует поля побайтово (**shallow**).
- Требует, чтобы класс реализовал маркер `Cloneable`, иначе `CloneNotSupportedException`.

### Shallow copy

```java
class Address {
    String city;
    Address(String city) { this.city = city; }
}

class Person implements Cloneable {
    String name;
    Address address;

    Person(String name, Address address) { this.name = name; this.address = address; }

    @Override
    public Person clone() {
        try {
            return (Person) super.clone(); // shallow: address — та же ссылка!
        } catch (CloneNotSupportedException e) {
            throw new AssertionError();
        }
    }
}

Person p1 = new Person("Ann", new Address("Moscow"));
Person p2 = p1.clone();

p2.address.city = "Kazan";
System.out.println(p1.address.city); // Kazan — изменился и оригинал!
```

### Deep copy

```java
@Override
public Person clone() {
    try {
        Person copy = (Person) super.clone();       // shallow
        copy.address = new Address(this.address.city); // глубокая копия вложенного
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError();
    }
}
```

Теперь `p2.address.city = "Kazan"` не затронет `p1`.

### Конструктор копирования (предпочтительно)

```java
public class Person {
    private final String name;
    private final Address address;

    public Person(Person other) {            // конструктор копирования
        this.name = other.name;
        this.address = new Address(other.address.city);
    }
}
```

### Проблемы дизайна `clone`

1. `Cloneable` — «пустой» интерфейс, не содержит метода `clone`.
2. `clone()` объявлен в `Object` как `protected` — неудобно.
3. Легко получить неполную (shallow) копию по ошибке.
4. Работает в обход конструкторов.
5. Несовместим с `final`-полями в глубоком копировании.

### Альтернативы

| Способ | Тип копии | Плюсы | Минусы |
|---|---|---|---|
| `clone()` | shallow/deep | быстро | сложно, опасно |
| Конструктор копирования | deep | явно, безопасно | много кода |
| Сериализация | deep | универсально | медленно |
| `copy()`-метод / фабрика | любая | гибко | ручной код |

### Типичные ошибки

- ❌ Забыть реализовать `Cloneable` → `CloneNotSupportedException`.
- ❌ Считать `super.clone()` глубокой копией.
- ❌ Не копировать вложенные изменяемые объекты.
- ❌ Делать `clone()` без `@Override` и возвращать `Object`.

### Часто спрашивают на собеседовании

- **Чем shallow отличается от deep?** — При shallow ссылочные поля общие, при deep — полностью независимые.
- **Почему `Cloneable` считается плохим дизайном?** — Нет метода, обход конструкторов, легко ошибиться.
- **Что лучше `clone`?** — Конструктор копирования или статическая фабрика.

<a id="11"></a>
## 11. `final` vs `finally` vs `finalize`

### Аналогия из жизни

Три слова похожи, но значат совершенно разное:
- **`final`** — «запрещено менять/переопределять» (модификатор).
- **`finally`** — «сделай это в любом случае» (блок кода).
- **`finalize`** — «приберись перед уходом» (метод, устарел).

### `final` — все случаи применения

| Где | Что запрещает | Пример |
|---|---|---|
| Переменная | Переприсвоить значение | `final int x = 5;` |
| Поле | Изменить после конструктора | `private final String id;` |
| Метод | Переопределить в наследнике | `public final void run()` |
| Класс | Наследоваться | `public final class String` |
| Параметр метода | Менять внутри метода | `void f(final int x)` |

```java
class Config {
    final int MAX = 100;         // константа экземпляра
    static final int MIN = 1;    // константа класса

    final void show() { }        // нельзя переопределить
}

// class Child extends Config {
//     void show() { }           // ошибка компиляции
// }
```

**Важно:** `final` на ссылке не делает объект неизменяемым:

```java
final List<String> list = new ArrayList<>();
list.add("x");           // можно
// list = new ArrayList<>(); // нельзя
```

**Многопоточность:** поля, объявленные `final`, имеют гарантии видимости — после завершения конструктора их значения видны всем потокам (final field semantics).

### `finally`

- Блок, который выполняется **всегда** после `try`/`catch`.
- Выполняется даже при `return`, `break`, `continue`, исключении.
- **Не выполнится**, если: JVM аварийно завершилась, поток убит, или вызван `System.exit()`.

```java
public static int test() {
    try {
        return 1;
    } finally {
        System.out.println("finally");
    }
}
// Вывод: finally, затем вернётся 1
```

**`return` в `finally` перекрывает `return` из `try`:**

```java
public static int test() {
    try {
        return 1;
    } finally {
        return 2; // ПЛОХО: перекроет return из try
    }
}
// Результат: 2
```

**`System.exit` прерывает `finally`:**

```java
try {
    System.exit(0);
} finally {
    System.out.println("не напечатается");
}
```

**Использование:** закрытие ресурсов. Но современный способ — **try-with-resources**:

```java
try (BufferedReader r = new BufferedReader(new FileReader("f.txt"))) {
    System.out.println(r.readLine());
} catch (IOException e) {
    e.printStackTrace();
}
// close() вызовется автоматически, даже при исключении
```

### `finalize()`

- `protected void finalize()` в `Object`.
- Вызывается сборщиком мусора **перед** удалением объекта.
- **Deprecated** с Java 9.
- **Не гарантирован**: может не вызваться вообще.
- Замедляет GC, может «оживить» объект.
- **Никогда не используй** для освобождения ресурсов.

Замена — `java.lang.ref.Cleaner` (Java 9+):

```java
import java.lang.ref.Cleaner;

public class Resource implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    public Resource() {
        this.cleanable = CLEANER.register(this, () -> System.out.println("Очистка ресурса"));
    }

    @Override public void close() { cleanable.clean(); }
}
```

### Сравнительная таблица

| | `final` | `finally` | `finalize` |
|---|---|---|---|
| Тип | модификатор | блок | метод |
| Назначение | запрет изменения/наследования | гарантированное выполнение | очистка перед GC |
| Актуален | да | да | нет (deprecated) |

### Типичные ошибки

- ❌ `return` внутри `finally` (перекрывает результат и глотает исключения).
- ❌ Использовать `finalize` для закрытия файлов/соединений.
- ❌ Думать, что `final`-объект неизменяем.
- ❌ Писать `final` на локальной переменной в цикле без нужды.

### Часто спрашивают на собеседовании

- **Когда `finally` не выполнится?** — При `System.exit`, падении JVM, убийстве потока.
- **Что делает `return` в `finally`?** — Перекрывает возврат из `try`/`catch`.
- **Почему `finalize` устарел?** — Не гарантирован, вредит GC; вместо него `try-with-resources` и `Cleaner`.

## 12. JavaBeans

### Аналогия из жизни

JavaBean — это как **стандартизированная коробка** с понятными правилами: любой инструмент (Spring, Jackson) заранее знает, как её открыть.

### Требования к JavaBean

1. `public` класс с `public` конструктором **без аргументов**.
2. Все поля `private`.
3. Доступ через геттеры/сеттеры по соглашению.
4. Обычно реализует `Serializable`.
5. Не наследует специальные классы (кроме разрешённых).
6. Может поддерживать события.

### Соглашения именования

| Тип поля | Геттер | Сеттер |
|---|---|---|
| `String name` | `getName()` | `setName(String)` |
| `int age` | `getAge()` | `setAge(int)` |
| `boolean active` | `isActive()` | `setActive(boolean)` |
| `Boolean active` | `getActive()` | `setActive(Boolean)` |

> Для `boolean` (примитива) геттер — `isX()`, для `Boolean` — `getX()`.

### Пример

```java
import java.io.Serializable;

public class UserBean implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private int age;
    private boolean active;

    public UserBean() { } // обязательный конструктор без аргументов

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }

    public boolean isActive() { return active; }
    public void setActive(boolean active) { this.active = active; }
}
```

### Зачем нужны геттеры/сеттеры

- **Инкапсуляция:** поля скрыты.
- **Рефлексия:** фреймворки (Spring, JPA, Jackson, JSP EL) находят свойства через `get`/`is`/`set`.
- **Валидация:** в сеттере можно проверять данные.

```java
public void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("age < 0");
    this.age = age;
}
```

### Сериализация

`Serializable` — маркер. Позволяет сохранить объект в байты и восстановить.

```java
ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("user.ser"));
out.writeObject(user);
out.close();
```

- `serialVersionUID` — версия класса; при несовпадении — `InvalidClassException`.
- `transient` поля не сериализуются.
- `static` поля не сериализуются.

### События

Bean может генерировать события и уведомлять слушателей:

```java
import java.beans.PropertyChangeListener;
import java.beans.PropertyChangeSupport;

public class ModelBean {
    private final PropertyChangeSupport support = new PropertyChangeSupport(this);
    private int value;

    public void addPropertyChangeListener(PropertyChangeListener l) {
        support.addPropertyChangeListener(l);
    }

    public void setValue(int newValue) {
        int old = this.value;
        this.value = newValue;
        support.firePropertyChange("value", old, newValue);
    }
}
```

### `record` как альтернатива

Java 16+:

```java
public record UserDto(String name, int age) { }
// автоматически: конструктор, getName(), age(), equals, hashCode, toString
```

`record` — неизменяемый, лаконичный, но **не** JavaBean (нет конструктора без аргументов и сеттеров).

### Типичные ошибки

- ❌ Нет публичного конструктора без аргументов — фреймворки не смогут создать бин.
- ❌ Геттер `getActive()` для примитивного `boolean` вместо `isActive()`.
- ❌ Публичные поля вместо геттеров/сеттеров.
- ❌ Забыть `serialVersionUID`.

### Часто спрашивают на собеседовании

- **Каковы требования к JavaBean?** — Публичный класс, конструктор без аргументов, приватные поля, get/set, обычно `Serializable`.
- **Чем `record` отличается от бина?** — `record` неизменяем и не имеет сеттеров/пустого конструктора.
- **Зачем `serialVersionUID`?** — Контроль версии при десериализации.

## 13. Ассоциации: агрегация, композиция, наследование

### Аналогия из жизни

- **Ассоциация** — люди знакомы.
- **Агрегация** — команда и игроки: игрок может уйти в другую команду (слабая связь).
- **Композиция** — человек и сердце: сердце не живёт без человека (сильная связь).
- **Наследование** — «собака — это животное» (is-a).

### Виды связей

| Связь | Отношение | UML | Связь | Пример |
|---|---|---|---|---|
| Ассоциация | «знает» | линия | слабая | `Teacher` — `Student` |
| Агрегация | has-a | пустой ромб | слабая | `Car` — `Driver` |
| Композиция | part-of | заполненный ромб | сильная | `Car` — `Engine` |
| Наследование | is-a | пустая стрелка | сильная | `Dog` — `Animal` |

### Агрегация

Часть может существовать независимо от целого. Объект передаётся извне.

```java
class Engine {
    private final String type;
    Engine(String type) { this.type = type; }
    String getType() { return type; }
}

class Car {
    private final Engine engine; // ссылка, но не владеет жизненным циклом
    Car(Engine engine) { this.engine = engine; }
}
```

Здесь `Engine` создаётся снаружи и может использоваться другими объектами.

### Композиция

Часть создаётся и умирает вместе с целым. Целое владеет жизненным циклом.

```java
class Car {
    private final Engine engine = new Engine("V8"); // создаётся внутри
}
```

Если `Car` удаляется, `Engine` тоже больше не нужен.

### Наследование

```java
class Animal { void eat() {} }
class Dog extends Animal { void bark() {} }
```

### «Композиция лучше наследования» (Composition over Inheritance)

**Причины:**

1. **Слабая связанность:** наследник зависит от деталей реализации родителя (хрупкий базовый класс).
2. **Гибкость:** поведение можно менять во время выполнения, подставляя другой объект.
3. **Множественное поведение:** интерфейсы + композиция позволяют комбинировать возможности (в Java нет множественного наследования классов).
4. **Инкапсуляция:** внутренние изменения родителя не ломают наследника.

**Пример проблемы наследования:**

```java
class Bird {
    void fly() { System.out.println("fly"); }
}
class Penguin extends Bird { } // пингвин не летает, но унаследовал fly() — плохо!
```

**Решение через композицию:**

```java
interface FlyBehavior { void fly(); }

class CanFly implements FlyBehavior {
    public void fly() { System.out.println("fly"); }
}
class CannotFly implements FlyBehavior {
    public void fly() { System.out.println("can't fly"); }
}

class Bird {
    private final FlyBehavior flyBehavior;
    Bird(FlyBehavior flyBehavior) { this.flyBehavior = flyBehavior; }
    void fly() { flyBehavior.fly(); }
}

new Bird(new CanFly()).fly();       // fly
new Bird(new CannotFly()).fly();    // can't fly
```

### Когда наследование всё же уместно

- Отношение строго «is-a» и подкласс является полноценным частным случаем.
- Базовый класс спроектирован для наследования (есть документация, шаблонные методы).
- Подкласс не нарушает контракт родителя (принцип Лисков).

### Типичные ошибки

- ❌ Наследовать ради переиспользования кода (не «is-a»).
- ❌ Путать агрегацию и композицию: ключ — **кто владеет жизненным циклом части**.
- ❌ Создавать глубокие иерархии наследования.

### Часто спрашивают на собеседования

- **Чем агрегация отличается от композиции?** — В композиции часть не существует без целого, в агрегации — существует.
- **Почему композиция предпочтительнее наследования?** — Гибкость, слабая связанность, комбинируемость.
- **Как обозначаются на UML?** — Пустой ромб — агрегация, заполненный — композиция.

## 14. Шпаргалка

- **Литералы** → String Pool; `new String()` → Heap; `intern()` → вернуть из пула.
- **`==`** сравнивает ссылки, **`equals`** — содержимое. Строки сравнивай через `equals`.
- **String immutable:** `final` класс, `private final` данные, нет методов изменения. Причины: безопасность, кэш хэша, потоки, пул, ключи Map.
- **Java 8:** `char[] value` + `int hash`. **Java 9+:** `byte[] value` + `byte coder` (Compact Strings).
- **Unicode** — символы, **UTF-8/UTF-16** — кодировки. `char` = 2 байта.
- `"😀".length()` = 2 (суррогатная пара), `codePointCount` = 1.
- **Всегда** указывай кодировку при I/O: `StandardCharsets.UTF_8`.
- **String** immutable, **StringBuilder** быстрый небезопасный, **StringBuffer** синхронизированный.
- Конкатенация в цикле через `+=` → O(n²). Используй `StringBuilder`.
- `capacity` растёт как `old * 2 + 2`; по умолчанию 16.
- **Object:** `equals`, `hashCode`, `toString`, `getClass` (final), `clone`, `finalize` (deprecated), `wait/notify/notifyAll` (final).
- **ООП:** инкапсуляция, наследование, полиморфизм (compile/runtime через vtable), абстракция.
- **equals:** рефлексивность, симметричность, транзитивность, согласованность, `false` для `null`.
- **equals + hashCode** переопределяй вместе. Множитель **31**. Константа — плохо.
- **clone:** shallow по умолчанию, нужен `Cloneable`, лучше конструктор копирования.
- **final** — запрет; **finally** — всегда; **finalize** — deprecated, используй `Cleaner`/try-with-resources.
- **JavaBean:** публичный класс, конструктор без аргументов, приватные поля, get/is/set, Serializable.
- **Агрегация** — слабая (пустой ромб), **композиция** — сильная (заполненный ромб).
- **Композиция лучше наследования** — гибкость и слабая связанность.

## 15. Частые вопросы на собеседовании с короткими ответами

**1. Чем `==` отличается от `equals`?**
`==` сравнивает ссылки (или значения примитивов), `equals` — содержимое объектов.

**2. Сколько объектов создаёт `new String("abc")`?**
До двух: литерал `"abc"` в пуле (если ещё нет) и новый объект в куче.

**3. Почему `String` immutable?**
Безопасность, кэширование `hashCode`, потокобезопасность, работа String Pool, надёжные ключи коллекций.

**4. Что такое Compact Strings?**
Оптимизация Java 9: `byte[]` + `coder`; латиница хранится по 1 байту, остальное — по 2.

**5. Почему `"😀".length()` равно 2?**
Эмодзи вне BMP кодируется суррогатной парой из двух `char`.

**6. `StringBuilder` vs `StringBuffer`?**
`StringBuilder` быстрее и не потокобезопасен; `StringBuffer` синхронизирован и медленнее.

**7. Почему конкатенация в цикле медленная?**
Каждая операция создаёт новую строку и копирует старую → O(n²).

**8. Какие методы `Object` нельзя переопределить?**
`getClass`, `wait`, `notify`, `notifyAll` (они `final`).

**9. Назовите правила `equals`.**
Рефлексивность, симметричность, транзитивность, согласованность, `false` для `null`.

**10. Почему `equals` и `hashCode` переопределяют вместе?**
Коллекции ищут объект по хэшу, затем сравнивают через `equals`; иначе дубликаты и «не находится» ключ.

**11. Почему множитель 31?**
Простое, нечётное число; `31 * i == (i << 5) - i`, меньше коллизий.

**12. Что будет, если `hashCode` вернёт константу?**
Контракт выполнен, но все объекты в одной корзине → резкое падение производительности.

**13. Чем shallow copy отличается от deep?**
Shallow копирует ссылки (вложенные объекты общие), deep — создаёт независимые копии вложенных объектов.

**14. Почему `Cloneable` считают плохим дизайном?**
Пустой интерфейс без метода `clone`, обход конструкторов, легко ошибиться. Лучше конструктор копирования.

**15. Когда `finally` не выполнится?**
При `System.exit`, аварийном завершении JVM, убийстве потока.

**16. Что делает `return` в `finally`?**
Перекрывает возврат из `try`/`catch` — так писать нельзя.

**17. Почему `finalize` устарел?**
Не гарантирован, вредит производительности GC. Замены: try-with-resources, `Cleaner`.

**18. Требования к JavaBean?**
Публичный класс, конструктор без аргументов, приватные поля, get/is/set, обычно `Serializable`.

**19. Агрегация vs композиция?**
Агрегация — часть живёт независимо (пустой ромб); композиция — часть умирает с целым (заполненный ромб).

**20. Почему композиция лучше наследования?**
Слабая связанность, гибкость, возможность менять поведение в runtime, комбинирование через интерфейсы.

**21. Чем абстракция отличается от инкапсуляции?**
Абстракция скрывает сложность и моделирует «что делает», инкапсуляция скрывает данные и реализацию.

**22. Как JVM реализует runtime-полиморфизм?**
Через таблицу виртуальных методов (vtable) и dynamic dispatch.

**23. Где хранится String Pool?**
В куче (Heap); до Java 7 — в PermGen.

**24. Всегда ли `s1 + s2` создаёт новый объект?**
Для переменных — да (через `StringBuilder`); для констант компилятор сворачивает на этапе компиляции.

**25. Можно ли изменить `final`-коллекцию?**
Да, можно менять содержимое; `final` запрещает только переприсвоить ссылку.
