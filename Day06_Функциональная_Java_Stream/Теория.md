## 1. Функциональный интерфейс: SAM и @FunctionalInterface

### Простыми словами

**Функциональный интерфейс** — это интерфейс, в котором ровно **один абстрактный метод**. Английская аббревиатура — **SAM** (Single Abstract Method, «единственный абстрактный метод»).

Почему это так важно? Потому что именно к функциональному интерфейсу можно «приклеить» лямбду или ссылку на метод. Лямбда — это не отдельный тип. Это сокращённая запись реализации **одного** метода. Если методов два — непонятно, какой из них реализует лямбда, поэтому язык запрещает.

### Аналогия из жизни

Представьте бланк с **одним пустым полем** «Что сделать?». В это поле вы можете вписать любое действие. Если полей было бы два, вы бы запутались, что писать в каждое. Функциональный интерфейс — это такой бланк с ровно одним полем. Лямбда — это то, что вы вписываете в поле.

### Правила

- Ровно **один** абстрактный метод.
- `default`- и `static`-методов может быть **сколько угодно** — они не абстрактные.
- Методы `Object` (`equals`, `hashCode`, `toString`) **не считаются** абстрактными для этого правила.
- Аннотация `@FunctionalInterface` **не обязательна**, но она заставляет компилятор проверить, что метод действительно один. Это защита от случайного добавления второго метода.

```java
@FunctionalInterface
interface Calculator {
    int calc(int a, int b);          // единственный абстрактный метод

    default int twice(int a) {       // default не мешает
        return calc(a, a);
    }

    static Calculator add() {        // static не мешает
        return (a, b) -> a + b;
    }
}
```

```java
public class Demo {
    public static void main(String[] args) {
        Calculator add = (a, b) -> a + b;   // лямбда реализует calc
        Calculator mul = (a, b) -> a * b;

        System.out.println(add.calc(2, 3));   // 5
        System.out.println(mul.calc(2, 3));   // 6
        System.out.println(add.twice(5));     // 10 — default вызывает calc(5,5)
        System.out.println(Calculator.add().calc(7, 8)); // 15 — static
    }
}
```

Ожидаемый вывод:

```
5
6
10
15
```

### Примеры функциональных интерфейсов из JDK

| Интерфейс | Метод | Где встречается |
|---|---|---|
| `Runnable` | `void run()` | потоки, `new Thread(...)`, `ExecutorService` |
| `Callable<V>` | `V call() throws Exception` | возвращает результат, умеет бросать checked-исключения |
| `Comparator<T>` | `int compare(T a, T b)` | сортировка, `sorted()` |
| `ActionListener` | `void actionPerformed(ActionEvent e)` | Swing-кнопки |
| `Consumer<T>` | `void accept(T)` | `forEach` |
| `Predicate<T>` | `boolean test(T)` | `filter` |
| `Function<T,R>` | `R apply(T)` | `map` |

Важное отличие `Runnable` и `Callable`:

```java
Runnable r = () -> System.out.println("работаю");
Callable<Integer> c = () -> 42;   // может вернуть значение и бросить исключение

r.run();                          // работаю
try {
    System.out.println(c.call()); // 42
} catch (Exception e) {
    e.printStackTrace();
}
```

### Типичные ошибки

- **Добавить второй абстрактный метод** и удивиться, что лямбда не компилируется.
- Думать, что `@FunctionalInterface` обязательна. Нет — это лишь проверка.
- Считать, что интерфейс без методов функциональный. Нет: нужен ровно один абстрактный.
- Забыть, что методы `Object` не считаются: интерфейс с `boolean equals(Object)` и одним своим методом — всё ещё функциональный.

### Часто спрашивают на собеседовании

- **Что такое функциональный интерфейс?** Интерфейс с одним абстрактным методом.
- **Зачем @FunctionalInterface?** Документация + проверка компилятора.
- **Можно ли унаследовать один функциональный интерфейс от другого?** Да, если итоговый набор абстрактных методов остаётся одним. Если добавляется новый абстрактный метод — уже нет.
- **Чем Callable отличается от Runnable?** `Callable` возвращает значение и может бросать исключения, `Runnable` — нет.

## 2. java.util.function: полный разбор

Пакет `java.util.function` — это готовый «набор отверток» под любые задачи. Запоминать все не нужно, но 4 базовых и их родственников знать обязательно.

### 2.1. Четыре базовых интерфейса

| Интерфейс | Сигнатура | Смысл | Аналогия |
|---|---|---|---|
| `Function<T,R>` | `R apply(T t)` | превратить T в R | перевод текста на другой язык |
| `Supplier<T>` | `T get()` | отдать значение, ничего не принимая | кулер с водой: нажал — получил |
| `Consumer<T>` | `void accept(T t)` | принять и что-то сделать, ничего не вернуть | мусорка: бросил и забыл |
| `Predicate<T>` | `boolean test(T t)` | проверить условие | турникет: пропустить или нет |

```java
import java.util.function.*;

public class Basics {
    public static void main(String[] args) {
        Function<String, Integer> length = s -> s.length();
        Supplier<String> greeting = () -> "Привет";
        Consumer<String> printer = s -> System.out.println(">> " + s);
        Predicate<Integer> isEven = n -> n % 2 == 0;

        System.out.println(length.apply("Java"));  // 4
        System.out.println(greeting.get());        // Привет
        printer.accept("мир");                      // >> мир
        System.out.println(isEven.test(10));       // true
        System.out.println(isEven.test(7));        // false
    }
}
```

### 2.2. Двухаргументные (Bi) варианты

| Интерфейс | Сигнатура | Смысл |
|---|---|---|
| `BiFunction<T,U,R>` | `R apply(T t, U u)` | два входа — один выход |
| `BiConsumer<T,U>` | `void accept(T t, U u)` | два входа — ничего |
| `BiPredicate<T,U>` | `boolean test(T t, U u)` | два входа — boolean |
| `BinaryOperator<T>` | `T apply(T a, T b)` | два одинаковых входа — один выход |

```java
BiFunction<Integer, Integer, Integer> add = (a, b) -> a + b;
BiConsumer<String, Integer> print = (name, age) -> System.out.println(name + ": " + age);
BiPredicate<String, Integer> longerThan = (s, n) -> s.length() > n;

System.out.println(add.apply(3, 4));          // 7
print.accept("Аня", 25);                       // Аня: 25
System.out.println(longerThan.test("Java", 3));// true
```

### 2.3. Операторы: Unary и Binary

`UnaryOperator<T>` — это `Function<T,T>`, то есть вход и выход одного типа. `BinaryOperator<T>` — это `BiFunction<T,T,T>`.

```java
UnaryOperator<String> upper = s -> s.toUpperCase();
BinaryOperator<Integer> max = (a, b) -> a > b ? a : b;

System.out.println(upper.apply("java")); // JAVA
System.out.println(max.apply(3, 9));     // 9
```

Их удобно передавать в `Stream.reduce`, `Stream.iterate` и `Collectors.reducing`.

### 2.4. Примитивные специализации (зачем они нужны)

Проблема: дженерики в Java не работают с примитивами. Если вы пишете `Function<Integer, Integer>`, то на каждом вызове происходят **boxing/unboxing** (`int` ↔ `Integer`) и создаётся мусор для сборщика. Для горячего кода это дорого.

Решение: отдельные интерфейсы под `int`, `long`, `double`:

| Обычный | Примитивная специализация |
|---|---|
| `Function<T,R>` | `IntFunction<R>`, `LongFunction<R>`, `DoubleFunction<R>` |
| `Function<T,R>` (возврат int) | `ToIntFunction<T>`, `ToLongFunction<T>`, `ToDoubleFunction<T>` |
| `BiFunction` (возврат int) | `ToIntBiFunction<T,U>` и т.д. |
| `UnaryOperator<T>` | `IntUnaryOperator`, `LongUnaryOperator`, `DoubleUnaryOperator` |
| `BinaryOperator<T>` | `IntBinaryOperator`, `LongBinaryOperator`, `DoubleBinaryOperator` |
| `Predicate<T>` | `IntPredicate`, `LongPredicate`, `DoublePredicate` |
| `Supplier<T>` | `IntSupplier`, `LongSupplier`, `DoubleSupplier` |
| `Consumer<T>` | `IntConsumer`, `LongConsumer`, `DoubleConsumer` |

```java
IntFunction<String> label = i -> "число " + i;   // int -> String, без боксинга входа
ToIntFunction<String> len = String::length;        // String -> int, без боксинга выхода
IntPredicate positive = n -> n > 0;
IntUnaryOperator square = n -> n * n;

System.out.println(label.apply(5));    // число 5
System.out.println(len.applyAsInt("abc")); // 3
System.out.println(positive.test(-1)); // false
System.out.println(square.applyAsInt(4)); // 16
```

Обратите внимание: у примитивных специализаций имена методов отличаются — `applyAsInt`, `test`, `getAsInt`, `accept` — чтобы компилятор не путался с обычными.

### 2.5. Полезные default-методы этих интерфейсов

Функциональные интерфейсы умеют **комбинироваться**:

```java
Function<Integer, Integer> plus1 = x -> x + 1;
Function<Integer, Integer> times2 = x -> x * 2;

// andThen: сначала plus1, потом times2
System.out.println(plus1.andThen(times2).apply(3)); // (3+1)*2 = 8

// compose: сначала times2, потом plus1
System.out.println(plus1.compose(times2).apply(3)); // (3*2)+1 = 7

Predicate<Integer> even = n -> n % 2 == 0;
Predicate<Integer> positive = n -> n > 0;
System.out.println(even.and(positive).test(4));   // true
System.out.println(even.or(positive).test(-2));   // true (чётное)
System.out.println(even.negate().test(3));        // true

Consumer<String> a = s -> System.out.print("A" + s);
Consumer<String> b = s -> System.out.print("B" + s);
a.andThen(b).accept("x");  // AxBx
```

Запомните разницу:

- `andThen` — «сделай меня, потом следующего» (я первый).
- `compose` — «сделай сначала его, потом меня» (я второй).
- `and`/`or`/`negate` — логические комбинации предикатов.

### Типичные ошибки

- Писать `Function<int,int>` — так нельзя, дженерики не принимают примитивы. Нужны специализации.
- Путать `andThen` и `compose` (порядок применения).
- Использовать `Consumer` там, где нужен возврат значения (и наоборот).
- Забыть, что `Supplier` **ленивый**: код внутри выполнится только при вызове `get()`.

### Часто спрашивают на собеседовании

- **Чем `UnaryOperator` отличается от `Function`?** `UnaryOperator<T>` — это `Function<T,T>` (один тип).
- **Зачем примитивные специализации?** Избежать боксинга и лишних аллокаций.
- **Разница `andThen` и `compose`?** Порядок вызовов.
- **Что такое `Supplier`?** Поставщик значения без аргументов, часто ленивый.

## 3. default и static методы интерфейсов

### 3.1. Зачем появились default-методы

До Java 8 интерфейс мог содержать только абстрактные методы. Это создавало проблему: если добавить метод в интерфейс, **все** существующие реализации перестанут компилироваться. А в JDK есть миллионы чужих реализаций.

Решение — `default`-метод: метод с готовой реализацией прямо в интерфейсе. Классы могут его не переопределять.

Именно так в Java 8 добавили в `Collection` метод `stream()`, не сломав весь существующий код.

### Аналогия из жизни

Интерфейс — это договор. Раньше в договор можно было добавить только новый пункт-обязательство, и все подписанты обязаны были его выполнить. `default`-метод — это «пункт по умолчанию»: если у подписанта нет своего мнения, применяется стандартное поведение.

### 3.2. Синтаксис

```java
interface Greeter {
    void greet(String name);                       // абстрактный

    default void greetLoud(String name) {          // реализация по умолчанию
        System.out.println(greetText(name).toUpperCase());
    }

    static Greeter english() {                     // утилита, вызывается через Greeter.english()
        return name -> System.out.println("Hello, " + name);
    }

    private String greetText(String name) {        // Java 9+: приватный вспомогательный
        return "Hi, " + name;
    }
}
```

```java
public class Demo {
    public static void main(String[] args) {
        Greeter g = name -> System.out.println("Привет, " + name);
        g.greet("Аня");        // Привет, Аня
        g.greetLoud("Аня");    // HI, АНЯ

        Greeter.english().greet("Bob"); // Hello, Bob
    }
}
```

### 3.3. static-методы в интерфейсе

- Вызываются только через имя интерфейса: `Greeter.english()`.
- **Не наследуются** реализующими классами (в отличие от default).
- Часто используются как фабрики: `Comparator.comparing(...)`, `Stream.of(...)`.

```java
Comparator<String> byLen = Comparator.comparingInt(String::length);
Comparator<String> byLenDesc = byLen.reversed(); // default-метод reversed
```

### 3.4. Конфликты default-методов

Java не поддерживает множественное наследование классов, но класс может реализовать несколько интерфейсов. Если два интерфейса имеют одинаковый default-метод — возникает конфликт, и **компилятор заставит** вас разрешить его явно.

```java
interface A {
    default String hello() { return "A"; }
}
interface B {
    default String hello() { return "B"; }
}

class C implements A, B {
    @Override
    public String hello() {
        return A.super.hello() + B.super.hello(); // явно указываем, что взять
    }
}
```

```java
System.out.println(new C().hello()); // AB
```

Правила разрешения конфликтов (по приоритету):

1. Метод из **класса** (или суперкласса) всегда побеждает default-метод интерфейса.
2. Если конфликтуют два интерфейса — нужен явный выбор через `A.super.method()`.
3. Более конкретный интерфейс (наследник) побеждает менее конкретный.

### 3.5. private-методы (Java 9)

Зачем: чтобы вынести общую логику нескольких `default`-методов, не делая её публичной. До Java 9 приходилось либо дублировать код, либо создавать отдельный утилитный класс.

```java
interface Validator {
    default boolean validName(String s) {
        return notBlank(s) && s.length() <= 50;
    }
    default boolean validCity(String s) {
        return notBlank(s);
    }
    private boolean notBlank(String s) {   // скрыт от внешнего мира
        return s != null && !s.isBlank();
    }
}
```

Приватный метод интерфейса **не является** абстрактным и не мешает интерфейсу быть функциональным.

### Типичные ошибки

- Пытаться вызвать static-метод интерфейса через экземпляр: `g.english()` — ошибка.
- Думать, что default-метод можно сделать `final` — нельзя.
- Забыть разрешить конфликт двух default-методов.
- Считать, что `private`-метод нарушает «функциональность» интерфейса. Не нарушает.

### Часто спрашивают на собеседовании

- **Зачем default-методы?** Обратная совместимость при эволюции интерфейсов.
- **Как разрешить конфликт default-методов?** Явно переопределить и вызвать `A.super.m()`.
- **Наследуются ли static-методы интерфейса?** Нет.
- **Что нового в Java 9 про интерфейсы?** `private` и `private static` методы.

## 4. Лямбда-выражения

### 4.1. Что это такое

**Лямбда-выражение** — это короткая запись реализации функционального интерфейса. Она позволяет передавать «кусок поведения» как аргумент метода.

### Аналогия из жизни

Раньше, чтобы поручить кому-то работу, вы писали целый класс-исполнителя (анонимный класс). Лямбда — это как записка: «сделай вот это». Коротко, по делу, без лишней бюрократии.

### 4.2. Все формы синтаксиса

```java
// 1. Полный синтаксис с типами
Function<Integer, Integer> f1 = (Integer x) -> x * x;

// 2. Типы выводятся компилятором
Function<Integer, Integer> f2 = (x) -> x * x;

// 3. Один параметр — скобки можно опустить
Function<Integer, Integer> f3 = x -> x * x;

// 4. Без параметров — пустые скобки
Supplier<String> s1 = () -> "привет";

// 5. Тело-выражение (неявный return)
Function<Integer, Integer> f4 = x -> x + 1;

// 6. Тело-блок (нужен явный return, если есть результат)
Function<Integer, Integer> f5 = x -> {
    int y = x + 1;
    return y * 2;
};

// 7. Несколько параметров
BiFunction<Integer, Integer, Integer> f6 = (a, b) -> a + b;

// 8. Многострочный блок с побочными эффектами
Consumer<String> c1 = msg -> {
    System.out.println("Начинаю");
    System.out.println(msg);
    System.out.println("Готово");
};
```

Правило простое: если в блоке `{ }` есть результат — нужен `return`. Если тело без скобок — `return` не пишется (это выражение).

### 4.3. Лямбда vs анонимный класс

```java
// Анонимный класс (Java 7-)
Runnable r1 = new Runnable() {
    @Override
    public void run() {
        System.out.println("старый стиль");
    }
};

// Лямбда (Java 8+)
Runnable r2 = () -> System.out.println("новый стиль");
```

Лямбда короче, но это **не просто синтаксический сахар** над анонимным классом. Под капотом работают разные механизмы.

### 4.4. Как это работает под капотом: invokedynamic и LambdaMetafactory

- Анонимный класс компилируется в отдельный `.class`-файл (`Demo$1.class`). Каждое создание объекта — это `new`, аллокация, загрузка класса.
- Лямбда **не создаёт отдельный класс** на этапе компиляции. Компилятор вставляет инструкцию байт-кода `invokedynamic` со ссылкой на `LambdaMetafactory`.
- При первом исполнении `LambdaMetafactory` динамически «фабрикует» реализацию интерфейса (обычно через `MethodHandle`). Результат кэшируется, поэтому последующие создания лямбд дешёвые.

```
// Упрощённо:
invokedynamic #bootstrap -> LambdaMetafactory.metafactory(...)
```

Практические следствия:

- Лямбда, не захватывающая контекст, может быть закэширована и переиспользована (один экземпляр).
- Лямбда, захватывающая переменные, при каждом создании получает новый объект с этими значениями.
- Анонимный класс всегда создаёт новый объект.

Это популярный вопрос на собеседовании: **«Что генерирует компилятор для лямбды?»** — Ответ: `invokedynamic` + `LambdaMetafactory`, а не анонимный класс.

### 4.5. Замыкания и effectively final

**Замыкание** — это функция, которая «запоминает» переменные из места, где она создана.

Лямбда может читать локальные переменные окружающего метода, но только если они **effectively final** — то есть фактически не меняются после инициализации (даже если ключевого слова `final` нет).

```java
public class Closure {
    public static void main(String[] args) {
        int base = 10;                        // effectively final
        Function<Integer, Integer> add = x -> x + base;
        System.out.println(add.apply(5));     // 15

        // base = 20;  // если раскомментировать — ошибка компиляции
    }
}
```

Если попытаться изменить `base` после лямбды, компилятор скажет: *variable used in lambda expression should be final or effectively final*.

**Почему так?** Лямбда захватывает **значение** переменной (копию), а не саму изменяемую ячейку памяти. Если бы переменная менялась, возникла бы неоднозначность: какое значение должна видеть лямбда, особенно если она выполняется в другом потоке позже.

```java
// Классический запрещённый пример:
int sum = 0;
list.forEach(x -> sum += x);   // ошибка: sum не effectively final
```

Как обойти, если очень нужно накапливать:

```java
// Вариант 1: массив (элемент массива менять можно)
int[] sum = {0};
list.forEach(x -> sum[0] += x);
System.out.println(sum[0]);

// Вариант 2: AtomicInteger (потокобезопасно)
AtomicInteger total = new AtomicInteger();
list.forEach(total::addAndGet);

// Вариант 3 (правильный): reduce/collect вместо побочного эффекта
int result = list.stream().reduce(0, Integer::sum);
```

### 4.6. Поля объекта vs локальные переменные

Локальные переменные должны быть effectively final. А **поля объекта** — можно менять свободно, потому что захватывается ссылка на `this`, а не значение поля.

```java
class Counter {
    private int count = 0;              // поле

    void run() {
        Runnable r = () -> count++;     // так можно — меняем поле
        r.run();
        System.out.println(count);      // 1
    }
}
```

### 4.7. this внутри лямбды vs анонимного класса

Это ключевое отличие!

- В **анонимном классе** `this` указывает на **сам анонимный объект**.
- В **лямбде** `this` указывает на **внешний объект**, в котором лямбда определена. Лямбда не создаёт свою «область видимости this».

```java
public class ThisDemo {
    String name = "внешний";

    void test() {
        Runnable anon = new Runnable() {
            String name = "анонимный";
            @Override
            public void run() {
                System.out.println(this.name);   // анонимный
            }
        };

        Runnable lambda = () -> System.out.println(this.name); // внешний

        anon.run();    // анонимный
        lambda.run();  // внешний
    }

    public static void main(String[] args) {
        new ThisDemo().test();
    }
}
```

Почему так: лямбда — это не новый объект-класс, а просто код внутри метода, поэтому `this` остаётся тем же.

### 4.8. Лямбда не может менять состояние сама по себе

Лямбда должна быть **stateless** (без внутреннего изменяемого состояния), особенно в стримах. Если лямбда что-то меняет снаружи — это **side effect** (побочный эффект), и в параллельных стримах он приводит к гонкам.

### Типичные ошибки

- Менять захваченную локальную переменную — ошибка компиляции.
- Думать, что лямбда — это объект анонимного класса.
- Использовать `this` в лямбде, ожидая анонимный объект.
- Делать побочные эффекты в `map`/`filter` (особенно в параллельных стримах).
- Забыть `return` в блочной лямбде.

### Часто спрашивают на собеседовании

- **Что такое effectively final?** Переменная, которая не меняется после присваивания.
- **Почему нельзя менять захваченную переменную?** Захватывается значение, а не ячейка.
- **Чем `this` в лямбде отличается от анонимного класса?** В лямбде `this` — внешний объект.
- **Что генерирует компилятор для лямбды?** `invokedynamic` + `LambdaMetafactory`.

## 5. Ссылки на методы (Method references)

### 5.1. Идея

**Ссылка на метод** — ещё более короткая запись лямбды, которая **просто делегирует вызов** уже существующему методу. Синтаксис: `::`.

### Аналогия из жизни

Лямбда — это записка «возьми x и вызови у него length». Ссылка на метод — это просто имя человека: «позови Аню, она сама знает, что делать». Если действие уже описано методом, не нужно его пересказывать.

### 5.2. Четыре вида

| Вид | Синтаксис | Пример | Эквивалентная лямбда |
|---|---|---|---|
| 1. Метод экземпляра конкретного объекта | `obj::method` | `System.out::println` | `x -> System.out.println(x)` |
| 2. Метод экземпляра произвольного объекта класса | `Class::method` | `String::length` | `s -> s.length()` |
| 3. Статический метод | `Class::staticMethod` | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| 4. Конструктор | `Class::new` | `Person::new` | `(...) -> new Person(...)` |

Разберём каждый.

**Вид 1 — метод конкретного объекта:**

```java
Consumer<String> printer = System.out::println;
printer.accept("Привет");  // Привет

String prefix = ">> ";
Consumer<String> logger = prefix::concat;  // вызывает prefix.concat(arg)
// (не самый практичный пример, но показывает суть)
```

**Вид 2 — метод экземпляра, где первый аргумент становится получателем:**

```java
Function<String, Integer> len = String::length;   // s -> s.length()
BiFunction<String, String, Boolean> eq = String::equalsIgnoreCase;
// эквивалент: (a, b) -> a.equalsIgnoreCase(b)

System.out.println(len.apply("Java"));            // 4
System.out.println(eq.apply("java", "JAVA"));     // true
```

Ключевая тонкость: `String::length` — это метод экземпляра, но у нас нет конкретного объекта. Первый параметр лямбды становится объектом, у которого вызывается метод.

**Вид 3 — статический метод:**

```java
Function<String, Integer> parse = Integer::parseInt;   // s -> Integer.parseInt(s)
Supplier<Double> random = Math::random;                // () -> Math.random()

System.out.println(parse.apply("123"));  // 123
```

**Вид 4 — конструктор:**

```java
Supplier<ArrayList<String>> listFactory = ArrayList::new;   // () -> new ArrayList<>()
Function<String, StringBuilder> sbFactory = StringBuilder::new;

System.out.println(listFactory.get());         // []
System.out.println(sbFactory.apply("hi"));     // hi

// Конструктор с аргументами
BiFunction<String, Integer, Person> personFactory = Person::new; // (name, age) -> new Person(name, age)

// Конструктор массива
IntFunction<String[]> arrFactory = String[]::new; // n -> new String[n]
System.out.println(Arrays.toString(arrFactory.apply(3))); // [null, null, null]
```

### 5.3. `this::method` и `super::method`

Внутри класса можно ссылаться на методы текущего объекта и родителя:

```java
class Parent {
    void hello() { System.out.println("parent"); }
}
class Child extends Parent {
    void hello() { System.out.println("child"); }

    void test() {
        Runnable r1 = this::hello;   // вызовет Child.hello -> child
        Runnable r2 = super::hello;  // вызовет Parent.hello -> parent
        r1.run();
        r2.run();
    }
}
```

### 5.4. Когда использовать

Используйте ссылку на метод, когда лямбда **только вызывает** существующий метод без дополнительной логики:

```java
// Хорошо:
names.forEach(System.out::println);

// Хуже (избыточно):
names.forEach(s -> System.out.println(s));

// Но если есть дополнительная логика — только лямбда:
names.forEach(s -> System.out.println(">> " + s));
```

### Типичные ошибки

- Пытаться сделать ссылку на метод с несколькими аргументами, которые не соответствуют сигнатуре (`Class::method` работает только когда получатель — первый аргумент).
- Путать `Class::method` (вид 2) и `Class::staticMethod` (вид 3).
- Использовать ссылку на метод, где нужна доп. логика.
- Ошибки с перегрузками: компилятор выбирает подходящую перегрузку по контексту.

### Часто спрашивают на собеседовании

- **Какие виды ссылок на методы есть?** Четыре: `obj::m`, `Class::staticM`, `Class::m`, `Class::new`.
- **Чем `String::length` отличается от `String::valueOf`?** Первый — метод экземпляра, второй — статический.
- **Что такое ссылка на конструктор?** `Class::new`, эквивалент `(...) -> new Class(...)`.

## 6. Stream vs Collection

### 6.1. Что такое Stream

**Stream (поток)** — это последовательность элементов, над которой можно выполнять декларативные операции (что сделать, а не как). Стрим **не хранит** данные — он их обрабатывает из источника.

### Аналогия из жизни

**Collection** — это склад с коробками. Товары лежат, их можно переставлять, добавлять, забирать.
**Stream** — это **конвейер** на заводе. Детали едут по ленте, на каждой станции с ними что-то делают. Сам конвейер детали не хранит, он их пропускает.

### 6.2. Таблица отличий

| Критерий | Collection | Stream |
|---|---|---|
| Хранение данных | хранит элементы | не хранит, обрабатывает источник |
| Изменяемость | можно добавлять/удалять | неизменяемый конвейер, только чтение |
| Обход | внешняя итерация (`for`, `Iterator`) | внутренняя итерация (API сам решает) |
| Многоразовость | можно обходить многократно | **одноразовый** |
| Ленивость | операции выполняются сразу | ленивый до терминальной операции |
| Параллелизм | вручную (threads, executors) | `.parallelStream()` / `.parallel()` |
| Стиль | императивный | декларативный/функциональный |
| Материализация | уже материализован | результат получаем через терминальную операцию |

### 6.3. Одноразовость стрима

Стрим можно использовать **только один раз**. Повторное использование бросит `IllegalStateException: stream has already been operated upon or closed`.

```java
Stream<String> stream = Stream.of("a", "b", "c");
stream.forEach(System.out::println); // a b c

// stream.forEach(System.out::println); // IllegalStateException!
```

Если нужно пройти дважды — создайте новый стрим из источника:

```java
List<String> list = List.of("a", "b", "c");
list.stream().forEach(System.out::println);
list.stream().forEach(System.out::println); // ок — новый стрим
```

### 6.4. Источники стримов

```java
// 1. Коллекция
List<String> list = List.of("a", "b");
list.stream();
list.parallelStream();

// 2. Массив
int[] nums = {1, 2, 3};
Arrays.stream(nums);

// 3. Явное перечисление
Stream.of("x", "y", "z");

// 4. Генераторы
Stream.iterate(0, n -> n + 1);        // бесконечный: 0,1,2,...
Stream.generate(Math::random);        // бесконечный случайных

// 5. Файлы (каждая строка — элемент)
try (Stream<String> lines = Files.lines(Path.of("data.txt"))) {
    lines.filter(s -> !s.isBlank()).count();
} catch (IOException e) {
    e.printStackTrace();
}

// 6. Примитивные стримы
IntStream.range(0, 5);        // 0,1,2,3,4
IntStream.rangeClosed(1, 5);  // 1,2,3,4,5

// 7. Из строки / регулярки
"a,b,c".chars();
Pattern.compile(" ").splitAsStream("hello world");

// 8. Пустой
Stream.empty();

// 9. Builder
Stream.<String>builder().add("a").add("b").build();
```

### 6.5. Полный пример

```java
import java.util.*;
import java.util.stream.*;

public class StreamDemo {
    record Person(String name, int age) {}

    public static void main(String[] args) {
        List<Person> people = List.of(
            new Person("Аня", 25),
            new Person("Борис", 17),
            new Person("Вера", 30)
        );

        List<String> names = people.stream()
            .filter(p -> p.age() > 18)     // оставить совершеннолетних
            .map(Person::name)             // взять имена
            .sorted()                      // отсортировать
            .collect(Collectors.toList()); // собрать в список

        System.out.println(names); // [Аня, Вера]
    }
}
```

### Типичные ошибки

- Переиспользовать стрим → `IllegalStateException`.
- Думать, что стрим что-то хранит.
- Изменять коллекцию-источник во время обработки стрима (особенно параллельного) → `ConcurrentModificationException` или некорректные результаты.
- Забывать, что без терминальной операции ничего не выполняется.

### Часто спрашивают на собеседовании

- **Чем Stream отличается от Collection?** Не хранит данные, ленивый, одноразовый, внутренняя итерация.
- **Можно ли переиспользовать стрим?** Нет.
- **Какие источники стримов знаете?** Коллекции, массивы, `Stream.of`, генераторы, файлы, примитивные стримы.
- **Что такое внутренняя итерация?** Управление обходом берёт на себя API, а не программист.

## 7. Промежуточные и терминальные операции

### 7.1. Два типа операций

- **Промежуточные (intermediate)** — принимают стрим, возвращают стрим, **ленивы**. Примеры: `filter`, `map`, `flatMap`, `distinct`, `sorted`, `peek`, `limit`, `skip`, `takeWhile`, `dropWhile`.
- **Терминальные (terminal)** — запускают весь конвейер и возвращают результат (не стрим): `collect`, `forEach`, `reduce`, `count`, `anyMatch`, `allMatch`, `noneMatch`, `findFirst`, `findAny`, `min`, `max`, `toArray`, `toList` (Java 16+), `forEachOrdered`.

Правило: **конвейер без терминальной операции не выполняется вообще**.

### 7.2. Lazy evaluation (ленивые вычисления)

Пока нет терминальной операции — ничего не происходит. Это позволяет избежать лишней работы.

```java
Stream.of("a", "b", "c")
    .filter(s -> {
        System.out.println("filter " + s);
        return true;
    });
// Вывод: пусто! Терминальной операции нет — ничего не выполнилось.
```

Добавим терминальную:

```java
Stream.of("a", "b", "c")
    .filter(s -> {
        System.out.println("filter " + s);
        return true;
    })
    .count();
```

Вывод:

```
filter a
filter b
filter c
```

### 7.3. Loop fusion (склеивание проходов)

Элементы обрабатываются **по одному через все стадии**, а не стадия за стадией. Это называется loop fusion — экономит проходы по данным.

```java
Stream.of("a", "b", "c")
    .filter(s -> {
        System.out.println("filter " + s);
        return true;
    })
    .map(s -> {
        System.out.println("map " + s);
        return s.toUpperCase();
    })
    .forEach(s -> System.out.println("result " + s));
```

Вывод (обратите внимание на чередование filter/map для каждого элемента):

```
filter a
map a
result A
filter b
map b
result B
filter c
map c
result C
```

А не «сначала все filter, потом все map». Вот это и есть loop fusion.

### 7.4. Short-circuit (досрочное завершение)

Некоторые операции могут остановить обработку раньше времени: `limit`, `findFirst`, `findAny`, `anyMatch`, `allMatch`, `noneMatch`.

```java
Stream.of("a", "b", "c")
    .filter(s -> {
        System.out.println("filter " + s);
        return true;
    })
    .findFirst();
```

Вывод:

```
filter a
```

Потому что `findFirst` нашёл первый элемент и сразу остановил конвейер. `b` и `c` даже не обрабатывались.

Пример с `limit`:

```java
Stream.iterate(1, n -> n + 1)      // бесконечный поток
    .filter(n -> n % 2 == 0)       // чётные
    .limit(3)                       // первые 3
    .forEach(System.out::println); // 2 4 6
```

Без `limit` бесконечный стрим никогда не завершится.

### 7.5. Пример filter + findFirst

```java
record User(String name, int age) {}

List<User> users = List.of(
    new User("Аня", 25),
    new User("Борис", 17),
    new User("Вера", 30)
);

Optional<User> firstAdult = users.stream()
    .filter(u -> u.age() >= 18)
    .findFirst();

firstAdult.ifPresent(u -> System.out.println(u.name())); // Аня
```

### 7.6. Полный список операций

**Промежуточные:**

| Операция | Что делает |
|---|---|
| `filter(Predicate)` | оставляет подходящие элементы |
| `map(Function)` | преобразует каждый элемент |
| `mapToInt/Long/Double` | в примитивный стрим |
| `flatMap(Function)` | разворачивает вложенные стримы |
| `distinct()` | убирает дубликаты (`equals`/`hashCode`) |
| `sorted()` / `sorted(Comparator)` | сортировка |
| `peek(Consumer)` | посмотреть элемент (отладка) |
| `limit(n)` | оставить первые n |
| `skip(n)` | пропустить первые n |
| `takeWhile(Predicate)` | брать, пока условие true (Java 9) |
| `dropWhile(Predicate)` | пропускать, пока условие true (Java 9) |
| `boxed()` | примитив → обёртка |
| `parallel()` / `sequential()` | режим выполнения |

**Терминальные:**

| Операция | Возвращает |
|---|---|
| `collect(Collector)` | коллекцию/значение |
| `forEach(Consumer)` | void (порядок не гарантирован в parallel) |
| `forEachOrdered(Consumer)` | void (порядок гарантирован) |
| `reduce(...)` | свёртку |
| `count()` | long |
| `anyMatch(Predicate)` | boolean |
| `allMatch(Predicate)` | boolean |
| `noneMatch(Predicate)` | boolean |
| `findFirst()` | Optional |
| `findAny()` | Optional (эффективнее в parallel) |
| `min(Comparator)` / `max(Comparator)` | Optional |
| `toArray()` | массив |
| `toList()` | List (Java 16+) |
| `sum()` / `average()` | для примитивных стримов |

### 7.7. Маленькая проверка на понимание

```java
System.out.println(
    Stream.of(1, 2, 3, 4, 5)
        .filter(n -> n % 2 == 0)
        .map(n -> n * 10)
        .findFirst()
        .orElse(0)
);
```

Ответ: `20`. `filter` оставит `2` и `4`, `map` превратит `2` в `20`, `findFirst` вернёт первый — `20`. Элемент `4` уже не обрабатывался.

### Типичные ошибки

- Ожидать выполнения без терминальной операции.
- Использовать `peek` для бизнес-логики (он для отладки).
- Думать, что `filter`/`map` идут стадиями, а не поэлементно.
- Забыть, что бесконечный стрим требует `limit`/`takeWhile`.
- Ожидать порядок от `forEach` в параллельном стриме.

### Часто спрашивают на собеседовании

- **Что такое lazy evaluation?** Операции не выполняются до терминальной.
- **Что такое loop fusion?** Обработка элементов поэлементно через все стадии.
- **Какие операции short-circuit?** `limit`, `findFirst`, `findAny`, `anyMatch`, `allMatch`, `noneMatch`.
- **Разница `findFirst` и `findAny`?** `findFirst` строго первый, `findAny` любой (быстрее в parallel).

## 8. map vs flatMap

### 8.1. Разница в одном предложении

- **`map`**: 1 элемент → 1 элемент (`Stream<R>`).
- **`flatMap`**: 1 элемент → много элементов, «сплющивает» вложенность.

### Аналогия из жизни

`map` — это как переводчик: каждое слово переводится в одно слово.
`flatMap` — это как повар, который из одной корзины продуктов достаёт много отдельных ингредиентов и выкладывает их на общий стол. Была корзина — стали отдельные продукты.

### 8.2. map: один к одному

```java
List<String> words = List.of("java", "stream");
List<Integer> lengths = words.stream()
    .map(String::length)
    .collect(Collectors.toList());

System.out.println(lengths); // [4, 6]
```

### 8.3. flatMap: разворачивание вложенных списков

```java
List<List<Integer>> nested = List.of(
    List.of(1, 2),
    List.of(3, 4),
    List.of(5)
);

// map даст Stream<Stream<Integer>>
List<Stream<Integer>> bad = nested.stream()
    .map(List::stream)
    .collect(Collectors.toList());

// flatMap даст Stream<Integer>
List<Integer> flat = nested.stream()
    .flatMap(List::stream)
    .collect(Collectors.toList());

System.out.println(flat); // [1, 2, 3, 4, 5]
```

### 8.4. flatMap: split строк на слова

```java
List<String> lines = List.of("привет мир", "java streams");

List<String> words = lines.stream()
    .flatMap(line -> Arrays.stream(line.split(" ")))
    .collect(Collectors.toList());

System.out.println(words); // [привет, мир, java, streams]
```

### 8.5. Наглядное сравнение

```java
List<String> input = List.of("a b", "c");

// map: [["a","b"], ["c"]] -> Stream<String[]> -> списки массивов
List<String[]> mapped = input.stream()
    .map(s -> s.split(" "))
    .collect(Collectors.toList());
System.out.println(mapped.size());              // 2
System.out.println(Arrays.toString(mapped.get(0))); // [a, b]

// flatMap: ["a","b","c"]
List<String> flattened = input.stream()
    .flatMap(s -> Arrays.stream(s.split(" ")))
    .collect(Collectors.toList());
System.out.println(flattened);                  // [a, b, c]
```

### 8.6. flatMap для Optional и Stream

`flatMap` есть и у `Optional`, и у `Stream`. У `Optional` он разворачивает `Optional<Optional<T>>`:

```java
Optional<String> value = Optional.of("user");
Optional<Integer> len = value.flatMap(s -> Optional.of(s.length()));
System.out.println(len); // Optional[4]
```

### Типичные ошибки

- Использовать `map` и получать `Stream<Stream<T>>` вместо `Stream<T>`.
- Забывать, что `flatMap` требует функцию, возвращающую `Stream` (или `Optional` для Optional).
- Смешивать `map`/`flatMap` там, где нужен `mapMulti` (Java 16) для эффективности.
- Путать `flatMap` стримов и `flatMap` Optional.

### Часто спрашивают на собеседовании

- **Разница map и flatMap?** 1→1 против 1→N со сплющиванием.
- **Когда нужен flatMap?** При вложенных коллекциях, split строк, `Optional<Optional<T>>`.
- **Что вернёт `map` от функции, возвращающей список?** `Stream<List<T>>`, а не `Stream<T>`.

## 9. Коллекторы (Collectors)

`Collectors` — это набор готовых стратегий «как собрать стрим в результат». Используется с терминальной операцией `collect`.

### 9.1. toList / toSet / toCollection

```java
List<String> list = Stream.of("a", "b", "a")
    .collect(Collectors.toList());
System.out.println(list); // [a, b, a] — дубликаты сохраняются

Set<String> set = Stream.of("a", "b", "a")
    .collect(Collectors.toSet());
System.out.println(set); // [a, b] — дубликаты убраны

// В конкретную реализацию
LinkedList<String> linked = Stream.of("a", "b")
    .collect(Collectors.toCollection(LinkedList::new));

// Java 16+: Stream.toList() — неизменяемый список
List<String> immutable = Stream.of("a", "b").toList();
```

Важно: `Collectors.toList()` **не даёт гарантий** по изменяемости/типу (обычно `ArrayList`), а `Stream.toList()` возвращает **неизменяемый** список.

### 9.2. toMap и merge при дубликатах

```java
record Person(int id, String name) {}

List<Person> people = List.of(
    new Person(1, "Аня"),
    new Person(2, "Борис")
);

Map<Integer, String> byId = people.stream()
    .collect(Collectors.toMap(Person::id, Person::name));
System.out.println(byId); // {1=Аня, 2=Борис}
```

Если ключи дублируются — `IllegalStateException: Duplicate key`. Нужна **merge-функция**:

```java
List<Person> withDup = List.of(
    new Person(1, "Аня"),
    new Person(1, "Борис")
);

Map<Integer, String> merged = withDup.stream()
    .collect(Collectors.toMap(
        Person::id,
        Person::name,
        (oldVal, newVal) -> oldVal   // что делать при конфликте: оставить старое
    ));
System.out.println(merged); // {1=Аня}
```

Можно указать и тип Map:

```java
Map<Integer, String> linked = people.stream()
    .collect(Collectors.toMap(
        Person::id,
        Person::name,
        (a, b) -> a,
        LinkedHashMap::new
    ));
```

### 9.3. joining

Склеивает строки. Есть три перегрузки:

```java
List<String> names = List.of("Аня", "Борис", "Вера");

System.out.println(names.stream().collect(Collectors.joining()));
// АняБорисВера

System.out.println(names.stream().collect(Collectors.joining(", ")));
// Аня, Борис, Вера

System.out.println(names.stream().collect(Collectors.joining(", ", "[", "]")));
// [Аня, Борис, Вера]
```

### 9.4. groupingBy (и downstream)

Самая мощная и частая операция. Группирует элементы по ключу.

```java
record Person(String name, String city, int age) {}

List<Person> people = List.of(
    new Person("Аня", "Москва", 25),
    new Person("Борис", "Казань", 17),
    new Person("Вера", "Москва", 30)
);

// Простейший случай: Map<String, List<Person>>
Map<String, List<Person>> byCity = people.stream()
    .collect(Collectors.groupingBy(Person::city));
System.out.println(byCity.keySet()); // [Казань, Москва]
```

**Downstream** — второй аргумент, что делать с группой:

```java
// Считаем количество в каждой группе
Map<String, Long> countByCity = people.stream()
    .collect(Collectors.groupingBy(Person::city, Collectors.counting()));
System.out.println(countByCity); // {Казань=1, Москва=2}

// Средний возраст по городу
Map<String, Double> avgAge = people.stream()
    .collect(Collectors.groupingBy(Person::city,
        Collectors.averagingInt(Person::age)));
System.out.println(avgAge); // {Казань=17.0, Москва=27.5}

// Имена по городам
Map<String, List<String>> namesByCity = people.stream()
    .collect(Collectors.groupingBy(Person::city,
        Collectors.mapping(Person::name, Collectors.toList())));
System.out.println(namesByCity); // {Казань=[Борис], Москва=[Аня, Вера]}
```

С указанием типа Map:

```java
Map<String, List<Person>> tree = people.stream()
    .collect(Collectors.groupingBy(
        Person::city,
        TreeMap::new,
        Collectors.toList()
    ));
```

### 9.5. partitioningBy

Особый случай `groupingBy` по булеву условию. Всегда возвращает **ровно две** группы: `true` и `false` (даже если одна пуста).

```java
Map<Boolean, List<Person>> adults = people.stream()
    .collect(Collectors.partitioningBy(p -> p.age() >= 18));

System.out.println(adults.get(true));  // [Аня, Вера]
System.out.println(adults.get(false)); // [Борис]

// С downstream
Map<Boolean, Long> adultCount = people.stream()
    .collect(Collectors.partitioningBy(
        p -> p.age() >= 18,
        Collectors.counting()));
System.out.println(adultCount); // {false=1, true=2}
```

### 9.6. summarizingInt / averagingInt / counting / summingInt

```java
IntSummaryStatistics stats = people.stream()
    .collect(Collectors.summarizingInt(Person::age));

System.out.println(stats);            // IntSummaryStatistics{count=3, sum=72, min=17, average=24.0, max=30}
System.out.println(stats.getAverage()); // 24.0
System.out.println(stats.getMax());     // 30

// Отдельные агрегаты
System.out.println(people.stream().collect(Collectors.counting()));       // 3
System.out.println(people.stream().collect(Collectors.summingInt(Person::age))); // 72
System.out.println(people.stream().collect(Collectors.averagingInt(Person::age))); // 24.0
```

### 9.7. reducing

Обобщённая свёртка внутри коллектора. Полезна как downstream для `groupingBy`.

```java
// Сумма возрастов через reducing
Integer total = people.stream()
    .collect(Collectors.reducing(0, Person::age, Integer::sum));
System.out.println(total); // 72

// Самый старший человек в каждом городе
Map<String, Optional<Person>> oldestByCity = people.stream()
    .collect(Collectors.groupingBy(
        Person::city,
        Collectors.reducing((a, b) -> a.age() >= b.age() ? a : b)
    ));
```

### 9.8. teeing (Java 12)

Позволяет применить **два** коллектора к одному стриму одновременно и объединить результаты.

```java
record Stats(long count, int sum) {}

Stats stats = people.stream().collect(Collectors.teeing(
    Collectors.counting(),
    Collectors.summingInt(Person::age),
    (count, sum) -> new Stats(count, sum)
));
System.out.println(stats); // Stats[count=3, sum=72]
```

### 9.9. Function.identity()

Это просто `t -> t` — возвращает аргумент как есть. Часто нужна в `toMap`, когда значение — сам элемент.

```java
Map<Integer, Person> map = people.stream()
    .collect(Collectors.toMap(Person::id, Function.identity()));
```

### 9.10. Сводная таблица коллекторов

| Коллектор | Результат |
|---|---|
| `toList()` | `List` |
| `toSet()` | `Set` |
| `toCollection(Supplier)` | конкретная коллекция |
| `toMap(k, v)` | `Map` |
| `toMap(k, v, merge)` | `Map` с разрешением конфликтов |
| `joining(...)` | `String` |
| `groupingBy(classifier)` | `Map<K, List<T>>` |
| `groupingBy(classifier, downstream)` | `Map<K, R>` |
| `partitioningBy(predicate)` | `Map<Boolean, List<T>>` |
| `counting()` | `Long` |
| `summingInt/Long/Double` | число |
| `averagingInt/Long/Double` | `Double` |
| `summarizingInt/Long/Double` | статистика |
| `mapping(mapper, downstream)` | преобразование внутри группы |
| `reducing(...)` | свёртка |
| `teeing(a, b, merger)` | объединение двух коллекторов |

### Типичные ошибки

- `toMap` без merge при дубликатах → `IllegalStateException`.
- Путать `groupingBy` (много групп по ключу) и `partitioningBy` (всегда 2 группы).
- Забывать downstream в `groupingBy`, когда нужен не список.
- Считать `Collectors.toList()` неизменяемым (он обычно `ArrayList`).
- Использовать `Function.identity()` там, где проще `p -> p` (стилистика, не ошибка).

### Часто спрашивают на собеседовании

- **Как сгруппировать по полю?** `groupingBy`.
- **Что делать при дубликатах ключей в `toMap`?** Передать merge-функцию.
- **Разница `groupingBy` и `partitioningBy`?** Вторая всегда 2 группы (`true`/`false`).
- **Что такое downstream?** Второй аргумент, определяющий, что делать с группой.
- **Что такое `teeing`?** Два коллектора за один проход.

## 10. reduce

### 10.1. Что такое reduce

**`reduce`** — это терминальная операция свёртки: превращает много элементов в одно значение, последовательно применяя операцию.

### Аналогия из жизни

Складываем деньги в копилку: начинаем с 0, добавляем купюру за купюрой, в конце — одна сумма.

### 10.2. Три варианта reduce

**1. С начальным значением (identity) — всегда возвращает значение:**

```java
int sum = Stream.of(1, 2, 3, 4)
    .reduce(0, (acc, x) -> acc + x); // 10
System.out.println(sum);
```

**2. Без начального значения — возвращает Optional:**

```java
Optional<Integer> sum = Stream.of(1, 2, 3, 4)
    .reduce((acc, x) -> acc + x);
System.out.println(sum); // Optional[10]

Optional<Integer> empty = Stream.<Integer>of().reduce((a, b) -> a + b);
System.out.println(empty); // Optional.empty
```

**3. Трёхаргументный (для параллельных стримов):**

```java
// identity, accumulator, combiner
int result = Stream.of(1, 2, 3, 4).parallel()
    .reduce(0,
        (acc, x) -> acc + x,       // как объединять элемент с аккумулятором
        (a, b) -> a + b);          // как объединять частичные результаты
System.out.println(result); // 10
```

В последовательном стриме combiner не используется. В параллельном — объединяет результаты подзадач.

### 10.3. reduce vs collect

| | `reduce` | `collect` |
|---|---|---|
| Тип результата | обычно тот же/примитив | может быть другой (коллекция) |
| Изменяемость | иммутабельная свёртка | mutable reduction (изменяемый контейнер) |
| Типичное использование | сумма, максимум, конкатенация | списки, карты, группировки |
| Производительность | хуже для коллекций (создаёт новые объекты) | лучше (мутирует контейнер) |

Пример: сборка строки.

```java
// reduce — квадратичная сложность из-за конкатенации строк
String r = Stream.of("a", "b", "c").reduce("", (acc, s) -> acc + s);

// collect — эффективно через StringBuilder
String c = Stream.of("a", "b", "c").collect(Collectors.joining());
```

`collect` называется **mutable reduction** — он использует изменяемый контейнер (например, `ArrayList`), а `reduce` — **immutable reduction**, каждый шаг создаёт новое значение.

### 10.4. Примитивные стримы: sum, average, min, max

Для `IntStream`, `LongStream`, `DoubleStream` есть готовые методы без боксинга:

```java
int sum = IntStream.rangeClosed(1, 10).sum();          // 55
OptionalDouble avg = IntStream.rangeClosed(1, 10).average(); // OptionalDouble[5.5]
OptionalInt max = IntStream.of(3, 1, 4).max();         // OptionalInt[4]
int product = IntStream.of(1, 2, 3, 4).reduce(1, (a, b) -> a * b); // 24
```

`sum()` возвращает примитив, `average()` — `OptionalDouble` (потому что для пустого стрима среднего нет).

### 10.5. Рекомендации

- Для примитивов используйте `IntStream`/`LongStream`/`DoubleStream` и их `sum()`/`average()`.
- Для сбора в коллекцию — `collect`, не `reduce`.
- `reduce` отлично подходит для математических свёрток (произведение, максимум, НОД).

### Типичные ошибки

- Использовать `reduce` для сборки коллекций — неэффективно, нужен `collect`.
- Забыть, что reduce без identity возвращает `Optional`.
- Неправильный combiner в параллельном reduce (не ассоциативная операция) → неверный результат.
- Конкатенация строк через reduce → O(n²).

### Часто спрашивают на собеседовании

- **Разница reduce и collect?** Immutable vs mutable reduction.
- **Сколько перегрузок reduce?** Три: с identity, без identity, с combiner.
- **Зачем combiner?** Для объединения результатов в параллельном стриме.
- **Как посчитать сумму примитивов?** `IntStream.sum()`.

## 11. Другие полезные операции

### 11.1. distinct

Убирает дубликаты, используя `equals`/`hashCode`.

```java
List<Integer> unique = Stream.of(1, 2, 2, 3, 3, 3)
    .distinct()
    .collect(Collectors.toList());
System.out.println(unique); // [1, 2, 3]
```

Важно: `distinct` на **неупорядоченном** параллельном стриме может быть дороже. Для объектов обязательно корректные `equals`/`hashCode`.

### 11.2. sorted с Comparator

```java
List<String> words = List.of("java", "c", "python", "go");

// Естественный порядок
System.out.println(words.stream().sorted().collect(Collectors.toList()));
// [c, go, java, python]

// По длине
System.out.println(words.stream()
    .sorted(Comparator.comparingInt(String::length))
    .collect(Collectors.toList()));
// [c, go, java, python]

// Обратный порядок
System.out.println(words.stream()
    .sorted(Comparator.reverseOrder())
    .collect(Collectors.toList()));
// [python, java, go, c]

// Составной компаратор
record Person(String name, int age) {}
List<Person> people = List.of(
    new Person("Аня", 30),
    new Person("Борис", 25),
    new Person("Вера", 30)
);
List<Person> sorted = people.stream()
    .sorted(Comparator.comparingInt(Person::age)
        .thenComparing(Person::name))
    .collect(Collectors.toList());
System.out.println(sorted);
// [Person[name=Борис, age=25], Person[name=Аня, age=30], Person[name=Вера, age=30]]
```

Полезные фабрики `Comparator`: `comparing`, `comparingInt`, `thenComparing`, `reversed`, `naturalOrder`, `nullsFirst`, `nullsLast`.

### 11.3. peek

`peek` позволяет «заглянуть» в элемент, не меняя его. Обычно для отладки.

```java
List<String> result = Stream.of("a", "bb", "ccc")
    .peek(s -> System.out.println("до фильтра: " + s))
    .filter(s -> s.length() > 1)
    .peek(s -> System.out.println("после фильтра: " + s))
    .collect(Collectors.toList());
System.out.println(result);
```

Вывод:

```
до фильтра: a
до фильтра: bb
после фильтра: bb
до фильтра: ccc
после фильтра: ccc
[bb, ccc]
```

Внимание: `peek` может **не выполниться**, если конвейер завершился раньше (short-circuit). Не используйте его для бизнес-логики.

### 11.4. takeWhile и dropWhile (Java 9)

Работают с **упорядоченными** стримами, основаны на предикате.

```java
List<Integer> nums = List.of(1, 2, 3, 10, 4, 5);

// Брать, пока условие true (на 10 остановится)
System.out.println(nums.stream()
    .takeWhile(n -> n < 5)
    .collect(Collectors.toList())); // [1, 2, 3]

// Пропускать, пока условие true, потом взять всё
System.out.println(nums.stream()
    .dropWhile(n -> n < 5)
    .collect(Collectors.toList())); // [10, 4, 5]
```

Отличие от `filter`: `filter` проверяет **все** элементы, а `takeWhile`/`dropWhile` останавливаются на первом несоответствии.

### 11.5. iterate и generate

```java
// iterate: начальное значение + функция
List<Integer> powers = Stream.iterate(1, n -> n * 2)
    .limit(5)
    .collect(Collectors.toList());
System.out.println(powers); // [1, 2, 4, 8, 16]

// Java 9: iterate с условием (как for)
List<Integer> range = Stream.iterate(0, n -> n < 5, n -> n + 1)
    .collect(Collectors.toList());
System.out.println(range); // [0, 1, 2, 3, 4]

// generate: поставщик, без начального значения
List<Double> randoms = Stream.generate(Math::random)
    .limit(3)
    .collect(Collectors.toList());
System.out.println(randoms.size()); // 3
```

Оба создают **бесконечные** стримы, поэтому нужен `limit`/`takeWhile`.

### 11.6. IntStream.range и rangeClosed

```java
IntStream.range(0, 5).forEach(System.out::print);       // 01234 (5 не входит)
System.out.println();
IntStream.rangeClosed(1, 5).forEach(System.out::print); // 12345 (5 входит)
System.out.println();
```

Удобно для индексов, сумм, генерации диапазонов.

### 11.7. boxed

Превращает примитивный стрим в стрим объектов (для использования с дженерик-операциями).

```java
List<Integer> boxed = IntStream.rangeClosed(1, 5)
    .boxed()
    .collect(Collectors.toList());
System.out.println(boxed); // [1, 2, 3, 4, 5]

// Обратное преобразование
int sum = boxed.stream().mapToInt(Integer::intValue).sum();
System.out.println(sum); // 15
```

### 11.8. Прочие полезные методы

| Метод | Что делает |
|---|---|
| `count()` | количество элементов |
| `skip(n)` | пропустить первые n |
| `limit(n)` | взять первые n |
| `anyMatch/allMatch/noneMatch` | проверки |
| `mapToObj` | примитив → объект |
| `mapToInt/Long/Double` | объект → примитив |
| `flatMapToInt` | разворачивание в примитивный стрим |
| `summaryStatistics()` | статистика примитивного стрима |

### Типичные ошибки

- `takeWhile`/`dropWhile` на неупорядоченном стриме — результат непредсказуем.
- Использовать `peek` для побочных эффектов, на которые рассчитываете.
- Забыть `limit` у бесконечного `iterate`/`generate`.
- `sorted()` на объектах без `Comparable` → `ClassCastException`.

### Часто спрашивают на собеседовании

- **Разница filter и takeWhile?** `filter` по всем, `takeWhile` останавливается на первом false.
- **Что делает `boxed`?** Превращает примитивный стрим в стрим обёрток.
- **Как сделать бесконечный стрим?** `iterate`/`generate` + `limit`.
- **Чем `range` отличается от `rangeClosed`?** Верхняя граница не включается/включается.

## 12. Параллельные стримы

### 12.1. Как включить

```java
list.parallelStream();          // сразу параллельный
list.stream().parallel();       // переключить
```

### 12.2. ForkJoinPool.commonPool

Параллельные стримы используют общий пул потоков — **`ForkJoinPool.commonPool()`**. По умолчанию он создаёт `Runtime.getRuntime().availableProcessors() - 1` рабочих потоков.

Как работает:

1. `Spliterator` разбивает источник на части.
2. Части обрабатываются параллельно в `ForkJoinPool`.
3. Результаты объединяются (combine).

### Аналогия из жизни

Большую кучу кирпичей вы раздаёте бригаде рабочих. Каждый укладывает свою часть, потом вы соединяете стену. Если кирпичей мало или рабочие всё время ждут друг друга — выгоднее было сделать самому.

### 12.3. Когда ускорение, а когда вред

**Хорошо работает, когда:**

- элементов **много** (десятки тысяч+);
- операции **дорогие** (CPU-bound, например, сложные вычисления);
- источник **хорошо разбивается**: `ArrayList`, массивы (отлично), `HashSet` (средне), `LinkedList` (плохо).

**Вредит, когда:**

- коллекция маленькая — накладные расходы больше выгоды;
- операции **блокирующие** (I/O, сеть, БД) — потоки простаивают;
- есть общее изменяемое состояние — гонки;
- используется `limit` — плохо разбивается;
- порядок важен — сложнее гарантировать.

### 12.4. Требования: stateless и без side effects

Операции должны быть:

- **Stateless** — не зависеть от изменяемого внешнего состояния.
- **Без побочных эффектов** — не менять общие структуры.
- **Ассоциативными** — для корректного объединения результатов (`(a+b)+c == a+(b+c)`).

Плохо:

```java
List<Integer> result = new ArrayList<>();
IntStream.range(0, 1000).parallel()
    .forEach(result::add); // ГОНКА! ArrayList не потокобезопасен
```

Хорошо:

```java
List<Integer> result = IntStream.range(0, 1000).parallel()
    .boxed()
    .collect(Collectors.toList()); // безопасно
```

Если очень нужен изменяемый контейнер — используйте потокобезопасный (`ConcurrentLinkedQueue`, `Collections.synchronizedList`) или `collect`.

### 12.5. forEach vs forEachOrdered

```java
List<Integer> list = List.of(1, 2, 3, 4, 5);

// parallel + forEach — порядок НЕ гарантирован
list.parallelStream().forEach(System.out::print);
System.out.println();

// parallel + forEachOrdered — порядок гарантирован (но медленнее)
list.parallelStream().forEachOrdered(System.out::print);
System.out.println();
```

`forEachOrdered` заставляет обрабатывать в исходном порядке, частично теряя выгоду параллелизма.

### 12.6. Свой пул потоков

Иногда commonPool перегружен или нужно ограничить параллелизм. Тогда запускают задачи в **своём** `ForkJoinPool`:

```java
ForkJoinPool customPool = new ForkJoinPool(4);
try {
    List<Integer> result = customPool.submit(() ->
        IntStream.range(0, 1_000_000).parallel()
            .filter(n -> n % 2 == 0)
            .boxed()
            .collect(Collectors.toList())
    ).get();
    System.out.println(result.size());
} catch (Exception e) {
    e.printStackTrace();
} finally {
    customPool.shutdown();
}
```

Важно: **внутри** задачи `parallel()` использует пул вызывающего потока. Не рекомендуется надолго занимать commonPool блокирующими операциями — это влияет на всё приложение.

### 12.7. Spliterator

`Spliterator` — «разбиватель» источника. Он умеет:

- `tryAdvance` — взять следующий элемент;
- `trySplit` — отделить часть элементов для другой задачи;
- `estimateSize` — оценить размер;
- характеристики (`ORDERED`, `SORTED`, `SIZED`, `DISTINCT` и т.д.), помогающие оптимизации.

От качества `trySplit` зависит эффективность параллелизма: `ArrayList`/массивы делятся идеально, `LinkedList` — плохо.

### Типичные ошибки

- Использовать parallel для маленьких коллекций (медленнее).
- Побочные эффекты и общие изменяемые структуры → гонки.
- Занимать commonPool блокирующими вызовами.
- Ожидать порядок от `forEach`.
- Использовать неассоциативные операции в `reduce`.
- Забыть про накладные расходы на boxing в параллельных стримах.

### Часто спрашивают на собеседовании

- **Какой пул используют параллельные стримы?** `ForkJoinPool.commonPool()`.
- **Когда parallel быстрее?** Много элементов, дорогие CPU-bound операции, хорошо разбиваемый источник.
- **Когда вреден?** Мало данных, I/O, side effects, `limit`, порядок.
- **Разница forEach и forEachOrdered?** Гарантия порядка.
- **Можно ли задать свой пул?** Да, через `ForkJoinPool` и `submit`.
- **Что такое Spliterator?** Механизм разбиения источника для параллельной обработки.

## 13. Optional + Stream идиомы

### 13.1. Optional как результат find*

```java
record User(String name, String city) {}

List<User> users = List.of(
    new User("Аня", "Москва"),
    new User("Борис", null)
);

Optional<User> u = users.stream()
    .filter(x -> x.name().equals("Аня"))
    .findFirst();
System.out.println(u.map(User::city).orElse("Unknown")); // Москва
```

### 13.2. Безопасное извлечение с orElse

```java
String city = users.stream()
    .filter(x -> x.city() != null)
    .map(User::city)
    .findFirst()
    .orElse("Unknown");
System.out.println(city); // Москва
```

`orElse(value)` вычисляет `value` всегда, `orElseGet(Supplier)` — лениво, только если пусто:

```java
// orElseGet эффективнее, если значение дорогое
String c = users.stream().map(User::city).findFirst()
    .orElseGet(() -> expensiveDefault());
```

### 13.3. Optional.flatMap для вложенных Optional

```java
Optional<Optional<String>> nested = Optional.of(Optional.of("x"));

// map даст Optional<Optional<String>>
// flatMap развернёт
Optional<String> flat = nested.flatMap(o -> o);
System.out.println(flat); // Optional[x]
```

### 13.4. Полезные методы Optional

| Метод | Что делает |
|---|---|
| `isPresent()` / `isEmpty()` | проверка наличия |
| `get()` | получить (опасно без проверки) |
| `orElse(T)` | значение или дефолт |
| `orElseGet(Supplier)` | ленивый дефолт |
| `orElseThrow()` | бросить исключение, если пусто |
| `ifPresent(Consumer)` | выполнить, если есть |
| `ifPresentOrElse(c, r)` | ветвление (Java 9) |
| `map(Function)` | преобразовать содержимое |
| `flatMap(Function)` | развернуть вложенный Optional |
| `filter(Predicate)` | оставить, если подходит |
| `stream()` | `Stream` из 0 или 1 элемента |

### 13.5. Optional.stream() — мост к стримам

```java
List<Optional<String>> optionals = List.of(
    Optional.of("a"),
    Optional.empty(),
    Optional.of("b")
);

List<String> present = optionals.stream()
    .flatMap(Optional::stream)   // пустые отбрасываются
    .collect(Collectors.toList());
System.out.println(present); // [a, b]
```

### 13.6. Антипаттерны Optional

- `Optional` как поле класса (не сериализуется, создан для возвращаемых значений).
- `optional.get()` без проверки — снова риск `NoSuchElementException`.
- `Optional.of(null)` → `NullPointerException`; для nullable нужен `Optional.ofNullable`.
- Использовать `isPresent()` + `get()` вместо `map`/`ifPresent`.

```java
// Плохо
if (opt.isPresent()) {
    System.out.println(opt.get().toUpperCase());
}

// Хорошо
opt.map(String::toUpperCase).ifPresent(System.out::println);
```

### Типичные ошибки

- `Optional.of(null)`.
- `get()` без проверки.
- Пытаться использовать Optional везде, включая поля и параметры.
- Забыть про `flatMap` для вложенных Optional.
- `orElse(expensive())` вместо `orElseGet(() -> expensive())`.

### Часто спрашивают на собеседовании

- **Зачем Optional?** Явно выразить «значения может не быть», избежать NPE.
- **Разница orElse и orElseGet?** Второй ленивый.
- **Чем flatMap полезен в Optional?** Разворачивает `Optional<Optional<T>>`.
- **Где Optional применять не стоит?** Поля, параметры, коллекции.
- **Что делает `Optional.stream()`?** Даёт стрим из 0/1 элемента.

## 14. Шпаргалка

- **Функциональный интерфейс** = ровно 1 абстрактный метод; `@FunctionalInterface` проверяет.
- **Базовые из `java.util.function`**: `Function`, `Supplier`, `Consumer`, `Predicate`; Bi- и Unary/Binary-вариации; примитивные специализации против боксинга.
- **default-методы** — для эволюции интерфейсов; конфликт решается `A.super.m()`; `static` вызывается через имя интерфейса; `private` методы с Java 9.
- **Лямбда** — реализация функционального интерфейса; компилируется в `invokedynamic` + `LambdaMetafactory`; захватывает effectively final; `this` — внешний объект.
- **Ссылки на методы**: `obj::m`, `Class::staticM`, `Class::m`, `Class::new`.
- **Stream**: не хранит данные, ленивый, одноразовый, внутренняя итерация.
- **Промежуточные операции** ленивы; без терминальной ничего не выполняется; loop fusion + short-circuit.
- **map** 1→1, **flatMap** 1→N.
- **Коллекторы**: `toList/toSet/toMap` (+ merge), `joining`, `groupingBy` (+ downstream), `partitioningBy`, `summarizingInt`, `reducing`, `teeing`, `Function.identity()`.
- **reduce** — immutable reduction; **collect** — mutable reduction.
- **Параллельные стримы** — `ForkJoinPool.commonPool()`; stateless, без side effects, ассоциативные операции; `forEachOrdered` для порядка.
- **Optional** — для возвращаемых значений; `map`/`flatMap`/`ifPresent` вместо `get()`.

## 15. Частые вопросы на собеседовании с короткими ответами

**1. Что такое функциональный интерфейс?**
Интерфейс с одним абстрактным методом; к нему можно присвоить лямбду или ссылку на метод.

**2. Обязательна ли `@FunctionalInterface`?**
Нет, но она даёт проверку компилятора.

**3. Чем `Function` отличается от `Supplier`?**
`Function` принимает аргумент и возвращает результат; `Supplier` только возвращает.

**4. Чем `Consumer` отличается от `Function`?**
`Consumer` ничего не возвращает (`void`), только потребляет.

**5. Зачем примитивные специализации?**
Чтобы избежать boxing/unboxing и лишних аллокаций.

**6. Зачем default-методы?**
Чтобы добавлять методы в интерфейсы, не ломая существующие реализации.

**7. Как разрешить конфликт default-методов?**
Явно переопределить и вызвать `A.super.method()`.

**8. Что такое effectively final?**
Переменная, которая после инициализации не меняется; только такие можно захватывать в лямбду.

**9. Почему лямбда не может менять локальную переменную?**
Захватывается значение (копия), а не изменяемая ячейка.

**10. Чем `this` в лямбде отличается от анонимного класса?**
В лямбде `this` — внешний объект; в анонимном классе — сам анонимный объект.

**11. Что генерирует компилятор для лямбды?**
Инструкцию `invokedynamic` и бутстрап `LambdaMetafactory`, а не отдельный класс.

**12. Четыре вида ссылок на методы?**
`obj::m`, `Class::staticM`, `Class::m`, `Class::new`.

**13. Чем Stream отличается от Collection?**
Не хранит данные, ленивый, одноразовый, внутренняя итерация, легко параллелится.

**14. Что такое lazy evaluation в стримах?**
Промежуточные операции не выполняются до терминальной.

**15. Что такое loop fusion?**
Обработка элементов по одному через все стадии, а не стадия за стадией.

**16. Какие операции short-circuit?**
`limit`, `findFirst`, `findAny`, `anyMatch`, `allMatch`, `noneMatch`.

**17. Разница `findFirst` и `findAny`?**
`findFirst` строго первый; `findAny` любой, быстрее в параллельном стриме.

**18. Разница `map` и `flatMap`?**
`map` — 1→1; `flatMap` — 1→N со сплющиванием.

**19. Как сгруппировать элементы?**
`Collectors.groupingBy(classifier[, downstream])`.

**20. Что делать при дубликатах ключей в `toMap`?**
Передать merge-функцию третьим аргументом.

**21. Разница `groupingBy` и `partitioningBy`?**
`partitioningBy` всегда даёт 2 группы (`true`/`false`).

**22. Разница `reduce` и `collect`?**
`reduce` — immutable reduction, `collect` — mutable reduction (изменяемый контейнер).

**23. Зачем combiner в reduce?**
Объединять частичные результаты в параллельном стриме.

**24. Разница `filter` и `takeWhile`?**
`filter` проверяет все элементы; `takeWhile` останавливается на первом несоответствии.

**25. Что делает `peek`?**
Позволяет заглянуть в элемент (для отладки), может не выполниться при short-circuit.

**26. Какой пул используют параллельные стримы?**
`ForkJoinPool.commonPool()`.

**27. Когда параллельные стримы вредны?**
Мало данных, I/O, побочные эффекты, `limit`, важен порядок.

**28. Разница `forEach` и `forEachOrdered`?**
`forEachOrdered` гарантирует исходный порядок.

**29. Что такое Spliterator?**
Интерфейс разбиения источника на части для параллельной обработки.

**30. Зачем Optional?**
Явно показать, что значение может отсутствовать, и уменьшить число NPE.

**31. Разница `orElse` и `orElseGet`?**
`orElseGet` ленивый: дефолт вычисляется только если Optional пуст.

**32. Чем `Optional.flatMap` отличается от `map`?**
`flatMap` разворачивает вложенный Optional (`Optional<Optional<T>>` → `Optional<T>`).

**33. Можно ли использовать один стрим дважды?**
Нет, повторное использование бросит `IllegalStateException`.

**34. Что такое `boxed`?**
Преобразование примитивного стрима (`IntStream`) в стрим объектов (`Stream<Integer>`).

**35. Разница `range` и `rangeClosed`?**
`range` не включает верхнюю границу, `rangeClosed` включает.

**36. Что такое `teeing`?**
Коллектор, который применяет два других коллектора за один проход и объединяет результаты.

**37. Наследуются ли static-методы интерфейса?**
Нет, вызываются только через имя интерфейса.

**38. Что нового для интерфейсов в Java 9?**
Приватные и приватные статические методы.

**39. Что делает `Function.identity()`?**
Возвращает переданный аргумент без изменений (`t -> t`).

**40. Как посчитать сумму примитивов эффективно?**
Через `IntStream`/`LongStream`/`DoubleStream` и `sum()`/`average()`.
