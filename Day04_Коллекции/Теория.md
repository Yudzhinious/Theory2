# День 4. Коллекции (Java Collections Framework)

> **Цель дня:** уверенно ориентироваться в иерархии коллекций, понимать внутреннее устройство `HashMap`/`ArrayList`, отличия реализаций, потокобезопасные коллекции и правила работы с `equals`/`hashCode`.

Коллекции — это, пожалуй, самая «рабочая» тема на Java-собеседовании. Почти каждую задачу на интервью решают через `List`, `Map` или `Set`, поэтому важно не просто знать названия классов, а понимать, **что внутри** и **почему выбрана та или иная реализация**.

Главная мысль всего дня: **коллекция — это компромисс**. Быстрый доступ по индексу — значит массив. Быстрая вставка в середину — значит список. Быстрый поиск по ключу — значит хэш-таблица. Не бывает «лучшей коллекции вообще», бывает подходящая под задачу.

## 1. Иерархия коллекций

### Аналогия

Представьте библиотеку. Есть **полки с книгами, где важен порядок** (`List`). Есть **каталог уникальных читательских билетов** (`Set`). Есть **очередь на выдачу** (`Queue`). А есть **алфавитный указатель «автор → книги»**, где по имени автора вы находите его произведения (`Map`). Это разные сущности, но все они — «хранилища данных».

### Общая схема

```
Iterable                          (умеет отдавать Iterator → можно for-each)
 └── Collection                   (базовые операции: add, remove, size, contains)
      ├── List                    (ArrayList, LinkedList, Vector, Stack, CopyOnWriteArrayList)
      ├── Set                     (HashSet, LinkedHashSet, TreeSet, EnumSet, CopyOnWriteArraySet)
      └── Queue                   (PriorityQueue, ArrayDeque, LinkedList, BlockingQueue)
           └── Deque              (ArrayDeque, LinkedList)

Map (НЕ Collection!)              (ключ → значение)
 ├── HashMap
 ├── LinkedHashMap
 ├── TreeMap
 ├── Hashtable
 ├── ConcurrentHashMap
 ├── WeakHashMap
 ├── IdentityHashMap
 └── EnumMap
```

### Ключевые интерфейсы

| Интерфейс | Смысл | Порядок | Дубликаты | Индексы |
|---|---|---|---|---|
| `Iterable` | Можно перебрать в `for-each` | — | — | — |
| `Collection` | Базовые операции над группой | — | — | — |
| `List` | Упорядоченный список | Да, по позиции | Да | Да |
| `Set` | Множество уникальных элементов | Зависит от реализации | Нет | Нет |
| `Queue` | Очередь (FIFO / приоритет) | Да (правило очереди) | Да | Нет |
| `Deque` | Двусторонняя очередь (стек + очередь) | Да | Да | Нет |
| `Map` | Словарь ключ → значение | Зависит | Ключи уникальны | Нет (по ключу) |

### Почему `Map` не наследует `Collection`?

Это классический вопрос на собеседовании. Причины:

1. **Разные контракты.** `Collection` — это коллекция **одиночных** элементов: `add(E)`, `contains(Object)`, `iterator()`. У `Map` элементы — **пары** `ключ → значение`, поэтому методы были бы `add(K, V)` — другая сигнатура, несовместимая с `Collection`.
2. **Концептуально `Map` — не набор, а отображение.** Нельзя сказать «множество пар» и при этом сохранить уникальность по ключу без конфликта с `Set`.
3. **Зато представления (`views`) — это `Collection`:**

```java
Map<String, Integer> map = new HashMap<>();
map.put("a", 1);
map.put("b", 2);

Collection<String> keys   = map.keySet();     // Set (тоже Collection)
Collection<Integer> vals  = map.values();     // Collection
Collection<Map.Entry<String, Integer>> entries = map.entrySet(); // Set
```

### Пример: один и тот же обход разными способами

```java
import java.util.*;

public class HierarchyDemo {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("яблоко", "банан", "яблоко"));
        System.out.println("list = " + list);            // list = [яблоко, банан, яблоко]

        Set<String> set = new HashSet<>(list);
        System.out.println("set  = " + set);             // set  = [яблоко, банан] (дубликат убран)

        Map<String, Integer> map = new HashMap<>();
        map.put("яблоко", 1);
        map.put("банан", 2);
        for (Map.Entry<String, Integer> e : map.entrySet()) {
            System.out.println(e.getKey() + " -> " + e.getValue());
        }
    }
}
```

### Типичные ошибки

- Путать `Collection` и `Collections`. `Collection` — интерфейс, `Collections` — утилитный класс со статическими методами (`sort`, `synchronizedList`, `unmodifiableList`).
- Думать, что `Map` — это `Collection`. Нет, это отдельная ветка.
- Считать, что `Set` гарантирует порядок. Порядок зависит от реализации (`HashSet` — не гарантирует, `LinkedHashSet` — порядок вставки, `TreeSet` — сортировка).

### Часто спрашивают на собеседовании

- **Почему Map не Collection?** — разные контракты (пары vs одиночные элементы), но `keySet/values/entrySet` являются `Collection`.
- **Что общего у List и Set?** — оба наследуют `Collection`, оба хранят одиночные элементы, но `List` разрешает дубликаты и порядок, `Set` — нет.
- **В чём разница Collection и Collections?** — интерфейс vs утилитный класс.

## 2. ArrayList vs LinkedList

### Аналогия

- **ArrayList** — это **шеренга учеников в спортзале**. Каждый стоит на своём месте с номером. Сказать «ученик №5, выйди» — мгновенно (O(1)). Но втиснуть нового в середину шеренги — придётся всем подвинуться (O(n)).
- **LinkedList** — это **хоровод, взявшийся за руки**. Чтобы встать между двумя людьми, достаточно разомкнуть руки в одном месте (O(1)). Но чтобы найти «пятого по счёту» — надо идти от начала и считать (O(n)).

### Устройство

**ArrayList** внутри — обычный массив `Object[] elementData`:

```java
// упрощённо
public class ArrayList<E> {
    transient Object[] elementData; // буфер
    private int size;               // сколько занято
}
```

**LinkedList** внутри — двусвязный список из узлов:

```java
// упрощённо
public class LinkedList<E> {
    private static class Node<E> {
        E item;
        Node<E> next;
        Node<E> prev;
    }
    Node<E> first;
    Node<E> last;
    int size;
}
```

### Сравнение операций

| Операция | ArrayList | LinkedList |
|---|---|---|
| `get(i)` / `set(i)` | **O(1)** | O(n) |
| `add(e)` в конец | амортизированно **O(1)** | **O(1)** |
| `add(0, e)` в начало | O(n) | **O(1)** |
| `add(i, e)` в середину | O(n) | O(n) на поиск + O(1) на вставку |
| `remove(0)` | O(n) | **O(1)** |
| `remove(i)` | O(n) | O(n) |
| `contains(e)` | O(n) | O(n) |
| Память на элемент | ~4–8 байт (ссылка в массиве) | ~24+ байт (узел + 2 ссылки + заголовок) |
| Кэш-локальность | **высокая** | низкая |

> **Важно:** «LinkedList быстрее вставляет в середину» — верно только если у вас **уже есть** `ListIterator` на нужной позиции. Если позицию нужно искать по индексу — сначала O(n) на проход.

### Кэш-локальность — почему это важно

Современный процессор читает память не по одному байту, а **блоками (кэш-линиями, обычно 64 байта)**. Массив лежит в памяти непрерывно, поэтому при обращении к `elementData[0]` в кэш подтягиваются и `elementData[1..15]` — следующая итерация почти бесплатна. Узлы `LinkedList` разбросаны по куче, и каждый переход по ссылке — потенциальный **промах кэша (cache miss)**, который в десятки раз дороже.

Именно поэтому на практике `ArrayList` часто **быстрее** `LinkedList` даже там, где по Big-O должен проигрывать.

### Пример: сравнение производительности на ощупь

```java
import java.util.*;

public class ListBenchmark {
    public static void main(String[] args) {
        int n = 100_000;

        List<Integer> array = new ArrayList<>();
        List<Integer> linked = new LinkedList<>();

        long t1 = System.nanoTime();
        for (int i = 0; i < n; i++) array.add(0, i);   // вставка в начало
        long t2 = System.nanoTime();

        for (int i = 0; i < n; i++) linked.add(0, i);  // вставка в начало
        long t3 = System.nanoTime();

        System.out.println("ArrayList add(0): " + (t2 - t1) / 1_000_000 + " ms");
        System.out.println("LinkedList add(0): " + (t3 - t2) / 1_000_000 + " ms");
        // LinkedList здесь выигрывает, потому что add(0) не ищет позицию
    }
}
```

### `RandomAccess` — маркерный интерфейс

`ArrayList` реализует `RandomAccess`. Это «флаг» для алгоритмов: если список поддерживает быстрый доступ по индексу — обходить его циклом `for (int i...)`, иначе — итератором.

```java
List<String> list = new ArrayList<>();
if (list instanceof RandomAccess) {
    for (int i = 0; i < list.size(); i++) { /* быстро */ }
} else {
    for (String s : list) { /* для LinkedList — через итератор */ }
}
```

### Когда что выбирать

- **ArrayList** — по умолчанию, почти всегда. Особенно когда много чтения, обхода, доступа по индексу.
- **LinkedList** — как `Deque`/`Queue` (быстрые операции с головы и хвоста) или когда очень много вставок/удалений именно через `ListIterator` в середине и мало случайного доступа.
- В современном коде вместо `LinkedList` как очереди чаще берут **`ArrayDeque`** — он быстрее и экономнее.

### Типичные ошибки

- Использовать `LinkedList` «потому что вставка O(1)», а потом постоянно вызывать `get(i)` — получается O(n²).
- Забывать, что `remove(int index)` и `remove(Object o)` — разные перегрузки. `list.remove(1)` удаляет по индексу, а `list.remove(Integer.valueOf(1))` — по значению.
- Считать, что `ArrayList` тратит память «ровно под элементы» — у него всегда есть запас ёмкости.

### Часто спрашивают на собеседовании

- **Что внутри ArrayList?** — динамический массив `Object[]`.
- **Что внутри LinkedList?** — двусвязный список узлов `Node` с `prev/next`.
- **Почему ArrayList часто быстрее?** — кэш-локальность и отсутствие накладных расходов на узлы.
- **Что такое RandomAccess?** — маркерный интерфейс, подсказывающий быстрый доступ по индексу.

## 3. HashMap vs Hashtable

### Аналогия

`Hashtable` — это старый **архив с одним ключом на всю комнату**: пока один человек что-то достаёт, остальные ждут у двери. `HashMap` — новый архив без охраны: быстро, но если двое полезут одновременно — может случиться бардак. `ConcurrentHashMap` — архив с ключом на каждый ящик: большинство работают параллельно.

### Сравнение

| Критерий | HashMap | Hashtable |
|---|---|---|
| Появился в | Java 1.2 | Java 1.0 (legacy) |
| Потокобезопасность | Нет | Да (`synchronized` на каждом методе) |
| `null`-ключ | Разрешён ровно один | **Запрещён** |
| `null`-значения | Разрешены | **Запрещены** |
| Родитель | `AbstractMap` | `Dictionary` (устаревший) |
| Итератор | fail-fast | fail-fast (`Enumeration` — нет) |
| Производительность | Выше | Ниже (глобальная блокировка) |
| Обход | `Iterator`, `forEach` | `Iterator` / `Enumeration` |

### Почему `Hashtable` запрещает `null`

`Hashtable` — ровно ровесник самой первой версии Java, и там `null` не разрешался, потому что `get(null)` не смог бы отличить «нет такого ключа» от «значение равно null». В `HashMap` эту проблему решили отдельной веткой: `null`-ключ всегда кладётся в корзину с индексом 0.

```java
Map<String, String> map = new HashMap<>();
map.put(null, "ноль");        // ок
map.put("a", null);           // ок
System.out.println(map.get(null)); // ноль

Hashtable<String, String> ht = new Hashtable<>();
ht.put(null, "ноль");         // NullPointerException!
```

### Чем заменять `Hashtable`

- **`ConcurrentHashMap`** — лучший вариант: нет глобальной блокировки, высокая конкурентность, запрещает `null`.
- **`Collections.synchronizedMap(new HashMap<>())`** — если нужен именно `Map` и простая синхронизация.
- **`HashMap` + внешняя синхронизация** — когда доступ редкий и вы контролируете блокировки сами.

### Типичные ошибки

- Использовать `Hashtable` в новом коде. Это legacy.
- Думать, что `ConcurrentHashMap` разрешает `null` — нет, он тоже бросает `NullPointerException` (чтобы не было неоднозначности в многопоточной среде).
- Путать потокобезопасность и «правильную» работу. Даже потокобезопасная коллекция не спасает от гонок на уровне бизнес-логики (нужны составные атомарные операции).

### Часто спрашивают на собеседовании

- **Чем Hashtable отличается от HashMap?** — синхронизацией, запретом `null`, наследованием от `Dictionary`.
- **Почему Hashtable legacy?** — глобальная блокировка убивает производительность.
- **Почему ConcurrentHashMap не разрешает null?** — чтобы `get` не был двусмысленным в конкурентной среде.

## 4. Set: HashSet, LinkedHashSet, TreeSet, EnumSet

### Аналогия

- **HashSet** — мешок с билетами, где порядок случаен.
- **LinkedHashSet** — тот же мешок, но билеты нанизаны на нитку в порядке появления.
- **TreeSet** — билеты, разложенные по алфавиту в ящике.
- **EnumSet** — набор лампочек-переключателей (включён/выключен) для фиксированного списка enum-значений.

### Устройство и свойства

| Реализация | Основа | Порядок | Сложность `add/contains` | `null` |
|---|---|---|---|---|
| `HashSet` | `HashMap` | Не гарантирован | O(1) в среднем | 1 null |
| `LinkedHashSet` | `LinkedHashMap` | Порядок вставки | O(1) в среднем | 1 null |
| `TreeSet` | `TreeMap` (красно-чёрное дерево) | Отсортирован | O(log n) | **Нет** (NPE) |
| `EnumSet` | битовая маска | Порядок объявления enum | O(1) | Нет |
| `CopyOnWriteArraySet` | `CopyOnWriteArrayList` | Порядок вставки | O(n) | 1 null |

### Как `Set` определяет дубликат

`HashSet` — это «обёртка» над `HashMap`, где элементы множества служат **ключами**, а значением всегда является одна и та же заглушка `PRESENT`.

```java
// упрощённо внутри HashSet
private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}
public boolean contains(Object o) {
    return map.containsKey(o);
}
```

Значит, дубликат определяется так же, как уникальность ключа в `HashMap`:
1. Вычисляется `hashCode()`.
2. Находится корзина.
3. Среди элементов корзины ищется совпадение по `equals()`.

**Если `equals`/`hashCode` не переопределены** — два «логически равных» объекта будут считаться разными.

```java
class User {
    String name;
    User(String name) { this.name = name; }
}

Set<User> set = new HashSet<>();
set.add(new User("Аня"));
set.add(new User("Аня"));
System.out.println(set.size()); // 2 — потому что equals/hashCode не переопределены!
```

С переопределёнными `equals`/`hashCode`:

```java
import java.util.Objects;

class User {
    String name;
    User(String name) { this.name = name; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        return Objects.equals(name, ((User) o).name);
    }
    @Override public int hashCode() {
        return Objects.hash(name);
    }
}

Set<User> set = new HashSet<>();
set.add(new User("Аня"));
set.add(new User("Аня"));
System.out.println(set.size()); // 1 — теперь дубликат распознан
```

### `TreeSet` и сравнение

`TreeSet` определяет «одинаковость» через `compareTo`/`compare`, **а не через `equals`**. Это коварно: два элемента могут быть `equals == false`, но `compareTo == 0`, и тогда второй не добавится.

```java
import java.util.*;

public class TreeSetTrap {
    static class Item implements Comparable<Item> {
        int id; String name;
        Item(int id, String name) { this.id = id; this.name = name; }
        public int compareTo(Item o) { return Integer.compare(id, o.id); } // только по id!
    }

    public static void main(String[] args) {
        Set<Item> set = new TreeSet<>();
        set.add(new Item(1, "A"));
        set.add(new Item(1, "B")); // compareTo == 0 → не добавится
        System.out.println(set.size()); // 1
    }
}
```

### `EnumSet` — самый быстрый `Set`

`EnumSet` хранит элементы как **битовую маску** (`long`/`long[]`). Операции — это битовые операции, поэтому он быстрее любого другого `Set` для enum.

```java
import java.util.*;

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

public class EnumSetDemo {
    public static void main(String[] args) {
        EnumSet<Day> weekend = EnumSet.of(Day.SAT, Day.SUN);
        EnumSet<Day> work    = EnumSet.range(Day.MON, Day.FRI);
        EnumSet<Day> all     = EnumSet.allOf(Day.class);
        EnumSet<Day> none    = EnumSet.noneOf(Day.class);

        System.out.println(weekend);          // [SAT, SUN]
        System.out.println(work.contains(Day.MON)); // true
        System.out.println(all.size());       // 7
    }
}
```

### Типичные ошибки

- Добавлять изменяемые объекты в `HashSet`, а потом менять их поля — элемент «теряется».
- Ожидать, что `HashSet` сохранит порядок вставки.
- Использовать `TreeSet` с элементами, не реализующими `Comparable` (без `Comparator`) — `ClassCastException`.
- Путать порядок: `LinkedHashSet` — порядок **вставки**, а не сортировки.

### Часто спрашивают на собеседовании

- **Как HashSet определяет дубликат?** — через `hashCode` + `equals` (он построен на `HashMap`).
- **Чем TreeSet отличается от HashSet?** — сортировка, O(log n), сравнение через `compareTo`.
- **Когда EnumSet?** — всегда, когда множество состоит из enum-значений.
- **Почему в TreeSet нельзя null?** — при сравнении `compareTo`/`compare` бросится NPE.

## 5. HashMap внутри

Это ядро собеседования. Разберём по слоям.

### Аналогия

`HashMap` — это **шкаф с ячейками (корзинами)**. У каждой ячейки есть номер. Чтобы положить вещь, вы по «паспорту» вещи (её `hashCode`) вычисляете номер ячейки. Если ячейка занята другой вещью — кладёте рядом (в цепочку). Когда ячеек становится мало, шкаф **расширяют вдвое** и перекладывают вещи.

### Структура

```java
// упрощённо
public class HashMap<K,V> {
    transient Node<K,V>[] table;    // массив корзин
    transient int size;             // сколько пар
    int threshold;                  // порог resize = capacity * loadFactor
    final float loadFactor;         // 0.75 по умолчанию

    static class Node<K,V> {
        final int hash;   // кэш хэша
        final K key;
        V value;
        Node<K,V> next;   // следующая нода в корзине
    }
}
```

- **capacity** — размер массива `table`, всегда **степень двойки**, по умолчанию 16.
- **load factor** — доля заполнения, при которой происходит расширение, по умолчанию **0.75**.
- **threshold** — `capacity * loadFactor`, при превышении `size` вызывается `resize()`.

### Как кладётся элемент (`put`)

1. **Хэш ключа:** `h = key.hashCode()`.
2. **Spread (перемешивание):** `h ^ (h >>> 16)`. Это XOR старших 16 бит с младшими. Зачем? Индекс берётся только из младших бит (`(n-1) & hash`), а младшие биты часто «неинформативны». Spread подмешивает старшие биты, чтобы уменьшить коллизии.
3. **Индекс корзины:** `index = (n - 1) & hash`, где `n` — длина массива (степень двойки). Это то же, что `hash % n`, но быстрее (побитовое И).
4. Если корзина **пуста** — создаём новый `Node`.
5. Если корзина **занята**:
   - сравниваем `hash`, затем `==` или `equals` ключа;
   - если ключ совпал — **перезаписываем** значение и возвращаем старое;
   - иначе идём по цепочке/дереву и добавляем в конец (Java 8) или в голову (Java 7).
6. Если `size > threshold` — **`resize()`**: capacity × 2, все элементы перераспределяются.

### Визуализация

```
table (capacity = 16)
┌────┐
│ 0  │ → Node("a",1) → Node("q",9)
│ 1  │ → null
│ 2  │ → Node("b",2)
│ 3  │ → null
│... │
│ 15 │ → null
└────┘
       ↑ коллизия: "a" и "q" попали в одну корзину
```

### Формула индекса и почему степень двойки

Пусть `n = 16` (`10000₂`), тогда `n-1 = 15` (`01111₂`). `(n-1) & hash` оставляет только младшие 4 бита — это число от 0 до 15, идеально для индекса.

Если бы `n` не была степенью двойки, у `n-1` были бы «дырки» в битах, и часть корзин никогда не использовалась бы → неравномерное распределение. Поэтому `HashMap` **всегда округляет** заданную capacity вверх до степени двойки.

```java
Map<String,Integer> m = new HashMap<>(10); // фактическая capacity будет 16
```

### Load factor 0.75 — почему именно 0.75

Компромисс между временем и памятью:
- Меньше 0.75 → меньше коллизий, но больше памяти и частые resize.
- Больше 0.75 → экономнее по памяти, но больше коллизий (длинные цепочки).

0.75 — эмпирически найденный баланс. В терминах теории вероятностей при таком коэффициенте средняя длина цепочки остаётся около 1, а вероятность длинных цепочек мала.

### Resize (расширение)

Когда `size > threshold`, массив увеличивается **вдвое**. В Java 8 элементы не пересчитывают индекс с нуля: поскольку capacity — степень двойки, новый индекс либо **тот же**, либо **старый + старая capacity**. Это оптимизация `lo/hi`-списков.

```
старая capacity = 16, новая = 32
элемент из корзины 5 → либо 5, либо 5+16=21
```

### Java 7 vs Java 8 — что изменилось

| Аспект | Java 7 | Java 8 |
|---|---|---|
| Вставка в корзину | В **голову** цепочки | В **хвост** |
| Структура при коллизиях | Только связный список | Список → **красно-чёрное дерево** при длине ≥ 8 |
| Порядок при resize | Мог **переворачиваться** | Сохраняется |
| Проблема конкурентного resize | Возможен **цикл** в списке (зависание) | Исправлено |
| Сложность худшего случая | O(n) | O(log n) |

**Java 7 — баг с циклом:** при одновременном `resize` из двух потоков вставка в голову могла создать кольцевую ссылку, и `get` зацикливался навсегда (100% CPU). В Java 8 вставка в хвост и новый алгоритм это устранили.

**Java 8 — treeify:** если в одной корзине накопилось ≥ `TREEIFY_THRESHOLD = 8` узлов **и** capacity ≥ `MIN_TREEIFY_CAPACITY = 64`, цепочка превращается в **красно-чёрное дерево** (TreeNode). Поиск становится O(log n) вместо O(n). Если узлов становится ≤ `UNTREEIFY_THRESHOLD = 6` — дерево обратно превращается в список.

### Ключевые константы

| Константа | Значение | Смысл |
|---|---|---|
| `DEFAULT_INITIAL_CAPACITY` | 16 | начальная capacity |
| `MAXIMUM_CAPACITY` | 1 << 30 | максимальная capacity |
| `DEFAULT_LOAD_FACTOR` | 0.75f | коэффициент загрузки |
| `TREEIFY_THRESHOLD` | 8 | порог превращения в дерево |
| `UNTREEIFY_THRESHOLD` | 6 | порог обратного превращения в список |
| `MIN_TREEIFY_CAPACITY` | 64 | минимальная capacity для treeify |

### Коллизии

**Коллизия** — разные ключи дают одинаковый индекс. Это нормально, но если `hashCode` плохой (например, всегда возвращает `1`), все элементы соберутся в одну корзину, и `HashMap` выродится в список O(n) (или дерево O(log n)).

```java
class BadKey {
    @Override public int hashCode() { return 1; } // все в одну корзину!
    @Override public boolean equals(Object o) { return this == o; }
}
```

### Требования к ключу

- **Стабильный `hashCode`** — не должен меняться, пока объект лежит в `HashMap`.
- **Корректный `equals`** — согласованный с `hashCode`.
- **Лучше неизменяемый (immutable)** — `String`, `Integer`, `Long`. Если ключ изменить, `hashCode` изменится, и элемент «потеряется» (его никто не найдёт).

```java
Map<List<String>, Integer> map = new HashMap<>();
List<String> key = new ArrayList<>(List.of("a"));
map.put(key, 1);
key.add("b");                 // изменили ключ!
System.out.println(map.get(key)); // null — элемент потерян
```

### `null`-ключ

`HashMap` разрешает один `null`-ключ. Его `hash` равен 0, поэтому он всегда лежит в корзине с индексом 0.

```java
Map<String,Integer> m = new HashMap<>();
m.put(null, 42);
System.out.println(m.get(null)); // 42
m.put(null, 43);                 // перезапишет
System.out.println(m.get(null)); // 43
```

### Типичные ошибки

- Использовать изменяемые объекты как ключи.
- Переопределить `equals`, но забыть `hashCode` (или наоборот).
- Задавать маленькую capacity при большом объёме данных — лишние resize.
- Ожидать от `HashMap` упорядоченности.
- Считать, что `HashMap` потокобезопасен.

### Часто спрашивают на собеседовании

- **Как работает `put`?** — spread-хэш → индекс `(n-1)&hash` → сравнение/перезапись → при переполнении resize.
- **Зачем `h ^ (h >>> 16)`?** — подмешать старшие биты в младшие для равномерности.
- **Почему capacity — степень двойки?** — чтобы `(n-1)&hash` работал как быстрый `%`.
- **Что такое load factor 0.75?** — баланс памяти и коллизий.
- **Что нового в Java 8?** — дерево при 8 элементах в корзине, вставка в хвост, исправлен баг с циклом.
- **Когда treeify?** — длина корзины ≥ 8 и capacity ≥ 64.
- **Почему HashMap не потокобезопасен?** — resize из двух потоков ломает структуру (в Java 7 — зацикливание).

## 6. ArrayList vs Vector

### Аналогия

`Vector` — старый **телефон с одной линией**: пока один говорит, все ждут. `ArrayList` — современный телефон без общей блокировки.

### Сравнение

| Критерий | ArrayList | Vector |
|---|---|---|
| Появился | Java 1.2 | Java 1.0 (legacy) |
| Синхронизация | Нет | Все методы `synchronized` |
| Рост capacity | ×1.5 | ×2 (по умолчанию) |
| Производительность | Выше | Ниже |
| Итератор | fail-fast | fail-fast (`Enumeration` — нет) |
| `RandomAccess` | Да | Да |

```java
// внутри ArrayList: рост примерно в 1.5 раза
int newCapacity = oldCapacity + (oldCapacity >> 1);

// внутри Vector: рост в 2 раза (или capacityIncrement)
int newCapacity = oldCapacity + ((capacityIncrement > 0) ? capacityIncrement : oldCapacity);
```

### `Stack` — тоже legacy

`Stack` наследует `Vector` и страдает теми же проблемами (синхронизация, странная иерархия). Современная замена — **`ArrayDeque`**:

```java
// Старый способ
Stack<Integer> stack = new Stack<>();
stack.push(1); stack.pop();

// Современный способ
Deque<Integer> stack2 = new ArrayDeque<>();
stack2.push(1); stack2.pop();
```

### Чем заменять `Vector`

- `ArrayList` + внешняя синхронизация — если доступ редкий.
- `CopyOnWriteArrayList` — если чтений много, а записей мало.
- `Collections.synchronizedList(new ArrayList<>())` — простая обёртка.

### Типичные ошибки

- Использовать `Vector`/`Stack` в новом коде.
- Думать, что синхронизация каждого метода = потокобезопасная логика. Составные операции (проверить-и-вставить) всё равно не атомарны.

### Часто спрашивают на собеседовании

- **Чем Vector отличается от ArrayList?** — синхронизацией и коэффициентом роста ×2 vs ×1.5.
- **Почему Vector legacy?** — глобальная блокировка на каждый метод.
- **Чем заменить Stack?** — `ArrayDeque`.

## 7. Потокобезопасные коллекции (`java.util.concurrent`)

### Аналогия

Обычные коллекции — как **общая кухня без правил**: если двое одновременно режут на одной доске, будет хаос. Concurrent-коллекции — кухня с **разделёнными рабочими зонами** и продуманными правилами доступа.

### `ConcurrentHashMap` (Java 8)

В Java 7 был **сегментированный** дизайн (по умолчанию 16 сегментов, каждый со своим замком). В Java 8 перешли на **CAS + синхронизацию отдельных корзин**:

- Чтения (`get`) вообще **без блокировок** (используется `volatile`-чтение узлов).
- Запись — через **CAS** при пустой корзине, иначе `synchronized` только на **первой ноде корзины**.
- Запрещены `null` (ключ и значение).
- `size()` приблизителен (не блокирует всю структуру).

```java
import java.util.concurrent.*;

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

map.put("a", 1);
map.putIfAbsent("a", 99);                 // не перезапишет, вернёт 1
map.compute("a", (k, v) -> v + 10);       // атомарно: 11
map.merge("a", 5, Integer::sum);          // 16
map.computeIfAbsent("b", k -> 100);       // положит 100

System.out.println(map.get("a"));         // 16
System.out.println(map.get("b"));         // 100
```

Атомарные составные операции — главное преимущество перед `synchronizedMap`:

| Метод | Что делает |
|---|---|
| `putIfAbsent(k, v)` | кладёт, только если ключа нет |
| `compute(k, fn)` | пересчитывает значение |
| `computeIfAbsent(k, fn)` | вычисляет и кладёт, если нет |
| `computeIfPresent(k, fn)` | обновляет, если есть |
| `merge(k, v, fn)` | объединяет старое и новое |

### `CopyOnWriteArrayList` / `CopyOnWriteArraySet`

При **каждой записи** создаётся **новая копия** всего массива. Чтения происходят по неизменяемому снимку и потому **не блокируются**.

```java
import java.util.concurrent.*;

CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("A");
list.add("B");

for (String s : list) {      // итерация по снимку
    list.add(s + "!");       // не бросает ConcurrentModificationException
}
System.out.println(list);    // [A, B, A!, B!]
```

**Когда использовать:** много чтений, мало записей (списки слушателей, конфигурации).
**Когда нельзя:** частые записи — каждая копирует весь массив, это O(n) на запись.

### `BlockingQueue` — для producer-consumer

`put` блокируется, если очередь полна; `take` — если пуста.

| Реализация | Особенность |
|---|---|
| `ArrayBlockingQueue` | фиксированный размер, массив |
| `LinkedBlockingQueue` | опционально ограниченная, связный список |
| `PriorityBlockingQueue` | приоритет, неограниченная |
| `SynchronousQueue` | без буфера: `put` ждёт `take` |
| `DelayQueue` | элементы доступны по истечении задержки |
| `LinkedTransferQueue` | высокая пропускная способность |

```java
import java.util.concurrent.*;

BlockingQueue<String> q = new ArrayBlockingQueue<>(2);
q.put("job1");            // не блокируется, есть место
new Thread(() -> {
    try { System.out.println("took " + q.take()); } catch (InterruptedException ignored) {}
}).start();
q.put("job2");
```

### `ConcurrentLinkedQueue`

Неблокирующая, потокобезопасная очередь на алгоритме **Michael-Scott** (CAS). Не поддерживает блокирующие операции. Хороша для высоконагруженных сценариев без ожидания.

```java
ConcurrentLinkedQueue<Integer> clq = new ConcurrentLinkedQueue<>();
clq.offer(1);
clq.offer(2);
System.out.println(clq.poll()); // 1
```

### `ConcurrentSkipListMap` / `ConcurrentSkipListSet`

Потокобезопасные **отсортированные** коллекции (аналог `TreeMap`/`TreeSet`) на основе **skip-list**. Операции O(log n), без глобальных блокировок.

```java
ConcurrentSkipListMap<Integer, String> m = new ConcurrentSkipListMap<>();
m.put(3, "c"); m.put(1, "a"); m.put(2, "b");
System.out.println(m);              // {1=a, 2=b, 3=c} — отсортировано
System.out.println(m.firstKey());   // 1
```

### Обёртки `Collections`

```java
List<String> base = new ArrayList<>();

// 1. Синхронизированная обёртка — блокировка на весь объект
List<String> sync = Collections.synchronizedList(base);
synchronized (sync) {                 // при итерации синхронизируемся вручную!
    for (String s : sync) System.out.println(s);
}

// 2. Только для чтения — бросает UnsupportedOperationException на изменение
List<String> ro = Collections.unmodifiableList(base);
// ro.add("x"); // UnsupportedOperationException

// 3. Неизменяемые фабрики Java 9+ — нельзя null
List<String> immutable = List.of("a", "b");
// immutable.set(0, "z"); // UnsupportedOperationException
```

> **Важно:** `synchronizedList` синхронизирует **отдельные** методы. Итерация — это несколько вызовов, поэтому её нужно оборачивать в `synchronized (list)` вручную, иначе `ConcurrentModificationException`.

### Типичные ошибки

- Итерировать `synchronizedList` без внешней синхронизации.
- Использовать `CopyOnWriteArrayList` при частых записях.
- Считать, что `unmodifiableList` делает копию. Нет — это **представление**, изменения в исходном списке видны.
- Пытаться положить `null` в `ConcurrentHashMap`.

### Часто спрашивают на собеседовании

- **Чем ConcurrentHashMap лучше Hashtable?** — блокировка не на всей таблице, а на корзинах/CAS.
- **Как устроен ConcurrentHashMap в Java 8?** — CAS + `synchronized` на корзине, чтение без блокировок.
- **Когда CopyOnWriteArrayList?** — много чтений, мало записей.
- **Чем `synchronizedList` опасен?** — итерация не синхронизирована, нужна ручная блокировка.
- **Разница `unmodifiableList` и `List.of`?** — первая — представление (может меняться извне), вторая — настоящая неизменяемая копия и не допускает null.

## 8. Итераторы: fail-fast vs fail-safe

### Аналогия

**fail-fast** — это как проверка билетов у двери: заметили нарушение — сразу остановка с ошибкой. **fail-safe** — как работа с **фотографией** зала: вы смотрите на снимок, даже если в зале уже всё переставили.

### Как работает fail-fast

У `ArrayList`/`HashMap` есть счётчик **`modCount`** — сколько раз структура изменялась. Итератор запоминает его при создании и на каждом `next()` сравнивает. Если не совпало — бросает `ConcurrentModificationException`.

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if (s.equals("b")) list.remove(s); // ConcurrentModificationException
}
```

### Правильный способ удаления

Только через `Iterator.remove()`:

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove(); // корректно
}
System.out.println(list); // [a, c]
```

Альтернативы: `list.removeIf(s -> s.equals("b"))` (Java 8+) или обычный цикл по индексу сзади.

### fail-safe

`CopyOnWriteArrayList`, `ConcurrentHashMap` итерируются по **снимку/слабо-согласованному виду**, поэтому `ConcurrentModificationException` не бросают, но могут не видеть свежие изменения.

```java
import java.util.concurrent.*;

List<String> list = new CopyOnWriteArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if (s.equals("b")) list.remove(s); // исключения НЕТ
}
System.out.println(list); // [a, c] (в исходном), но итератор видел старый снимок
```

### Сравнение

| | fail-fast | fail-safe |
|---|---|---|
| Примеры | `ArrayList`, `HashMap`, `HashSet` | `CopyOnWriteArrayList`, `ConcurrentHashMap` |
| Реакция на изменение | `ConcurrentModificationException` | Нет исключения |
| Работает по | Живой структуре | Снимку |
| Память | Экономично | Доп. копия (COW) |
| Актуальность данных | Актуальные | Может отставать |

> `ConcurrentModificationException` можно получить даже **в одном потоке** — это не только про многопоточность.

### Типичные ошибки

- Удалять элементы `list.remove(...)` прямо в `for-each`.
- Думать, что fail-fast — гарантия безопасности. Это «best effort»: счётчик может не сработать при гонке.
- Считать, что `ConcurrentHashMap` итератор всегда даёт актуальный снимок (он слабо-согласованный).

### Часто спрашивают на собеседовании

- **Что такое fail-fast?** — итератор падает при структурном изменении через `modCount`.
- **Что такое fail-safe?** — итерация по копии, без исключений.
- **Как безопасно удалять при итерации?** — `Iterator.remove()` или `removeIf`.
- **Может ли CME быть в одном потоке?** — да.

## 9. Вставка в ArrayList пошагово

### Устройство роста

```java
// add(e) — упрощённо
public boolean add(E e) {
    ensureCapacityInternal(size + 1); // хватит ли места?
    elementData[size++] = e;          // кладём и увеличиваем size
    return true;
}

// рост примерно в 1.5 раза
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1); // x1.5
    if (newCapacity < minCapacity) newCapacity = minCapacity;
    elementData = Arrays.copyOf(elementData, newCapacity); // копирование
}
```

### Почему ×1.5, а не ×2

- ×2 тратит больше памяти (запас вдвое).
- ×1.5 — компромисс: и resize не слишком частые, и памяти не жалко.
- Амортизированная сложность добавления в конец — **O(1)**: редкие дорогие resize «размазываются» по множеству дешёвых вставок.

### `ensureCapacity` — оптимизация

Если заранее известен размер, можно избежать лишних копирований:

```java
List<Integer> list = new ArrayList<>(10_000); // сразу нужная capacity
// или
ArrayList<Integer> list2 = new ArrayList<>();
list2.ensureCapacity(10_000); // зарезервировать заранее
```

### Вставка в середину — `System.arraycopy`

```java
// add(index, element) — сдвигаем хвост вправо
System.arraycopy(elementData, index,
                 elementData, index + 1,
                 size - index);
elementData[index] = element;
size++;
```

Это **O(n)** — отсюда медленные вставки/удаления в середине.

### `subList` — это view

`subList(from, to)` возвращает **представление** исходного списка. Изменения в нём влияют на оригинал и наоборот.

```java
List<Integer> list = new ArrayList<>(List.of(0, 1, 2, 3, 4));
List<Integer> sub = list.subList(1, 4); // [1, 2, 3]
sub.set(0, 100);                         // меняем view
System.out.println(list);                // [0, 100, 2, 3, 4] — оригинал изменился!
sub.clear();
System.out.println(list);                // [0, 4] — хвост тоже удалился
```

> Если нужно **удалить** диапазон — `list.subList(1, 4).clear()` работает и эффективно. Но после структурного изменения оригинала `subList` становится «инвалидированным» (`ConcurrentModificationException`).

### `Arrays.asList` — фиксированный размер

```java
List<String> fixed = Arrays.asList("a", "b", "c");
fixed.set(0, "z");        // ок
// fixed.add("d");        // UnsupportedOperationException
// fixed.remove(0);       // UnsupportedOperationException
```

`Arrays.asList` возвращает **view поверх массива**, а не `java.util.ArrayList` (это `Arrays$ArrayList`).

### `List.of` — полностью неизменяемый (Java 9+)

```java
List<String> immutable = List.of("a", "b");
// immutable.set(0, "z"); // UnsupportedOperationException
// immutable.add("c");    // UnsupportedOperationException
// List.of("a", null);    // NullPointerException
```

### Шпаргалка по «видам» списков

| Метод | Размер | Изменение элементов | add/remove | null |
|---|---|---|---|---|
| `new ArrayList<>()` | динамический | Да | Да | Да |
| `Arrays.asList(...)` | фиксированный | Да (`set`) | Нет | Да |
| `List.of(...)` | неизменяемый | Нет | Нет | Нет |
| `Collections.unmodifiableList(x)` | как у x | Нет | Нет | как у x |
| `subList(a,b)` | view | Да | Да (меняет оригинал) | как у оригинала |

### Типичные ошибки

- Делать `Arrays.asList(arr)` и пытаться туда `add` — `UnsupportedOperationException`.
- Путать `List.of` и `Arrays.asList` по поддержке `null`.
- Держать `subList` после изменения оригинала — «инвалидированный» view.
- Ожидать, что `new ArrayList<>(existing)` — это view; нет, это **копия**.

### Часто спрашивают на собеседовании

- **Как растёт ArrayList?** — в 1.5 раза, через `Arrays.copyOf`.
- **Амортизированная сложность add в конец?** — O(1).
- **Что такое `subList`?** — view, влияет на оригинал.
- **Разница `Arrays.asList` и `List.of`?** — первый фиксированный (set можно, add нельзя, null можно), второй полностью неизменяемый (null нельзя).
- **Зачем `ensureCapacity`?** — избежать лишних resize.

## 10. Прочие важные классы

### `LinkedHashMap` и LRU-кэш

`LinkedHashMap` наследует `HashMap`, но дополнительно ведёт **двусвязный список** элементов. Есть режим `accessOrder`:
- `false` (по умолчанию) — порядок **вставки**.
- `true` — порядок **доступа** (при `get` элемент переезжает в конец).

Это позволяет сделать **LRU-кэш** (Least Recently Used) — «выкидывать самый давно использованный», переопределив `removeEldestEntry`.

```java
import java.util.*;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;

    public LruCache(int maxSize) {
        super(16, 0.75f, true); // accessOrder = true
        this.maxSize = maxSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize; // true → старейший удаляется
    }

    public static void main(String[] args) {
        LruCache<Integer, String> cache = new LruCache<>(3);
        cache.put(1, "a");
        cache.put(2, "b");
        cache.put(3, "c");
        cache.get(1);            // 1 становится "свежим"
        cache.put(4, "d");       // вытеснится 2 (самый старый по доступу)
        System.out.println(cache.keySet()); // [3, 1, 4]
    }
}
```

### `TreeMap` и навигационные методы

`TreeMap` — красно-чёрное дерево, ключи отсортированы. Все операции O(log n). Есть «навигационные» методы:

```java
TreeMap<Integer, String> tm = new TreeMap<>();
tm.put(10, "a"); tm.put(20, "b"); tm.put(30, "c");

System.out.println(tm.firstKey());        // 10
System.out.println(tm.lastKey());         // 30
System.out.println(tm.floorKey(25));      // 20  ≤ 25
System.out.println(tm.ceilingKey(25));    // 30  ≥ 25
System.out.println(tm.lowerKey(20));      // 10  < 20
System.out.println(tm.higherKey(20));     // 30  > 20
System.out.println(tm.headMap(20));       // {10=a}
System.out.println(tm.tailMap(20));       // {20=b, 30=c}
System.out.println(tm.subMap(10, 30));    // {10=a, 20=b}
System.out.println(tm.descendingMap());   // {30=c, 20=b, 10=a}
```

### `WeakHashMap`

Ключи хранятся как **слабые ссылки** (`WeakReference`). Если на ключ больше никто не ссылается, запись удаляется сборщиком мусора. Подходит для **кэшей**, привязанных к объектам, которые не должны жить вечно.

```java
import java.util.*;

WeakHashMap<Object, String> whm = new WeakHashMap<>();
Object key = new Object();
whm.put(key, "value");
System.out.println(whm.size()); // 1
key = null;                     // потеряли сильную ссылку
System.gc();
Thread.sleep(100);
System.out.println(whm.size()); // 0 (может быть 0 после GC)
```

> Значения хранятся как сильные ссылки. Если значение ссылается на ключ — утечка.

### `IdentityHashMap`

Сравнивает ключи по **ссылке (`==`)**, а не по `equals`. Полезен, когда важна именно идентичность объектов.

```java
import java.util.*;

Map<String, String> m = new IdentityHashMap<>();
String a = new String("x");
String b = new String("x");
m.put(a, "first");
m.put(b, "second");
System.out.println(m.size());       // 2 — разные объекты
System.out.println(m.get(a));       // first
System.out.println(a.equals(b));    // true — но для IdentityHashMap это неважно
```

### `PriorityQueue`

**Бинарная куча**. `peek` — O(1), `add`/`poll` — O(log n). Голова — минимальный элемент (или по `Comparator`). Итерация **не отсортирована**, сортировку даёт только последовательное извлечение.

```java
import java.util.*;

PriorityQueue<Integer> pq = new PriorityQueue<>();
pq.add(5); pq.add(1); pq.add(3);
System.out.println(pq.peek()); // 1
System.out.println(pq.poll()); // 1
System.out.println(pq.poll()); // 3

// Максимум — через reverseOrder
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
```

### `ArrayDeque`

Быстрая реализация `Deque` на **круговом массиве**. Используется и как стек (`push/pop`), и как очередь (`offer/poll`). Быстрее и экономнее `Stack` и `LinkedList`.

```java
Deque<Integer> deque = new ArrayDeque<>();
deque.offerLast(1);   // очередь
deque.offerLast(2);
System.out.println(deque.pollFirst()); // 1

deque.push(10);       // стек
deque.push(20);
System.out.println(deque.pop());       // 20
```

> `ArrayDeque` **не допускает `null`** (в отличие от `LinkedList`).

### Сводная таблица

| Класс | Структура | Порядок | Сложность | Особенность |
|---|---|---|---|---|
| `LinkedHashMap` | хэш + список | вставки/доступа | O(1) | LRU-кэш |
| `TreeMap` | красно-чёрное дерево | сортировка | O(log n) | навигация |
| `WeakHashMap` | хэш + weak-ключи | — | O(1) | ключи под GC |
| `IdentityHashMap` | хэш | — | O(1) | сравнение `==` |
| `PriorityQueue` | бинарная куча | по приоритету | poll O(log n) | heap |
| `ArrayDeque` | круговой массив | двусторонний | O(1) | стек/очередь |

### Типичные ошибки

- Ждать от `PriorityQueue` отсортированной итерации.
- Использовать `WeakHashMap` без учёта GC — записи исчезают недетерминированно.
- Класть `null` в `ArrayDeque`/`PriorityQueue` (`PriorityQueue` — NPE при сравнении).
- Путать `IdentityHashMap` с обычным `HashMap`.

### Часто спрашивают на собеседовании

- **Как сделать LRU-кэш?** — `LinkedHashMap` с `accessOrder=true` и `removeEldestEntry`.
- **Чем TreeMap отличается от HashMap?** — сортировка, O(log n), навигационные методы.
- **Зачем WeakHashMap?** — кэш, не мешающий сборке мусора.
- **Чем IdentityHashMap?** — сравнение ключей по `==`.
- **Зачем ArrayDeque?** — быстрый стек/очередь вместо `Stack`/`LinkedList`.

## 11. equals/hashCode в коллекциях

### Контракт equals/hashCode

- Если `a.equals(b)`, то `a.hashCode() == b.hashCode()` (**обязательно**).
- Если `a.hashCode() == b.hashCode()`, то `a.equals(b)` **не обязательно** (коллизия).
- `equals` должен быть рефлексивным, симметричным, транзитивным, согласованным.
- `hashCode` не должен меняться, пока объект используется в хэш-коллекции.

```java
import java.util.Objects;

class Person {
    private final String name;
    private final int age;

    Person(String name, int age) { this.name = name; this.age = age; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Person p = (Person) o;
        return age == p.age && Objects.equals(name, p.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, age);
    }
}
```

### Сводная таблица: как коллекция определяет равенство/порядок

| Коллекция | Как определяет «равенство» | Как определяет порядок |
|---|---|---|
| `ArrayList` | `equals` (в `contains`/`remove`) | Индекс |
| `LinkedList` | `equals` | Позиция |
| `HashSet` / `HashMap` | `hashCode` + `equals` | Не гарантирован |
| `LinkedHashSet` / `LinkedHashMap` | `hashCode` + `equals` | Вставки/доступа |
| `TreeSet` / `TreeMap` | `compareTo` / `compare` (**не equals!**) | Сортировка |
| `PriorityQueue` | — | `compareTo` / `compare` |
| `EnumSet` / `EnumMap` | `==` (enum) | Порядок объявления |
| `IdentityHashMap` | `==` | Не гарантирован |
| `WeakHashMap` | `equals` + weak-ссылка | Не гарантирован |

> **Ключевой подвох:** `TreeSet`/`TreeMap` используют `compareTo`, а не `equals`. Поэтому «равными» считаются элементы с `compareTo == 0`, даже если `equals` вернул `false`. Рекомендуется, чтобы `compareTo` был согласован с `equals`.

### Правила выбора ключей

1. Ключ должен быть **неизменяемым** (`String`, `Integer`, `enum`, `record`).
2. Если ключ изменяемый — не менять поля, участвующие в `hashCode`/`equals`.
3. Всегда переопределяйте `equals` **и** `hashCode` вместе.
4. В `TreeMap`/`TreeSet` — следите за согласованностью `compareTo` и `equals`.
5. Не используйте в качестве ключей объекты с «плавающим» состоянием.

### Пример: ошибка «переопределил только equals»

```java
class Key {
    String id;
    Key(String id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof Key && ((Key) o).id.equals(id);
    }
    // hashCode НЕ переопределён → используется identity
}

Map<Key, Integer> map = new HashMap<>();
map.put(new Key("1"), 10);
System.out.println(map.get(new Key("1"))); // null! hashCode разный
```

### Типичные ошибки

- Переопределить только один из методов.
- Использовать изменяемые поля в `hashCode`.
- В `TreeSet` класть элементы, несогласованные по `compareTo`/`equals`.
- Забывать, что `hashCode` по умолчанию — identity-хэш (адрес объекта).

### Часто спрашивают на собеседовании

- **Какой контракт equals/hashCode?** — равные объекты → равные хэши; обратное не обязательно.
- **Что будет, если переопределить только equals?** — `HashMap`/`HashSet` не найдут элемент.
- **Чем определяется равенство в TreeSet?** — `compareTo`/`compare`, не `equals`.
- **Почему String — хороший ключ?** — immutable и стабильный `hashCode` (кэшируется).

## 12. Шпаргалка

**Иерархия**
- `Map` — не `Collection`. Ветки `Collection` и `Map` независимы.
- `List` — порядок + дубликаты; `Set` — уникальность; `Queue/Deque` — очередь/стек.

**Списки**
- `ArrayList`: массив, доступ O(1), вставка в середину O(n), рост ×1.5, `RandomAccess`, кэш-локальность.
- `LinkedList`: двусвязный список, вставка через итератор O(1), доступ O(n), больше памяти.
- `Vector`/`Stack` — legacy, синхронизированы; заменять на `ArrayList`/`ArrayDeque`.

**HashMap**
- Индекс: `(n - 1) & (h ^ (h >>> 16))`.
- capacity — степень двойки, load factor 0.75, resize ×2.
- Java 7: вставка в голову, возможен цикл при конкурентном resize.
- Java 8: вставка в хвост, treeify при длине ≥ 8 и capacity ≥ 64, untreeify при ≤ 6.
- Один `null`-ключ, много `null`-значений.

**Set**
- `HashSet` — на `HashMap`, без порядка, O(1).
- `LinkedHashSet` — порядок вставки.
- `TreeSet` — сортировка, O(log n), `compareTo` (не `equals`), null нельзя.
- `EnumSet` — битовая маска, самый быстрый.

**Concurrent**
- `ConcurrentHashMap` — CAS + `synchronized` на корзине, `null` запрещён.
- `CopyOnWriteArrayList` — копия при записи, много чтений / мало записей.
- `BlockingQueue` — producer-consumer, `put/take` блокируются.
- `Collections.synchronizedList` — при итерации нужна ручная синхронизация.
- `List.of` — неизменяемый и без `null`; `unmodifiableList` — view.

**Итераторы**
- fail-fast (`ArrayList`, `HashMap`) → `ConcurrentModificationException` по `modCount`.
- fail-safe (`CopyOnWriteArrayList`, `ConcurrentHashMap`) → итерация по снимку.
- Удалять — через `Iterator.remove()` или `removeIf`.

**equals/hashCode**
- Равные объекты → равные хэши. Переопределять всегда вместе.
- `TreeSet`/`TreeMap` — по `compareTo`/`compare`.
- Ключи — immutable.

## 13. Частые вопросы на собеседовании с короткими ответами

**1. Чем ArrayList отличается от LinkedList?**
`ArrayList` — массив (доступ O(1), вставка в середину O(n), хорошая кэш-локальность). `LinkedList` — двусвязный список (вставка O(1) при наличии итератора, доступ O(n), больше памяти).

**2. Что внутри HashMap?**
Массив корзин `Node[]`, где каждая корзина — список (или красно-чёрное дерево в Java 8). `Node` хранит `hash`, `key`, `value`, `next`.

**3. Как HashMap вычисляет индекс?**
`index = (n - 1) & (h ^ (h >>> 16))`, где `h = key.hashCode()`. Spread перемешивает биты, `&` работает как быстрый `%` для степени двойки.

**4. Зачем load factor 0.75?**
Компромисс: меньше коллизий, чем при 1.0, но экономнее памяти, чем при 0.5.

**5. Почему capacity — степень двойки?**
Чтобы `(n-1) & hash` давал равномерное распределение по всем корзинам и работал быстрее `%`.

**6. Что такое resize в HashMap?**
Удвоение capacity при `size > capacity * loadFactor` и перераспределение элементов. В Java 8 индекс либо сохраняется, либо сдвигается на старую capacity.

**7. Что изменилось в HashMap между Java 7 и 8?**
Java 7: вставка в голову, возможен цикл при конкурентном resize. Java 8: вставка в хвост, treeify при 8 элементах, исправлен цикл.

**8. Когда цепочка превращается в дерево?**
При длине корзины ≥ 8 (`TREEIFY_THRESHOLD`) и capacity ≥ 64 (`MIN_TREEIFY_CAPACITY`). Обратно — при ≤ 6.

**9. HashMap vs Hashtable?**
`HashMap` не синхронизирован, разрешает один null-ключ; `Hashtable` синхронизирован, null запрещён, legacy. Замена — `ConcurrentHashMap`.

**10. HashMap vs ConcurrentHashMap?**
`ConcurrentHashMap` потокобезопасен (CAS + блокировка корзины), null запрещён, есть атомарные `compute/merge/putIfAbsent`.

**11. Почему Map не Collection?**
`Map` хранит пары ключ→значение, а `Collection` — одиночные элементы; разные контракты. Но `keySet/values/entrySet` — это `Collection`.

**12. Как HashSet определяет дубликат?**
Через `hashCode` + `equals` (он построен на `HashMap`, элемент — ключ, значение — заглушка `PRESENT`).

**13. HashSet vs TreeSet?**
`HashSet` — без порядка, O(1), по `equals`; `TreeSet` — сортировка, O(log n), по `compareTo`, null нельзя.

**14. HashSet vs LinkedHashSet?**
`LinkedHashSet` дополнительно хранит двусвязный список и сохраняет порядок вставки.

**15. Когда EnumSet?**
Всегда, когда множество состоит из enum — это битовая маска, самый быстрый `Set`.

**16. fail-fast vs fail-safe?**
fail-fast (`ArrayList`, `HashMap`) бросает `ConcurrentModificationException` по `modCount`; fail-safe (`CopyOnWriteArrayList`, `ConcurrentHashMap`) итерируется по снимку.

**17. Как удалить элемент во время итерации?**
Через `Iterator.remove()`, `list.removeIf(...)` или цикл с конца по индексу.

**18. Может ли `ConcurrentModificationException` возникнуть в одном потоке?**
Да, если менять коллекцию во время `for-each`.

**19. Чем ArrayList отличается от Vector?**
`Vector` синхронизирован и растёт ×2 (legacy); `ArrayList` не синхронизирован и растёт ×1.5.

**20. Чем заменить Stack?**
`ArrayDeque` (`push/pop`).

**21. Что делает `ensureCapacity`?**
Заранее резервирует ёмкость, чтобы избежать лишних resize при массовом добавлении.

**22. Что такое `subList`?**
Представление (view) исходного списка; изменения отражаются в обе стороны.

**23. Разница `Arrays.asList` и `List.of`?**
`Arrays.asList` — фиксированный размер (set можно, add/remove нельзя, null можно). `List.of` — полностью неизменяемый и не допускает null.

**24. Разница `unmodifiableList` и `List.of`?**
`unmodifiableList` — view (меняется при изменении оригинала), `List.of` — настоящая неизменяемая коллекция.

**25. Как сделать LRU-кэш?**
`LinkedHashMap` с `accessOrder=true` и переопределённым `removeEldestEntry`.

**26. Чем TreeMap отличается от HashMap?**
`TreeMap` сортирует ключи, операции O(log n), есть навигация (`floorKey`, `ceilingKey`, `subMap`).

**27. Зачем WeakHashMap?**
Ключи — слабые ссылки; запись исчезает при GC, когда на ключ нет ссылок. Для кэшей.

**28. Чем IdentityHashMap?**
Сравнивает ключи по `==`, а не по `equals`.

**29. Как работает PriorityQueue?**
Бинарная куча: `peek` O(1), `add/poll` O(log n). Итерация не отсортирована.

**30. Каков контракт equals/hashCode?**
Если `a.equals(b)`, то `hashCode` равны. Обратное не обязательно. Переопределять только вместе.

**31. Что если переопределить только equals?**
`HashMap`/`HashSet` не найдут элемент, потому что `hashCode` останется identity-хэшем.

**32. Чем определяется равенство в TreeSet?**
`compareTo`/`compare`, а не `equals`. `compareTo == 0` → элемент считается дубликатом.

**33. Почему String — хороший ключ?**
Immutable, стабильный и кэшируемый `hashCode`, корректный `equals`.

**34. Можно ли null в ConcurrentHashMap?**
Нет, ни ключ, ни значение — `NullPointerException`.

**35. Когда CopyOnWriteArrayList?**
Когда чтений много, а записей мало (списки слушателей, конфигурации).

**36. Что такое `Collections.synchronizedList` и в чём подвох?**
Синхронизированная обёртка; при итерации нужно вручную синхронизироваться на коллекции, иначе `ConcurrentModificationException`.
