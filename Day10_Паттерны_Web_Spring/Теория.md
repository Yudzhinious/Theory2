# Часть A. Паттерны проектирования

## A.1. Зачем нужны паттерны

### Что это такое

**Паттерн проектирования** (design pattern) — это типовое, многократно проверенное решение часто встречающейся проектной задачи. Это не библиотека, не фреймворк и не готовый код. Это **шаблон описания решения**: как расположить классы и объекты, чтобы решить конкретную проблему гибко и понятно.

### Аналогия из жизни

Представь, что ты строишь дома. Есть типовые решения: «винтовая лестница», «несущая стена», «эркер». Архитектор не изобретает их каждый раз заново — он берёт проверенный проект и адаптирует. Паттерны — это такие же «типовые узлы» в программировании.

Другая аналогия: **кулинарная книга**. Паттерн — это рецепт борща. Ты можешь варить борщ в разных кастрюлях, с разным мясом, но последовательность действий и идея остаются узнаваемыми.

### Почему это важно на практике

1. **Общий язык.** Сказать коллеге «давай тут применим Strategy» в десять раз быстрее, чем полчаса объяснять структуру классов.
2. **Проверенные решения.** Паттерн уже обкатан тысячами проектов — ты не изобретаешь велосипед.
3. **Поддерживаемость.** Код, написанный по знакомому паттерну, легче читать новому разработчику.
4. **Гибкость к изменениям.** Паттерны часто решают именно проблему «как менять поведение, не ломая всё вокруг».

### Чего паттерны НЕ делают

- Не заменяют понимание задачи. Паттерн, прикрученный «потому что модно», делает код **хуже** (это называют *over-engineering*).
- Не дают готового кода. Их приходится реализовывать руками.
- Не отменяют принципы SOLID — наоборот, опираются на них.

### Классификация GoF

В 1994 году четыре автора (Gang of Four: Gamma, Helm, Johnson, Vlissides) в книге «Design Patterns» описали **23 паттерна**, разделив их на три группы. Это деление до сих пор спрашивают.

| Группа | Что решает | Паттерны |
|---|---|---|
| **Порождающие** (Creational) | Как создавать объекты, не привязываясь к конкретным классам | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| **Структурные** (Structural) | Как собирать объекты в крупные структуры | Adapter, Decorator, Proxy, Composite, Facade, Bridge, Flyweight |
| **Поведенческие** (Behavioral) | Как распределять обязанности и взаимодействие между объектами | Command, Observer, Strategy, State, Chain of Responsibility, Iterator, Template Method, Mediator, Visitor, Memento, Interpreter |

**Мнемоника для запоминания:** порождающие — «кто родился», структурные — «как устроено», поведенческие — «как общается».

### Часто спрашивают на собеседовании

- **Сколько паттернов GoF?** — 23.
- **Паттерн и фреймворк — в чём разница?** — Паттерн это описание решения (идея), фреймворк — готовый код.
- **Всегда ли нужны паттерны?** — Нет, только когда есть соответствующая проблема; иначе усложняют код.

## A.2. Factory Method

### Проблема

Клиентскому коду нужно создать объект, но он не должен знать, **какой именно конкретный класс** создаётся. Иначе при добавлении нового типа придётся менять клиента.

### Аналогия из жизни

Ты приходишь в **кафе** и говоришь «американо». Тебе не важно, кто и как его варит, какая марка кофемашины и какой бариста. Ты работаешь с абстракцией «напиток», а конкретику выбирает кухня. Фабрика — это бармен, который по названию выдаёт готовый объект.

### Реализация

```java
interface Transport {
    void deliver();
}

class Truck implements Transport {
    public void deliver() { System.out.println("Доставка грузовиком"); }
}

class Ship implements Transport {
    public void deliver() { System.out.println("Доставка кораблём"); }
}

abstract class Logistics {
    // Фабричный метод — переопределяется наследниками
    protected abstract Transport createTransport();

    public void planDelivery() {
        Transport t = createTransport();
        t.deliver();
    }
}

class RoadLogistics extends Logistics {
    protected Transport createTransport() { return new Truck(); }
}

class SeaLogistics extends Logistics {
    protected Transport createTransport() { return new Ship(); }
}
```

Клиент работает с `Logistics` и не знает, что внутри `Truck`. Добавить новый вид доставки — значит добавить новый подкласс, не трогая клиента (принцип Open/Closed).

### Где встречается в JDK

- `Calendar.getInstance()` — возвращает платформо-зависимую реализацию.
- `NumberFormat.getInstance()` — локаль-зависимый форматтер.
- `List.of()`, `Map.of()` — статические фабричные методы (вариант «Simple Factory»).
- `valueOf()` в обёртках и enum.

### Типичные ошибки

- Путать **Factory Method** (создание через наследование, переопределение метода) с **Simple Factory** (один класс с `switch`). Simple Factory — не паттерн GoF, но очень частый приём.
- Возвращать из фабрики `null` вместо исключения или `Optional` — клиент потом падает с NPE.
- Делать фабрику на всё подряд — получается «божественный» класс с гигантским `switch`.

### Часто спрашивают на собеседовании

- **Чем Factory Method отличается от Abstract Factory?** — Factory Method создаёт **один** продукт через наследование; Abstract Factory создаёт **семейство** связанных продуктов через композицию.
- **Приведи пример из JDK.** — `Calendar.getInstance()`, `NumberFormat.getInstance()`.

## A.3. Abstract Factory

### Проблема

Нужно создавать **целое семейство** взаимосвязанных объектов (например, кнопка, чекбокс и окно в одном стиле), при этом не привязываясь к конкретным классам и не смешивая стили.

### Аналогия из жизни

**Мебельный гарнитур.** Ты выбираешь стиль: «модерн» или «классика». Внутри стиля есть диван, стол, стул, и они должны сочетаться. Ты не покупаешь диван из модерна и стол из классики — фабрика стиля выдаёт всё согласованно.

### Реализация

```java
interface Button { void paint(); }
interface Checkbox { void paint(); }

class WinButton implements Button { public void paint() { System.out.println("Windows button"); } }
class MacButton implements Button { public void paint() { System.out.println("Mac button"); } }
class WinCheckbox implements Checkbox { public void paint() { System.out.println("Windows checkbox"); } }
class MacCheckbox implements Checkbox { public void paint() { System.out.println("Mac checkbox"); } }

interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}

class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}
```

Клиент получает одну фабрику и создаёт через неё согласованный набор. Замена фабрики = замена всей темы оформления.

### Factory Method vs Abstract Factory

| | Factory Method | Abstract Factory |
|---|---|---|
| Что создаёт | Один продукт | Семейство продуктов |
| Механизм | Наследование (переопределение метода) | Композиция (объект-фабрика) |
| Аналогия | Бармен делает один напиток | Фабрика делает весь гарнитур |
| Масштабирование | Новый подкласс | Новый класс-фабрика |

### Типичные ошибки

- Создавать Abstract Factory там, где семейство состоит из одного продукта — это лишний слой.
- Смешивать продукты разных фабрик (взять кнопку из Win, а чекбокс из Mac) — теряется весь смысл.

### Часто спрашивают на собеседовании

- **Реальный пример Abstract Factory?** — `javax.xml.parsers.DocumentBuilderFactory`, `javax.xml.transform.TransformerFactory`; UI-тулкиты (AWT/Swing/JavaFX).

## A.4. Builder

### Проблема

У объекта много необязательных параметров, и конструктор превращается в «телескоп» из 10 аргументов, где легко перепутать порядок.

### Аналогия из жизни

**Сборка заказа в Burger King.** Ты не диктуешь всё одной скороговоркой: сначала «булка», потом «котлета», потом «сыр», потом «без лука». Каждый шаг возвращает тебе конструктор, и в конце `build()` выдаёт готовый бургер.

### Плохо vs хорошо

```java
// Плохо: телескопический конструктор
new User("Ivan", "Ivanov", 25, "Moscow", "ivan@mail.ru", true, false, null);

// Хорошо: Builder
User u = User.builder()
        .name("Ivan")
        .age(25)
        .email("ivan@mail.ru")
        .active(true)
        .build();
```

### Реализация вручную

```java
public class User {
    private final String name;
    private final int age;
    private final String email;

    private User(Builder b) {
        this.name = b.name;
        this.age = b.age;
        this.email = b.email;
    }

    public static Builder builder() { return new Builder(); }

    public static class Builder {
        private String name;
        private int age;
        private String email;

        public Builder name(String name) { this.name = name; return this; }
        public Builder age(int age) { this.age = age; return this; }
        public Builder email(String email) { this.email = email; return this; }

        public User build() {
            // здесь можно валидировать обязательные поля
            if (name == null) throw new IllegalStateException("name is required");
            return new User(this);
        }
    }
}
```

### Где встречается

- `StringBuilder` — классический пример.
- `Stream.Builder`.
- `HttpRequest.newBuilder()` (Java 11 HTTP Client).
- Lombok `@Builder` — генерирует всё автоматически.
- `ResponseEntity.status(...).header(...).body(...)` в Spring.

### Типичные ошибки

- Делать `build()` без валидации обязательных полей — ошибка вылезет позже и в другом месте.
- Делать сеттеры билдера публичными мутирующими объект — тогда теряется иммутабельность.
- Писать Builder руками, когда подключён Lombok — трата времени.

### Часто спрашивают на собеседовании

- **Зачем Builder, если есть сеттеры?** — Иммутабельность, читаемость, валидация в одном месте, безопасность в многопоточности.
- **Что такое fluent interface?** — Цепочка вызовов, где методы возвращают `this` (или новый объект).

## A.5. Singleton

### Проблема

Нужно, чтобы у класса был **ровно один экземпляр** на JVM (или на контейнер) и глобальная точка доступа к нему.

### Аналогия из жизни

**Главный выключатель электричества в доме.** Он один. Неважно, из какой комнаты ты к нему обращаешься — ты управляешь одним и тем же рубильником.

### Реализация 1. Enum (лучший способ)

```java
public enum Config {
    INSTANCE;

    private final String url = "jdbc:postgresql://localhost/db";
    public String getUrl() { return url; }
}

// Использование
Config.INSTANCE.getUrl();
```

**Почему enum лучший:** JVM гарантирует единственность экземпляра даже при сериализации (сериализация enum не создаёт новый объект) и защищает от создания через рефлексию (в конструкторе enum выбрасывается исключение при попытке `newInstance`).

### Реализация 2. Static Holder (ленивый, потокобезопасный, без synchronized)

```java
public class Config {
    private Config() {}

    private static class Holder {
        private static final Config INSTANCE = new Config();
    }

    public static Config getInstance() {
        return Holder.INSTANCE; // класс Holder загрузится только при первом обращении
    }
}
```

**Почему работает:** инициализация класса в JVM потокобезопасна (гарантия спецификации языка). `Holder` загружается только при первом вызове `getInstance()` — ленивая инициализация без блокировок. Идиома называется *Initialization-on-demand holder*.

### Реализация 3. Double-Checked Locking + volatile

```java
public class Config {
    private static volatile Config instance;

    private Config() {}

    public static Config getInstance() {
        if (instance == null) {                 // первая проверка без блокировки
            synchronized (Config.class) {
                if (instance == null) {         // вторая проверка внутри блокировки
                    instance = new Config();
                }
            }
        }
        return instance;
    }
}
```

**Почему `volatile` обязателен:** без него возможна ситуация, когда поток видит «частично сконструированный» объект из-за переупорядочивания инструкций процессором и кэширования. `volatile` запрещает переупорядочивание и обеспечивает видимость.

### Где в Java SE

- `Runtime.getRuntime()` — доступ к среде исполнения.
- `System.getSecurityManager()`.
- `Desktop.getDesktop()`.
- В Spring бины по умолчанию `singleton` (но это **один экземпляр на контейнер**, а не на JVM).

### Как «сломать» Singleton и как защититься

| Атака | Суть | Защита |
|---|---|---|
| **Рефлексия** | `Constructor.setAccessible(true)` + `newInstance()` создаёт второй объект | Проверка в конструкторе: если `instance != null` — бросать исключение. **Enum защищён из коробки** |
| **Сериализация/десериализация** | При чтении объекта создаётся новый экземпляр | Реализовать `readResolve()` (возвращать существующий INSTANCE). **Enum защищён** |
| **Несколько ClassLoader'ов** | Каждый загрузчик загружает класс независимо → у каждого свой static | Архитектурно: один загрузчик на класс, либо признать, что singleton — на загрузчик |

```java
// Защита от рефлексии
private Config() {
    if (instance != null) {
        throw new IllegalStateException("Use getInstance()");
    }
}

// Защита от сериализации
private Object readResolve() {
    return getInstance();
}
```

### Типичные ошибки

- Делать singleton из всего подряд — это глобальное состояние, плохо тестируется и создаёт скрытые связи.
- Забыть `volatile` в DCL — тонкий баг, который «иногда» воспроизводится.
- Считать, что Spring `singleton` и классический GoF Singleton — одно и то же. Spring-бин может быть пересоздан при определённых условиях, а также «singleton» означает один экземпляр в рамках `ApplicationContext`.

### Часто спрашивают на собеседовании

- **Какой Singleton самый безопасный и почему?** — Через enum: защищён от рефлексии и сериализации.
- **Почему DCL требует volatile?** — Иначе возможна публикация частично инициализированного объекта.
- **Как сломать singleton?** — Рефлексия, сериализация, ClassLoader, клонирование (`clone`).
- **Singleton — это антипаттерн?** — В избытке да, из-за глобального состояния и сложности тестирования; в виде DI-бинов — норма.

## A.6. Prototype

### Проблема

Создание объекта «с нуля» дорого (много вычислений, запросов), а новый объект отличается от существующего лишь несколькими полями. Нужно **клонировать** уже готовый.

### Аналогия из жизни

**Ксерокопия документа.** Ты не набираешь документ заново, а делаешь копию и правишь пару строк.

### Реализация

```java
public class Sheep implements Cloneable {
    private String name;
    private int age;

    public Sheep(String name, int age) { this.name = name; this.age = age; }

    @Override
    public Sheep clone() {
        try {
            return (Sheep) super.clone(); // поверхностная копия
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

### Поверхностное vs глубокое копирование

- **Shallow copy** (`Object.clone()` по умолчанию) — копируются значения полей, но **ссылки** остаются общими. Изменил вложенный объект в копии — изменился и в оригинале.
- **Deep copy** — рекурсивно копируются все вложенные объекты. Реализуется вручную, через конструктор копирования или сериализацию.

```java
// Конструктор копирования — часто удобнее clone()
public Sheep(Sheep other) {
    this.name = other.name;
    this.age = other.age;
    this.tags = new ArrayList<>(other.tags); // глубокая копия коллекции
}
```

### Где встречается

- `Object.clone()` и `Cloneable`.
- `ArrayList`/`HashMap` конструкторы-копии.
- В Spring scope `prototype` — это **не** про клонирование, а про создание нового бина при каждом запросе. Не путать!

### Типичные ошибки

- Использовать `clone()` и забыть про вложенные mutable-объекты → получаешь общие ссылки.
- Не реализовать `Cloneable` и получить `CloneNotSupportedException`.
- Путать паттерн Prototype со Spring-scope `prototype`.

### Часто спрашивают на собеседовании

- **Чем shallow отличается от deep copy?** — Ссылками на вложенные объекты.
- **Почему `clone()` считается проблемным API?** — `Cloneable` — «магический» интерфейс без метода, поверхностная копия по умолчанию, checked-исключение; часто предпочитают конструктор копирования.

## A.7. Command

### Идея

Инкапсулировать **запрос как объект**: параметры, получатель и действие упакованы вместе. Позволяет ставить запросы в очередь, логировать, отменять.

### Аналогия из жизни

**Заказ в ресторане на бумажке.** Официант записывает заказ (объект) и несёт на кухню. Заказ можно отложить, поставить в очередь, отменить.

```java
interface Command {
    void execute();
    default void undo() {}
}

class LightOnCommand implements Command {
    private final Light light;
    LightOnCommand(Light light) { this.light = light; }
    public void execute() { light.on(); }
    public void undo() { light.off(); }
}

class RemoteControl {
    private Command slot;
    void setCommand(Command c) { this.slot = c; }
    void press() { slot.execute(); }
}
```

### Где встречается

- `Runnable` и `Callable` — команда без параметров/с результатом.
- `javax.swing.Action`, обработчики кнопок.
- Пул задач `ExecutorService.submit(...)`.
- Транзакции и undo/redo в редакторах.

### Часто спрашивают

- **Зачем Command, если есть лямбды?** — Для очередей, отмены, логирования, хранения состояния команды. Лямбда — это уже упрощённый Command.

## A.8. Composite

### Идея

Представить «часть-целое» в виде **дерева**, где и лист, и контейнер имеют общий интерфейс. Клиент работает с деревом единообразно.

### Аналогия из жизни

**Файловая система.** Файл и папка — оба «узлы». Папка содержит файлы и другие папки. Команда «показать размер» работает и для файла, и для папки.

```java
interface Node {
    int size();
}

class FileNode implements Node {
    private final int bytes;
    FileNode(int bytes) { this.bytes = bytes; }
    public int size() { return bytes; }
}

class FolderNode implements Node {
    private final List<Node> children = new ArrayList<>();
    void add(Node n) { children.add(n); }
    public int size() { return children.stream().mapToInt(Node::size).sum(); }
}
```

### Где встречается

- `java.nio.file.Path` (дерево путей), `File`.
- DOM `Node` в XML/HTML.
- `java.awt.Container` и компоненты Swing.
- Дерево UI-компонентов.

### Часто спрашивают

- **Чем Composite отличается от Decorator?** — Composite — дерево «много детей, часть-целое»; Decorator — обёртка вокруг **одного** объекта, добавляющая поведение.

## A.9. Chain of Responsibility

### Идея

Запрос передаётся по **цепочке обработчиков**. Каждый решает: обработать самому, передать дальше или прервать. Отправитель не знает, кто обработает.

### Аналогия из жизни

**Техподдержка по уровням.** Сначала бот, потом оператор первой линии, потом инженер. Если уровень не может решить — эскалирует дальше.

```java
abstract class Handler {
    protected Handler next;
    Handler setNext(Handler next) { this.next = next; return next; }
    abstract void handle(String request);
}

class AuthFilter extends Handler {
    void handle(String req) {
        System.out.println("Проверка аутентификации: " + req);
        if (next != null) next.handle(req);
    }
}
```

### Где встречается

- **Servlet `Filter`** и `FilterChain.doFilter()` — главный пример для Java-веба.
- `java.util.logging.Logger` (уровни и родительские логгеры).
- Spring Security `SecurityFilterChain`.
- Обработка исключений по цепочке.

### Часто спрашивают

- **Как связан с сервлет-фильтрами?** — Фильтры образуют цепочку, `FilterChain.doFilter()` вызывает следующий; логика «до» идёт по порядку, «после» — в обратном.

## A.10. State

### Идея

Поведение объекта зависит от его **состояния**, и каждое состояние вынесено в отдельный класс. Объект делегирует поведение текущему состоянию.

### Аналогия из жизни

**Светофор.** Один и тот же объект «светофор» ведёт себя по-разному: на красном — «стоять», на зелёном — «идти». Состояние меняется, поведение — тоже.

```java
interface State {
    void handle(Order ctx);
}

class NewState implements State {
    public void handle(Order ctx) {
        System.out.println("Оплата");
        ctx.setState(new PaidState());
    }
}

class PaidState implements State {
    public void handle(Order ctx) {
        System.out.println("Отправка");
        ctx.setState(new ShippedState());
    }
}
```

### State vs Strategy

| | State | Strategy |
|---|---|---|
| Смена | Состояния **сами** переключают друг друга | Клиент выбирает стратегию снаружи |
| Смысл | Модель состояний объекта | Сменный алгоритм |
| Пример | Заказ: New → Paid → Shipped | Способы сортировки |

### Где встречается

- `Thread.State` (NEW, RUNNABLE, BLOCKED…).
- Конечные автоматы в бизнес-процессах (заказы, платежи).
- Парсеры.

## A.11. Iterator

### Идея

Последовательный доступ к элементам коллекции **без раскрытия** её внутреннего устройства.

### Аналогия из жизни

**Пульт листания каналов.** Ты нажимаешь «следующий», не зная, как устроен список каналов.

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.isEmpty()) it.remove(); // безопасное удаление
}
```

### Важное правило

Нельзя менять коллекцию во время итерации напрямую (`list.remove`) — будет `ConcurrentModificationException`. Используй `Iterator.remove()` или `removeIf()`.

### Где встречается

- `Iterator`, `ListIterator`, `Enumeration`.
- Внутри `for-each` (компилятор разворачивает в Iterator).
- `Stream` — это уже не Iterator, а ленивый конвейер.

### Часто спрашивают

- **Почему `ConcurrentModificationException`?** — Из-за fail-fast: коллекция отслеживает `modCount`, а итератор проверяет его на каждом шаге.

## A.12. Proxy

### Идея

**Суррогат** (заместитель), контролирующий доступ к реальному объекту. Может добавить ленивую загрузку, кэш, права, логирование, транзакции.

### Аналогия из жизни

**Секретарь.** Чтобы попасть к директору, ты общаешься с секретарём. Он может записать на приём, отказать или переадресовать.

### Виды прокси

- **Виртуальный** — ленивая инициализация тяжёлого объекта.
- **Защитный** — проверка прав.
- **Удалённый** — вызов через сеть (RMI, gRPC-стабы).
- **Кэширующий** — кэш результатов.

### Где встречается

- `java.lang.reflect.Proxy` (динамический прокси для интерфейсов).
- Spring AOP: `@Transactional`, `@Cacheable`, `@Async`.
- Ленивая загрузка в Hibernate (lazy loading).

### Часто спрашивают

- **Чем Proxy отличается от Decorator и Adapter?** — Proxy контролирует доступ (тот же интерфейс), Decorator **добавляет** поведение, Adapter **меняет** интерфейс.

---

## A.13. Observer

### Идея

Объект-издатель уведомляет подписчиков об изменениях, не зная о них конкретно. Слабая связанность.

### Аналогия из жизни

**Подписка на YouTube-канал.** Канал (subject) публикует видео, подписчики (observers) получают уведомление. Канал не знает, кто именно смотрит.

```java
interface Observer {
    void update(String event);
}

class EventManager {
    private final List<Observer> observers = new ArrayList<>();
    void subscribe(Observer o) { observers.add(o); }
    void notifyAll(String e) { observers.forEach(o -> o.update(e)); }
}
```

### Где встречается

- `java.util.EventListener`, `PropertyChangeListener`.
- Swing: `addActionListener`.
- Реактивные потоки: RxJava, Reactor, `Flow` API.
- Spring `ApplicationEventPublisher`.

### Часто спрашивают

- **Какие минусы Observer?** — Утечки памяти, если не отписываться; непредсказуемый порядок уведомлений; «лавина» событий.

## A.14. Decorator / Adapter / Wrapper

Три похожих по структуре паттерна, которые часто путают.

| Паттерн | Что делает | Интерфейс | Пример |
|---|---|---|---|
| **Decorator** | Добавляет поведение обёрткой | Тот же | `BufferedInputStream`, `Collections.unmodifiableList` |
| **Adapter** | Превращает один интерфейс в другой | Другой | `InputStreamReader`, `Collections.enumeration` |
| **Proxy** | Контролирует доступ | Тот же | Spring AOP, lazy loading |
| **Facade** | Упрощает подсистему одним интерфейсом | Новый, простой | `JdbcTemplate` над JDBC |

**Wrapper** — общее бытовое название для «обёрток» (Decorator/Adapter/Proxy).

### Decorator пример

```java
InputStream in = new BufferedInputStream(
        new FileInputStream("data.bin"));
```

Каждая обёртка добавляет функциональность (буферизацию, подсчёт байт и т.д.), не меняя интерфейс.

### Adapter пример

```java
// InputStreamReader адаптирует байтовый поток к символьному
Reader r = new InputStreamReader(new FileInputStream("f.txt"), StandardCharsets.UTF_8);
```

### Часто спрашивают

- **Adapter vs Decorator?** — Adapter меняет интерфейс, Decorator сохраняет и расширяет.
- **Фасад vs Proxy?** — Фасад упрощает **много** классов, Proxy подменяет **один**.

## A.15. Immutable

### Идея

Объект, состояние которого нельзя изменить после создания. Потокобезопасен по определению, удобен для кэширования и ключей.

### Аналогия из жизни

**Напечатанная книга.** Содержимое зафиксировано, можно передавать кому угодно, никто случайно не перепишет.

### Правила создания

1. Класс `final` (нельзя унаследовать и переопределить поведение).
2. Все поля `private final`.
3. Нет сеттеров.
4. Mutable-поля (коллекции, даты) копируются при создании и при выдаче (defensive copy).
5. Возвращаются копии/неизменяемые представления.

```java
public final class Money {
    private final long amount;
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public long amount() { return amount; }
    public String currency() { return currency; }

    public Money plus(Money other) {
        return new Money(this.amount + other.amount, currency);
    }
}
```

### Где встречается

- `String`, `Integer` и обёртки.
- `java.time` (LocalDate, Instant).
- `record` — компилятор делает почти всё сам.
- `List.of()`, `Map.of()` — неизменяемые коллекции.

### Типичные ошибки

- Сделать поля final, но хранить `Date`/`List` и отдавать ссылку наружу — объект перестаёт быть неизменяемым.
- Считать `record` абсолютно неизменяемым: если внутри mutable-поле, оно остаётся изменяемым.

### Часто спрашивают

- **Зачем иммутабельность?** — Потокобезопасность, кэшируемость, безопасные ключи, отсутствие побочных эффектов.
- **`String` immutable — почему?** — Безопасность (пароли, пути), кэш `hashCode`, пул строк, безопасное использование в качестве ключей.

## A.16. MVC

### Идея

Разделить приложение на три части:

- **Model** — данные и бизнес-логика.
- **View** — представление (UI).
- **Controller** — принимает ввод и координирует Model и View.

### Аналогия из жизни

**Ресторан.** Кухня (Model) готовит, зал (View) показывает, официант (Controller) принимает заказ и связывает их.

### В Spring MVC

- **Model** — `Model`/`ModelMap`, сущности, сервисы.
- **View** — JSP, Thymeleaf, JSON (через `@ResponseBody`).
- **Controller** — `@Controller`/`@RestController`, `DispatcherServlet` — фронт-контроллер.

```java
@Controller
public class UserController {
    @GetMapping("/users/{id}")
    public String user(@PathVariable Long id, Model model) {
        model.addAttribute("user", userService.findById(id));
        return "user"; // имя view
    }
}
```

### Варианты MVC

- **MVC** — контроллер и модель, view пассивна.
- **MVP** — Presenter связывает View и Model, View максимально «тупая».
- **MVVM** — ViewModel с двусторонним связыванием (Android, WPF).

## A.17. DAO vs Repository

| | DAO | Repository |
|---|---|---|
| Уровень | Низкий, доступ к данным | Доменный |
| Мышление | Таблицами и SQL | Объектами и агрегатами |
| Интерфейс | CRUD к источнику | Коллекция агрегатов |
| Пример | `UserDao.findById`, `insert` | `UserRepository.findAll`, `save` |
| Связь с БД | Знает SQL/ORM детали | Может скрывать несколько DAO |

- **DAO** — про персистентность: как сохранить/прочитать.
- **Repository** — про домен: «дай мне заказы пользователя», «добавь заказ». Внутри может использовать DAO.
- В Spring Data JPA интерфейсы `JpaRepository` — это уже готовые репозитории.

### Часто спрашивают

- **Разница DAO и Repository?** — DAO ближе к БД и таблицам, Repository ближе к домену и агрегатам.
- **Зачем Repository, если есть JPA?** — Абстракция домена, тестируемость, возможность подменить хранилище.

# Часть B. Web и сервлеты

## B.1. Веб-сервер vs сервер приложений

### Аналогия из жизни

- **Веб-сервер** — это **вахтёр** и **регистратура**: принимает посетителей, раздаёт брошюры (статику), перенаправляет к нужному кабинету. Он не лечит и не считает.
- **Сервер приложений** — это **сама поликлиника с врачами**: выполняет сложную логику, хранит состояние, работает с базами.

| | Веб-сервер | Сервер приложений |
|---|---|---|
| Примеры | Nginx, Apache HTTPD, IIS | Tomcat, Jetty, WildFly, WebLogic, GlassFish |
| Что делает | HTTP, статика, прокси, балансировка, TLS | Исполнение бизнес-логики, контейнер сервлетов, пулы, JNDI, транзакции |
| Java-код | Не исполняет | Исполняет |
| Типичная роль | Фронт, reverse proxy | Бэкенд |

**Тонкость:** Tomcat формально — **контейнер сервлетов**, но часто играет роль сервера приложений. Полноценные серверы приложений (Jakarta EE) добавляют EJB, JMS, JTA и т.д.

### Зачем ставят Nginx перед Tomcat

- Раздача статики быстрее и дешевле.
- Терминация TLS.
- Балансировка между несколькими Tomcat.
- Защита бэкенда от медленных клиентов, лимиты, кэш.

### Часто спрашивают

- **Может ли Tomcat работать без Nginx?** — Да, для разработки и небольших проектов; в продакшене часто ставят reverse proxy.
- **Что такое контейнер сервлетов?** — Среда, управляющая жизненным циклом сервлетов, сессиями, маппингом URL, многопоточностью.

---

## B.2. Контейнер сервлетов и сервлет

- **Контейнер сервлетов** (Servlet Container, он же Servlet Engine) — часть сервера, которая:
  - загружает и инстанцирует сервлеты;
  - вызывает `init`, `service`, `destroy`;
  - маппит URL на сервлеты;
  - управляет `HttpSession`;
  - предоставляет `ServletContext`;
  - обеспечивает многопоточную обработку запросов.
- **Сервлет** — Java-класс, расширяющий `HttpServlet`, обрабатывающий HTTP-запросы.

```java
public class HelloServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        resp.setContentType("text/plain;charset=UTF-8");
        resp.getWriter().write("Привет, " + req.getParameter("name"));
    }
}
```

---

## B.3. Жизненный цикл сервлета

### Пошагово

1. **Загрузка класса** контейнером (ClassLoader).
2. **Инстанцирование** — контейнер создаёт **один** экземпляр сервлета (обычно при первом запросе или при старте, если `load-on-startup`).
3. **`init(ServletConfig config)`** — вызывается **один раз** при инициализации. Здесь читают параметры, открывают ресурсы.
4. **`service(ServletRequest, ServletResponse)`** — вызывается **на каждый запрос** в отдельном потоке. `HttpServlet.service` смотрит на HTTP-метод и вызывает `doGet`, `doPost`, `doPut`, `doDelete`, `doHead`, `doOptions`, `doTrace`.
5. **`destroy()`** — вызывается **один раз** перед выгрузкой (остановка приложения). Закрывают ресурсы.

```
Первый запрос:   new → init() → service() → service() → ... → destroy()
Последующие:                         service() (тот же объект!)
```

### Потокобезопасность — ключевой момент

Один экземпляр сервлета обслуживает **много запросов параллельно в разных потоках**. Значит:

- **Поля сервлета — общие для всех потоков.** Хранить в них данные конкретного запроса нельзя.
- Локальные переменные внутри `doGet` — безопасны (у каждого потока свой стек).
- `ServletContext` и `HttpSession` — разделяемые, требуют осторожности.

```java
public class BadServlet extends HttpServlet {
    private String userName; // ОШИБКА: общее поле для всех потоков!

    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        userName = req.getParameter("name"); // гонка данных
        resp.getWriter().write(userName);    // может вывести чужое имя
    }
}
```

Правильно — передавать данные через локальные переменные или request-атрибуты.

### Типичные ошибки

- Хранить состояние запроса в полях сервлета.
- Ленивая инициализация «тяжёлых» объектов без синхронизации.
- Считать, что `init` вызывается на каждый запрос.
- Держать в `service` изменяемые общие коллекции без синхронизации.

### Часто спрашивают

- **Сколько экземпляров сервлета создаёт контейнер?** — Один (по умолчанию).
- **Кто вызывает `service`?** — Контейнер, на каждый запрос.
- **Может ли сервлет быть потокобезопасным?** — Только если не хранит изменяемое состояние в полях; сам по себе класс — нет.

## B.4. JSP и её жизненный цикл

### Что это

**JSP (JavaServer Pages)** — HTML с вставками Java. Устаревшая, но всё ещё встречается в легаси и на собеседованиях.

### Жизненный цикл

1. **Translation** — контейнер превращает `.jsp` в сервлет `.java`.
2. **Compilation** — компилирует в `.class`.
3. **`jspInit()`** — один раз, аналог `init`.
4. **`_jspService()`** — на каждый запрос, аналог `service`.
5. **`jspDestroy()`** — один раз при выгрузке.

```
login.jsp → login_jsp.java → login_jsp.class → сервлет
```

### Основные элементы

```jsp
<%-- комментарий --%>
<%  // scriptlet: Java-код
    String name = request.getParameter("name");
%>
<%= name %>                  <%-- выражение, вывод --%>
<%! int counter = 0; %>      <%-- объявление поля/метода --%>

<c:if test="${user != null}">Привет, ${user.name}</c:if>  <%-- JSTL + EL --%>
```

### Почему JSP уходит

- Смешивание логики и представления.
- Плохо тестируется.
- Вытеснена Thymeleaf, FreeMarker, Mustache и SPA (React/Vue) + REST.

### Типичные ошибки

- Писать бизнес-логику в scriptlet.
- Забывать про потокобезопасность `<%! %>`-полей (они — поля сервлета!).
- Считать JSP интерпретируемой на лету — на самом деле она компилируется один раз (до изменения файла).

---

## B.5. HttpSession и JSESSIONID

### Что это

**`HttpSession`** — способ хранить состояние пользователя между запросами **на сервере**. HTTP сам по себе stateless, сессия это «костыль» поверх него.

### Как работает

1. Клиент впервые обращается — сервер создаёт сессию, генерирует уникальный ID.
2. ID отправляется клиенту в cookie **`JSESSIONID`**.
3. Клиент присылает cookie с каждым запросом.
4. Сервер по ID находит сессию и её данные.

```java
HttpSession session = request.getSession();          // создать/получить
session.setAttribute("user", user);
User u = (User) session.getAttribute("user");
session.invalidate();                                // завершить
```

### Альтернатива cookie — URL rewriting

Если cookies выключены, контейнер может добавлять `;jsessionid=...` в URL (`response.encodeURL`). Сейчас почти не используется.

### Жизненный цикл

- Создание (`getSession()`).
- Использование.
- Инвалидация (`invalidate()`, logout).
- Таймаут бездействия (`session-timeout` в web.xml / `server.servlet.session.timeout`).

### Проблемы серверных сессий

- Память на сервере (много пользователей).
- Sticky sessions / репликация при масштабировании.
- CSRF-риски, если cookie не `HttpOnly`/`SameSite`.

### REST и stateless

Stateless-подход предпочитает **JWT**: вся информация в токене, сервер ничего не хранит.

### Типичные ошибки

- Хранить в сессии огромные объекты.
- Хранить там же данные, которые должны быть в БД.
- Забывать про инвалидацию при logout → угон сессии.

---

## B.6. HttpServletRequest

`HttpServletRequest` — объект, создаваемый контейнером на **каждый** запрос. Даёт доступ к:

| Что | Метод |
|---|---|
| HTTP-метод | `getMethod()` |
| URL/путь | `getRequestURI()`, `getContextPath()`, `getServletPath()`, `getPathInfo()` |
| Параметры | `getParameter()`, `getParameterMap()` |
| Заголовки | `getHeader()`, `getHeaderNames()` |
| Cookies | `getCookies()` |
| Тело | `getReader()`, `getInputStream()` |
| Сессия | `getSession()` |
| Атрибуты | `getAttribute()`, `setAttribute()` |
| IP клиента | `getRemoteAddr()` |

### Жизненный цикл

Создаётся контейнером → проходит через фильтры → обрабатывается сервлетом → уничтожается после ответа. `getInputStream` и `getReader` можно вызвать только **один раз** (тело читается потоком).

### Часто спрашивают

- **Почему нельзя читать тело дважды?** — Поток одноразовый; для повторного чтения оборачивают в `ContentCachingRequestWrapper`.

---

## B.7. Cookies

### Что это

Небольшие пары key-value, хранящиеся **на клиенте** и отправляемые с каждым запросом к домену.

```java
// Установить
Cookie c = new Cookie("theme", "dark");
c.setMaxAge(60 * 60 * 24);  // 1 день; 0 — удалить; -1 — до закрытия браузера
c.setHttpOnly(true);        // недоступна из JS (защита от XSS)
c.setSecure(true);          // только по HTTPS
c.setPath("/");
response.addCookie(c);

// Прочитать
Cookie[] cookies = request.getCookies();
if (cookies != null) {
    for (Cookie ck : cookies) {
        if ("theme".equals(ck.getName())) {
            String value = ck.getValue();
        }
    }
}
```

### Как удалить cookie

Клиент может удалить cookie, только если сервер пришлёт её с тем же именем/путём и `maxAge = 0`:

```java
Cookie kill = new Cookie("theme", "");
kill.setMaxAge(0);
kill.setPath("/");
response.addCookie(kill);
```

### Cookie vs серверная сессия

| | Cookie | HttpSession |
|---|---|---|
| Где данные | Клиент | Сервер |
| Размер | ~4 КБ | Ограничен памятью |
| Безопасность | Виден/правится клиентом | Данные на сервере |
| Идентификация | Самодостаточна | По `JSESSIONID` |

**Важный нюанс:** удаление `JSESSIONID` на клиенте **не убивает** серверную сессию. Данные останутся на сервере до таймаута или `invalidate()`. Клиент просто потеряет связь с ней. Cookie — только идентификатор, а не хранилище.

### Типичные ошибки

- Не ставить `HttpOnly` → XSS может украсть cookie.
- Не ставить `Secure` → cookie утечёт по HTTP.
- Класть в cookie пароли/токены без шифрования.
- Думать, что удаление cookie чистит серверную сессию.

## B.8. GET vs POST

| Критерий | GET | POST |
|---|---|---|
| Где данные | В URL (query string) | В теле запроса |
| Назначение | Получить данные | Отправить/изменить данные |
| Идемпотентность | Да | Нет |
| Кэширование | Да | Нет (по умолчанию) |
| Остаётся в истории | Да | Нет |
| Длина | Ограничена (~2000–8000 символов) | Практически не ограничена |
| Закладки | Да | Нет |
| Безопасность | Данные видны в URL/логах | В теле |
| Тип по умолчанию в HTML-форме | **GET** | — |

```html
<!-- method не указан → GET -->
<form action="/search">
    <input name="q">
</form>

<!-- явный POST -->
<form action="/users" method="post">
    <input name="name">
</form>
```

### Часто спрашивают

- **Почему пароль нельзя передавать через GET?** — Он попадёт в URL, историю, логи, Referer.
- **Что идемпотентно?** — GET, PUT, DELETE, HEAD, OPTIONS. Не идемпотентны POST и PATCH.
- **Какой метод по умолчанию у формы?** — GET.

---

## B.9. doPost vs doPut и идемпотентность

### Идемпотентность

Операция **идемпотентна**, если повторный вызов даёт тот же результат, что и один. Для HTTP — состояние ресурса на сервере после N одинаковых запросов такое же, как после одного.

### Разбор

- **`doPost`** — создание ресурса. Повторишь — создашь **ещё один**. Не идемпотентен.
- **`doPut`** — создание или **полная замена** ресурса по известному URI. Повторишь — ресурс останется тем же. Идемпотентен.
- **`doDelete`** — удаление. Первый раз удалил, второй — 404/204, но состояние то же. Идемпотентен.

```java
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    // POST /users — создать нового пользователя (новый id генерирует сервер)
}

protected void doPut(HttpServletRequest req, HttpServletResponse resp) {
    // PUT /users/42 — полностью заменить пользователя 42
}
```

### Типичные ошибки

- Использовать POST для обновления, потому что «так проще» — теряется семантика и кэшируемость.
- Считать PATCH идемпотентным всегда (нет — операция «прибавить 1» не идемпотентна).
- Путать идемпотентность и безопасность (safe): GET/HEAD — безопасны (не меняют состояние), PUT/DELETE идемпотентны, но не безопасны.

## B.10. Scopes в JSP/сервлетах

| Scope | Область | Время жизни | Где |
|---|---|---|---|
| **page** | Текущая JSP | До конца рендера страницы | `pageContext` |
| **request** | Один запрос | До конца обработки запроса (forward сохраняет) | `request.setAttribute` |
| **session** | Сессия пользователя | До таймаута/инвалидации | `session.setAttribute` |
| **application** | Всё приложение | Пока живёт приложение | `ServletContext.setAttribute` |

Порядок поиска значения: **page → request → session → application** (от узкого к широкому).

```java
request.setAttribute("msg", "ok");            // request scope
session.setAttribute("user", user);           // session scope
getServletContext().setAttribute("cfg", cfg); // application scope
```

### Типичные ошибки

- Класть пользовательские данные в `application` — их увидят все пользователи.
- Ждать, что request-атрибуты переживут redirect (не переживут — это новый запрос).
- Путать `pageContext` (JSP) с `ServletContext` (application).

## B.11. forward vs redirect

### Аналогия

- **forward** — тебя **внутри здания** переводят в другой кабинет. Ты не заметил, адрес тот же.
- **redirect** — тебя **отправили в другое здание**: браузер сам идёт по новому адресу (два похода).

```java
// forward — на сервере, один запрос, URL не меняется
request.getRequestDispatcher("/WEB-INF/view.jsp").forward(request, response);

// redirect — ответ 302, клиент делает новый запрос, URL меняется
response.sendRedirect(request.getContextPath() + "/login");
```

| Критерий | forward | redirect |
|---|---|---|
| Где происходит | На сервере | На клиенте (браузер) |
| Количество запросов | 1 | 2 |
| URL в браузере | Не меняется | Меняется |
| Request scope | Сохраняется | Теряется |
| Метод | Сохраняется | Обычно GET |
| Скорость | Быстрее | Медленнее |
| Кто выполняет | `RequestDispatcher` | Клиент по `Location` |
| Типичный код | `getRequestDispatcher().forward()` | `sendRedirect()` |

### Практическое правило

- **forward** — когда нужно передать данные и показать результат без смены URL (например, отрендерить view).
- **redirect** — после POST (паттерн **Post/Redirect/Get**), чтобы F5 не отправлял форму заново; при смене «страницы», при авторизации.

### Типичные ошибки

- Делать forward после записи в response (может быть `IllegalStateException`).
- Хотеть передать request-атрибут через redirect — не сработает, используй flash/сессию.
- Использовать forward после POST — F5 повторно отправит форму.

## B.12. getAttribute vs getParameter

| | `getParameter` | `getAttribute` |
|---|---|---|
| Источник | HTTP-запрос (query string, form) | Серверный код (`setAttribute`) |
| Тип | Всегда `String` | `Object` |
| Scope | Параметры запроса | page/request/session/application |
| Изменить | Нельзя (только клиент) | Можно (`setAttribute`) |
| Пример | `req.getParameter("id")` | `req.getAttribute("user")` |

```java
String id = request.getParameter("id");     // из URL: ?id=5
User user = (User) request.getAttribute("user"); // установлен сервером
```

### Часто спрашивают

- **Почему getParameter возвращает String?** — HTTP-параметры передаются как текст.
- **Как передать объект между сервлетами?** — `setAttribute` в request scope + forward.

## B.13. Структура URL

```
scheme://user:password@host:port/path?query#fragment
  │         │              │    │    │      │       │
  │         │              │    │    │      │       └─ фрагмент (якорь), не уходит на сервер
  │         │              │    │    │      └───────── query string: key=value&...
  │         │              │    │    └──────────────── путь ресурса
  │         │              │    └───────────────────── порт
  │         │              └────────────────────────── хост (домен/IP)
  │         └───────────────────────────────────────── userinfo (логин/пароль, устарело)
  └─────────────────────────────────────────────────── схема/протокол
```

Пример:

```
https://example.com:8443/api/users?page=1&size=20#top
```

| Часть | Значение |
|---|---|
| scheme | `https` |
| host | `example.com` |
| port | `8443` |
| path | `/api/users` |
| query | `page=1&size=20` |
| fragment | `top` |

**В сервлете** для `http://host/app/users/42`:

- `getContextPath()` → `/app`
- `getServletPath()` → `/users`
- `getPathInfo()` → `/42`
- `getRequestURI()` → `/app/users/42`
- `getQueryString()` → `null`

### Часто спрашивают

- **Fragment уходит на сервер?** — Нет, обрабатывается браузером.
- **Чем URI отличается от URL?** — URI идентифицирует ресурс, URL дополнительно говорит, **как** его достать (схема доступа). URL — подмножество URI.

## B.14. Порядок фильтров и FilterChain

### Что такое фильтр

`Filter` перехватывает запрос **до** сервлета и ответ **после**. Используется для аутентификации, логирования, CORS, кодировки, сжатия.

```java
public class LogFilter implements Filter {
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        System.out.println("До сервлета");       // pre-processing
        chain.doFilter(req, res);                 // передать дальше
        System.out.println("После сервлета");     // post-processing
    }
}
```

### Порядок вызова

Фильтры образуют цепочку. Важно: **pre-логика** выполняется в порядке цепочки, **post-логика** — в обратном (как матрёшка).

```
F1.pre → F2.pre → F3.pre → Servlet → F3.post → F2.post → F1.post
```

### Как задать порядок

- `@WebFilter` — порядок **не гарантирован** (зависит от контейнера и алфавита имён).
- `web.xml` — порядок объявления `<filter-mapping>`.
- Spring Boot `FilterRegistrationBean` — через `.setOrder(n)` (меньше — раньше).
- Spring Security — цепочка `SecurityFilterChain` с явными позициями.

### Типичные ошибки

- Полагаться на порядок `@WebFilter` — он неопределён.
- Забыть `chain.doFilter()` — запрос «застрянет».
- Писать в response до `doFilter` и потом удивляться.
- Изменять request в фильтре без wrapper — параметры не изменятся.

### Часто спрашивают

- **Разница между Filter и Interceptor?** — Filter — часть сервлет-контейнера (до DispatcherServlet), Interceptor — часть Spring MVC (после DispatcherServlet, знает о handler).
- **Как гарантировать порядок?** — `web.xml` или `FilterRegistrationBean`/`@Order`.

# Часть C. Docker

## C.1. Суть Docker и решаемая проблема

### Проблема «у меня работает»

Приложение работает на машине разработчика, но падает на тестовом/проде, потому что отличаются версии Java, библиотек, ОС, переменные окружения. Docker упаковывает приложение **вместе со всем окружением** в образ.

### Аналогия из жизни

**Морской контейнер.** Неважно, что внутри — бананы, техника или одежда. Контейнер стандартного размера можно поставить на любой корабль, поезд или грузовик. Docker-контейнер так же стандартен для любой машины с Docker.

### Контейнер vs виртуальная машина

| | Контейнер (Docker) | Виртуальная машина |
|---|---|---|
| Изоляция | Процессы, namespaces | Полное железо |
| Ядро ОС | Общее с хостом | Своё ядро |
| Размер | Мегабайты | Гигабайты |
| Старт | Секунды/мс | Десятки секунд/минуты |
| Плотность | Высокая | Низкая |
| ОС внутри | Нет своей | Полная ОС |

### Как устроена изоляция

- **namespaces** — изоляция видимости: PID (процессы), NET (сеть), MNT (файловая система), UTS (hostname), IPC, USER.
- **cgroups** (control groups) — ограничение ресурсов: CPU, память, диск, сеть.
- **UnionFS** — слоёная файловая система образа.

### Ключевые понятия

| Термин | Что это |
|---|---|
| **Image (образ)** | Шаблон, неизменяемый набор слоёв |
| **Container (контейнер)** | Запущенный экземпляр образа (образ + writable-слой) |
| **Dockerfile** | Инструкция сборки образа |
| **Registry** | Хранилище образов (Docker Hub, GHCR) |
| **Volume** | Постоянное хранилище данных |
| **Layer (слой)** | Промежуточный результат инструкции |

### Часто спрашивают

- **Docker — это виртуализация?** — Это контейнеризация: изоляция процессов на общем ядре, а не эмуляция железа.
- **Чем образ отличается от контейнера?** — Образ — неизменяемый шаблон; контейнер — запущенный экземпляр с изменяемым слоем.

---

## C.2. Dockerfile

### Все основные инструкции

| Инструкция | Назначение |
|---|---|
| `FROM` | Базовый образ (обязательна, первая) |
| `RUN` | Выполнить команду при сборке (создаёт слой) |
| `COPY` | Скопировать файлы из контекста |
| `ADD` | Как COPY + распаковка архивов/URL (лучше избегать) |
| `WORKDIR` | Рабочая директория |
| `ENV` | Переменная окружения (в рантайме) |
| `ARG` | Аргумент сборки (только при build) |
| `EXPOSE` | Документирует порт (не публикует!) |
| `CMD` | Команда по умолчанию (переопределяема) |
| `ENTRYPOINT` | Основная команда (жёстче) |
| `VOLUME` | Точка монтирования тома |
| `USER` | Пользователь для запуска |
| `HEALTHCHECK` | Проверка здоровья контейнера |
| `LABEL` | Метаданные |
| `SHELL` | Сменить shell для RUN/CMD |

### Пример простого Dockerfile

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### CMD vs ENTRYPOINT

| | CMD | ENTRYPOINT |
|---|---|---|
| Роль | Аргументы/команда по умолчанию | Неизменяемая основная команда |
| Переопределение | Легко (`docker run image cmd`) | Только через `--entrypoint` |
| Комбинация | `ENTRYPOINT ["java","-jar"]` + `CMD ["app.jar"]` | CMD становятся аргументами ENTRYPOINT |

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--server.port=8080"]   # аргументы по умолчанию, можно переопределить
```

### Multi-stage build

Собираем в одном образе (с Maven/JDK), запускаем в другом (только JRE) — итоговый образ меньше и безопаснее.

```dockerfile
# ---- Этап сборки ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q clean package -DskipTests

# ---- Этап запуска ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
RUN useradd -r appuser
USER appuser
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### .dockerignore

Исключает лишнее из контекста сборки — ускоряет сборку и не тащит секреты/мусор.

```
target/
.git/
*.iml
.idea/
node_modules/
*.log
.env
```

### Типичные ошибки

- `ADD` вместо `COPY` без необходимости.
- Запуск от `root`.
- Копирование всего проекта одним `COPY . .` до установки зависимостей — ломает кэш.
- Хранение секретов в `ENV`/`ARG` — попадут в историю образа.
- Забыть `.dockerignore` → в образ улетает `target/`, `.git/`.

### Часто спрашивают

- **CMD vs ENTRYPOINT?** — ENTRYPOINT — основная команда, CMD — переопределяемые аргументы/дефолт.
- **Зачем multi-stage?** — Уменьшить образ и убрать сборочные инструменты из рантайма.
- **Публикует ли EXPOSE порт?** — Нет, только документирует; публикация — `-p`/`ports:`.

## C.3. Docker Compose

### Зачем

Описывает и запускает **несколько** контейнеров одной командой: приложение, БД, кэш, брокер. Идеально для локальной разработки и интеграционных тестов.

### Пример

```yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/appdb
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: secret
    depends_on:
      - db
    networks:
      - backend

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

  cache:
    image: redis:7
    networks:
      - backend

volumes:
  pgdata:

networks:
  backend:
```

### Команды

```bash
docker compose up -d        # поднять всё в фоне
docker compose ps           # статус
docker compose logs -f app  # логи сервиса
docker compose exec db psql -U app appdb
docker compose down -v      # остановить и удалить тома
docker compose build        # пересобрать
```

### depends_on

Управляет **порядком запуска**, но не ждёт готовности сервиса (БД может ещё инициализироваться). Для ожидания используют healthcheck + `condition: service_healthy` или retry в приложении.

### Часто спрашивают

- **Compose заменяет Kubernetes?** — Нет. Compose — локально/просто; Kubernetes — оркестрация в кластере.
- **Как сервисы находят друг друга?** — По имени сервиса через встроенный DNS Compose.

## C.4. Слои образа и кэш

### Как это работает

Каждая инструкция создаёт **слой**. Слои иммутабельны и кэшируются. Если инструкция и её входные данные не изменились — берётся кэш.

```
FROM ubuntu            ← слой 1
RUN apt-get update     ← слой 2
COPY app.jar /app/     ← слой 3
```

Если меняется `COPY app.jar`, инвалидируются этот и **все последующие** слои. Поэтому тяжёлое и редко меняющееся (зависимости) ставят **раньше**, а исходники — **позже**.

### Правильный порядок для Maven

```dockerfile
COPY pom.xml .
RUN mvn dependency:go-offline   # кэшируется, пока не изменился pom.xml
COPY src ./src
RUN mvn package -DskipTests
```

### Типичные ошибки

- `COPY . .` в начале — любой изменённый файл сбрасывает кэш зависимостей.
- `RUN apt-get update` отдельно от `install` — устаревший кэш.
- Слишком много мелких слоёв без причины.
- Кэш не учитывает содержимое файлов при `ADD` из URL.

### Часто спрашивают

- **Почему образ неизменяем, а контейнер — нет?** — При запуске создаётся тонкий writable-слой; образ (слои) не меняется.
- **Что инвалидирует кэш?** — Изменение инструкции, порядка, входных файлов; для `RUN` — обычно предыдущие слои и аргументы.

## C.5. Типы сетей Docker

| Драйвер | Описание | Когда |
|---|---|---|
| **bridge** | Изолированная сеть, NAT, DNS по именам | По умолчанию, локальная разработка |
| **host** | Контейнер использует сеть хоста | Максимальная производительность, нет изоляции портов |
| **none** | Без сети | Полная изоляция |
| **overlay** | Сеть между несколькими хостами | Docker Swarm, кластер |
| **macvlan** | Контейнер с собственным MAC/IP в физической сети | Когда нужен «настоящий» IP в LAN |

### DNS по именам сервисов

В пользовательской bridge-сети (в т.ч. в Compose) Docker поднимает встроенный DNS. Сервисы резолвят друг друга **по имени сервиса** (или по `container_name`/алиасу), а не по IP.

```yaml
services:
  app:
    environment:
      DB_HOST: db   # 'db' — имя сервиса, резолвится Docker DNS
  db:
    image: postgres:16
```

### Команды

```bash
docker network ls
docker network create mynet
docker network inspect mynet
docker run --network mynet --name app myimage
docker run -p 8080:80 nginx    # публикация порта
```

### Часто спрашивают

- **Почему сервисы видят друг друга по имени?** — Встроенный DNS Docker в пользовательской сети.
- **Чем bridge отличается от host?** — Bridge изолирует сеть и делает NAT; host делит сетевой стек с хостом.
- **Что такое overlay?** — Сеть поверх нескольких хостов для кластера.

# Часть D. Git

## D.1. Git и DVCS

### Что такое распределённая система

**DVCS (Distributed Version Control System)** — у каждого разработчика **полная копия** репозитория со всей историей. Git — DVCS. SVN — централизованная (CVCS).

### Аналогия

- **SVN** — как **библиотека с одним экземпляром книги**: чтобы что-то сделать, нужно идти в библиотеку (сервер).
- **Git** — как **личная электронная книга**: можно читать, писать заметки, делать закладки офлайн, а потом синхронизировать.

### DVCS vs SVN

| | Git (DVCS) | SVN (CVCS) |
|---|---|---|
| История | Полная у каждого | На сервере |
| Работа офлайн | Да | Нет |
| Ветки | Лёгкие, мгновенные | Тяжёлые (копии директорий) |
| Коммит | Локальный | Сразу на сервер |
| Слияния | Хорошо развиты | Сложнее |
| Надёжность | Копии у всех | Единая точка отказа |

### Часто спрашивают

- **Почему Git быстрее?** — Большинство операций локальные, история на диске.
- **Что такое `origin`?** — Имя удалённого репозитория по умолчанию.

---

## D.2. Локальный и удалённый репозиторий

- **Локальный** — папка `.git` внутри проекта, хранит все объекты, ветки, историю.
- **Удалённый** (remote) — общий репозиторий на сервере (GitHub/GitLab/Bitbucket).

```bash
git remote -v                       # список remote
git remote add origin <url>         # добавить
git clone <url>                     # склонировать
git fetch origin                    # скачать изменения
git push origin main                # отправить
git pull origin main                # скачать + слить
```

Типичный поток: `clone` → правки → `add` → `commit` → `push` → Pull Request → merge.

---

## D.3. HEAD и detached HEAD

### Что такое HEAD

`HEAD` — указатель на **текущую ветку** (а ветка — на коммит). Это «где ты сейчас находишься».

```
HEAD → refs/heads/main → коммит C3
```

### Detached HEAD

Если сделать `git checkout <commit-hash>` (или тег), HEAD указывает **прямо на коммит**, а не на ветку. Новые коммиты не привязаны к ветке и могут «потеряться».

```
HEAD → коммит C1   (не на ветке!)
```

Если случайно попал в detached HEAD:

```bash
git switch -c new-branch   # сохранить работу в новую ветку
# или
git switch main            # просто вернуться, потеряв незакоммиченное
```

### Обозначения

| Обозначение | Значение |
|---|---|
| `HEAD` | Текущий коммит |
| `HEAD~1` | Первый родитель (назад на 1) |
| `HEAD~2` | Первый родитель родителя |
| `HEAD^` | Первый родитель (для merge-коммита) |
| `HEAD^2` | Второй родитель merge-коммита |

### Часто спрашивают

- **Что такое detached HEAD?** — HEAD указывает на коммит, а не на ветку.
- **Опасен ли detached HEAD?** — Сам по себе нет; опасна потеря коммитов, сделанных вне ветки.

---

## D.4. Устройство коммита

Коммит — это объект, содержащий:

| Поле | Описание |
|---|---|
| **hash** | SHA-1 (или SHA-256) — уникальный ID, зависит от содержимого |
| **tree** | Снимок дерева файлов (blob'ы + поддеревья) |
| **parent(s)** | Ссылка(и) на родительские коммиты (0 — корень, 1 — обычный, 2 — merge) |
| **author** | Кто написал (имя, email, дата) |
| **committer** | Кто закоммитил (может отличаться при rebase/cherry-pick) |
| **message** | Сообщение |

Коммит **неизменяем**: изменение содержимого меняет хэш, значит это уже другой коммит.

### Ветки

**Ветка** — просто лёгкий указатель (файл с хэшем коммита). Поэтому ветки в Git создаются мгновенно.

```bash
git branch feature       # создать
git switch feature       # переключиться
git switch -c hotfix     # создать + переключиться
git branch -d feature    # удалить (если слита)
git branch -D feature    # удалить принудительно
```

### Типы объектов Git

| Объект | Что хранит |
|---|---|
| **blob** | Содержимое файла |
| **tree** | Структура каталога (ссылки на blob/tree) |
| **commit** | Снимок + метаданные |
| **tag** | Именованная ссылка на объект (аннотированный тег — отдельный объект) |

### Часто спрашивают

- **Что входит в хэш коммита?** — Дерево, родители, автор, committer, сообщение.
- **Почему нельзя «изменить» коммит?** — Меняется содержимое → меняется хэш → это новый коммит.

---

## D.5. Ветки и merge

### Fast-forward

Если целевая ветка не diverged (нет собственных новых коммитов), Git просто передвигает указатель вперёд. Merge-коммит не создаётся.

```
До:    A---B (main)
            \
             C---D (feature)
После: A---B---C---D (main, feature)   ← указатель main передвинулся
```

### Merge commit

Если ветки разошлись, создаётся **коммит слияния** с двумя родителями.

```
      A---B---E (main)
           \ /
            C---D (feature)
```

```bash
git switch main
git merge feature
# при конфликтах: правим → git add → git commit
```

### Опции

- `git merge --no-ff feature` — всегда создавать merge-коммит (сохранить историю ветки).
- `git merge --ff-only feature` — только fast-forward, иначе ошибка.
- `git merge --squash feature` — «схлопнуть» ветку в один коммит (без merge-коммита).

### Часто спрашивают

- **Fast-forward vs merge commit?** — FF — без коммита слияния (линейно); merge commit — с двумя родителями.
- **Что такое «запах» истории?** — Много merge-коммитов; лечится rebase до пуша.

---

## D.6. fetch vs pull

| | `git fetch` | `git pull` |
|---|---|---|
| Что делает | Скачивает объекты и обновляет remote-ветки | `fetch` + `merge` (или `rebase`) |
| Рабочая копия | Не меняется | Меняется |
| Безопасность | Безопасно, можно посмотреть | Может создать merge/конфликты |
| Когда | Хочу посмотреть перед слиянием | Хочу сразу обновиться |

```bash
git fetch origin
git log HEAD..origin/main    # посмотреть, что нового
git merge origin/main

# pull с rebase вместо merge
git pull --rebase origin main
```

**Совет:** безопаснее `fetch` + осознанный `merge/rebase`, чем слепой `pull`.

### Часто спрашивают

- **Чем pull отличается от fetch?** — pull = fetch + слияние; fetch только скачивает.

---

## D.7. Rebase

### Что делает

Переносит коммиты текущей ветки на новую базу, **переписывая** их (создавая новые с новыми хэшами). История становится линейной.

```
До:
      A---B---C (main)
           \
            D---E (feature)

После git rebase main (находясь в feature):
      A---B---C (main)
               \
                D'---E' (feature)   ← новые хэши!
```

```bash
git switch feature
git rebase main
# конфликты: правим → git add → git rebase --continue
# отменить: git rebase --abort
```

### Когда использовать

- Перед Pull Request: подтянуть свежий main и убрать «шумные» merge-коммиты.
- Локальная чистка истории (interactive rebase: squash, reword, drop).

### Почему нельзя ребейзить опубликованное

Если ветка уже запушена и другие работают с ней, переписывание хэшей ломает их историю: у них остаются старые коммиты, а у тебя новые. Возникают дубликаты и конфликты. **Золотое правило: не ребейзь то, что другие уже получили.**

### Типичные ошибки

- Rebase публичной ветки → force-push → сломанная история у команды.
- Rebase во время активной работы коллег над той же веткой.
- Путать `git rebase --continue` и `git commit` во время конфликта rebase.

### Часто спрашивают

- **Merge vs rebase?** — Merge сохраняет историю с коммитом слияния; rebase делает линейную, переписывая коммиты.
- **Почему rebase опасен?** — Переписывает опубликованную историю.

---

## D.8. revert vs reset

### revert

Создаёт **новый** коммит, отменяющий изменения указанного. Безопасно для публичной истории.

```bash
git revert <commit>
git revert <commit> --no-commit   # подготовить, но не коммитить
```

### reset

Перемещает HEAD/ветку, переписывая историю. Три режима:

| Режим | Коммиты | Индекс (staging) | Рабочая копия |
|---|---|---|---|
| `--soft` | Откат | Сохраняются изменения | Сохраняется |
| `--mixed` (по умолчанию) | Откат | Сброс | Сохраняется |
| `--hard` | Откат | Сброс | **Удаляются безвозвратно** |

```bash
git reset --soft HEAD~1   # «раскоммитить», оставив в индексе
git reset --mixed HEAD~1  # «раскоммитить», оставив в рабочей копии
git reset --hard HEAD~1   # выбросить последний коммит и изменения
git reset --hard origin/main  # жёстко синхронизироваться с remote
```

| | revert | reset |
|---|---|---|
| История | Добавляет коммит | Переписывает |
| Безопасно публично | Да | Нет |
| Откат | На один/несколько | На любой коммит |
| Потеря данных | Нет | При `--hard` — да |

### Часто спрашивают

- **revert vs reset?** — revert добавляет отменяющий коммит (безопасно), reset двигает ветку (переписывает).
- **Как откатить уже запушенный коммит?** — `git revert`.

---

## D.9. Разрешение конфликтов

### Когда возникают

При `merge`/`rebase`/`cherry-pick`, если одни и те же строки изменены по-разному.

### Как выглядят маркеры

```
<<<<<<< HEAD
версия из текущей ветки
=======
версия из вливаемой ветки
>>>>>>> feature
```

### Пошагово

1. `git status` — список конфликтных файлов.
2. Открыть файл, выбрать/объединить нужное, **удалить маркеры**.
3. `git add <file>` — отметить как решённый.
4. Завершить:
   - merge: `git commit`;
   - rebase: `git rebase --continue`;
   - cherry-pick: `git cherry-pick --continue`.
5. Отменить: `git merge --abort` / `git rebase --abort`.

### Инструменты

```bash
git mergetool          # настроенный инструмент
git config merge.tool vscode
git checkout --ours <file>   # взять версию своей ветки
git checkout --theirs <file> # взять версию вливаемой
```

**Осторожно:** в rebase `--ours`/`--theirs` «перевёрнуты» относительно интуиции, потому что ветки меняются ролями.

### Типичные ошибки

- Оставить маркеры конфликта в файле.
- Механически выбрать одну сторону, не поняв логику.
- Коммитить несохранённые/сломанные файлы.

# Часть E. Spring Framework

## E.1. Жизненный цикл бина (по шагам)

### Аналогия

Контейнер Spring — как **отдел кадров и прораб** на стройке: сначала читает чертежи (BeanDefinition), нанимает рабочих (инстанцирует), выдаёт инструменты (DI), проводит инструктаж (Aware, post-processors), даёт команду «в работу» (@PostConstruct), а при закрытии объекта — «сдай инструменты» (@PreDestroy).

### Полный порядок

1. **Создание контекста** (`ApplicationContext`), чтение конфигурации (аннотации/XML/Java).
2. **Регистрация `BeanDefinition`** — метаданные о бине (класс, scope, зависимости, lazy).
3. **Инстанцирование** — вызов конструктора.
4. **Внедрение зависимостей (DI)** — setter/field-инъекция; constructor-инъекция происходит на шаге 3.
5. **Aware-интерфейсы**: `BeanNameAware`, `BeanFactoryAware`, `ApplicationContextAware` — бин получает ссылки на инфраструктуру.
6. **`BeanPostProcessor.postProcessBeforeInitialization`**.
7. **Инициализация**: `@PostConstruct` → `InitializingBean.afterPropertiesSet()` → `init-method`.
8. **`BeanPostProcessor.postProcessAfterInitialization`** — здесь AOP создаёт **прокси** (транзакции, кэш, async).
9. **Бин готов** и используется.
10. **Уничтожение** при закрытии контекста: `@PreDestroy` → `DisposableBean.destroy()` → `destroy-method`.

```java
@Component
public class MyBean implements InitializingBean, DisposableBean {
    public MyBean() { System.out.println("1. Конструктор"); }

    @Autowired
    public void setDep(Dep d) { System.out.println("2. DI"); }

    @PostConstruct
    public void postConstruct() { System.out.println("3. @PostConstruct"); }

    public void afterPropertiesSet() { System.out.println("4. afterPropertiesSet"); }

    @PreDestroy
    public void preDestroy() { System.out.println("5. @PreDestroy"); }

    public void destroy() { System.out.println("6. destroy"); }
}
```

### Порядок инициализации (важно)

```
@PostConstruct → InitializingBean.afterPropertiesSet() → init-method
```

Порядок уничтожения:

```
@PreDestroy → DisposableBean.destroy() → destroy-method
```

### Типичные ошибки

- Считать, что `@PostConstruct` вызывается до DI — нет, после внедрения.
- Пытаться использовать прокси внутри `@PostConstruct` — прокси создаётся **после** (шаг 8); возможны сюрпризы с `@Transactional`.
- Думать, что `BeanPostProcessor` применяется к самим `BeanPostProcessor` — нет (иначе цикл).

### Часто спрашивают

- **Когда создаётся прокси?** — В `postProcessAfterInitialization`.
- **Порядок @PostConstruct/afterPropertiesSet/init-method?** — Именно в этом порядке.
- **Что такое BeanDefinition?** — Метаданные бина до его создания.

## E.2. Способы объявления бинов

| Способ | Пример | Плюсы | Минусы |
|---|---|---|---|
| Стереотипы | `@Component`, `@Service`, `@Repository`, `@Controller` | Кратко | Меньше контроля |
| `@Bean` в `@Configuration` | `@Bean public DataSource ds()` | Контроль, сторонние классы, условия | Больше кода |
| XML | `<bean id=... class=...>` | Легаси, внешняя конфигурация | Многословно, нет типобезопасности |
| Java Config | `@Configuration` + `@Bean` | Типобезопасно, рефакторинг | — |

```java
@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper().findAndRegisterModules();
    }
}
```

- `@ComponentScan` — автоматический поиск стереотипов в пакете.
- `@Bean` полезен для классов из сторонних библиотек, где нельзя поставить аннотацию.

### Часто спрашивают

- **@Component vs @Bean?** — `@Component` — на классе (сканирование), `@Bean` — на методе (ручное создание).
- **Что делает @Configuration?** — Помечает класс-источник бинов; проксируется (CGLIB), чтобы `@Bean`-методы возвращали один и тот же экземпляр.

## E.3. Scope бинов

| Scope | Что означает |
|---|---|
| **singleton** (по умолчанию) | Один экземпляр на контейнер |
| **prototype** | Новый экземпляр при каждом `getBean`/инъекции |
| **request** | Один на HTTP-запрос |
| **session** | Один на HTTP-сессию |
| **application** | Один на `ServletContext` |
| **websocket** | Один на WebSocket-сессию |

```java
@Component
@Scope("prototype")
public class Task { }
```

### Проблема prototype внутри singleton

Singleton создаётся один раз и «замораживает» один экземпляр prototype. Внедрили prototype в singleton → получили один и тот же объект навсегда.

**Решения:**

1. **`@Lookup`** — контейнер подставит метод, возвращающий новый бин:
```java
@Component
public abstract class TaskManager {
    @Lookup
    protected abstract Task createTask();
}
```
2. **`ObjectProvider<T>`** — `provider.getObject()` даёт новый экземпляр.
3. **`ScopedProxy`** (`@Scope(proxyMode = TARGET_CLASS)`) — внедряется прокси, который при каждом вызове обращается к актуальному бину.

### Типичные ошибки

- Хранить состояние пользователя в singleton-бине → гонки данных.
- Ждать нового prototype при каждом вызове метода singleton (без Lookup/Provider).
- Использовать prototype для «тяжёлых» бинов без нужды.

### Часто спрашивают

- **Default scope?** — singleton.
- **Prototype уничтожается контейнером?** — Нет, Spring не управляет полным жизненным циклом prototype (не вызывает destroy).
- **Как внедрить prototype в singleton?** — `@Lookup`, `ObjectProvider`, scoped proxy.

## E.4. Dynamic Proxy vs CGLIB

| | JDK Dynamic Proxy | CGLIB |
|---|---|---|
| Механизм | Реализация интерфейсов | Подкласс класса (байт-код) |
| Требование | Интерфейс | Не-final класс, не-final методы |
| Пакет | `java.lang.reflect.Proxy` | сторонний (в Spring встроен) |
| Spring Boot default | — | **Да** (`proxyTargetClass=true`) |
| Проблемы | Нет интерфейса → не работает | final-классы/методы → не проксируются |

```java
// JDK Proxy — только интерфейс
Object proxy = Proxy.newProxyInstance(
        cl, new Class[]{Service.class},
        (p, method, args) -> method.invoke(real, args));
```

### Зачем прокси

AOP: `@Transactional`, `@Cacheable`, `@Async`, `@Secured`, логирование, метрики. Вызов идёт через прокси, который добавляет поведение вокруг метода.

### Типичные ошибки

- Проксировать `final`-класс CGLIB — не выйдет.
- Ждать `@Transactional` на `private`/`final` методе — не сработает.
- Self-invocation — вызов метода через `this` обходит прокси.

### Часто спрашивают

- **Почему Spring Boot использует CGLIB?** — Чтобы проксировать классы без интерфейсов.
- **Когда JDK-прокси?** — Когда бин реализует интерфейс и включён `proxyTargetClass=false` (или интерфейсные прокси).

## E.5. Spring MVC vs Spring Boot

| | Spring MVC | Spring Boot |
|---|---|---|
| Что это | Веб-фреймворк | Надстройка/платформа над Spring |
| Конфигурация | Ручная (DispatcherServlet, web.xml/Java config) | Авто-конфигурация |
| Сервер | Внешний (Tomcat как WAR) | Встроенный (embedded Tomcat) |
| Запуск | Деплой WAR | `java -jar` / `main` |
| Зависимости | Собираешь вручную | Стартеры |
| Свойства | — | `application.properties/yaml` |
| Мониторинг | — | Actuator |

**Spring Boot не заменяет Spring MVC**, а делает его запуск простым. Внутри Boot — тот же `DispatcherServlet`, `@Controller`, `@RequestMapping`.

```java
@SpringBootApplication   // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}
```

### Часто спрашивают

- **Что такое авто-конфигурация?** — Условное создание бинов на основе classpath и свойств (`@ConditionalOnClass` и т.д.).
- **Что такое стартер?** — Набор согласованных зависимостей + авто-конфигурация.

---

## E.6. @Component vs @Service vs @Repository vs @Controller

Все — `@Component` (мета-аннотация), регистрируются как бины. Отличия **семантические** и частично технические:

| Аннотация | Слой | Особенность |
|---|---|---|
| `@Component` | Общий | Базовый стереотип |
| `@Service` | Бизнес-логика | Только семантика |
| `@Repository` | Доступ к данным | Трансляция исключений в `DataAccessException` |
| `@Controller` | Веб | Обработка HTTP, рендер view |
| `@RestController` | Веб (REST) | `@Controller` + `@ResponseBody` |

```java
@Repository
public class UserDao { }        // SQLException → DataAccessException

@Service
public class UserService { }    // бизнес-логика

@RestController
public class UserController { } // JSON-ответы
```

### Часто спрашивают

- **Техническая разница @Component и @Repository?** — `@Repository` включает `PersistenceExceptionTranslationPostProcessor`.
- **@Controller vs @RestController?** — Второй автоматически добавляет `@ResponseBody`.

## E.7. Нативный запрос в Spring Data JPA

### @Query nativeQuery

```java
public interface UserRepo extends JpaRepository<User, Long> {

    @Query(value = "SELECT * FROM users WHERE email = :email", nativeQuery = true)
    User findNative(@Param("email") String email);

    @Query("SELECT u FROM User u WHERE u.email = :email") // JPQL
    User findJpql(@Param("email") String email);
}
```

### Альтернативы

- **JPQL** — запрос по сущностям и полям, переносим между СУБД.
- **EntityManager** — `createNativeQuery` для полного контроля:
```java
@PersistenceContext
private EntityManager em;

List<User> users = em.createNativeQuery("SELECT * FROM users", User.class).getResultList();
```
- **JdbcTemplate** — чистый SQL без ORM.
- **Projections** — интерфейсы/классы для выборки части полей.

### Плюсы и минусы native

| Плюсы | Минусы |
|---|---|
| Использование фич конкретной СУБД | Привязка к СУБД |
| Сложные запросы, оптимизация | Нет автоматической переносимости |
| Работа с несущностями | Нужно вручную маппить результат |

### Типичные ошибки

- Забыть `nativeQuery = true` — Spring попытается распарсить как JPQL.
- Использовать native для простых запросов, где хватит derived-методов.
- Не указывать `@Param` при именованных параметрах.

### Часто спрашивают

- **JPQL vs native SQL?** — JPQL — по сущностям и переносим; native — реальный SQL, привязан к БД.
- **Как сделать нативный запрос?** — `@Query(nativeQuery=true)`, `EntityManager.createNativeQuery`, `JdbcTemplate`.

## E.8. @Transactional

### Как работает

Spring создаёт **прокси** вокруг бина. При вызове метода прокси:
1. открывает транзакцию (или присоединяется к существующей);
2. вызывает целевой метод;
3. коммитит при успехе;
4. откатывает при исключении.

### Откат по умолчанию

- **`RuntimeException` и `Error`** → откат.
- **Checked-исключения** → **НЕ** откатывают (если не указать `rollbackFor`).

```java
@Transactional(rollbackFor = Exception.class) // теперь откат и по checked
public void process() throws IOException { }
```

### Propagation (распространение)

| Propagation | Поведение |
|---|---|
| **REQUIRED** (по умолчанию) | Присоединиться к текущей или создать новую |
| **REQUIRES_NEW** | Всегда новая, текущая приостанавливается |
| **NESTED** | Вложенная через savepoint |
| **SUPPORTS** | Использовать текущую, если есть |
| **NOT_SUPPORTED** | Приостановить текущую, выполнить без транзакции |
| **MANDATORY** | Обязательно в текущей, иначе исключение |
| **NEVER** | Только без транзакции, иначе исключение |

### Isolation (изоляция)

| Уровень | Проблемы |
|---|---|
| DEFAULT | По умолчанию СУБД |
| READ_UNCOMMITTED | Грязное чтение |
| READ_COMMITTED | Нет грязного чтения |
| REPEATABLE_READ | Нет неповторяющегося чтения |
| SERIALIZABLE | Полная изоляция, медленно |

### Прочие атрибуты

- `readOnly = true` — оптимизация для чтения (подсказка СУБД/ORM).
- `timeout` — предел выполнения.
- `rollbackFor` / `noRollbackFor` — настройка исключений.

### Ловушки

1. **Self-invocation** — вызов метода того же класса через `this` не проходит через прокси, транзакция не применяется.
```java
public void a() { b(); }         // b() без транзакции
@Transactional public void b() { }
```
Решения: вынести в другой бин, self-injection, `AopContext.currentProxy()`.

2. **private/final методы** — прокси не перехватывает.
3. **Откат только по unchecked** по умолчанию.
4. **Смена propagation внутри того же прокси** — self-invocation ломает и это.
5. **Транзакция на уровне прокси, а не БД** — если исключение «проглотили» внутри, отката не будет.

### Часто спрашивают

- **По каким исключениям откат по умолчанию?** — По unchecked (`RuntimeException`, `Error`).
- **Что такое self-invocation?** — Внутренний вызов метода класса минует прокси.
- **REQUIRED vs REQUIRES_NEW?** — REQUIRED переиспользует транзакцию; REQUIRES_NEW приостанавливает и создаёт новую.
- **Работает ли @Transactional на private?** — Нет.

## E.10. DI и IoC

### IoC (Inversion of Control)

**Инверсия управления** — управление созданием объектов и их связыванием передаётся контейнеру, а не коду. Код не вызывает `new`, а получает готовое.

### Аналогия

Без IoC: ты сам готовишь обед (сам создаёшь всё). С IoC: ты приходишь в столовую, и тебе выдают уже готовый обед (контейнер создал).

### DI (Dependency Injection)

**Внедрение зависимостей** — конкретный способ IoC: зависимости передаются объекту извне.

| Вид | Как | Плюсы | Минусы |
|---|---|---|---|
| **Constructor** | Через конструктор | Иммутабельность, обязательность, тестируемость | Многословно без Lombok |
| **Setter** | Через сеттер | Гибкость, опциональные зависимости | Мутабельность |
| **Field** | `@Autowired` на поле | Кратко | Скрытые зависимости, тяжело тестировать без Spring |

```java
// Constructor — предпочтительно
@Service
public class UserService {
    private final UserRepo repo;
    public UserService(UserRepo repo) { this.repo = repo; }
}
```

### Плюсы DI/IoC

- Слабая связанность (loose coupling).
- Легко подменять зависимости в тестах (mock).
- Единая точка конфигурации.
- Управление жизненным циклом и scope.

### Типичные ошибки

- Field injection — скрытые зависимости, невозможно `final`.
- Циклические зависимости (A → B → A) — решаются редизайном, `@Lazy`.
- Слишком большой конструктор — сигнал, что класс делает слишком много.

### Часто спрашивают

- **IoC и DI — одно и то же?** — IoC — принцип, DI — способ его реализации.
- **Какой вид инъекции предпочтителен и почему?** — Constructor: иммутабельность, явные зависимости, тестируемость.
- **Что такое ApplicationContext?** — Расширенный BeanFactory: события, i18n, AOP, ресурсы.

# Часть F. REST и NoSQL

## F.1. Ресурсная ориентация

### Идея

**REST (Representational State Transfer)** — архитектурный стиль, где центральный элемент — **ресурс** (сущность), идентифицируемый URI. Действия выражаются HTTP-методами, а не глаголами в URL.

### Аналогия

Ресурс — это **объект в каталоге**: «пользователь 42», «заказы пользователя 42». Ты не командуешь «получи-пользователя», ты указываешь на объект и говоришь «GET».

### Примеры ресурсов

```
/users                       коллекция пользователей
/users/42                    конкретный пользователь
/users/42/orders             заказы пользователя 42
/users/42/orders/7           заказ 7 пользователя 42
/users/42/orders/7/items     позиции заказа
```

Плохо (RPC-стиль):

```
/getUser?id=42
/createUser
/deleteUser?id=42
```

### Именование

- Существительные во множественном числе: `/users`, `/orders`.
- Без глаголов.
- Иерархия через `/`.
- Фильтры — через query: `/users?role=admin&page=1`.

### Часто спрашивают

- **Что такое ресурс?** — Сущность, идентифицируемая URI.
- **Почему не глаголы в URL?** — Действие выражает HTTP-метод, URI идентифицирует ресурс.

---

## F.2. Уникальные URI

Каждый ресурс имеет **уникальный** идентификатор. Это даёт:

- **Кэшируемость** — по URI кэшируются ответы.
- **Предсказуемость** — структура API понятна.
- **Связность (HATEOAS)** — ответы содержат ссылки на связанные ресурсы.
- **Идемпотентность операций** — понятно, что именно меняется.

Пример HATEOAS:

```json
{
  "id": 42,
  "name": "Ivan",
  "_links": {
    "self": { "href": "/users/42" },
    "orders": { "href": "/users/42/orders" }
  }
}
```

### Часто спрашивают

- **Что такое HATEOAS?** — Hypermedia as the Engine of Application State: клиент идёт по ссылкам из ответа.
- **Зачем уникальные URI?** — Кэш, однозначность, связность.

---

## F.3. HTTP-методы и CRUD

| CRUD | HTTP | Пример | Идемпотентно | Безопасно |
|---|---|---|---|---|
| Create | POST | `POST /users` | Нет | Нет |
| Read | GET | `GET /users/42` | Да | Да |
| Read (все) | GET | `GET /users` | Да | Да |
| Update (замена) | PUT | `PUT /users/42` | Да | Нет |
| Update (частично) | PATCH | `PATCH /users/42` | Обычно нет | Нет |
| Delete | DELETE | `DELETE /users/42` | Да | Нет |
| Метаданные | HEAD | `HEAD /users/42` | Да | Да |
| Возможности | OPTIONS | `OPTIONS /users` | Да | Да |

### Часто спрашивают

- **Чем PUT отличается от POST?** — PUT идемпотентен и заменяет ресурс по известному URI; POST создаёт и не идемпотентен.
- **Что значит «безопасный» метод?** — Не меняет состояние (GET, HEAD, OPTIONS).

---

## F.4. PUT vs PATCH

### PUT — полная замена

Тело содержит **весь** ресурс. Отсутствующие поля становятся null/дефолтом.

```http
PUT /users/42
{ "name": "Ivan", "age": 25, "email": "i@mail.ru" }
```

### PATCH — частичное изменение

Тело содержит **только изменения**.

```http
PATCH /users/42
{ "email": "new@mail.ru" }
```

| | PUT | PATCH |
|---|---|---|
| Что меняет | Весь ресурс | Часть |
| Идемпотентность | Да | Обычно нет (зависит от операции) |
| Отсутствующие поля | Сбрасываются | Не трогаются |
| Размер тела | Больше | Меньше |

### Типичные ошибки

- Использовать PUT для частичного обновления → затираются поля.
- Считать PATCH всегда идемпотентным.
- PATCH со сложными операциями (JSON Patch, merge patch) без документации.

### Часто спрашивают

- **PUT vs PATCH?** — PUT заменяет целиком, PATCH меняет часть.
- **Идемпотентен ли PATCH?** — Не обязательно.

---

## F.5. Statelessness

### Что это

Каждый запрос **самодостаточен**: содержит всю информацию для обработки. Сервер не хранит состояние клиента между запросами.

### Аналогия

**Автомат с кофе.** Каждая покупка независима: ты кидаешь монеты и получаешь кофе. Автомат не помнит, что ты покупал раньше. Если он «помнит» — это уже сессия (и её надо где-то хранить).

### Преимущества

- **Масштабируемость** — любой инстанс обработает запрос, не нужны sticky sessions.
- **Отказоустойчивость** — падение инстанса не теряет состояние.
- **Простота** — нет серверного состояния, проще кэш и балансировка.
- **Видимость** — запрос несёт всю информацию.

### Аутентификация

Вместо серверных сессий — **токены**: JWT, OAuth2. Токен передаётся в `Authorization: Bearer ...`.

```http
GET /api/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

### Часто спрашивают

- **Почему stateless важно для масштабирования?** — Любой инстанс обработает запрос, не нужна привязка к серверу.
- **Как быть с корзиной покупок в stateless API?** — Хранить на клиенте или в БД, а не в серверной сессии.

### 1xx — информационные

| Код | Значение |
|---|---|

| Код | Значение |
|---|---|

### 4xx — ошибка клиента

| Код | Значение |
|---|---|

| 405 | Method Not Allowed |
| 409 | Conflict |
| 415 | Unsupported Media Type |

|---|---|

### Часто спрашивают

- **201 vs 200 при создании?** — 201 с `Location`, если создан ресурс.
- **Какой код при ошибке валидации?** — 400 или 422.

## F.7. Разделение клиент/сервер и масштабируемость

REST разделяет клиента и сервер:

- Клиент не знает деталей реализации сервера.
- Сервер не знает, кто клиент (браузер, мобильное приложение, другой сервис).
- Эволюция независима: меняется сервер — клиент работает, пока контракт стабилен.

### Масштабирование

- **Горизонтальное** — добавляем инстансы; stateless позволяет балансировать.
- **Кэширование** — HTTP-кэш, CDN, ETag, Cache-Control.
- **Разные клиенты** — один API для web/mobile.

```http
Cache-Control: max-age=3600
ETag: "abc123"
```

### Часто спрашивают

- **Почему REST хорошо масштабируется?** — Stateless + кэшируемость + независимые инстансы.
- **Что такое идемпотентность в контексте ретраев?** — Повторный запрос безопасен для идемпотентных методов.

## F.8. SQL vs NoSQL

### Таблица сравнения

| | SQL (реляционные) | NoSQL |
|---|---|---|
| Схема | Фиксированная | Гибкая / schemaless |
| Транзакции | ACID | Обычно BASE (eventual consistency) |
| Масштабирование | Вертикальное (чаще) | Горизонтальное (шардирование) |
| Связи | JOIN | Денормализация, вложенность |
| Язык | SQL | Разные API/языки |
| Примеры | PostgreSQL, MySQL, Oracle, MS SQL | MongoDB, Redis, Cassandra, Neo4j |
| Когда | Сложные связи, целостность | Объём, гибкость, высокая нагрузка |

### Типы NoSQL

| Тип | Модель | Примеры | Когда |
|---|---|---|---|
| **Key-Value** | Ключ → значение | Redis, Memcached | Кэш, сессии |
| **Document** | JSON-документы | MongoDB, CouchDB | Гибкая схема, каталоги |
| **Wide-column** | Колонки/семейства | Cassandra, HBase | Огромные объёмы, запись |
| **Graph** | Вершины и рёбра | Neo4j | Связи, соцсети, рекомендации |
| **Time-series** | Временные ряды | InfluxDB | Метрики, IoT |

### ACID vs BASE

- **ACID** (SQL): Atomicity, Consistency, Isolation, Durability — строгая целостность.
- **BASE** (NoSQL): Basically Available, Soft state, Eventual consistency — доступность и гибкость в ущерб мгновенной согласованности.

### Когда что выбирать

- **SQL** — финансы, сложные отчёты, строгая целостность, связи.
- **NoSQL** — большие объёмы, гибкая/меняющаяся схема, горизонтальное масштабирование, кэш, real-time.
- **Polyglot persistence** — часто используют вместе: PostgreSQL для транзакций + Redis для кэша + Elasticsearch для поиска.

### Типичные ошибки

- Выбирать NoSQL «потому что модно» без анализа связей и транзакций.
- Ожидать ACID от всех NoSQL.
- Думать, что NoSQL не умеет транзакции (MongoDB 4+ умеет много-документные).

### Часто спрашивают

- **SQL vs NoSQL?** — Схема, транзакции, масштабирование, связи.
- **Что такое eventual consistency?** — Данные со временем согласуются между репликами.
- **Когда NoSQL лучше?** — Большие объёмы, гибкая схема, горизонтальный масштаб.

# Шпаргалка

## Паттерны

- **GoF: 23 паттерна**, три группы: порождающие, структурные, поведенческие.
- **Factory Method** — один продукт через наследование; **Abstract Factory** — семейство продуктов.
- **Builder** — пошаговая сборка сложного объекта, fluent interface.
- **Singleton**: enum (лучший) > holder > DCL+volatile. Ломается рефлексией, сериализацией, ClassLoader.
- **Prototype** — клонирование; shallow vs deep copy.
- **Command** — запрос как объект (очередь, undo). **Observer** — подписка.
- **Composite** — дерево «часть-целое». **Chain of Responsibility** — цепочка (фильтры).
- **State** — поведение от состояния. **Iterator** — обход коллекции.
- **Proxy** — контроль доступа; **Decorator** — добавить поведение; **Adapter** — сменить интерфейс.
- **Immutable** — final-класс, final-поля, defensive copy.
- **MVC** — Model/View/Controller. **DAO** — таблицы, **Repository** — домен.

## Web

- **Веб-сервер** (Nginx) — HTTP/статика/прокси; **сервер приложений** (Tomcat/WildFly) — Java-логика.
- **Сервлет**: init (1 раз) → service (каждый запрос, многопоточно) → destroy (1 раз). Поля не потокобезопасны.
- **JSP**: translation → compilation → jspInit → _jspService → jspDestroy.
- **HttpSession** — состояние на сервере, ID в cookie `JSESSIONID`. Удаление cookie не убивает сессию.
- **Cookies**: `getCookies()`, `addCookie()`, удаление `maxAge=0`; `HttpOnly`, `Secure`, `SameSite`.
- **GET** — в URL, идемпотентен, кэшируется; **POST** — в теле, не идемпотентен. Форма по умолчанию — GET.
- **doPut** идемпотентен (замена), **doPost** — нет. Идемпотентны: GET, PUT, DELETE, HEAD, OPTIONS.
- **Scopes**: page → request → session → application.
- **forward** — сервер, 1 запрос, request сохраняется; **redirect** — клиент, 2 запроса, URL меняется.
- **getParameter** — String из HTTP; **getAttribute** — Object от сервера.
- **URL**: scheme://host:port/path?query#fragment.
- **Фильтры**: порядок через web.xml/FilterRegistrationBean; pre — прямой, post — обратный.

## Docker

- **Контейнер** — изоляция (namespaces) + лимиты (cgroups), общее ядро; **VM** — своё ядро.
- **Образ** — неизменяемые слои; **контейнер** — образ + writable-слой.
- **Dockerfile**: FROM, RUN, COPY, WORKDIR, ENV, ARG, EXPOSE, CMD, ENTRYPOINT, VOLUME, USER, HEALTHCHECK.
- **CMD** — дефолт (переопределяем); **ENTRYPOINT** — основная команда.
- **Multi-stage** — сборка отдельно от рантайма; **.dockerignore** — меньше контекст.
- **Compose** — несколько контейнеров, сети, тома, depends_on.
- **Слои кэшируются**: зависимости — раньше, исходники — позже.
- **Сети**: bridge (default, DNS по именам), host, none, overlay, macvlan.

## Git

- **DVCS** — полная история у каждого; SVN — централизованная.
- **HEAD** — указатель на ветку/коммит; **detached HEAD** — прямо на коммит.
- **Коммит**: hash, tree, parent(s), author, committer, message.
- **merge** — fast-forward или merge-commit; **rebase** — перенос с перезаписью истории.
- **fetch** — скачать; **pull** = fetch + merge/rebase.
- **revert** — новый отменяющий коммит (безопасно); **reset** --soft/--mixed/--hard.
- **Конфликты**: маркеры `<<<<<<<`/`=======`/`>>>>>>>`, `git add`, продолжить.
- Не ребейзить опубликованное!

## Spring

- **Жизненный цикл**: BeanDefinition → инстанцирование → DI → Aware → BPP.before → @PostConstruct/afterPropertiesSet/init → BPP.after (прокси) → готов → @PreDestroy/destroy.
- **Бины**: @Component/@Service/@Repository/@Controller, @Bean, XML.
- **Scope**: singleton (default), prototype, request, session, application, websocket. prototype в singleton — @Lookup/ObjectProvider/scoped proxy.
- **Прокси**: JDK (интерфейсы) vs CGLIB (подкласс, default в Boot).
- **MVC** — фреймворк; **Boot** — авто-конфигурация + встроенный сервер + стартеры.
- **@Repository** транслирует исключения в DataAccessException.
- **Native query**: `@Query(nativeQuery=true)`, `EntityManager.createNativeQuery`, `JdbcTemplate`.
- **@Transactional**: прокси; откат по RuntimeException/Error; self-invocation не работает; propagation REQUIRED/REQUIRES_NEW/NESTED/...; isolation DEFAULT/READ_COMMITTED/...
- **DI**: constructor (предпочтительно), setter, field. **IoC** — принцип.

## REST / NoSQL

- Ресурсы + уникальные URI + HTTP-методы; без глаголов в URL.
- **PUT** — полная замена (идемпотентен); **PATCH** — частично.
- **Stateless** — каждый запрос самодостаточен, JWT вместо сессий.
- **Статусы**: 2xx успех, 3xx редирект, 4xx клиент (401 vs 403), 5xx сервер.
- **SQL** — ACID, JOIN, вертикально; **NoSQL** — BASE, гибкость, горизонтально.
- NoSQL типы: KV, document, wide-column, graph, time-series.

# Частые вопросы на собеседовании с короткими ответами

1. **Сколько паттернов GoF и на какие группы делятся?**
   23; порождающие, структурные, поведенческие.

2. **Лучший способ реализовать Singleton?**
   Enum — защищён от рефлексии и сериализации.

3. **Почему в double-checked locking нужен volatile?**
   Иначе возможна публикация частично инициализированного объекта из-за переупорядочивания.

4. **Чем Factory Method отличается от Abstract Factory?**
   Factory Method — один продукт через наследование; Abstract Factory — семейство через композицию.

5. **Shallow vs deep copy?**
   Shallow копирует ссылки на вложенные объекты; deep — сами объекты.

6. **Чем Proxy отличается от Decorator?**
   Proxy контролирует доступ, Decorator добавляет поведение; интерфейс у обоих тот же.

7. **DAO vs Repository?**
   DAO про таблицы/персистентность, Repository про домен/агрегаты.

8. **Веб-сервер vs сервер приложений?**
   Первый — HTTP/статика/прокси, второй исполняет Java-логику.

9. **Жизненный цикл сервлета?**
   init (один раз) → service (каждый запрос, много потоков) → destroy (один раз).

10. **Почему поля сервлета опасны?**
    Один экземпляр обслуживает много потоков; общее изменяемое состояние — гонка.

11. **forward vs redirect?**
    forward — на сервере, 1 запрос, request сохраняется; redirect — 2 запроса, URL меняется.

12. **getParameter vs getAttribute?**
    Parameter — String из HTTP; Attribute — Object, установленный сервером.

13. **Как удалить cookie?**
    Послать cookie с тем же именем/путём и maxAge=0. Сессия на сервере при этом живёт.

14. **GET vs POST?**
    GET — в URL, идемпотентен, кэшируется; POST — в теле, нет.

15. **Что идемпотентно?**
    GET, PUT, DELETE, HEAD, OPTIONS.

16. **Порядок фильтров?**
    Через web.xml/FilterRegistrationBean/@Order; @WebFilter — не гарантирован.

17. **Что такое Docker namespaces и cgroups?**
    Namespaces — изоляция видимости; cgroups — лимиты ресурсов.

18. **CMD vs ENTRYPOINT?**
    CMD — переопределяемые аргументы/дефолт; ENTRYPOINT — основная команда.

19. **Зачем multi-stage build?**
    Уменьшить образ и убрать сборочные инструменты из рантайма.

20. **Как сервисы в Compose находят друг друга?**
    По имени сервиса через встроенный DNS.

21. **fetch vs pull?**
    fetch скачивает, pull = fetch + merge/rebase.

22. **Почему нельзя ребейзить опубликованное?**
    Переписывает историю, ломая работу коллег.

23. **revert vs reset?**
    revert добавляет отменяющий коммит; reset двигает ветку и переписывает историю.

24. **Что такое detached HEAD?**
    HEAD указывает прямо на коммит, а не на ветку.

25. **Порядок жизненного цикла бина Spring?**
    BeanDefinition → инстанцирование → DI → Aware → BPP.before → @PostConstruct/afterPropertiesSet/init → BPP.after (прокси) → готов → @PreDestroy/destroy.

26. **Как внедрить prototype в singleton?**
    @Lookup, ObjectProvider, scoped proxy.

27. **JDK Proxy vs CGLIB?**
    JDK — через интерфейсы; CGLIB — подкласс класса (default в Boot), не работает для final.

28. **Spring MVC vs Spring Boot?**
    MVC — фреймворк; Boot — авто-конфигурация, встроенный сервер, стартеры.

29. **@Component vs @Repository?**
    @Repository добавляет трансляцию исключений в DataAccessException.

30. **Как сделать нативный запрос в Spring Data JPA?**
    @Query(nativeQuery=true), EntityManager.createNativeQuery, JdbcTemplate.

31. **По каким исключениям @Transactional откатывает по умолчанию?**
    По RuntimeException и Error; checked — только с rollbackFor.

32. **Что такое self-invocation в @Transactional?**
    Вызов метода того же класса через this не проходит через прокси — транзакция не применяется.

33. **REQUIRED vs REQUIRES_NEW?**
    REQUIRED присоединяется к текущей; REQUIRES_NEW приостанавливает и создаёт новую.

34. **Какой вид DI предпочтителен?**
    Constructor — иммутабельность, явные зависимости, тестируемость.

35. **PUT vs PATCH?**
    PUT — полная замена, PATCH — частичное изменение.

36. **Почему REST stateless?**
    Масштабируемость, отказоустойчивость, независимые инстансы.

37. **401 vs 403?**
    401 — не аутентифицирован; 403 — аутентифицирован, но нет прав.

38. **SQL vs NoSQL?**
    SQL — схема, ACID, JOIN, вертикально; NoSQL — гибкость, BASE, горизонтально.

39. **Типы NoSQL?**
    Key-Value, document, wide-column, graph, time-series.

40. **Что такое eventual consistency?**
    Реплики согласуются со временем, не мгновенно.
